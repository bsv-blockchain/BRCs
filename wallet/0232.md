# BRC-232: Non-Expiring Prefunded `noSend` Actions (`p nosend expiry none`)

David Case

## Abstract

This document adds a fourth expiry mode, `none`, to [BRC-177](./0177.md). The wallet prefunds the action exactly as BRC-177 does — one dedicated anchor output, sized under the wallet's own fee policy, spent by a `noSend` action that carries no automatically generated change — but there is no deadline and no reclaim. The action is recorded as `nosend` with its inputs spent, and the wallet never broadcasts it or watches for it.

## Motivation

In a peer-to-peer payment the sender does not broadcast. The sender hands the recipient a complete, signed transaction — in a [BRC-29](../payments/0029.md) remittance or a [BRC-169](../peer-to-peer/0169.md) envelope — and the recipient broadcasts it when they collect it. The sender's wallet needs a record of what it sent and must never reuse those inputs, but it has no further interest in the outcome and should not depend on a spend index or proof service to learn it.

BRC-177 already builds such a transaction correctly: it mints an anchor of exactly the required size and builds the action on it with no change, so no larger coin or change output gets locked into a transaction the wallet will never broadcast. An application cannot do this from outside the wallet, because it would have to guess the wallet's fee model. What BRC-177 adds on top — the deadline, the pre-signed reclaim and the anchor reserve that pays for it — is for a sender who may want the value back. A sender who has handed the payment over never does, and the reserve actively blocks small payments: an anchor for a 1-satoshi output cannot also carry a reclaim fee, so the request is rejected. The `none` mode keeps the prefunding and drops the expiry.

## Specification

### Label

| Label | Meaning |
| --- | --- |
| `p nosend expiry none` | Prefund and protect the action; never expire, never reclaim |

It is one of the `p nosend expiry` forms, so BRC-177's "exactly one such label" rule still holds. A wallet that does not implement this document rejects it as an unknown mode, as BRC-177 already requires.

### Behaviour

A `p nosend expiry none` action is a BRC-177 protected action with these differences and no others:

1. **Anchor.** Sized to fund the protected action under the wallet's current fee policy, and nothing more. The reclaim-fee reserve and minimum-output rules of BRC-177 do not apply.
2. **No expiry.** No deadline is computed or stored, no reclaim transaction is built, requested at `signAction`, or scheduled.
3. **Record.** The protected action is stored as `nosend`, its inputs — the anchor and every caller-supplied input — marked as spent by it, listable through `listActions` and retrievable, so the application can deliver it and find it again.
4. **No observation.** Nothing in this mode requires the wallet to learn whether the transaction was broadcast.
5. **Abort.** BRC-177's post-release reclamation does not apply; `abortAction` releases the reservation locally, as for any `noSend` action. The case for it is exception handling: the recipient reports out of band that the transaction can no longer be broadcast (a fee spike, say), the sender aborts and issues a replacement.

### Relationship to BRC-177

BRC-177's rule that a wallet rejects "unknown expiry modes" is amended to exclude `none` as defined here. Nothing else in BRC-177 changes. One prefunding implementation serves all four modes; only the anchor sizing and the post-release lifecycle differ.

## Security Considerations

- Aborting after release does not invalidate the transaction already handed over; if the recipient broadcasts it after all, it competes with whatever the sender built from the released inputs. The application must settle that out of band before aborting.
