# BRC-207: Mandala Token Wallet Module

Ty Everett (ty@projectbabbage.com)

## Abstract

This specification defines the canonical `mandala` wallet module for fungible
assets under [BRC-162](../tokens/0162.md), including the
[BRC-161](../tokens/0161.md) encoding of the same token model. It combines
counterparty-derived P2PKH custody, per-asset baskets, overlay-verified admission,
amount-aware spending consent, input selection, change, issuance, authority
operations, burns and composable multi-asset swaps. It supports arbitrary foreign
scripts and both complete and partially signed transactions through the existing
[BRC-100](./0100.md) interface.

MUST, MUST NOT, SHOULD and MAY express requirements for conforming implementations.
A wallet without this module MUST reject its reserved identifiers. Module support
does not reduce the mandatory core wallet interface or authorize an operation.

## Asset identity, amounts and custody

An `assetId` is the canonical BRC-162 API token ID: a lowercase display-order
transaction ID, an underscore, and a decimal deploy uint32 output index without leading
zeroes, for example `<64 hex characters>_0`. Its binary prefix representation,
including the legacy nonzero-index form, is exactly BRC-162's. The wallet MUST
identify assets by this issuance outpoint, never by symbol, icon, decimals or a
caller label. BRC-161 JSON and BRC-162 binary outputs with the same ID represent
the same asset; BRC-162's binary-prefix precedence applies.

Amounts MUST be processed as exact integers in the domain specified by the
applicable token encoding. BRC-162 value outputs carry 1 through `2^64 - 1` units;
zero designates authority, not an empty value balance. JSON quantities in this
module's metadata MUST be decimal strings without leading zeroes. Sums MUST use
exact arithmetic that cannot overflow when adding multiple maximum-sized inputs.
Deploy `dec` affects display only; there is no conversion between token units and
satoshis, and no floating-point accounting.

Wallet custody requires an admissible BRC-162 prefix, with its optional payload,
followed by an ordinary P2PKH remainder controlled by the module-derived wallet
key. BRC-161 equivalents MAY be received and spent in the same managed baskets;
the wallet MUST recognize and validate both encodings. New wallet-generated
issuance, transfer and change outputs MUST use BRC-162. Arbitrary valid scripts
remain supported for foreign inputs and destinations; the custody restriction
only determines which outputs the wallet can automatically manage and sign.

## Namespace and counterparty derivation

The logical derivation identifier is:

```text
p mandala <assetId | ISSUE> <derivationPrefix> <derivationSuffix>
```

The prefix distinguishes a payment or issuance and the suffix distinguishes each
output, as in [BRC-29](../payments/0029.md). Exact remittance strings MUST be
preserved, even when they contain base64. They MUST be nonempty strict UTF-8,
without whitespace, and SHOULD be freshly generated. An application origin,
transaction, amount, basket or permission grant MUST NOT silently alter keys.

For interoperability with [BRC-43](../key-derivation/0043.md)'s lowercase
alphanumeric protocol grammar, the wire representation is defined as follows:

- `assetTag` is the asset ID's 64 lowercase txid hex characters, `v`, and its
  canonical decimal output index, or the literal `issue` for `ISSUE`.
- `prefixTag` and `suffixTag` are lowercase hex encodings of the **UTF-8 bytes of
  the exact remittance strings**, not hex encodings of decoded base64 data.
- `protocolID` is `[2, "p mandala " + assetTag + " " + prefixTag + " " + suffixTag]`.
- `keyID` is the fixed string `mandala`.
- The BRC-42 invoice is `2-<complete protocol name>-mandala`.

The complete protocol name MUST satisfy BRC-43's 280-character bound. Invalid or
oversized identifiers MUST fail before key derivation; truncation, case folding
of remittance strings and alternate wire aliases are prohibited. For example,
`ISSUE`, prefix `AQ==`, suffix `Ag==` encodes as protocol name
`p mandala issue 41513d3d 41673d3d`. The logical form above is not a second wire
spelling. This encoding introduces no exception to BRC-43 normalization.

Derivation follows BRC-42's same sender/recipient counterparty relationship used
by the TypeScript Wallet Toolbox's [BRC-29 script template](https://github.com/bsv-blockchain/wallet-toolbox/blob/master/src/utility/ScriptTemplateBRC29.ts):
the sender derives the recipient's child public key using the recipient identity,
and the recipient derives its child private key using the sender identity.
`getPublicKey.forSelf` MUST select the intended owner's child. `self`, `anyone`
and compressed public-key counterparties retain their BRC-100 meanings. Receipt
metadata MUST represent `anyone` by the compressed public key for private key 1.
Ordinary and privileged root selection retain their meanings and authorization;
public derivation from an ordinary identity cannot reproduce a privileged key.

A deploy output uses `ISSUE` because its own transaction ID does not yet exist.
That derivation remains its spend key after issuance: finalizing the asset ID
MUST NOT rederive the deploy's key. Subsequent outputs use the known asset ID.
A wallet MUST store the exact original tuple for every managed output, including
legacy-encoding inputs and authority outputs.

### Baskets and dispatch

The logical baskets are `p mandala <assetId>` and
`p mandala <assetId>-AUTHORITY`. Their BRC-100-compatible wire names are:

```text
p mandala <assetTag>
p mandala <assetTag> authority
```

There is one value basket and one authority basket per asset, never a global
Mandala balance basket. `issue` is not a stored basket. After a deploy transaction
has its final transaction ID, the wallet MUST assign its derived asset basket,
or authority basket when its amount is zero. Provisional issuance records MUST
remain pending until that ID is final. Authority output counts and capabilities
MUST NOT be presented as fungible value amounts.

The `mandala` scheme is defined in [BRC-98](./0098.md) protocol,
[BRC-99](./0099.md) basket, and [BRC-111](./0111.md) action-label namespaces.
Labels carry the action plan below; they do not change derivation. The wallet
MUST dispatch these identifiers to trusted module code before generic permission
defaults. Application code cannot install its own handler or bypass custody by
renaming baskets, deleting metadata, choosing an originator, or obtaining a
generic signing grant. Reads and organizational operations use module-aware
permissions; relinquishing tracking does not release protected keys.

`getPublicKey` and `verifySignature` retain their normal public semantics.
`createSignature` accepts only the transaction request below. Encryption,
decryption, HMAC and linkage operations in this protocol MUST be rejected.
Protected keys and root linkages MUST NOT be exposed through auxiliary methods.
BRC-29 satoshi keys remain separate and are signed only by the normal wallet
transaction path.

## Overlay spendability contract

For each asset, the topic and lookup service are deterministically:

```text
tm_mandala_<assetId>
ls_mandala_<assetId>
```

These names use the canonical underscore asset ID, not the key-derivation
`assetTag`. They cover both token encodings, value and authority. The wallet MUST
derive both names independently. Caller hints MUST identify the asset ID and
matching topic; they MUST NOT select a service URL, alternate topic or asset.
Every supplied input MUST have an explicit hint: `{outpoint, assetId, topic}` for
a token input, or `{outpoint, assetId:null, topic:null}` for a bare-satoshi input.
Hints MUST agree with independently parsed, authenticated source outputs. Missing,
contradictory, duplicate or undisclosed token hints MUST fail. Wallet-selected
inputs receive hints from the wallet's own verified records.

The wallet uses [BRC-88](../overlays/0088.md) SLAP trackers configured or
initialized by its owner to find trustworthy services for each issuance ID.
The caller's declarations and arbitrary lookup endpoints are not trust anchors.
An implementation MUST verify provider identity and response provenance under
that configuration and obtain current answers before releasing authorization or
accepting custody. Conflicting trusted answers, transport failure, an unavailable
provider or inability to establish current state MUST fail the operation. A
historical proof or cached permission does not replace a current check.

A conforming service MUST support this [BRC-24](../overlays/0024.md) query:

```json
{
  "service": "ls_mandala_<assetId>",
  "query": {
    "type": "mandala-spendability",
    "version": 1,
    "assetId": "<assetId>",
    "topic": "tm_mandala_<assetId>",
    "outpoints": ["<txid>.<vout>"]
  }
}
```

Query outpoints use canonical [BRC-36](../outpoints/0036.md) dot form. The response
MUST be BRC-24 `output-list`, containing exactly the queried outputs that are
currently admitted and unspent in that asset's topic. Each item MUST include its
`outputIndex` and BEEF sufficient to authenticate its source output. An empty
list is a valid negative answer. Any missing queried token outpoint fails its
spendability check; unrelated, duplicate or conflicting returned outputs are
invalid responses. The wallet MUST reconstruct each returned outpoint and match
its bytes to the supplied source transaction, asset ID, role, amount and script.

Services MUST additionally support the same query shape with
`type: "mandala-admission"`. This returns exactly the queried outputs that were
validly admitted to the topic, including outputs now spent. It provides historical
membership for receipt validation, not current spendability. Missing historical
outputs fail unless the wallet independently establishes their admitted lineage
through a complete BRC-176 proof and verifies the received output's current
membership. Both queries use the same source-byte matching and response rules.

These query contracts do not limit other service queries or token-specific
functions. Services MUST apply BRC-161/162 admission and authority rules; script
prefix presence alone does not prove membership. A successful response attests
current service state, not a miner-enforced token rule or a future guarantee that
an output remains unspent. Pending actions require fresh validation on completion.

## Transaction evidence and admission

The caller MUST provide the complete transaction context, authenticated source
outputs, required BEEF/SPV evidence and the input topic hints. A bare preimage,
digest, amount declaration or list of hashes is insufficient. Txid-only entries
may be resolved from authoritative wallet knowledge; unresolved sources fail.
[BRC-176](../tokens/0176.md) packets MAY supply token-lineage evidence but MUST
be validated under that profile rather than stripped as ordinary Atomic BEEF.
They do not replace current overlay spendability. Neither `trustSelf` nor
`knownTxids` waives token admission or currentness checks.

The wallet MUST validate all source output identities, scripts, satoshi amounts,
proofs and token roles; reject duplicate inputs and conflicting representations;
and, before releasing a spend signature, check every token input against its
asset overlay's current spendability. For a completed receipt, consumed inputs
instead require authenticated historical admission or valid BRC-176 lineage;
checking them as currently unspent would incorrectly reject ordinary receipts. Foreign inputs contribute
amounts only after this authentication and topical-membership check. The wallet
MUST evaluate the resulting transaction per issuance ID under BRC-161/162:

- A deploy is admitted only at the position and under the rules of its encoding.
- Apply the encoding-specific BRC-161/162 balance and authority rules exactly,
  aggregating by the same issuance ID across encodings. Without authority,
  BRC-162 value outputs require input balance coverage; any shortfall in output
  total is a burn requiring consent.
- BRC-161 `mint` outputs require valid authority. Its `transfer` and `burn`
  totals require value-input coverage even when authority is present. Legacy
  `burn` outputs have no spendable token value and MUST NOT enter custody or
  incoming-value accounting; explicit and implicit burns both require consent.
- With valid authority, BRC-162 minting and authority split, combine, transfer
  and termination follow its rules. Authority contributes zero to value totals.
- All value outputs of an asset are admitted or rejected together. An
  over-output transaction that destroys its inputs MUST fail wallet authorization.
- Metadata and decimals never create supply, confer authority, or waive checks.

The wallet MUST perform independent satoshi conservation and fee validation.
There is no module-wide one-satoshi rule: service admission policy and actual
script consensus rules determine accepted satoshi values. Nonzero bare-satoshi
payments, token-carrier satoshis and fees remain fully accounted for.

Every completed transaction MUST pass consensus-valid script execution for all
inputs, including arbitrary foreign scripts. An incomplete subject may omit
unlocking scripts only in an explicitly pending action; its available context,
source evidence, overlay state and token transition must still be checked.
Invalid provided scripts MUST fail. The wallet MUST NOT represent a pending
transaction as fully validated, admitted, mined or immediately spendable.

## Structured authorization facts

Authorization MUST be based on trusted, validated facts for the entire action:

- authenticated originator, network and selected wallet/root context;
- every asset's issuance ID, encoding, value and authority inputs and outputs,
  scripts, outpoints, overlay topic and current check results;
- per-asset wallet input total, wallet-owned output total, incoming amount,
  outgoing amount, net debit or credit, burn, mint and authority changes;
- satoshi inputs, wallet receipts, outgoing payments, carrier values and fees;
- recipients as verified control identities where known, otherwise script-based
  destinations with the limits of that identification stated;
- wallet-selected inputs, generated change, caller-fixed positions, sequences,
  locktime, transaction version, signature modes and exact commitment coverage;
- completeness, pending status and terms that remain conditional or mutable.

Netting MUST be computed separately for each asset from authenticated inputs and
wallet-controlled outputs. Foreign funding can offset a debit only to the extent
it validly funds wallet-owned outputs of that **same** asset. Recognizing an
output's key requires the stored or supplied remittance tuple and comparison
against its actual P2PKH hash; an application annotation cannot establish wallet
ownership. Satoshis are accounted separately under normal spending permissions,
including [BRC-116](./0116.md) DSAP where implemented. Token-carrier satoshis MUST
appear in total satoshi accounting without also being counted as a bare-satoshi
payment. Internal transfers and change are not external spending.

When value of one asset leaves and another enters, the wallet MUST present the
action as a swap with all legs. Bare satoshis are an asset for this presentation;
a swap may have any number of token and satoshi legs, including three or more
assets. Different assets MUST NOT cancel each other's debits or disappear from
the presentation. Burns and authority delegation, duplication or destruction
require clear consent even when the fungible net debit is zero. Display metadata
is untrusted descriptive information; the issuance ID remains available.

The user MUST consent to the actual authorized consequences. Rendering and
permission organization are wallet-specific: wallets MAY use per-action approval,
origin-scoped limits, monthly allowances, thresholds, manifest-informed rules or
other user-authorized policies. This specification mandates no particular quota,
permission-token encoding, UI framework, or frequency of prompts. A generic
cryptographic protocol grant does not substitute for asset spending consent.
Concurrent operations and retries MUST NOT exceed a wallet's granted permission
or consume an allowance twice for the same authorized action.

## Metadata types and validation

Every envelope, plan, hint, remittance, operation and constraint is a JSON object
with exactly the named members. Duplicate JSON members and unknown members MUST
fail at every nesting level. The optional `tokenProofs` member is permitted in signature envelopes, action
plans and receipt custom instructions; omission means an empty array. Each item
is exactly `{assetId, subjects, beef}`: a canonical asset ID, a nonempty array
of unique canonical subject outpoints, and a nonempty numeric byte array encoding
one BRC-176 packet. The packet MUST be validated for exactly those subjects and
that asset; contradictory or duplicate proof scopes fail. Packet presence does
not assert current admission or spendability. These bytes count toward the
containing request's resource bound. Wallet-fetched proofs may be used only after
the same validation. The `tx` field separately uses BRC-95 subject framing and
ancestor inclusion; incomplete subject script execution is deferred until
completion, and MUST NOT be described as fully validated Atomic BEEF.

Arrays MUST have the types specified here; `null`
is allowed only where explicitly stated. Strings MUST be strict UTF-8. Numeric
indices and versions MUST be integers, not fractions, booleans or strings.
`version` is exactly `1`. An index is in `0..2^32-1` and MUST select an actual
input/output or a satisfiable planned position. `sighashType` is an integer in
`0..255`, further subject to consensus rules. `tx` is a nonempty numeric array
of integer bytes in `0..255`, not base64 or a numeric-key object.

All metadata `outpoint` fields use canonical lowercase BRC-36 dot form with a
uint32 decimal index without leading zeroes. `assetId` and `ISSUE` use the exact
identity rules above; ISSUE is prohibited for existing inputs. Topics are exact
strings derived from the asset ID. `senderIdentityKey` is a valid compressed
secp256k1 public key. Prefix/suffix strings and resulting derivation must satisfy
the namespace rules. `inputTopics` contains exactly one hint per explicit input,
with no extra or duplicate outpoints. `ownedOutputs` contains at most one
remittance per output index. A receipt supplies hints for every transaction input.
Every hint and remittance MUST match authenticated transaction bytes.

Plan `assets` is an array of unique strings and MUST exactly enumerate token
assets found in the planned sources and outputs, including ISSUE only when
creating a deploy. `operations` is an array of unique `{assetId, operation}` pairs;
`operation` is one of the table's enumerated strings. Each constraint array
contains objects of exactly the stated shape. Duplicate outpoints, asset change
constraints or target positions within an array MUST fail. Cross-array conflicts
and positions incompatible with requested output order MUST fail. Override
outpoints MUST identify managed inputs actually consumed. A selected input
without an override uses the default signature mode. Any malformed metadata
MUST fail without signing, mutation of balances or receipt acceptance.

## Signature requests and composability

An application requests one module-key signature using existing fields:

```text
createSignature({ protocolID, keyID: "mandala", counterparty,
  data: UTF8(JSON({version:1, tx:[...Atomic BEEF bytes...], inputIndex,
    sighashType, inputTopics:[...hints...], ownedOutputs:[...remittances...]})),
  seekPermission }, originator)
```

The six JSON members shown are required; `ownedOutputs` may be empty.
An optional `tokenProofs` member carries lineage packets as defined below. A
remittance is `{outputIndex, assetId, derivationPrefix, derivationSuffix,
senderIdentityKey}`; `assetId` may be `ISSUE` only for a deploy output. Root
selection for newly managed outputs is the action's selected root; mixed-root
custody MUST NOT be inferred. Additional JSON members, duplicate members,
invalid UTF-8, invalid byte arrays and invalid indices MUST fail.
`hashToDirectlySign` MUST be absent. The envelope is limited to 16 MiB before
allocation; a documented lower host limit MUST fail explicitly rather than
truncate. All hints and remittances are checked, not trusted.

The wallet MUST verify that the protocol's asset selector identifies the selected
source asset; ISSUE is valid only for the preserved original deploy tuple.
It MUST derive the selected key, match it to the selected managed P2PKH
source (or a recognized module-key signing role in a foreign script), construct
the exact consensus preimage from authenticated source data and authorize its
coverage. A foreign source requiring another module's or a BRC-29 key is not an
alias into this signer. Executed `OP_CODESEPARATOR`, when applicable, MUST be
handled using its actual executed script path and consensus script code; a
caller-provided code separator offset or signature slot is not evidence of that
path. If partial foreign execution needs missing material to determine the
preimage, the request fails until that material is supplied. This does not limit
foreign scripts that the module need not sign.

The result is BRC-100 `{signature: Byte[]}`: DER low-S ECDSA over the
wallet-computed transaction digest, without the script sighash byte. Verification
uses `hashToDirectlyVerify` and the same tuple, not the JSON envelope as `data`.
The wallet MUST reserve managed inputs and record consent before releasing a
signature. A signature request may spend module-managed balances; it MUST NOT
silently sign default-basket funding inputs.

### All signature modes

The module MUST support all consensus-valid sighash modes, including ALL, NONE,
SINGLE and ANYONECANPAY combinations, applying the relevant FORKID and script
rules. It MUST NOT impose the earlier four-mode restriction. Invalid consensus
modes or contexts fail through consensus validation, not a token-specific
whitelist. Standard wallet-generated managed-input signatures SHOULD use
ALL|FORKID without ANYONECANPAY unless the authorized agreement needs another mode.

The wallet MUST calculate what each signature actually commits to. With FORKID,
`hashPrevouts` commits all input outpoints only when ANYONECANPAY is absent;
ANYONECANPAY zeros that component. ALL commits all outputs, SINGLE only its
corresponding output, and NONE no outputs. These components MUST NOT be described
as interchangeable. A named, unspent counterparty input committed by a signature
prevents a completed transaction from consuming it after a conflicting spend;
that fact alone does not commit the requested outputs or guarantee token delivery.

A wallet MAY release a partially signed offer before receiving the counterparty's
unlocking scripts. For a guaranteed swap, the named incoming inputs and promised
wallet-owned outputs MUST be committed by the released signature, validated
covenant conditions, or other independently verified commitments that remain
binding in every valid completion. Otherwise the wallet MUST identify the
uncommitted terms and obtain consent to the possible outcomes, including token
loss or burn, missing consideration, or authority delegation where applicable.
It MUST NOT present conditional terms as guaranteed receipts or authorize only
the displayed favorable completion. This permits every signature mode without
inventing a commitment it does not provide.

Revalidation before wallet completion is mandatory but cannot restrict an
external party using an already released signature. A pending reference, UI
cancellation or expired allowance does not retract that capability. Composable
agreements remain possible with arbitrary scripts and independently supplied
signatures; the wallet enforces accurate authorization rather than a fixed swap
transaction template.

## Action planning, selection and change

Ordinary BRC-100 calls keep their existing argument and result shapes. The
module action plan is strict UTF-8 JSON, hex encoded and split into consecutive
chunks of at most 200 hex characters. It is carried in existing `labels`:

```text
p mandala plan <partIndex> <partCount> <hexChunk>
```

Hex chunks MUST contain an even, nonzero number of lowercase hex digits.
Indices are zero-based; index and count are decimal without leading zeroes and
bounded to uint32. Concatenate chunks by index, decode hex once, then decode
strict UTF-8 JSON with duplicate-member rejection. Nonfinal chunks MUST contain
exactly 200 hex characters; the final chunk contains at most 200. Reject missing
parts, inconsistent counts, invalid encodings or bounds before large allocation.
There MUST be exactly one complete plan, with each part present once and a
consistent positive count. Parts may occur among ordinary action labels; their
index determines reconstruction. A plan is bounded to 16 MiB decoded JSON and
existing per-label limits. A host with lower action limits MUST report an error.
Plan labels are module metadata and MUST NOT be interpreted as consent or as
[BRC-177](./0177.md) expiry labels. `listActions` queries using these exact labels
retain ordinary matching semantics with module-aware read permissions.

The plan has these required members and the optional `tokenProofs` member
defined above, with no other members:

| Member | Meaning |
| --- | --- |
| `version` | Integer `1`. |
| `assets` | Unique canonical asset IDs involved, plus `ISSUE` for a deploy. |
| `inputTopics` | Required hints for every explicit input; newly selected inputs are added by the wallet. |
| `ownedOutputs` | Remittances for requested outputs to be managed; same format as the signature envelope. |
| `operations` | Per-asset intent: `transfer`, `burn`, `deploy-fixed`, `deploy-authority`, `mint`, `authority-split`, `authority-combine`, `authority-transfer`, or `authority-end`; declare every applicable operation and validate against actual scripts. |
| `inputPositions` | Array of `{outpoint, index}` constraints on explicit inputs; empty when unconstrained. |
| `changePositions` | Array of `{assetId, index}` constraints for generated token change, or `{assetId:null,index}` for ordinary satoshi change; empty when unconstrained. |
| `sighashTypes` | Array of `{outpoint, sighashType}` overrides for managed inputs; empty uses the default above. |

An operation is `{assetId, operation}`. Authority operations and burns must be
explicit; inferred transfer intent never authorizes them. A plan's `ISSUE`
identifies only its deploy, not any existing asset. The transaction's prefix and
validated sources determine quantities and operations; the plan cannot override
them. A deploy plan MUST have exactly one deploy. After finalization, its record
is indexed under the resulting ID without changing the signed plan or derivation.

`createAction` MUST recognize plan labels, token-encoded requested outputs,
relevant module baskets, and explicit inputs already managed by the module. Missing required plans or hints fail.
The module MUST authenticate foreign inputs, select sufficient unreserved value
inputs separately per asset, and make fresh per-asset change outputs under the
custody profile. Valid foreign amounts are netted before wallet selection.
Authority operations select actual authority inputs, not a numeric balance.
Applications MAY supply required inputs or input/output positions. Setting
`options.randomizeOutputs:false` preserves requested output order; explicit
position constraints and generated change MUST be satisfied without inserting,
shuffling or replacing covenant-sensitive outputs. An impossible layout,
insufficient asset or satoshi balance, or absent overlay membership MUST fail
before signing. Newly generated keys and authoritative ownership facts belong to
the wallet; application selection does not make an input foreign.

Only declared burns may suppress value change; mint and issuance outputs follow
their declared supply rules. Satoshi funding, outputs and change use the ordinary
wallet action machinery alongside the token plan. The wallet MUST authorize the
final funded layout, not an earlier estimate. `createAction` MAY automatically
sign managed P2PKH inputs when that final action is valid and authorized, including
colored-coin payments and multi-asset swaps. Missing foreign unlocking scripts
or `signAndProcess:false` returns the existing `signableTransaction` reference.
Applications may exchange the resulting partial transaction and signatures.

`signAction` MUST preserve the pending plan, reservations, constraints and
previously committed fields; validate supplied unlocking scripts; refresh overlay
spendability and permission validity; and validate the final transaction before
returning it as complete or processing it. A changed context needs revalidation
and consent covering the change, with new signatures where required. A module
signature and an action reference for the same inputs MUST share one authoritative
reservation and authorization record rather than conflict or charge twice.

Reservations are atomic across all assets and satoshi funding. Failed checks
before signature release roll back provisional reservations. After signature
release, aborting an action may cancel processing but MUST retain the relevant
exposure record; inputs MUST NOT be offered to a conflicting action until the
wallet establishes that the capability can no longer consume them, or explicitly
authorizes a conflicting spend that invalidates the earlier offer. Unspentness
checks, observed external completion and conflicts update this record. Wallets
MUST distinguish pending exposure from settled spending. Quota implementation is
wallet-specific, but released capabilities cannot be hidden by resetting a
pending action. `noSend`, `sendWith` and ordinary two-phase flows remain supported;
returning a noSend transaction does not establish overlay admission.

## Internalization

`internalizeAction` uses the existing `basket insertion` protocol with the
module's per-asset basket and `insertionRemittance.customInstructions` containing
strict JSON `{version:1, assetId, derivationPrefix, derivationSuffix,
senderIdentityKey, inputTopics}`, optionally with `tokenProofs`. A deploy receipt uses `assetId: "ISSUE"` for key
derivation and derives its actual asset ID and basket from the supplied completed
transaction. The root is the wallet's selected root. Unknown or duplicate members
and missing required fields MUST fail. An incorrect basket MUST fail rather than
be silently reclassified; an issuance initiated by this wallet uses its automatic
final-ID assignment. `paymentRemittance` for ordinary satoshis remains BRC-29.

Before accepting a receipt the wallet MUST validate complete transaction scripts,
source evidence, foreign-input authentication, historical topical admission
of consumed inputs, per-asset amount and authority rules, and its control of each
requested custody output. It MUST NOT demand current unspentness of inputs
already consumed by that receipt.
The same encoding, lineage, amount and ownership checks apply to foreign inputs
used by `createAction` and prospective wallet-owned outputs used in signing
accounting. A candidate output is not yet admitted: its prospective credit is
conditional on transaction completion and overlay acceptance, and MUST NOT be
added to spendable local balance before receipt admission. The received outpoint itself MUST
already appear as admitted and unspent in its asset's spendability lookup.
Internalization MUST NOT silently submit an absent transaction to make this test
pass. Missing overlay admission MUST reject internalization. The sender or
higher-level flow is responsible for submission before requesting receipt.

For wallet-created completed actions, normal processing MUST submit the
transaction to every involved token topic and record each topic's actual
admission result. A `noSend` or partial action defers submission. Admission into
one asset's overlay does not imply admission into another's; local receipt and
spendable balances MUST only be credited after all required admission checks.
If Bitcoin completion occurs but an overlay operation fails, record the actual
pending/error state without claiming reversal of the on-chain spend. Retries MUST
be idempotent. Partial transactions cannot be internalized as completed receipts.

## Discovery, compatibility and security boundaries

This specification defines the optional [BRC-205](./0205.md) attribute
`brc207-mandala`. Its sole decoded value is `1`, meaning the wallet implements this
version's `mandala` protocol, basket and action-plan contract. Example:

```text
example-1.2.3; brc207-mandala=1;
```

Encoding, single occurrence and outer bounds follow BRC-205. Unknown values MUST
be ignored as unsupported metadata. A wallet MAY omit the attribute for privacy,
while locked, or to meet bounds; omission is not proof of non-support. Presence
is a snapshot, not authorization, proof of safe code or core-method negotiation.
It MUST contain no user-specific balances, grants, asset inventory or history.
Consumers SHOULD refresh on the selected connection before starting a workflow,
and MUST discard cached values on provider/account changes or disconnection.
Every actual call still checks current support and permissions. BRC-205's
extended-string compatibility configuration is required before emission; legacy
paths continue to return base-only versions. BRC-185 discovery is independent.
BRC-185 and BRC-205 are unmerged companion specifications at publication of this
revision; canonical links identify their intended locations after merge.
Implementations MUST independently adopt BRC-205's profile before using this
attribute; this document does not assert deployment or adoption of that profile.

The module supports the BRC-161/162 token model; it does not assume compatibility
with existing `p mandala`, BTMS, generic application keys or other basket profiles.
Migration and recovery are outside this specification. An application MUST NOT
strip the reserved prefix or fall back to generic signing when this module is
unavailable. No software implementation, universal deployment, or live-wallet
conformance is asserted here.

Overlay trust is explicit and independent of SPV and Bitcoin consensus. A
current spendability answer cannot promise future availability; consensus input
commitments and script conditions establish completion constraints. Metadata,
caller hints, permissions and partial transaction references cannot change those
constraints. Trusted module code retains private keys and validates the facts
supplied to wallet policy and presentation. Arbitrary foreign scripts retain
composability without receiving access to internal wallet signing capabilities.

## Conformance cases

| Case | Required behavior |
| --- | --- |
| Same identities and remittance tuple | Sender-derived recipient public key matches recipient-derived private key; exact encoding and owner selection agree. |
| Deploy finalized | Asset ID and value/authority basket assigned from final outpoint; ISSUE-derived key preserved. |
| BRC-161 and BRC-162 inputs for one ID | One asset account, encoding-specific validation, BRC-162 generated outputs. |
| Missing/wrong hints, service substitution, missing overlay output | Fail without signing or crediting. |
| Foreign input provenance | Reconstruct and verify source; matching current topic admission required before amount netting. |
| Split, merge, burn, mint and all authority operations | Exact per-asset rules and consent; no authority-as-value arithmetic. |
| Three-asset swap or token-for-satoshis swap | Every leg and satoshi fee represented independently. |
| Wallet selection and change with fixed positions | Sufficient eligible inputs and fresh change; preserve constraints or fail. |
| Partial offer before foreign unlocks | Pending status, verified sources, accurate commitments and authorization of possible outcomes. |
| ALL, NONE, SINGLE and ANYONECANPAY | Consensus preimage correctness; no fictitious hashPrevouts or output coverage. |
| Completed foreign-script spend | Full consensus script validation before use or processing. |
| Internalization absent from overlay | Reject; do not silently submit. |
| Retry, concurrent requests, abort and noSend | Shared reservations and accurate exposure; no duplicate credits or quota charges. |
| Capability omitted or stale | Handle actual call results; no generic-signing fallback. |
