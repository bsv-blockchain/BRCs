# BRC-207: Transaction-Context Signing in a BRC-98 Module

Ty Everett (ty@projectbabbage.com)

## Abstract

This draft proposes a standard wallet module that signs one application-owned
transaction input with a key in a separate permission namespace. The application
supplies the transaction and the input index. The wallet validates the source
outputs, computes the signature hash itself, and authorizes the transaction
through trusted module policy. It never accepts a caller-computed digest.

The proposed scheme is `spendablepreimage`. It uses the existing BRC-100
`getPublicKey`, `createSignature` and `verifySignature` methods, with module
semantics selected by BRC-98. It adds no method, argument, result field or wire
call code. It does not sign BRC-29 keys or replace normal wallet spending.

## Status and motivation

This is a proposal for review, not an implementation or a claim of consensus.
The normative contract below is a concrete baseline; the open questions must
be resolved before adoption or minting assets into this domain. The uppercase
terms MUST, MUST NOT, SHOULD and MAY indicate normative requirements for an
implementation adopting this profile.

A data-signing grant does not describe which asset is consumed or which outputs
are authorized. Moving an asset key into another ordinary data-signing protocol
alone does not supply that context. BRC-98 allows a trusted module to own the
signing permission decision and the key domain while retaining the stable
[BRC-100](./0100.md) interface. [BRC-229](./0229.md) provides the model for
semantic dispatch inside an existing method; its point-operation permissions
are not spending permissions and are not reused here.

For example, an application can ask the wallet to sign input 0 of a transaction
spending an application covenant, then place the returned signature in its
unlocking script and complete an already authorized `signAction`. Funding and
change managed by the wallet still go through `createAction`/`signAction`.
The module neither selects wallet coins nor broadcasts the transaction.

## Specification

### 1. Namespace and derivation

The exact protocol-name grammar is:

```text
p spendablepreimage <logicalProtocolID>
```

The scheme ID deliberately contains no hyphen: BRC-43's canonical derivation
names permit letters, numbers and spaces. A display name such as “Spendable
Preimage” is not a wire alias. `p spendable-preimage` MUST NOT silently normalize
to this scheme or select its keys. Final spelling is an adoption question.

`logicalProtocolID` MUST contain only lowercase ASCII letters, digits and single
spaces, with no leading, trailing or repeated spaces. It MUST be 5–260
characters and MUST NOT end in ` protocol`. The complete protocol name is thus
25–280 ASCII characters, within BRC-43 and BRC-100 limits. Nested `admin` or `p`
text in the logical name has no dispatch significance and cannot select another
key domain.

Let `s`, `L`, `K` and `C` be the security level, logical name, key ID and
counterparty. All supported methods MUST use the same BRC-42/43 tuple:

```text
protocolID   = [s, "p spendablepreimage " + L]
keyID        = K
counterparty = C
invoice      = "<s>-p spendablepreimage <L>-<K>"
```

Key IDs MUST be 1–800 UTF-8 bytes, using BRC-100's normative byte limit
(which is narrower than BRC-43's 1033-byte limit). The counterparty defaults to `self`;
`self`, `anyone`, and a canonical compressed secp256k1 public identity key are
legal. Resolve `self` to the selected wallet root's public key, and `anyone`
to the public private-key-1 counterparty, under BRC-43.

Transaction bytes, input index, flags, application originator and authorization
grants MUST NOT change the derivation tuple. A trusted host MUST enforce
originator isolation through authorization, not by silently changing the invoice.
Ordinary and privileged root selection retain their BRC-100 meanings. Privileged
access requires a valid `privilegedReason`, explicit authorization and available
trusted privileged derivation; unavailable access fails closed. Different roots
must not share grants.

For `anyone`, third parties can derive the wallet's child public key from its
selected root's public key, the invoice and private key 1 using BRC-42.
The ordinary identity public key does not reproduce privileged-root child keys. This does not
reveal the wallet's child private key or give the application spending authority.

### 2. Methods and containment

A wallet lacking this module MUST reject the reserved namespace as BRC-98
requires. A supporting wallet MUST dispatch before generic cryptographic
permission defaults or generic data signing, including when a generic signing
prompt is disabled.

| Method | Module behavior |
| --- | --- |
| `getPublicKey` | Normal BRC-42 public derivation using the tuple above and appropriate public-key permissions; `forSelf` retains its normal meaning. `identityKey: true` is outside this module and MUST NOT be combined with its protocol. |
| `createSignature` | Transaction-context operation in section 3; never generic data or digest signing. |
| `verifySignature` | Ordinary BRC-3 verification using the same tuple and BRC-100 `data` or `hashToDirectlyVerify` arguments; verification grants no signing permission. |
| Encryption, decryption, HMAC, specific linkage and all other protocol operations | MUST reject within this scheme. |

The module MUST NOT provide an alias to BRC-29, an `admin` protocol, an ordinary
application protocol, another module or the root identity private key. No private
scalar or key-deriver capability may leave trusted wallet/module code. A public
module call cannot invoke an unrestricted internal signer. The host MUST also
prevent root-linkage disclosure that would expose this protected domain; a
protocol-specific restriction alone does not constrain BRC-69 Method 1's scope.

For minting an output controlled by the wallet, select its child explicitly:

```ts
wallet.getPublicKey({
  protocolID: [2, 'p spendablepreimage example covenant'],
  keyID: 'owner 1',
  counterparty: 'anyone',
  forSelf: true
}, originator)
```

BRC-100 defaults `forSelf` to false; that selects the counterparty's child,
not the wallet child this module signs. Third-party public derivation must
likewise select the intended owner's child. Public derivation permissions
remain distinct from module spending authorization.

### 3. Transaction request and response

The outer request uses only existing BRC-100 fields:

```ts
wallet.createSignature({
  protocolID: [2, 'p spendablepreimage example covenant'],
  keyID: 'owner 1',
  counterparty: 'anyone',
  data: utf8Bytes(JSON.stringify({
    version: 1,
    tx: atomicBEEFBytes,
    inputIndex: 0,
    sighashType: 193
  })),
  seekPermission: true
}, originator)
```

`utf8Bytes` and `atomicBEEFBytes` are explanatory placeholders, not new wallet
arguments. The JSON member `tx` is a numeric byte array, not base64 or a typed
array serialized as an object. `hashToDirectlySign` MUST be absent. Reject a
request containing it, even if `data` is also present.

The `data` bytes MUST decode as strict UTF-8 JSON with exactly four members:

| Member | Requirement |
| --- | --- |
| `version` | Integer `1`. |
| `tx` | Nonempty array of integer bytes, each 0–255, encoding one BRC-95 Atomic BEEF subject transaction and its supporting BRC-62/BRC-96 data. |
| `inputIndex` | Unsigned integer selecting an existing input in that subject transaction. |
| `sighashType` | Integer equal to one of `65`, `67`, `193`, `195` (section 5). |

Reject duplicate/unknown members, invalid UTF-8, fractions, nonfinite values,
incorrect types, trailing non-whitespace data and malformed BEEF or invalid source ancestry. The subject transaction is
unsigned or partially signed: final subject-input script execution is deferred
as specified below. Member order
and insignificant JSON whitespace do not matter. Limit the complete UTF-8
request to 16 MiB; a host MAY impose a documented smaller resource limit and
MUST return an error without signing if it is exceeded. Validation must enforce
bounds before unbounded allocation. The request does not contain a raw digest,
preimage, claimed source amount, caller-selected script code or replacement key.

A successful response is exactly the normal `{ signature: Byte[] }`, containing
a strict DER-encoded low-S secp256k1 ECDSA signature over the wallet-computed
SHA256d signature preimage. It MUST NOT include the sighash byte. The application
appends the selected sighash byte when its unlocking template requires it.
Verification uses `verifySignature.hashToDirectlyVerify` with the computed
SHA256d transaction digest and the same derivation tuple. Passing this JSON
envelope as ordinary `verifySignature.data` verifies a different message and
MUST NOT be treated as verification of the transaction signature.
No transaction reference, extra response member or signature-slot convention is
introduced. The module returns no wallet funding signatures.

### 4. Validation and wallet ownership

Before authorizing or signing, trusted module/host code MUST:

1. Parse the Atomic BEEF framing and identify its sole subject transaction
   by the header txid of the exact supplied, possibly incomplete bytes. This
   profile uses BRC-95 framing and ancestor-only inclusion, but defers BRC-95's
   final subject-input script execution until completion; it MUST NOT claim
   the incomplete subject is a fully valid or mined transaction. Resolve and
   validate every source transaction, output index, value and locking script
   through BEEF/SPV rules and wallet policy. A txid-only entry must be resolved
   by trusted wallet knowledge or rejected; caller claims are insufficient.
   Duplicate input outpoints, missing sources, invalid proofs, conflicting
   source representations and invalid monetary totals MUST fail. Ancestry
   script validity and SPV checks are not deferred. After inserting all final
   unlocking scripts, the completing action/recipient MUST validate the final
   transaction before accepting or broadcasting it; its final txid may differ
   from this signing request's header txid.
2. Derive the proposed signing public key using section 1, without substituting
   a spending or identity key. Validate public-key counterparties before use.
3. Check the selected outpoint against authoritative wallet ownership and
   reservation state. This draft's baseline refuses **every selected input
   managed by the wallet**, in `default` or any other basket, including reserved,
   pending, internally managed and unassigned wallet coins. `listOutputs`
   visibility, omission of a basket, or removal of organizational metadata is
   not evidence that the input is external. Unknown ownership fails closed.
   Check again immediately before releasing a signature, consistently with
   concurrent internalization and reservations. A mixed transaction may have
   other wallet-managed funding inputs signed only by the normal action path.
4. Validate that the selected source locking script commits to the derived
   public key in a supported signing template. P2PKH is the baseline template.
   Covenant templates require a trusted, reviewed recognizer establishing the
   key's role and deriving the exact script code. Finding matching bytes in an
   arbitrary script is insufficient. Unrecognized templates MUST fail closed.
   This base profile rejects any source locking script containing an executed
   or executable `OP_CODESEPARATOR`; bytes inside data pushes are not opcodes.
5. Build the signature preimage from the parsed transaction, verified source
   amount and validated script code. Use the transaction's actual version,
   locktime, selected input sequence, outpoint and outputs. No caller-supplied
   digest or preimage may be substituted. Apply section 5's flags and section
   6's authorization to this immutable context.

The base module does not accept a caller's claim that an output is an NFT or
that a satoshi value equals a fungible-token quantity. A template recognizer
establishes signing-key/script relationships; asset accounting additionally
requires an independently specified token validator and policy. SPV proves
transaction ancestry under its assumptions, not present unspentness or covenant
business semantics. The host MUST apply its ordinary currentness/conflict checks
and MUST NOT present unsupported provenance claims as verified.

### 5. Signature coverage

The supported flags are `SIGHASH_ALL|FORKID` (`0x41`),
`SIGHASH_SINGLE|FORKID` (`0x43`), and either with `ANYONECANPAY`
(`0xc1`, `0xc3`). Reject `NONE`, absent FORKID, unknown bits and a SINGLE request
without an output at the selected input index. The module MUST support `0x41`;
it MAY support the other three modes only with explicit coverage-aware policy.
Unsupported modes MUST produce a documented error.

The trusted UI/policy MUST distinguish what the signature commits to from what
is merely displayed. ALL commits to every output. SINGLE commits only to the
corresponding output; the others can change. ANYONECANPAY permits other inputs
to change. The caller MUST NOT treat a displayed full transaction as assurance
that all its fields are bound by a partial-coverage signature. Policy based on
uncommitted inputs or outputs MUST reject unless a validated covenant supplies
the missing commitment. A generic module cannot assume that it does.

Unlocking scripts are not transaction identity commitments. Applications MUST
NOT assume that an unconfirmed transaction's txid is stable merely because its
signature preimage is fixed. If a covenant workflow requires stable outpoints,
it must establish finality/currentness through its own protocol.

### 6. Module-owned authorization

The module MUST obtain spending authorization through trusted wallet policy,
independent of ordinary BRC-43 signing grants, security level 0, registry
metadata and generic permission-prompt defaults. A data-signing grant MUST NOT
satisfy this policy. Authenticate the originator through the substrate; a
caller-supplied string by itself is not authentication.

The authorization context MUST include the originator, logical protocol, key
ID, root selection, counterparty, selected outpoint and amount, source script
and recognized template, all outputs and satoshi amounts, fee, transaction
version/locktime/sequences, flags and exact signature coverage. Show recognized
asset quantities only with a validated asset profile; otherwise describe them
as unknown. Display caller descriptions as untrusted text.

The default authorization is for this exact validated context. Wallets MAY offer
revocable, expiring cached grants for an explicitly bounded application workflow.
Such a grant MUST identify its originator, logical protocol, root and
counterparty scopes, supported templates, permitted outpoints or validated asset
selector, signature modes, recipient/output constraints and amount/use limits.
Each request must be inspected against those bounds. Atomically account for
concurrent grants before release; equivalent pending requests SHOULD share one
prompt, and retries MUST NOT spend a quota twice or release extra distinct
capabilities. A whole-protocol raw-signing grant or unparsed tokenId is not a
bounded asset grant.

No prompt per signature is mandated when a valid bounded grant already covers
the request. If no applicable authorization exists and `seekPermission: false`,
fail without prompting. If it is true or absent, the module MAY seek trusted
user consent; denial, revocation, expired authorization or unavailable policy
MUST fail without signing. Ordinary and privileged grants remain separate.
Cached consent cannot bypass any structural or ownership check.

Each wallet deployment MUST provide a trusted presentation for this authorization
context using its own UI technology. The policy/module boundary MUST expose
structured validated facts to that presentation, rather than require arbitrary
application HTML or a particular framework. Native, browser and headless hosts
must enforce the same facts and scope; a headless host needs an already authorized
bounded policy or a trusted out-of-band approval surface. If neither is available,
fail closed. A React renderer in one wallet does not establish UI interoperability
in another. Showing satoshi amounts and scripts alone MUST NOT be described as
control over ordinal or higher-layer token balances.

### 7. Errors and host contract

Errors use existing BRC-100 error framing. They SHOULD distinguish unsupported
scheme/template/mode, invalid context, wallet-managed input, resource limit and
authorization denial without revealing keys or private inventory. This draft
allocates no new core error field or call code.

A host must provide trusted key derivation, BEEF validation/currentness,
authoritative ownership/reservation queries, template recognition, signature
preimage construction and authorization/accounting. Module installation is a
wallet trust decision; untrusted application code cannot register itself as a
permission module. A semantic handler may compute a conforming result directly
as in BRC-229. It MUST NOT forward the transaction envelope into ordinary
`createSignature`, which would sign the envelope's hash instead of the selected
transaction input. Internal derivation remains inaccessible to generic app calls.

## Action flows, baskets and labels

A covenant application may use `createAction` to obtain a `signableTransaction`,
validate final output order and source inputs, request the module signature, then
assemble its unlocking script and call `signAction`. Preserve the exact sequence
used for signing when providing `sequenceNumber`; changing any committed field
requires revalidation and appropriate authorization. For fixed output positions,
use `options.randomizeOutputs: false`. Wallet funding signatures remain subject
to normal spending limits and the action reference. `abortAction` governs wallet
reservations; it cannot retract a released external module signature.

`options.noSend` remains a normal action option. [BRC-177](./0177.md) separately
defines `p nosend expiry` behavior where supported; unsupported labels must fail
under BRC-111. BRC-177 does not supply a general covenant signer, guarantee the
reclaim wins, or revoke externally signed application inputs. Recipient-broadcast
and fee/change workflows need qualification against actual wallet implementations.
A permanent handoff with a wallet-sized dedicated funding input, no protected
change and no expiry/reclaim is a distinct requirement. This profile does not
add a `nosend` form or claim BRC-177 already implements that requirement.

This draft defines only a BRC-98 protocol module, no BRC-99 basket or BRC-111
label. The same scheme word must not be treated as allocating a basket or label
by implication. A future basket profile needs its own ownership, spend-policy
and query contract. Base-profile wallet-held inputs remain on the action path.
A future token module cannot route around this boundary merely by renaming a
basket or disabling generic signing permissions.

## Compatibility, rollout and recovery

BRC-29 payment invoice numbers, remittance bytes, public derivation and
verification stay unchanged. BRC-44's private-operation restriction is a
behavioral change for applications using payment keys for generic signatures;
it must be communicated as such. Ordinary BRC-100 methods and non-module
semantics remain available; supporting the full core interface does not imply
support for this optional module.

Wallets without the module MUST reject it. Applications MUST establish support
on the wallet actually selected before minting, using documented deployment
configuration or a permitted public derivation request. Successful derivation
alone does not establish support for a covenant template, signature mode,
privileged root, basket policy or token accounting. A refusal is not permission
to strip the `p` prefix or fall back to blind signing. No universal deployment is
claimed, and this proposal does not require adoption of unsettled ordinal
profiles to support the base module.

Draft [BRC-185](https://github.com/bsv-blockchain/BRCs/pull/272) and
[BRC-205](https://github.com/bsv-blockchain/BRCs/pull/302) discuss additive scheme
advertisements while preserving all core methods. Neither defines a scheme-list
attribute usable here. `getVersion` metadata is not an authorization grant;
legacy string/transport limits still apply. This proposal allocates no new
version attribute and must not rely on one being deployed.

Migration changes keys and on-chain locking scripts; a policy update or basket
rename cannot do that. Before rollout, applications and wallets SHOULD inventory
legacy key tuples/scripts, qualify destination support, publish recovery and
rollback guidance, and move new issuance directly to the final agreed domain.
Existing generic signatures should be verified with their old public keys.
Signing new non-asset data belongs in a separate non-spending protocol.

The module MUST NOT sign old BRC-29, admin or general-domain application keys,
even for an alleged rekey transaction. Normal internalized BRC-29 payments can
move through the authorized action path. Legacy custom scripts outside that
path require a separately reviewed, trusted wallet recovery mechanism that
verifies ownership, transaction context, destinations and fees without exposing
a blind signer. Such a recovery profile is not specified here. Preserve source
transactions and key metadata; do not claim that all legacy assets can migrate
or that rejection is lossless. If safe recovery is unavailable, report the
unsupported asset and recovery requirement explicitly. Do not silently delete,
relabel, or reopen raw signing to hide the incompatibility.

A coordinated release should qualify module dispatch, derivation and recovery
across wallets before applications depend on it. This document is a standards
proposal only; release timing and implementation work remain separate.

## Conformance review matrix

These are required behavioral cases for a future offline interoperability suite,
not executable vectors or a claim that deployed wallets pass.

| Case | Expected result |
| --- | --- |
| BRC-29 receive/send, including private-key-1 sender | Same payment invoice and accepted remittance representation; normal validation and spending policy. |
| BRC-29 public derivation/verification | Available under normal permissions, no spending grant. |
| BRC-29 generic signing in either payload form | Refused regardless of cached consent or privileged request. |
| Module absent | Reserved scheme rejected; core interface still present. |
| Module public derivation and third-party `anyone` derivation | Same child public key for the same root/tuple. |
| Different logical domain, root, key ID or counterparty | Different derivation identity; no grant crossover. |
| Same tuple, different transaction/input/flags | Same signing key, separately evaluated context and coverage. |
| Valid external P2PKH context, ALL and exact consent | DER low-S signature verifies over wallet-computed input digest. |
| Direct digest, missing source data, ambiguous JSON or invalid context | Rejected without signing. |
| Selected input in default, other basket, reserved or unassigned wallet state | Rejected; normal action path required. |
| Concurrent internalization or permission revocation | Ownership/grant rechecked; no signature after a failed boundary check. |
| Other wallet funding inputs in mixed transaction | Module signs only the external selected input; action policy controls funding. |
| Unknown covenant template or script-code ambiguity | Rejected until a reviewed profile exists. |
| NONE, legacy hash mode, unknown flags, SINGLE without matching output | Rejected. |
| SINGLE/ANYONECANPAY authorized by supported policy | UI and policy distinguish uncommitted fields; no false whole-transaction guarantee. |
| Generic signing prompts disabled; level 0; `seekPermission: false` without grant | Module authorization still enforced; no signing or prompt for the latter. |
| Bounded cached consent, concurrency, retry, revocation and expiry | Bounds enforced atomically without duplicate authorization prompts or quota consumption. |
| Two-phase action, fixed positions/sequences, `noSend`, expiry and abort | Correct action reference and commitments; no claim of retracting external signatures. |
| Wallet lacks ordinal/token/template module | Explicit unsupported status; no generic fallback or fabricated token limits. |
| Legacy custom-key asset migration | Recovery gate reported; no BRC-29/module-key substitution. |

Published cross-wallet derivation and complete benign transaction vectors,
independent preimage validation, template review and permission lifecycle tests
are adoption gates. They must be developed without live vulnerability probing.

## Open design questions

1. **Selected-input ownership:** retain this draft's refusal of all wallet-managed
   inputs, narrow it to `default`, or define an explicit BRC-99 basket scope?
   The latter choices need a normative replacement for basket authorization,
   reservations and asset accounting before they can be used. No exception is
   implied by this draft.
2. **Name and final key domain:** ratify `spendablepreimage` and the exact tuple,
   or specify a different grammar/derivation mapping before any minting. JSON
   carriage, the 16 MiB resource ceiling and supported flag set also need review.
3. **Covenant coverage:** which publicly specified templates and recognizers
   should form the first interoperable profile? P2PKH alone does not solve
   arbitrary covenants. Code-separator support and other signature-slot
   conventions require a separately precise contract if added.
4. **Token permissions and UI:** define validated token selectors, quantity accounting,
   recipient restrictions and concurrent/reorg-safe limits without one prompt
   per UTXO. Satoshi limits alone do not express token limits. No current ordinal
   scheme is adopted by this proposal. Qualify trusted renderers across wallet
   UI technologies; module installation alone does not establish presentation
   support.
5. **Legacy recovery:** define a safe migration profile for custom scripts under
   BRC-29 or ordinary application protocols before claiming complete recovery.
   A reserved-protocol rekey-only path was discussed but is not specified here.
6. **Deployment/discovery:** identify the first interoperable wallet set, how
   template/mode support is established, and whether a future BRC-205 scheme
   advertisement should be standardized. No runtime protected-protocol list is
   allocated. A generalized BRC-44 balance-key rule needs its own review.
7. **Proof availability:** application history/provenance export is a separate
   need; this signing profile cannot make `listActions` return arbitrary BEEF.
   Determine whether existing APIs or another proposal should cover it.

## Implementations

None is included or claimed by this draft. Wallet/module implementation,
production rollout and issue dispatch are separate work after standards review.
