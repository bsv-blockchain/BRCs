# BRC-112: Balance Baskets: Backwards-Compatible Basket Balance Queries

Ty Everett (ty@projectbabbage.com)

## Abstract

This specification defines a backwards-compatible extension to [BRC-100](../wallet/0100.md) that allows applications to query a basket's balance using a `balance ` prefix in `listOutputs`. The wallet returns no outputs and re-purposes `totalOutputs` to report the sum of satoshis contained in all outputs in the specified basket.

## Motivation

Applications often need a quick way to retrieve the total value of a basket without enumerating all outputs. Extending `listOutputs` with a special basket prefix preserves API compatibility while enabling efficient balance queries.

## Specification

### Balance Basket Prefix

A balance query is requested by using a basket name that begins with `balance ` (a lowercase "balance" followed by a space). The remainder of the basket string is treated as the target basket name.

Example:

- `listOutputs({ basket: "balance savings" })`

### Required Behavior

When `listOutputs` is called with a basket name beginning with `balance `:

- The wallet must return **no outputs** in the results array.
- The wallet must re-purpose `totalOutputs` to contain the sum (in satoshis) of **all** outputs currently in the target basket that match any provided tag filters.
- The wallet must still enforce all normal permission checks for access to the target basket.
- The wallet must apply any basket resolution, ownership, internalization, and tag-filtering rules as if the caller had requested outputs from the target basket directly.
- No regard is given to the `limit` or `offset` parameters, since this is a sum of total value.

This behavior is backwards compatible because existing callers will ignore the empty outputs array and read `totalOutputs` as the count of outputs; with this extension, `totalOutputs` is intentionally redefined **only** when the `balance ` prefix is used.

### BRC-99 Module Baskets

For module-defined baskets in [BRC-99](../wallet/0099.md):

- `balance p <module> <basket>` is **never** allowed and must be rejected.
- `p <module> balance <basket>` **may** be implemented at the module's discretion.

If a module chooses to implement balance semantics, it may interpret `balance <basket>` according to its own rules, including permissioning and aggregation behavior. If a module does not implement this, the wallet must reject the request as unsupported.

### Exact Module Balance Representation

A module MAY explicitly adopt this profile when its balance can exceed
JavaScript's safe-integer range. Adoption does not change ordinary output counts,
non-module basket semantics or other BRC-100 numeric fields. It preserves the
balance result shape: `outputs` is empty, `BEEF` is absent, and `totalOutputs`
contains the aggregate. The module MUST define the units, eligible records,
permission scope and tag-filter behavior of each query.

The result domain is the unsigned integer range `0..18446744073709551615`.
Implementations MUST compute the aggregate exactly in a sufficiently wide
integer domain before checking this response bound. In JavaScript, values in
`0..9007199254740991` MUST be exposed as `number`; larger values MUST be exposed
as `bigint`. Equivalent exact integer types may be used in other languages.
An unsafe or already-rounded `number` MUST NOT be accepted or repaired by
casting it to `bigint`.

- **Binary BRC-100:** encode the aggregate using the existing canonical unsigned
  VarInt, at most one marker plus eight little-endian bytes. Decode without an
  intermediate floating-point number. This field has no negative sentinel;
  eight `ff` payload bytes mean uint64 maximum, not `-1`. The ordinary uint32
  output-count check MUST NOT be applied to an adopted balance query. Normal
  output-list counts retain their ordinary bounds.
- **JSON substrates:** safe-range values MUST be JSON numbers; larger values
  MUST be canonical decimal strings matching `[1-9][0-9]*`, without signs,
  whitespace, leading zeroes, fractions or exponent notation. The decoded value
  must be within the larger range through uint64 maximum. Adapters MUST restore
  the exact API integer type before exposing a successful result. Unsafe JSON
  numeric values, small-range strings, tagged objects and out-of-range strings
  MUST fail validation. Standard JSON has no native `bigint` literal.
- **Direct or structured-clone APIs:** preserve the exact API integer type;
  a transport incapable of doing so MUST report an error.

All layers that validate, serialize or consume this result MUST recognize the
query's explicitly adopted profile. Unsupported profiles and aggregates above
uint64 MUST fail with an explicit error. They MUST NOT produce rounded, wrapped,
saturated or partial balances. An incapable receiver reports a local protocol
error rather than displaying a coerced value. This specification mandates no
output-enumeration fallback. A response overflow does not invalidate the user's
holdings. Existing implementations may require updates before supporting this
profile; no universal compatibility with deployed validators is asserted.

### Validation Rules

- The `balance ` prefix must be lowercase and followed by a single space.
- The target basket name that follows must conform to the basket naming rules in [BRC-100](../wallet/0100.md) and [BRC-99](../wallet/0099.md) where applicable.
- If the target basket does not exist or is not accessible, the wallet must return the appropriate error according to [BRC-100](../wallet/0100.md).

## Conclusion

By reserving a `balance ` prefix within basket queries, this specification enables efficient balance retrieval while remaining compatible with existing `listOutputs` behavior and the broader wallet permission model.
