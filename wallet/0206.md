# BRC-206: BRC-100 Wallet Discovery and Chooser

Richard Boase (@b0ase), The Bitcoin Corporation Ltd

## Abstract

A user can have several BRC-100 wallets on one machine: browser extensions,
a desktop wallet on `localhost:3321`, a wallet in a phone. Today an app
connects to whichever wallet the SDK finds first, and the user is never asked.

This BRC defines:

1. **Discovery events** that let every wallet in a page announce itself, so
   wallets stop competing for the single `window.CWI` slot.
2. **A discovery procedure** that also finds wallets that don't announce
   (legacy `window.CWI`, local HTTP wallets).
3. **A standard chooser panel**, so users see the same list, in the same
   order, with the same controls, on every BRC-100 app.

## Motivation

`WalletClient('auto')` in `@bsv/sdk` tries all substrates at once and picks
the first that answers, in a fixed priority with `window.CWI` at the top. That
causes three failures that users hit today:

- **The desktop wallet is unreachable while any extension is installed.**
  A user runs BSV Desktop, opens an app, and gets their Yours or bWalletX
  extension instead. The only fix is to disable extensions.
- **Extensions overwrite each other.** `window.CWI` holds one object. Two
  extensions that inject it race; the last content script wins silently.
  Forks of the same extension can also answer each other's page events,
  producing two approval prompts for one request.
- **Apps can't tell users what they're connected to.** A legacy `window.CWI`
  has no name or icon, so apps can't show "Connected to Yours Wallet" or
  offer "Switch wallet".

The principle: **the app never picks a wallet for the user.** It shows what
is available and remembers what the user chose.

## Specification

The key words MUST, SHOULD and MAY are used as in RFC 2119.

### 1. Wallet info

```ts
interface BRC100WalletInfo {
  /** Random per page load. Dedupes repeat announcements. */
  uuid: string
  /** Human-readable name, e.g. "BSV Desktop". MUST be the wallet's own name. */
  name: string
  /** Square icon as a data: URI (SVG or PNG), at least 96×96. */
  icon: string
  /** Stable reverse-DNS id of a domain the wallet controls, e.g. "com.bwalletx.extension". */
  rdns: string
  /** How the wallet is reached. */
  kind: 'extension' | 'desktop' | 'in-app' | 'web' | 'mobile' | 'other'
}

interface BRC100WalletAnnouncement {
  info: BRC100WalletInfo
  wallet: WalletInterface   // BRC-100
}
```

### 2. Discovery events

**App → wallets:**

```ts
window.dispatchEvent(new Event('brc100:requestWallet'))
```

**Wallet → app** (one per wallet):

```ts
window.dispatchEvent(new CustomEvent('brc100:announceWallet', {
  detail: Object.freeze({ info, wallet })
}))
```

Wallets injected into a page (extensions, in-app browsers):

- MUST dispatch `brc100:announceWallet` once when injected, and again every
  time they see `brc100:requestWallet`.
- MUST use a unique `rdns` and their own `name` and `icon`.
- MUST return their own name from `getVersion()` (e.g. `bwalletx-1.2.0`), not
  the name of a wallet they were forked from.
- MUST use transport event names unique to the wallet, so a request meant for
  one wallet is never answered by another built on the same library.
- SHOULD keep setting `window.CWI` for older apps, but only if it is empty.
  They MUST NOT overwrite another wallet's `window.CWI`.

Apps:

- MUST add their `brc100:announceWallet` listener before dispatching
  `brc100:requestWallet`.
- MUST dedupe by `rdns` (keep the latest announcement).
- MUST NOT pick among discovered wallets without the user's choice, except
  under §4 rule 4 (remembered choice) or rule 5 (single in-app wallet).

### 3. Discovery procedure

An app (or the SDK's `discoverWallets()`) builds the list in this order:

| # | Source | How | Default `rdns` / name |
|---|--------|-----|-----------------------|
| 1 | Announced wallets | §2, collect for 300–500 ms | as announced |
| 2 | In-app host | If the page is framed, try BRC-100 XDM `getVersion` (2.5 s) | as reported |
| 3 | Unannounced `window.CWI` | Present but not one of the announced wallet objects; name it from `getVersion()` | `legacy.window-cwi` / name from version, else "Browser wallet" |
| 4 | Local desktop wallet | `HTTPWalletJSON` to `http://localhost:3321`, `getVersion` with a 1.5 s timeout | `local.json-api.3321` / name from version, else "Desktop wallet" |
| 5 | Local secure desktop wallet | Same, `https://localhost:2121` | `local.secure-json-api.2121` |
| 6 | App-supplied wallets | e.g. phone pairing, web wallets | supplied by the app |

Rules:

- Local HTTP probes (4, 5) MUST NOT run on mobile user agents or inside
  in-app browsers, and SHOULD run only when the user starts connecting. Some
  webviews hang on `localhost` requests.
- A wallet found by two routes (an announced wallet that also owns
  `window.CWI`) MUST appear once, under its announced name.
- A wallet that answers `getVersion` but refuses other calls is **locked**,
  not absent. List it with status `locked`.

### 4. The standard chooser panel

Implementations MAY style the panel to match the app. They MUST keep this
structure and behaviour so users recognise it across apps.

```
┌ Connect a wallet ─────────────────────── ✕ ┐
│                                            │
│  [◆] bWalletX           Browser extension ›│
│  [◆] Yours Wallet       Browser extension ›│
│  [◆] BSV Desktop        This computer     ›│
│  [◆] Metanet Client     This computer  🔒 ›│
│                                            │
│  ── Last used on this site: BSV Desktop ── │
│                                            │
│  [ Refresh ]          Don't see yours? ↗   │
└────────────────────────────────────────────┘
```

**Contents**

1. Title "Connect a wallet" (localised).
2. One row per discovered wallet: icon, name, kind label, and status
   (ready, locked, connecting, failed). Rows are never merged.
3. Kind labels: `extension` "Browser extension", `desktop` "This computer",
   `in-app` "This app", `web` "Web wallet", `mobile` "Phone".
4. Order: last used on this site first, then announced extensions, then
   desktop, then others. Within a group, alphabetical. The order MUST NOT be
   chosen by payment or partnership.
5. A **Refresh** control that re-runs discovery (users often start their
   desktop wallet after opening the panel).
6. A "Don't see your wallet?" link the app configures (help or a wallet
   list). It MUST NOT be a default-wallet install link presented as the only
   option.
7. When nothing is found: an empty state saying no BRC-100 wallet was found,
   with Refresh and the help link.

**Behaviour**

1. Selecting a row calls `getPublicKey({ identityKey: true })` on that wallet.
   Success closes the panel with that wallet. Failure keeps the panel open and
   shows the wallet's error on that row (for example "Unlock BSV Desktop and
   try again").
2. Keyboard: arrow keys move between rows, Enter selects, Escape closes.
   The panel is a modal dialog (`role="dialog"`, `aria-modal`, focus trapped,
   focus returned on close). Rows are buttons with accessible names
   "Name, kind label".
3. The panel MUST show the app's origin it is connecting from, so a framed or
   spoofed panel is easier to spot.
4. **Remember per site**: store the chosen `rdns` (never keys) in the app's
   storage. Next time, reconnect to it silently if it is still present. If it
   has gone, show the panel with a note: "bWalletX is not available any more".
5. **One in-app wallet**: inside a wallet's in-app browser (`kind: 'in-app'`)
   with no other wallets, skip the panel.
6. Apps MUST offer **Switch wallet** wherever the connected wallet is shown;
   it opens the panel.

### 5. SDK integration (`@bsv/sdk`, non-normative)

Additive, no change to existing behaviour:

```ts
// Find every wallet; no UI.
const wallets: DiscoveredWallet[] = await discoverWallets({ originator, timeoutMs })

// Wallet side: announce in a few lines.
announceWallet({ name, icon, rdns, kind }, walletImpl)

// Connect to the wallet the user picked.
const client = new WalletClient(chosen.wallet, originator)
```

`WalletClient('auto')` keeps its current behaviour. A later major version MAY
make `'auto'` prefer a remembered or single wallet and require a chooser only
when several are present.

## Security considerations

- **Announcements are untrusted.** Any script in the page can announce a
  wallet called "BSV Desktop". The chooser shows what is offered; the user
  is the judge, as with EIP-6963. Wallets still enforce origin checks and
  approvals themselves. Apps MUST NOT treat `name`, `icon` or `rdns` as
  proof of identity.
- **Icons** MUST be rendered as `<img src>` only, never injected as markup,
  so a malicious SVG cannot run script in the app.
- **Remembered choice** stores only the `rdns`. Do not store identity keys
  as "the user's wallet"; ask the wallet each session.
- **Local probes** reveal to the page whether a desktop wallet runs. Probing
  only after the user starts connecting limits fingerprinting.
- **Phishing through the panel**: a malicious site can draw a fake panel.
  This standard doesn't change that; wallets' own approval windows remain the
  trust boundary.

## Backwards compatibility

- Apps using `WalletClient('auto')` see no change.
- Wallets that don't announce are still found via `window.CWI` and local
  probes (§3), named from `getVersion()`.
- Wallets that announce and also set `window.CWI` (only if empty) still work
  with old apps.
