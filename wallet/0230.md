# BRC-230: Wallet-Native Sigma-Protocol Proofs as a BRC-98 Module

Connor Murray (connor.murray@bsvassociation.org)

## Abstract

This specification defines `sigma`, a [BRC-98](./0098.md) permission-module scheme that lets an application obtain Schnorr-style Sigma-protocol proofs, and the public points they are about, from a [BRC-100](./0100.md) wallet. Three statements are supported: knowledge of the scalar `x` behind a statement point `P = x·G` (`schnorr`), knowledge of the same `x` behind `P` and behind `x·H` for a second base `H` (`dleq`, the Chaum–Pedersen proof), and knowledge of the scalar behind one of `n` ring points without revealing which (`or`, the Cramer–Damgård–Schoenmakers proof). The proof scalar is derived deterministically from the wallet's BRC-42/43 root for a protocol-scoped identity and never leaves the wallet.

The operation is carried over the existing BRC-100 `encrypt` method. Inside the reserved `p sigma` namespace, a supporting wallet interprets `encrypt` semantically as "produce a statement point" or "produce a proof over the plaintext" and returns the result in the ordinary `{ ciphertext }` byte-array result. No method, call code, Wallet Wire message, or optional member is added to BRC-100.

The proofs are the transcripts that Bitcoin Script contracts known as s-puzzles verify, with the Fiat–Shamir challenge computed exactly as those contracts compute it. The scheme therefore lets an output be locked to a wallet-held key under a zero-knowledge spending condition, and spent, without any application holding the secret. Proofs are deterministic: two conforming wallets holding the same root key return byte-identical results. Wallets that do not install the module retain BRC-98's required behavior and reject the reserved protocol.

## Motivation

An s-puzzle is a transaction output that can be spent by anyone who proves knowledge of a secret satisfying a stated relation, without revealing the secret. The proof is a Schnorr-style Sigma-protocol transcript: a commitment `R` and a response `s`. Its challenge is a hash over `R`, the statement, and data taken from the spending transaction, so a proof copied from the mempool cannot be used to redirect the funds. The locking script recomputes the challenge and checks the verification equation:

```
e = SHA256(R ‖ P ‖ outpoint ‖ hashOutputs) mod n      (the digest read little-endian)
accept iff s·G = R + e·P
```

Working contracts exist for four statements, compiled with the [Rúnar](https://github.com/icellan/runar) compiler and locked and spent on testnet: `SPuzzle` (`P = x·G`), `PedersenOpening` (the opening of a Pedersen commitment, which reduces to a Schnorr proof for `C − v·H`), `ChaumPedersen` (`P₁ = x·G` and `P₂ = x·H`), and `OrProof` (`P₁ = x·G` or `P₂ = x·G`, without revealing which). The equality and one-of-many statements cannot be expressed with `OP_CHECKSIG`; they are what the in-script verifier is for.

What is missing is a prover that respects wallet custody. Today the secret `x` is held by the application, which computes `R` and `s` itself. That defeats the custody model of BRC-100 wallets: the application holds the material that controls the locked funds, the user cannot audit or revoke its use through the wallet, and the secret is lost with the application state. A BRC-100 wallet signs ECDSA under `createSignature`, but no BRC-100 method produces a Schnorr response `s = k + e·x` over an application-chosen transcript, and neither `getPublicKey` nor `createSignature` can carry one: a `getPublicKey` result must be a 33-byte secp256k1 point, and a `createSignature` result must be DER of at most 72 bytes. Only `encrypt` and `decrypt` carry arbitrary byte arrays through every BRC-100 substrate.

This specification therefore adds a semantic operation behind BRC-98's reserved dispatch point, carried on `encrypt`, without changing BRC-100. It fixes every step that an implementation might otherwise choose differently, from scalar derivation to nonce derivation to the byte layout of the result, so that two conforming wallets holding the same root key return the same statement point and the same proofs, and so that a contract author can lock funds to a wallet's statement point and know that the wallet's proofs will verify against it.

## Relationship to BRC-98 and BRC-2

BRC-98 reserves protocol identifiers beginning with `p `, requires unsupported wallets to reject them, and permits a supported scheme to define its own rules for permitted operations, key IDs, counterparties, permission attributes, and execution.

The `sigma` scheme uses that reserved dispatch point to specialize the meaning of an existing BRC-100 method, in the same way that [BRC-206](./0206.md) specializes `encrypt` and [BRC-229](./0229.md) specializes `getPublicKey`. This specification does not amend BRC-98 or [BRC-2](./0002.md).

The semantic boundary is safe for compatibility:

1. Outside `p sigma`, `encrypt` retains its ordinary BRC-2 meaning.
2. Inside `p sigma`, a wallet either implements this scheme or rejects the request as BRC-98 already requires. A wallet that does not install the module MUST keep BRC-98's required behavior and reject every `p sigma` request.
3. The `ciphertext` returned under `p sigma` is not a BRC-2 ciphertext. It MUST NOT be passed to `decrypt`, and a conforming wallet rejects `decrypt` under `p sigma`.
4. Applications never infer support from a new optional wallet member. They use a configured supporting wallet or handle the standard unsupported-scheme error.

## Specification

### Scheme and method

The BRC-98 scheme ID is:

```
sigma
```

A conforming implementation MUST accept this scheme only through the existing BRC-100 `encrypt` method. It MUST reject every other BRC-100 method requested under `p sigma`, including `decrypt`, `getPublicKey`, `createSignature`, `verifySignature`, `createHmac`, `verifyHmac`, and the key-linkage methods. This keeps the proof scalar out of every other cryptographic purpose.

The protocol-name component of `EncryptArgs.protocolID` has this grammar:

```
p sigma <operation> <logicalProtocolID>
```

where:

- `operation` is exactly `key`, `schnorr`, `dleq`, or `or`;
- `logicalProtocolID` is the application protocol whose key universe is being requested.

The outer BRC-100 call remains:

```ts
wallet.encrypt(
  {
    protocolID: [
      securityLevel,
      `p sigma ${operation} ${logicalProtocolID}`
    ],
    keyID,
    counterparty,
    plaintext,
    privileged,
    privilegedReason,
    seekPermission
  },
  originator
)
```

`keyID`, `counterparty`, `privileged`, `privilegedReason`, `seekPermission`, and `originator` retain their existing BRC-100 meanings and locations. They MUST NOT be duplicated or encoded into the protocol string. The security level MUST be `0`, `1`, or `2`.

`counterparty` defaults to `self` under the existing method rules. `self`, `anyone`, and a canonical compressed public key are all permitted.

`plaintext` MUST be a byte array: a sequence of integers, each from 0 to 255. Its layout depends on the operation and is defined under Operations.

### Logical protocol ID

The logical protocol ID MUST:

- contain only lowercase ASCII letters, numbers, and single spaces;
- contain no leading, trailing, or repeated spaces;
- be at least 5 characters and no more than 272 characters; and
- not end with ` protocol`.

The 272-character ceiling ensures that the canonical derivation protocol `p sigma <logicalProtocolID>` remains within BRC-43's 280-character protocol-ID limit.

The complete outer `p sigma` string is a BRC-98 dispatch envelope, not the protocol ID used for BRC-43 derivation. It MUST be no more than 288 characters: a `key` request can be at most 284 characters, a `schnorr` request 288, a `dleq` request 285, and an `or` request 283. All permitted characters are ASCII, so these character and byte counts are identical. All four bounds remain within BRC-100's 400-character protocol-string limit.

A key ID MUST be 1 to 800 bytes of UTF-8. This is counted in bytes, not characters: it is at least as strict as the 800-character check that `@bsv/sdk` clients apply, and within BRC-43's 1033-byte limit, so a key ID the module accepts is never rejected by a conforming client. Non-ASCII key IDs are permitted; a module MUST apply the byte limit itself rather than rely on the client's character count.

### Canonical scalar derivation

Let:

- `s` be the security level in the outer `protocolID` tuple;
- `L` be `logicalProtocolID`;
- `K` be the separately supplied `keyID`; and
- `C` be the separately supplied `counterparty`, defaulting to `self`.

The module MUST derive a private key `d` using BRC-42/43 with:

```
protocolID   = [s, "p sigma " + L]
keyID        = K
counterparty = C
```

`d` MUST be the BRC-42 child private key for this tuple, as the wallet's ordinary private-key derivation computes it. The operation MUST NOT form part of the BRC-42 derivation identity, so `key`, `schnorr`, `dleq`, and `or` under one logical protocol, key ID, and counterparty all address the same key.

The proof scalar `x` is derived from `d` with HKDF using SHA-256 ([RFC 5869](https://www.rfc-editor.org/rfc/rfc5869)):

```
d32  = d as 32 bytes big-endian
PRK  = HKDF-Extract(salt = UTF8("p sigma v1"), IKM = d32)            (RFC 5869, SHA-256)
x_j  = HKDF-Expand(PRK, info = UTF8("p sigma v1 scalar") ‖ byte(j), 32)
x    = the first x_j, j = 0, 1, …, with 0 < x_j < n (as a big-endian integer)
```

Here `n` is the secp256k1 group order, `byte(j)` is the single byte with value `j`, and `‖` is concatenation. `d32` keeps its leading zero bytes. Because the output length is 32 bytes, each `HKDF-Expand` is a single block: `x_j = HMAC-SHA256(PRK, UTF8("p sigma v1 scalar") ‖ byte(j) ‖ 0x01)`. A candidate outside `0 < x_j < n` is skipped, never reduced. `j` is a single byte; if no `x_j` with `j` from 0 to 255 is in range, the wallet MUST fail. (Each candidate is out of range with probability below 2^-127.)

The statement point is:

```
P = x·G
```

where `G` is the secp256k1 generator.

**Scalar isolation.** A conforming implementation MUST derive `x` exactly as specified above. It MUST NOT use `d`, the wallet's identity key, a spending key, or a key from any other protocol as the proof scalar. `d` is used only as HKDF input keying material; it is never used as a secp256k1 key and is never returned. `x` is used only for `sigma` operations; it is never used for ECDSA and is never returned. This isolates every value the module returns from every other key of the wallet.

### Operations

#### Encodings

- A point in a request (`H`, a ring point, or a public-key `counterparty`) is a 33-byte compressed secp256k1 encoding.
- Every point inside the request digest `q` (see Deterministic derivation) and inside every challenge transcript is **64 bytes: the x-coordinate then the y-coordinate, each 32 bytes big-endian.** This includes `H` and `P2` in `dleq` and the ring points in `or`, even though `H` and the ring points arrive in the request as 33-byte compressed points. It is the encoding the contracts hash.
- Points in proof results are the same 64-byte encoding.
- Scalars in proof results are exactly 32 bytes big-endian.
- A `key` result is a 33-byte compressed point.
- `ctx` is application-supplied context: 1 to 4,096 bytes, opaque to the module. The s-puzzle contracts use 68 bytes, the 36-byte outpoint being spent followed by the transaction's 32-byte `hashOutputs`.

#### The challenge

The Fiat–Shamir challenge over a transcript `T` is:

```
challenge(T) = LE(SHA256(T)) mod n
```

that is, the 32-byte SHA-256 digest of `T` read as a little-endian unsigned integer (the first byte is the least significant), reduced modulo the secp256k1 group order `n`. This is the value a Bitcoin Script contract obtains from `bin2num(SHA256(T) ‖ 0x00) mod n`; the appended zero byte keeps the number non-negative.

#### Summary

| Operation | `plaintext` | Result | Transcript hashed for the challenge |
|---|---|---|---|
| `key` | empty, or `H` (33 bytes) | `P`, or `x·H` when `H` is given (33 bytes, compressed); no proof | none |
| `schnorr` | `ctx` | `R ‖ s` (96 bytes) | `R ‖ P ‖ ctx` |
| `dleq` | `H ‖ ctx` | `P2 ‖ R1 ‖ R2 ‖ s` (224 bytes), with `P2 = x·H` | `R1 ‖ R2 ‖ P ‖ P2 ‖ H ‖ ctx` |
| `or` | `n ‖ i ‖ others ‖ ctx` | `R_1 … R_n ‖ s_1 … s_n ‖ e_1 … e_(n−1)` (`128n − 32` bytes) | `R_1 ‖ … ‖ R_n ‖ P_1 ‖ … ‖ P_n ‖ ctx` |

In every transcript, each point is the 64-byte encoding.

#### Plaintext layouts

Byte offsets are zero-based. `len(ctx)` is the length of `ctx` in bytes.

`key`: the plaintext MUST be either empty (the result is `P`) or exactly 33 bytes, a compressed point `H` (the result is `x·H`).

`schnorr`:

| Bytes | Field |
|---|---|
| 0 to `len(ctx) − 1` | `ctx`, the whole plaintext |

`dleq`:

| Bytes | Field |
|---|---|
| 0–32 | `H`, a 33-byte compressed point |
| 33 to end | `ctx` |

`or`:

| Bytes | Field |
|---|---|
| 0 | `n`, the ring size, one byte, 2 to 8 |
| 1 | `i`, the wallet's position in the ring, one byte, 1-based, 1 to `n` |
| 2 to `2 + 33(n−1) − 1` | `others`: the other `n − 1` ring points in ring order, 33 bytes each, compressed |
| `2 + 33(n−1)` to end | `ctx` |

The plaintext lengths are therefore exactly 0 or 33 bytes for `key`, `len(ctx)` for `schnorr`, `33 + len(ctx)` for `dleq`, and `2 + 33(n − 1) + len(ctx)` for `or`. The longest valid plaintext is 4,329 bytes (`or` with `n = 8` and a 4,096-byte `ctx`).

#### Input validation

A conforming implementation MUST refuse a request before deriving anything when:

- the plaintext is not a byte array;
- any point in the plaintext (`H` or a ring point) is not a canonical compressed encoding: exactly 33 bytes, first byte `02` or `03`, x-coordinate less than the field prime `p` (checked before any parser that reduces coordinates modulo `p`), decoding to a point on the curve, and not the identity;
- `H` equals `G`, in `key` and in `dleq`;
- in `or`, `n` is outside 2 to 8, or `i` is outside 1 to `n`;
- in `or`, two of the `others` are the same point;
- `ctx` is shorter than 1 byte or longer than 4,096 bytes; or
- the plaintext length does not match the layout for the operation.

One check needs the statement point and so cannot precede derivation: in `or`, a ring point in `others` that equals the wallet's own point `P` MUST cause the request to be refused after `x` is derived and before any proof value is computed.

#### `key`

`key` returns a point and produces no proof. With an empty plaintext the result is the statement point `P = x·G`. With a 33-byte base `H` the result is `x·H`. Either result is the 33-byte compressed encoding.

`key` with `H` exists because a `ChaumPedersen` output needs `P2 = x·H` as a constructor argument before any outpoint exists, and so before any `dleq` proof can be bound to a spend.

#### `schnorr`

`schnorr` proves knowledge of `x` for `P = x·G`, bound to `ctx`. The verifier accepts a 96-byte `R ‖ s` if and only if `R` is a point on the curve and not the identity, `s` is in 1 to `n − 1`, and `s·G = R + e·P` with `e = challenge(R ‖ P ‖ ctx)`.

`schnorr` also serves the Pedersen opening. For a commitment `C = v·H + b·G` with a published `v`, the application chooses `b` to be the wallet's `x` by building `C = P + v·H` itself; the contract's derived statement point `C − v·H` is then `P`.

#### `dleq`

`dleq` proves that `P = x·G` and `P2 = x·H` share the same `x`, bound to `ctx`. The verifier accepts a 224-byte `P2 ‖ R1 ‖ R2 ‖ s` if and only if `P2`, `R1`, and `R2` are points on the curve and not the identity, `s` is in 1 to `n − 1`, and `s·G = R1 + e·P` and `s·H = R2 + e·P2` with `e = challenge(R1 ‖ R2 ‖ P ‖ P2 ‖ H ‖ ctx)`.

#### `or`

`or` proves knowledge of the scalar behind one point of the ring `P_1, …, P_n`, without revealing which, bound to `ctx`. The wallet builds the ring by inserting its own statement point `P` at the 1-based position `i` among `others`, so that `P_i = P` and the other positions hold `others` in order.

The verifier computes `e = challenge(R_1 ‖ … ‖ R_n ‖ P_1 ‖ … ‖ P_n ‖ ctx)` and the last challenge `e_n = e − (e_1 + … + e_(n−1)) mod n`. It accepts if and only if every `R_j` is a point on the curve and not the identity, every `s_j` and every `e_j`, including the derived `e_n`, is in 1 to `n − 1` (the group order), and `s_j·G = R_j + e_j·P_j` for every `j` from 1 to `n`. The result always omits `e_n`, the challenge of the last position, whatever the wallet's position `i` is.

Only `n = 2` has an on-chain verifier today, the `OrProof` contract. Larger rings are verified off-chain, for example by the reference module's pure verifier.

### Deterministic derivation

Every nonce, and for `or` every simulated challenge and simulated response, is derived from `x` and the complete request. A conforming implementation MUST NOT use a random source. The same request MUST always return the same bytes.

The request digest `q`, the candidate function `cand`, and the stream function `scalar` are:

```
q    = SHA256(UTF8("p sigma v1 request") ‖ op ‖ statement ‖ uint32be(len(ctx)) ‖ ctx)
       op: schnorr 0x01, dleq 0x02, or 0x03
       statement: schnorr  P
                  dleq     P ‖ P2 ‖ H
                  or       byte(n) ‖ byte(i) ‖ P_1 ‖ … ‖ P_n          (all points 64 bytes)

cand(a, label, pos, c) = HMAC-SHA256(key = x as 32 bytes big-endian,
                         msg = UTF8("p sigma v1 nonce") ‖ q ‖ uint32be(a) ‖ label ‖ byte(pos) ‖ uint32be(c))
scalar(a, label, pos)  = the first cand(a, label, pos, c), c = 0, 1, …, with 0 < value < n
       label: 0x01 nonce k, 0x02 simulated challenge, 0x03 simulated response
       pos:   0 for schnorr and dleq; the ring position for or
       a:     attempt counter, starting at 0
```

Notation:

- `uint32be(v)` is `v` as 4 bytes big-endian. `len(ctx)` is encoded in 4 bytes although `ctx` is bounded at 4,096 bytes.
- `op`, `label`, `byte(n)`, `byte(i)`, and `byte(pos)` are single bytes.
- `n` has two meanings in this section. Where it is a count or a subscript (`byte(n)` in the `or` statement, `P_1 ‖ … ‖ P_n`, `R_1 … R_n`, `s_1 … s_n`, `e_1 … e_(n−1)`) it is the ring size. In `mod n` and in `0 < value < n` it is the secp256k1 group order. The `or` proof uses both.
- Every point in `statement` is the 64-byte encoding, for every operation: `P` for `schnorr`; `P`, `P2`, and `H` for `dleq`; `P_1` to `P_n` for `or`, with the wallet's `P` at position `i`.
- Ring positions are 1-based: `byte(i)` in the `or` statement and `pos` in the stream both use 1 for the first ring position.
- Each `cand` value is a 32-byte big-endian integer. A candidate outside `0 < value < n` is skipped, never reduced.

The proofs are:

- **schnorr:** `k = scalar(a, 0x01, 0)`, `R = k·G`, `e = challenge(R ‖ P ‖ ctx)`, `s = k + e·x mod n`. If `s = 0`, increment `a` and redo. Result `R ‖ s`.
- **dleq:** `P2 = x·H`, `k = scalar(a, 0x01, 0)`, `R1 = k·G`, `R2 = k·H`, `e = challenge(R1 ‖ R2 ‖ P ‖ P2 ‖ H ‖ ctx)`, `s = k + e·x mod n`. If `s = 0`, increment `a` and redo. Result `P2 ‖ R1 ‖ R2 ‖ s`.
- **or:** for each `j ≠ i`: `e_j = scalar(a, 0x02, j)`, `s_j = scalar(a, 0x03, j)`, `R_j = s_j·G − e_j·P_j`. Then `k = scalar(a, 0x01, i)`, `R_i = k·G`, `e = challenge(R_1 ‖ … ‖ R_n ‖ P_1 ‖ … ‖ P_n ‖ ctx)`, `e_i = e − Σ_{j≠i} e_j mod n`, `s_i = k + e_i·x mod n`. If any `R_j` is the identity, or `e_i = 0`, or `s_i = 0`, increment `a` and redo. Result `R_1 … R_n ‖ s_1 … s_n ‖ e_1 … e_(n−1)`.

In `or`, the sum of the simulated challenges `Σ_{j≠i} e_j` is reduced modulo `n`, and `e_i` is reduced modulo `n` into `[0, n)`. Every redo starts the whole proof again with the next attempt counter `a`; values from an abandoned attempt are discarded. Each redo condition has negligible probability for an honestly derived `x`, so in practice `a = 0`; the rules exist so that every implementation makes the same decision.

### Result encoding

Results are returned as the ordinary `encrypt` result shape:

```ts
{ ciphertext: Byte[] }
```

The byte array is the concatenation of fixed-width fields. Points are the 64-byte encoding (x then y, each 32 bytes big-endian) except in `key`; scalars are 32 bytes big-endian.

| Operation | Length (bytes) | Layout |
|---|---|---|
| `key` | 33 | the compressed point `P` or `x·H` |
| `schnorr` | 96 | `R` (bytes 0–63) ‖ `s` (64–95) |
| `dleq` | 224 | `P2` (0–63) ‖ `R1` (64–127) ‖ `R2` (128–191) ‖ `s` (192–223) |
| `or` | `128n − 32` | `R_1 … R_n` (`64n` bytes) ‖ `s_1 … s_n` (`32n` bytes) ‖ `e_1 … e_(n−1)` (`32(n − 1)` bytes) |

For `or` with `n = 2` the result is 224 bytes; with `n = 3`, 352 bytes; with `n = 8`, 992 bytes.

**The result is not push-ready.** Unlike [BRC-206](./0206.md), whose fields are minimally encoded Script numbers, this scheme returns fixed-width big-endian scalars. A contract that takes `s`, `s1`, `s2`, or `e1` as a number needs it as a minimally encoded Script number: little-endian, with no leading zero bytes, and with a `0x00` sign byte appended when the top bit is set, so the push is 32 or 33 bytes (occasionally shorter). The application MUST convert each scalar before placing it in an unlocking script; in Rúnar terms, it converts the 32 bytes to a `bigint` and lets the SDK encode the argument. Result points can be pushed as they are: they are already Rúnar's 64-byte `Point` encoding. A `key` result is compressed; a contract constructor that takes a 64-byte point needs the application to expand it.

In terms of the s-puzzle contracts, with `ctx` the 68-byte outpoint and `hashOutputs` of the spend:

| Contract | Constructor arguments | Request | Unlocking arguments |
|---|---|---|---|
| `SPuzzle` | `P` (a `key` result, expanded) | `schnorr` | `R`, `s` |
| `PedersenOpening` | `C = P + v·H`, `H`, `v` | `schnorr` | `R`, `s` |
| `ChaumPedersen` | `P` and `x·H` (`key` results, expanded), `H` | `dleq` with the same `H` | `R1`, `R2`, `s` (the result's `P2` equals the constructor's `x·H` and is not pushed) |
| `OrProof` | `P_1`, `P_2` | `or` with `n = 2` | `R_1`, `R_2`, `s_1`, `s_2`, `e_1` |

### Privileged keys

The existing `privileged` and `privilegedReason` fields select privileged-key behavior.

When `privileged` is absent or false, the module derives `d` from the wallet's ordinary BRC-42/43 root.

When `privileged` is true:

1. `privilegedReason` MUST be present and satisfy the existing BRC-100 description constraint (5 to 50 bytes).
2. The wallet MUST obtain explicit authorization even at security level 0.
3. The wallet MUST derive `d` from its privileged key material using the same canonical derivation tuple, and MUST derive `x` from that `d` by the same procedure.
4. The privileged root or key-derivation capability MUST NOT be exposed to the application.
5. The wallet MUST fail closed if privileged derivation is unavailable.

A wallet implementation SHOULD request access to privileged material only after the operation and reason have been authorized, and SHOULD release that access according to its existing privileged-key policy.

Ordinary and privileged requests with otherwise identical arguments MUST produce different statement points.

### Permissions

BRC-98 dispatch bypasses a wallet's ordinary protocol-permission logic, so the module is solely responsible for authorization. It applies BRC-43 permission semantics to the logical `sigma` protocol:

- an ordinary security-level-0 request does not require a prompt;
- a security-level-1 grant is scoped to the originator, logical protocol ID, and ordinary-versus-privileged root selection;
- a security-level-2 grant additionally distinguishes the counterparty;
- grants are keyed by security level, so a level-1 grant MUST NOT satisfy a level-2 request, and a level-2 grant MUST NOT satisfy a level-1 request; and
- ordinary and privileged grants MUST NOT satisfy one another.

A wallet MAY narrow a privileged grant further, for example to the approved `privilegedReason`, as the reference module does.

**A grant is not scoped by operation or by context.** Once granted, it covers every operation (`key`, `schnorr`, `dleq`, and `or`) and any context under that scope until it expires. A trusted UI SHOULD NOT describe a grant as limited to one operation, one context, or one spend unless the wallet enforces that limit.

A wallet MAY cache a successful grant according to its normal permission lifecycle. The operation, the key ID, and, for `schnorr`, `dleq`, and `or`, the SHA-256 of `ctx` SHOULD be displayed or made available to the authorization UI as information, but they do not change the grant scope. A trusted UI SHOULD describe the grant as the application being allowed to produce proofs with a wallet key under the logical protocol, and so to spend any output locked to that key's statement point, not as encryption.

If permission is required and no applicable grant exists:

- `seekPermission: false` MUST fail without prompting;
- otherwise the wallet MAY seek authorization through its normal trusted UI.

Concurrent equivalent requests SHOULD share one pending authorization decision so that high-volume protocols cannot produce duplicate prompts.

Key material MUST NOT be derived before authorization succeeds.

Every operation in this scheme is cheap: a BRC-42 derivation, two HMAC computations for `x`, a few more for the nonces, and at most a few scalar multiplications per ring point. No key generation, scheduling, or cache is needed, and this specification defines none. The bounds that apply are those above (authorize before deriving) and the input bounds under Operations (a `ctx` of at most 4,096 bytes and a ring of at most 8 points).

**Display of application-controlled text.** The logical protocol ID, key ID, and privileged reason are chosen by the application. A trusted UI that shows them SHOULD neutralize ASCII control characters and Unicode format and bidirectional-override characters (for example by escaping or replacing them), SHOULD truncate or wrap over-long values, and SHOULD render them in a way that is visually distinct from the wallet's own text, so that an application cannot compose a prompt that reads as a wallet statement.

### Baskets and labels

This scheme defines no output baskets and no action labels. A conforming implementation MUST reject every basket or label beginning with `p sigma` in `createAction`, `internalizeAction`, `listActions`, `listOutputs`, and `relinquishOutput`, and MUST NOT pass such a request through to the underlying wallet. This is load-bearing in wallets whose BRC-98 dispatch hands `p `-prefixed baskets and labels to the scheme's module *instead of* applying the ordinary basket and label permission checks: a module that merely passed them through would turn the reserved namespace into a permission bypass.

### Counterparty validation

When `counterparty` is supplied as a public key, the same canonical validation as BRC-229 applies: exactly 33 bytes as 66 lowercase hexadecimal characters, prefix `02` or `03`, x-coordinate less than the field prime (checked before any reducing parser), a point on the curve, and finite. The special values `self` and `anyone` remain valid.

### Errors

A conforming wallet MUST fail without deriving `d` or `x` when:

- the installed method is not `encrypt`;
- the protocol grammar or any field constraint is invalid, including an unknown operation, a security level other than 0, 1, or 2, or a key ID outside 1 to 800 bytes;
- the plaintext is not a byte array, or fails any check under Input validation;
- the public-key counterparty is invalid;
- `privileged` is true and `privilegedReason` is missing or outside 5 to 50 bytes;
- authorization is unavailable or denied, or permission is required, no applicable grant exists, and `seekPermission` is false;
- privileged derivation is requested but unavailable;
- the originator is missing, longer than 1,024 bytes of UTF-8, or contains ASCII control characters; or
- a basket or label beginning with `p sigma` is used in any method.

It MUST fail after deriving `x` and before computing any proof value when, in `or`, a point in `others` equals the wallet's statement point `P`.

An implementation MAY refuse a plaintext longer than the longest valid plaintext (4,329 bytes) before reading it.

Errors SHOULD identify the unsupported scheme, invalid field, or denied capability without revealing key material.

## TypeScript reference module

The reference implementation is the `@bsv/sigma-permission-module` package, proposed for [bsv-blockchain/ts-stack](https://github.com/bsv-blockchain/ts-stack) at `packages/wallet/sigma-permission-module`. It uses the Wallet Toolbox permission-module interface's optional semantic handler:

```ts
handleRequest?: (
  request: { method: string; args: object; originator: string },
  next: (args: object) => Promise<unknown>
) => Promise<unknown>
```

The module returns the result directly and never forwards its request to ordinary `encrypt`; forwarding would produce a BRC-2 ciphertext, not a point or a proof. The module refuses every other method routed to it. A conforming wallet MUST route every request under the `p sigma` namespace to the scheme's module or reject it, as BRC-98 requires.

The Wallet Toolbox routes `p `-prefixed baskets and labels of `createAction`, `internalizeAction`, and `listActions` to the scheme module's `onRequest` and `onResponse` hooks, bypassing its basket and label permission checks. The module's hooks therefore throw for every method instead of passing the request through.

A wallet host installs it alongside other BRC-98 modules under the `sigma` scheme and supplies:

- its ordinary BRC-42/43 key deriver;
- its trusted authorization callback, which receives the originator, security level, logical protocol ID, key ID, counterparty, privileged selection and reason, operation, and, for a proof, the lowercase hexadecimal SHA-256 of `ctx`;
- optionally, a privileged-key-deriver provider; and
- optionally, the lifetime of a grant (five minutes by default, at most 24 hours).

The key derivers, `d`, `x`, and every nonce remain inside trusted wallet/module code and are never included in the BRC-100 response. The module exports pure verifiers (`verifySchnorr`, `verifyDleq`, and `verifyOr`) so that applications can check proofs without the wallet, and the encoding helpers `parsePoint33` and `point64`. It has no runtime dependency beyond its peer dependencies `@bsv/sdk` and `@bsv/wallet-toolbox-client`.

## Security

### Scalar isolation

The proof scalar `x` is derived from a BRC-42 child private key of the `p sigma <logicalProtocolID>` namespace through HKDF, and from nothing else. A wallet MUST derive `x` as specified under Canonical scalar derivation and MUST NOT use `d`, its identity key, a spending key, or a key from any other protocol as the proof scalar. `d` is used only as HKDF input keying material. This isolates every value the module returns from every other key of the wallet. The method restriction is equally mandatory: no other BRC-100 method may operate under `p sigma`.

> _Rationale for scalar isolation: to be added at publication._

### A proof is a signature over application-chosen context

A `schnorr` proof over application-chosen `ctx` is a key-prefixed Schnorr signature on `ctx` under `P`. When `ctx` is the outpoint and `hashOutputs` of a spend, it is exactly what the s-puzzle contract needs to release the output. An application that holds a grant can therefore obtain proofs that spend any output locked to `P`, to any outputs it chooses, for as long as the grant lasts. The same holds for `dleq` and `or` proofs and their contracts. This is the same served-code trust that a wallet extends to an application when it grants `createSignature`, and wallets SHOULD present it to the user in those terms. The module cannot tell what `ctx` means; binding a proof to a particular spend is the contract's job, not the wallet's.

### Security level 0

An ordinary security-level-0 request needs no prompt, and the originator is not part of the key derivation. Every application a wallet serves can therefore obtain proofs under a level-0 key, and so spend any output locked to its statement point. Keys that guard value SHOULD use security level 1 or 2.

### A Diffie–Hellman oracle on `x`

`key` with a base and `dleq` return `x·H` for an application-chosen `H`. Together they are a static Diffie–Hellman oracle on `x`. Because of scalar isolation, that oracle concerns `x` alone and says nothing about any other key of the wallet. Published results on static Diffie–Hellman oracles show that answering a very large number of such queries can lower the cost of recovering `x` below the generic discrete-logarithm bound; applications that need the full strength of `x` over a long-lived key SHOULD limit the number of distinct bases they request, and wallets MAY bound the rate of such requests.

### Deterministic nonces

Nonces are derived from `x` and the complete request, so two different requests use the same nonce only with negligible probability. Nonce reuse across two different challenges would reveal `x`, as it does for any Schnorr proof. The price is that a repeated request returns the same proof. That is harmless: the proof is the same transcript, and an observer learns only that the request was repeated. Implementations MUST NOT randomize nonces, because a randomized wallet would no longer return byte-identical results.

### Determinism and signer privacy

Because proofs are deterministic, a party able to query the wallet under the same key and request can recognise the wallet's `or` proof by repeating the request and comparing bytes. The `or` proof hides the prover's position in the ring only from parties without that access.

### Versioning

The strings `p sigma v1`, `p sigma v1 scalar`, `p sigma v1 request`, and `p sigma v1 nonce` identify the derivations of `x`, `q`, and the nonce stream defined here, and through `q` the request and statement that each nonce answers. The challenge transcripts carry no tag, because the contracts fix them. Any future change to a transcript, a layout, or a derivation MUST use new tag strings, so that one nonce is never used under two different challenges.

### Statement points must be checked by whoever locks funds

The module validates its own inputs: request points are canonical, on the curve, and not the identity; `H` is not `G`; ring points are distinct. Those checks protect the wallet's request, not the output. A contract validates the proof, not the statement: it accepts whatever points the locker published. If a statement point is the identity, anyone can spend; in an `OrProof` output, one identity point lets a spender who knows neither key through. Anyone relying on an output locked to `sigma` statement points MUST check those points off-chain before locking funds: each must be on the curve and not the identity, and any second base `H` must be derived so that nobody knows its discrete logarithm to base `G`, which the binding of a Pedersen commitment depends on.

### Permission and resource use

Every operation costs a BRC-42 derivation, a few HMAC computations, and a bounded number of scalar multiplications (at most two per ring point for `or`, with at most 8 ring points). Inputs are bounded (a `ctx` of at most 4,096 bytes, a plaintext of at most 4,329 bytes). Wallets MUST authorize before deriving, SHOULD bound request concurrency as they do for other modules, and SHOULD make the logical protocol, originator, operation, key ID, counterparty, context digest, and privileged reason available to trusted policy code.

### Capability containment

The public application interface exposes only `encrypt` and receives only a public point or a proof. The semantic module is trusted wallet code: it may use internal key-derivation capabilities, but it MUST NOT return those capabilities, `d`, `x`, a nonce, or privileged root material. Big-integer and elliptic-curve arithmetic in most scripting runtimes is not constant-time; implementers SHOULD be aware that proof generation time depends on `x` and avoid exposing fine-grained timing to untrusted callers where that is practical.

## Why existing primitives are insufficient

BRC-100 `createSignature` produces ECDSA over secp256k1 only, and its result validation admits nothing but DER of at most 72 bytes. `getPublicKey` admits only a 33-byte point. An ECDSA signature does not satisfy the s-puzzle verification equation `s·G = R + e·P` with a challenge the contract computes from its own transcript, and no BRC-100 method computes a response `s = k + e·x` for a transcript the application supplies. Point multiplication alone, as [BRC-229](./0229.md) provides, returns points; a response is a scalar computed from the secret, and cannot be assembled from points.

`OP_CHECKSIG` already gives a pay-to-public-key output the guarantee of a single-key `schnorr` proof in 35 bytes. It cannot express equality of discrete logarithms across two bases, or knowledge of one of several keys without revealing which, and those are the statements that need an in-script verifier and therefore a prover.

Holding the secret in the application is the status quo, and it is the problem: the key is outside the user's custody and recovery, its use cannot be permissioned by the wallet, and it is lost with the application. BRC-98 supplies the semantic dispatch; `encrypt` supplies a byte-carrying result that every substrate already passes through; BRC-42/43 supply a permissioned, recoverable, counterparty-separated key. This specification supplies everything in between so that the result is the same in every conforming wallet.
