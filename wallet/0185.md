# BRC-185: Wallet Substrate Discovery, Selection, and Encrypted Mobile Connections

- Ty Everett (ty@projectbabbage.com)
- [Deggen](https://x.com/deggen)

## Abstract

This proposal specifies how applications discover multiple wallets, select one wallet per connection, and carry the complete, unchanged BRC-100 interface over local, embedded, extension, and encrypted mobile substrates. It defines ascending localhost port allocation, a neutral chooser contract, origin-scoped selection memory, safe switching, a vendor-neutral pairing URI, and a mandatory encrypted mobile relay profile. Discovery, connection management, and user interfaces are composable components outside the core SDK. Applications can use automatic selection or supply their own user experience, including commercial onboarding wrappers.

**Status: proposed specification; draft for review.** The wire profiles and requirements below are proposed interoperability contracts, not claims that existing wallets implement them. No implementation or security-audit result is asserted.

## Motivation

An application should be able to use one wallet while another application uses another wallet on the same computer. A user should also be able to use a phone wallet from a desktop browser or move from a phone browser into a wallet and back. A single occupied localhost port, a last-writer-wins injected global, or a race between transports must not determine the user's wallet.

The September 23–24, 2026 discussion between Deggen, Ty Everett, and wallet users identified these problems and proposed ascending ports, selection among substrates, embedded-wallet defaults, and mobile QR pairing. The relevant public discussion and implementation inputs are linked in the references. This proposal turns those inputs into one connection contract while preserving the existing wallet interface.

## Specification

### 1. Scope, terminology, and conformance

The capitalized requirements use [BCP 14](https://www.rfc-editor.org/rfc/rfc8174). Sections 1–12 are normative. Subsequent sections are non-normative.

**BRC-100 is unchanging. `getVersion` capability discovery is expressly out of scope.** This proposal MUST NOT add methods, parameters, result fields, method-support lists, or feature negotiation to BRC-100. `getVersion` retains its existing version-string result. A legacy adapter MAY use the unchanged call as a noninteractive readiness probe; it MUST NOT interpret the version string as a capability manifest.

Every wallet claiming conformance MUST fully implement **all 28 BRC-100 methods**, and every conforming connection MUST carry all of them, with their complete arguments, results, errors, and originator semantics. An application is entitled to assume the full interface. An omitted implementation, method whitelist in a relay, or unsupported-method stub is nonconforming. A genuine permission denial, lock state, invalid argument, insufficient balance, or documented resource failure is not a missing method. Blanket denial used to conceal an absent implementation is nonconforming. [BRC-116](./0116.md) permission decisions continue to apply; neither discovery nor selection grants permission. A restricted tool-server facade is not a substitute for a conforming wallet connection.

| Term | Definition |
| --- | --- |
| Provider | One independently selectable wallet instance. A product name, account, transport, and provider are different things. |
| Substrate / adapter | A communications mechanism / its implementation behind the discovery and connection interfaces. |
| Candidate | One provider and its reachable transport aliases, with provenance and availability state. |
| Connection | An immutable binding to one provider, one application security context, and one connection epoch. |
| Epoch | A fresh, random UUIDv4 created when a binding is established. Wallet-specific references belong to that binding. |
| Controller | Framework-neutral discovery, selection, memory, and connection orchestration outside the core SDK. |
| Chooser | A replaceable presentation adapter; graphical, terminal, native, or application-defined. |
| Wrapper | Application-selected functionality around a bound `WalletInterface`, such as onboarding, funding, or monetization. |
| Application origin | For a web application, the serialized URL origin: scheme, ASCII host, and nondefault port. It is not merely a domain. |
| Originator | The BRC-100 application domain supplied to wallet methods. For web callers this is the origin's ASCII hostname, without scheme or port. |

A controller MUST distinguish the full application origin for connection/memory isolation from BRC-100's domain-shaped originator. It MUST NOT change existing BRC-100 permission semantics by treating its full origin as a new method argument. Non-web hosts MUST supply an explicit, stable application context and originator; a headless caller cannot acquire browser-origin authenticity by supplying a string.

Web URL parsing and origin serialization use the [WHATWG URL Standard](https://url.spec.whatwg.org/). A supplied origin MUST equal its parsed URL's serialized origin, with no credentials, path, query, or fragment; reject opaque `null` origins. For this profile loopback means `localhost`, a canonical dotted-decimal IPv4 address in 127.0.0.0/8, or `[::1]`. HTTP descriptor addresses MUST be serialized origins with one of those hosts and their actual port; no arbitrary DNS hostname, user information, path, query, redirect, or fragment is a loopback-discovery address. Display the complete ASCII origin when asking for approval; a friendly application name does not replace it.

Conformance is role-specific: a wallet implements the full interface and its advertised substrates; an adapter implements its advertised substrate; a controller and chooser implement their respective requirements; a mobile implementation implements sections 8–10. A wallet need not implement every physical substrate. Controllers MUST accept additional adapters through the same interfaces and MUST NOT exclude an otherwise usable provider because of vendor, commercial affiliation, or substrate family.

“Runtime support” means facts such as DOM availability, permitted loopback access, native bridge presence, or an interactive terminal. It MUST NOT mean a subset of BRC-100 methods. Wire version `1` below versions this connection protocol, not BRC-100.

### 2. Component boundaries and automatic WalletClient integration

The dependency direction MUST be:

```text
application / commercial wrapper
             |
       WalletInterface
             |
   bound connection / WalletClient
             |
 external connection controller ---- external chooser / onboarding hooks
             |
 interchangeable discovery and transport adapters
             |
           wallet
```

Discovery algorithms, scanners, provider registries, pairing, relay clients, storage, chooser state, and framework-specific UI MUST live outside the core SDK source and runtime dependencies. The SDK MAY define a small interface and delegate to an externally supplied controller. A controller MUST return a complete `WalletInterface`; it MUST NOT require applications to know which substrate supplied it.

The following behavioral interface is normative; equivalent language bindings are permitted:

```ts
interface ConnectionRequest {
  applicationContext: string
  originator: string
  mode: 'automatic' | 'ask' | 'explicit'
  explicitProvider?: string
  signal?: AbortSignal
}
interface ConnectionProvider {
  resolve(request: ConnectionRequest): Promise<BoundConnection>
}
interface BoundConnection {
  wallet: WalletInterface
  providerId: string
  epoch: string
  close(): Promise<void>
}
```

`providerId` is controller-local and MUST NOT be a wallet account identity key. The controller MUST expose state changes, a current candidate snapshot, explicit refresh, choose/change-wallet, forget-preference, and disconnect operations to presentation adapters. Subscription MUST return an unsubscribe function. Snapshot entries MUST include provider ID, display name, provenance, availability, transport aliases, and whether continuity was verified. Discovery completion MUST include per-adapter `complete`, `partial`, `blocked`, or `unsupported` coverage; an empty partial snapshot is not “no wallet installed.”

For JavaScript auto integration, an external package MAY register a `ConnectionProvider` under `globalThis[Symbol.for('brc185.connection-provider.v1')]`. Registration MUST be explicit application initialization, MUST reject replacement of a different registered provider unless the application explicitly requests replacement, and MUST finish before the first automatic connection. An explicitly supplied provider takes precedence over the registration. The registered provider MUST implement `resolve`; malformed registrations fail with `CONFIGURATION_ERROR`. This is a same-realm integration hook, not an authenticated extension discovery channel.

An upgraded `WalletClient` in automatic mode MUST delegate to the supplied or registered provider on its first connection attempt. The controller automatically invokes the chooser only when section 5 requires it. Concurrent first calls MUST share one pending resolution; they MUST NOT produce multiple chooser windows or multiple bindings. After resolution, calls use that binding until explicitly closed. Resolution cancellation MUST reject every waiting call without sending it to any wallet.

An explicitly supplied `WalletInterface` or explicitly selected legacy substrate MUST retain its existing behavior and MUST NOT unexpectedly open a chooser. In the absence of a supplied/registered provider, the SDK MUST preserve the existing automatic connection path and errors; upgrading the SDK alone MUST NOT add a DOM dependency, scan additional ports, open a popup, or install a global controller. A host with no chooser can use an explicit provider or unambiguous automatic selection; otherwise it receives `SELECTION_REQUIRED` with the snapshot. It MUST NOT hang awaiting nonexistent UI.

SDK documentation MUST show separately distributed browser/React, plain HTML/JavaScript, Node/terminal, and headless integrations, plus custom adapter, UI, storage, and wrapper composition. Example package names and APIs MUST be labeled as examples until those packages exist. Importing the core SDK in Node, a worker, React Native, or server rendering MUST not access DOM globals.

### 3. Discovery records, continuity, and privacy

Discovery MUST be noninteractive at the wallet-permission layer. It MUST NOT sign transactions, retrieve balances or account identity keys, unlock a wallet, or request BRC-100 permissions. Browser or OS permission to access a substrate is a separate state that the controller MUST explain and respect.

New providers expose the following descriptor. JSON in this BRC is UTF-8, rejects duplicate property names, invalid Unicode, nonfinite numbers, and unknown fields unless an explicit extension field is defined. Cryptographic canonicalization uses [RFC 8785 JCS](https://www.rfc-editor.org/rfc/rfc8785). Base64url uses the unpadded RFC 4648 alphabet; decoders MUST reject noncanonical encodings.

| Field | Type and requirement |
| --- | --- |
| `version` | Integer, exactly `1`. |
| `instanceId` | Lowercase UUIDv4, stable for this provider and application context. Different independently selectable profiles use different IDs. |
| `name` | Plain text, 1–80 UTF-8 bytes; product name, never executable markup. |
| `instanceLabel` | Plain text, 0–80 UTF-8 bytes; optional user-understandable distinction between instances, no secret/account identity. |
| `vendor` | Lowercase reverse-domain string, 1–253 ASCII bytes; self-asserted, not proof of domain ownership. |
| `continuityKey` | Base64url of a 32-byte Ed25519 public key generated independently of wallet spending/identity keys. |
| `endpoints` | 1–32 records `{id, type, address}`. IDs are unique 1–64-character ASCII tokens matching `[A-Za-z0-9._-]+`. |

`type` is `http-wire`, `http-json`, `https-json`, `window`, `xdm`, `react-native`, or an absolute HTTPS URI naming an extension's public specification. `address` is a URL for HTTP types and an opaque adapter-local handle for other types, at most 2048 UTF-8 bytes. An endpoint record never authorizes connecting to a different host. Adapter scope and application policy still apply.

The provider MUST maintain a distinct random continuity key and instance ID per application context; transports for the same instance/context share them. They MUST persist across ordinary restarts, MUST rotate on reset, and MUST NOT be derived by exposing an account identity key. Reset/rotation means a new provider for remembered-choice purposes. Private continuity material MUST be protected as a secret, using secure OS storage where available. It MUST never be returned to an application or relay.

`describe(origin, challenge)` returns `{descriptor, challenge, signature}`. `challenge` is a fresh 32-byte random base64url value supplied by the controller. The Ed25519 signature is over:

```text
UTF8("BRC-185 descriptor v1\n") || JCS({origin, challenge, descriptor})
```

Use pure Ed25519 from RFC 8032, not Ed25519ph or a wallet signing key. The controller MUST verify the signature, exact challenge and context before using continuity or merging aliases. The response is bounded to 16,384 bytes. `origin` is supplied by the trusted adapter context; a web request body's origin claim MUST NOT override the browser-supplied origin.

Two candidates MUST be merged only when they prove the same `(instanceId, continuityKey)` in the same context, or a trusted application-supplied adapter explicitly attests that they are aliases of the same object. Name, vendor, icon, port, wallet version, response speed, and account public key are insufficient. A single product can legitimately occupy several rows. Conflicting metadata for a proven identity is shown as a conflict and requires explicit selection; it MUST NOT silently overwrite an existing row.

Legacy providers lacking this record MUST remain usable through adapters. They are marked `legacy/unverified`; a controller MUST NOT invent verified continuity or silently persist a transport address as wallet identity. On a later resolution, a remembered legacy choice requires confirmation. Within a live, unmodified explicit object binding it remains usable normally.

Names and metadata MUST be rendered as inert text. The base descriptor has no remote icon, analytics URL, balance, certificate, account key, or method list. Optional UI artwork is application-supplied, treated as untrusted, and MUST NOT trigger network requests merely because a wallet announced itself. Discovery records and the candidate inventory MUST remain local to the application unless the user explicitly requests sharing them. Storage denial MUST degrade to in-memory preferences, not block connection.

Continuity proves possession of a previously seen transport key. It is not product certification, account authentication, code integrity, or protection against a compromised application, wallet, browser extension, or operating system.

### 4. Local and embedded substrate profiles

#### 4.1 Ascending localhost allocation

The starting ports are fixed:

| Substrate | First candidate | Subsequent candidates |
| --- | --- | --- |
| BRC-100 binary HTTP / BRC-5 | `http://localhost:3301` | 3302, 3303, …, 65535 |
| BRC-100 JSON HTTP / BRC-5 | `http://localhost:3321` | 3322, 3323, …, 65535 |
| BRC-100 JSON HTTPS / BRC-5 | `https://localhost:2121` | 2122, 2123, …, 65535 |

A wallet starting a listener MUST attempt an exclusive bind at the first port and increment by one after address-in-use failures until a bind succeeds or its configured allocation ceiling is reached. The bind itself is the allocation operation; a separate availability test is insufficient. Unrelated services also occupy ports. Other bind errors MUST be surfaced, not treated as evidence of an available wallet. No vendor owns a port. A wallet with several listeners allocates them independently and advertises all successfully bound endpoints; offsets need not match.

The sequences intentionally overlap. **Port number does not identify wire format.** For example, a binary listener may bind 3321 after earlier ports are occupied. New endpoints MUST serve `GET /.well-known/brc-wallet` for discovery independently of their RPC format. The controller reads the signed endpoint type before sending RPC. It MUST deduplicate identical scheme/host/port probes across scan sequences. A wallet MAY serve both formats on one listener if it dispatches by the BRC-5 content type and advertises both.

Listeners MUST bind only loopback interfaces, never wildcard/LAN interfaces for this profile, and MUST validate `Host` and web `Origin`. Implementations using both IPv4 and IPv6 MUST ensure both addresses route to the same instance for an advertised `localhost` endpoint; otherwise they MUST advertise the actual loopback literal as a distinct address and avoid ambiguous `localhost` binding. A failure to reserve one address family MUST NOT cause requests to be routed to a different wallet in that family.

The default discovery round examines offsets 0–63 inclusive from each base, in ascending offset order, with at most 16 simultaneous requests and a 1000 ms deadline per discovery request. It MUST NOT stop at the first gap or first successful wallet. `http://localhost` overlap is probed once; HTTP and HTTPS remain separate addresses. These are bounded default discovery windows, not reserved port ranges or allocation ceilings. A larger explicit window or explicit loopback endpoint MAY be configured. The snapshot MUST disclose the covered intervals and any blocked/timed-out probes. UI MUST offer refresh and a way to extend/configure the window when coverage is incomplete. It MUST NOT claim to have searched all ports or all installed wallets.

Discovery SHOULD begin only on an application wallet-use or connect action. A controller MUST NOT repeatedly rescan in the background, work around browser local-network permissions, disable certificate validation, or follow discovery redirects. A policy-blocked scan is `blocked`, not evidence of absence. A browser UI can ask for local-network access through normal browser controls or offer another substrate. The HTTPS profile requires a normally trusted certificate; the HTTP profile retains the local BRC-5 trust boundary and MUST NOT be presented as encrypted remote pairing.

The discovery request has query parameter `challenge` containing the 32-byte challenge. Web servers derive `origin` from the browser `Origin` header. Non-web adapters send an explicit `Originator` plus a configured application-context header `BRC-185-Context`; these are host assertions, not browser authentication. Responses are `200 application/json` with the section 3 proof, `Cache-Control: no-store`, and `Vary: Origin`. CORS MUST return the exact permitted origin, never reflect `null`, and MUST NOT enable credentials or authorize wallet operations through discovery. Preflight is noninteractive. Descriptors MUST advertise the responding endpoint with a matching scheme, host, port, and format.

To bind a new-profile HTTP connection, the controller sends `POST /.well-known/brc-wallet/connect` with JSON `{epoch, challenge, instanceId, continuityKey}` and the same origin rules as discovery. `epoch` is a new UUIDv4 and `challenge` is a new random 32-byte base64url value. A matching provider returns `{epoch, descriptor, challenge, signature}`, where signature covers `UTF8("BRC-185 connect v1\n") || JCS({origin, epoch, challenge, descriptor})`. A mismatch returns HTTP 412 without binding. The controller verifies this fresh proof and the selected identity before accepting the connection. The wallet binds epoch to this application context and its current account context; existing epochs cannot be rebound.

New-profile HTTP RPC uses `POST /brc185/v1/rpc/<BRC-100 methodName>` with headers `BRC-185-Epoch`, `BRC-185-Instance`, and `BRC-185-Key` carrying the bound epoch, instance ID, and continuity public key. Before dispatch, the wallet MUST validate all three against a live binding and the request origin. An unknown, retired, or mismatched binding returns HTTP 412 with a section 6 `PROVIDER_CHANGED` error and `not-sent` delivery. The distinct path is necessary: if the port is reused by a legacy wallet that ignores new headers, it must not accidentally execute a legacy method route. HTTP 404, missing binding validation support, and changed proofs MUST NOT trigger fallback/replay of that call onto legacy routes.

The new route carries the unchanged [BRC-5](./0005.md) binary or JSON method payload/result, content type, and origin semantics; it adds no BRC-100 argument. Success uses HTTP 200 and the original method result/error representation. `DELETE /.well-known/brc-wallet/connect/<epoch>` with the three binding headers closes the binding and returns HTTP 204; the same origin checks apply. CORS preflight MUST support those named headers and DELETE for permitted origins. Responses MUST be noncacheable. An actual listener/account restart invalidates in-memory bindings even if its continuity key persists.

Existing `POST /<methodName>` routes remain unchanged for legacy clients. No `/v1` prefix is added to those existing routes. Adapters MAY probe legacy default endpoints using unchanged `getVersion({})` when the well-known path is absent. Only the known legacy default format is assumed in that fallback; nondefault ambiguous endpoints require an explicit format configuration. An arbitrary HTTP response is not a wallet. A legacy HTTP binding lacks this new protection against port reuse and MUST be identified accordingly; probing a version string cannot supply it.

#### 4.2 Browser extensions and `window.CWI`

Multiple new providers MUST announce independently; they MUST NOT compete to overwrite `window.CWI`. The JavaScript event names are `brc185:request-provider` and `brc185:announce-provider`. A controller first installs its announcement listener, then dispatches a `CustomEvent` on `window` with detail `{version:1, requestId}` where `requestId` is a UUIDv4. Each provider responds with detail `{version:1, requestId, handle}`. `handle` exposes `describe(origin, challenge)` and `connect(origin, epoch, onClose): Promise<WalletInterface>`, where `onClose(reason)` reports `account-changed`, `revoked`, or `lost`. The returned interface is bound to that epoch and cannot be retargeted. Providers MUST answer each fresh request once and MUST NOT trigger wallet prompts when announcing or describing. The initial event collection window is 200 ms; late announcements MUST update the snapshot and never replace an already bound connection.

The controller MUST call `describe` with the actual `window.location.origin` and a fresh challenge, with a 1000 ms noninteractive discovery deadline. A timeout is partial coverage. `connect` MUST bind that origin. The handle also exposes `disconnect(epoch): Promise<void>` to close its binding without modifying any BRC-100 method. Browser extensions MUST derive the web origin at their trusted extension boundary and MUST NOT accept an override from page-supplied arguments. A controller MUST snapshot and validate metadata, limit unsolicited announcements, and retain a dismissal option for abusive providers. Page events and provider labels themselves are not authenticated extension installation evidence.

An adapter MUST also support an existing `window.CWI` object as a legacy provider. If a trusted host identifies it as the same object as an announced provider, it is one candidate. Otherwise a potentially duplicate entry remains distinguishable by provenance; guessing a merge is prohibited. A legacy overwrite cannot reveal providers that were already overwritten; controllers MUST not claim that it can.

#### 4.3 XDM and React Native

A top-level browser document whose parent is itself has no parent-XDM provider; that adapter reports `unsupported` without sending a message. A missing native bridge similarly reports `unsupported`, rather than waiting on a nonexistent channel.

New XDM discovery sends `{type:"brc185:request-provider",version:1,requestId,challenge}` and returns `{type:"brc185:announce-provider",version:1,requestId,proof}` through JSON `postMessage` data. The request ID is a UUIDv4 and challenge is a fresh random 32-byte base64url value. The discovery response deadline is 1000 ms; a timeout is partial coverage. Initial discovery MAY send only those nonsensitive values to the direct parent with target `*` when its origin is not yet known. The receiver derives the application origin from `MessageEvent.origin`. The controller MUST accept an announcement only from that expected parent window, reject opaque/null origins, verify the proof, and pin `event.source` and `event.origin` for every subsequent message. It MUST NOT broadcast wallet calls to all windows. Application-registered wallet frames require an explicit expected source and origin.

XDM connection establishment sends `{type:"brc185:connect", version:1, instanceId, continuityKey, epoch, challenge}` to the pinned source/origin. The wallet validates identity and returns `{type:"brc185:connected", version:1, proof}` with the same signed connect proof as HTTP. The controller verifies it before invoking methods. A new epoch binds the current account context; mismatches return `{type:"brc185:connection-error", version:1, epoch, error}` carrying a section 6 error. Wallets MUST reject invocation before establishment.

New XDM invocation envelopes are `{type:"brc185:invoke", version:1, instanceId, epoch, id, method, params}`. `epoch` and `id` are UUIDv4 values. Responses are `{type:"brc185:result", version:1, instanceId, epoch, id, result}` or the same routing fields with `type:"brc185:error"` and `error:{code, message, data?}`. `code` and optional `data` preserve the underlying wallet error; stack traces SHOULD be withheld. The wallet derives originator from the pinned caller's hostname. All routing fields MUST match the active binding; unknown methods and mismatched fields are rejected before dispatch. Every BRC-100 method and its existing JSON representation is carried. Result and error are mutually exclusive. New envelopes coexist with, and MUST NOT reinterpret, legacy BRC-6 `CWI` envelopes. Either side closes with `{type:"brc185:closed", version:1, instanceId, epoch, reason}`, with reason `account-changed`, `revoked`, or `lost`; it MUST come from the pinned peer. Closed epochs are never reused.

React Native adapters use those JSON envelopes over the host's registered WebView bridge, with origin derived from the native host's verified current document URL. The host MUST invalidate a binding on navigation to another origin and MUST distinguish independent WebViews/providers. A page-provided origin string, `isTrusted` alone, or the presence of a `postMessage` function is not origin validation. Legacy XDM and React Native bridges remain eligible through their existing adapters. A trusted host-provided `WalletInterface` can be supplied directly with no discovery at all.

### 5. Selection policy and neutral presentation

Applications select `automatic`, `ask`, or `explicit` behavior when instantiating the controller/chooser integration. The default is `automatic`. An application MAY declare an embedded provider as its preferred/default provider; it MUST do so explicitly through configuration or a trusted host binding, never by recognizing a favored vendor name.

Apply the following order after adapter coverage is known:

| Condition | Required behavior |
| --- | --- |
| Explicit object/provider supplied | Bind that provider or return its error; do not substitute another. |
| `ask` | Present the chooser even for one candidate; await selection. |
| Valid remembered choice, verified as the same provider | Reuse it without a chooser. Other newly discovered wallets do not disrupt it. |
| Remembered choice missing, changed, conflicting, or unverifiable | Ask again; do not fall through to a different single candidate. Preserve the old preference until replaced or forgotten. |
| App-configured embedded default available | Select it without a chooser; other adapters may be deferred until Change wallet. |
| Exactly one candidate and discovery coverage complete within the configured scope | Select it without a chooser. |
| Multiple candidates, or unresolved coverage that could change an automatic choice | Present the chooser with the coverage state. |
| No candidates, discovery complete | Offer phone pairing and application-provided onboarding/install paths. |
| No candidates and blocked/partial discovery | Explain access/coverage, offer retry, phone pairing and onboarding; do not assert no wallet is installed. |
| Choice required but no UI adapter | Return `SELECTION_REQUIRED`; include candidates and coverage. |

“Complete” is completion of the configured discovery scope, not proof that no other wallet exists anywhere. An explicitly configured embedded-only initial scope is valid and normally gives a single automatic default. An expanded chooser MUST include all usable candidates returned by all configured adapters, including extensions, localhost, window.CWI, XDM, React Native, and established mobile connections. It MUST expose unavailable/blocked adapters as coverage information. Application/runtime restrictions must be disclosed, not disguised as vendor incompatibility.

Phone pairing and wallet installation are actions, not fictitious discovered wallets. Their availability alone MUST NOT force a chooser popup when an existing desktop or embedded wallet can be automatically selected. Applications MUST have an API to request the chooser/phone path explicitly. A graphical integration MUST provide a reachable Change wallet/Use phone control, even when initial selection is automatic; an app-defined settings or connection menu satisfies this requirement.

Chooser rows MUST use equal typography, icon area, interaction affordances, and information density. No sponsorship, vendor relationship, port number, response speed, or adapter priority may influence wallet ordering, default selection, prominence, or omission. The default order is ascending Unicode code-point order of `name`, then `instanceLabel`, then `providerId`; UI MAY instead preserve a user-set order. A label identifying the user's current/remembered choice or the application's embedded default is permitted factual state, not an endorsement. Different transport aliases of one proven provider are one row with inspectable connection details.

Lock state is not absence. The controller MUST not silently move to another wallet because the selected wallet is locked, denied a permission, needs funding, or is temporarily offline. Wallet authentication and method permission remain wallet-controlled steps after selection. The chooser MUST support keyboard access, visible focus, accessible names, screen-reader status updates, cancel/back, and an equivalent non-QR path for users who cannot scan a code. Modal styling is not prescribed.

Selection memory is scoped to the full application context and provider proof. The default is to remember a successful selection for future visits when local storage is available; the UI MUST expose the remember setting and a forget action. Store only the provider identifier, continuity key, instance ID, selected mode, and necessary adapter-local locator. Do not store wallet keys, permissions, balances, account identity, pairing secrets, or a full discovered-wallet inventory. A changed account/identity notification invalidates the binding and requires a fresh explicit selection. When a legacy substrate cannot signal account changes, the integration MUST disclose that limitation; it MUST never claim to verify account continuity through `getVersion`.

### 6. Binding, switching, and error semantics

An application MAY hold several explicitly created connections concurrently. Each has its own immutable provider and epoch. No ambient “active wallet” may retarget existing connections. Transport aliases MAY be selected before binding using app-configured runtime suitability; once requests have been dispatched, changing an alias requires a new epoch and the switching rules below. Selection does not migrate keys, funds, baskets, certificates, account sessions, or action references.

A new-profile wallet MUST bind an epoch to its selected internal account context without exposing an account identity key in discovery. Changing that context invalidates the epoch before another call can execute. In-flight work either completes against the original context or fails with its true delivery certainty; it MUST NOT move to the new context. Object/XDM/native adapters notify closure as specified above; HTTP invalidates the binding so the next request returns 412; mobile sends an encrypted `PROVIDER_CHANGED` session FAILURE and closes. The controller requires an explicit new selection after such invalidation, even when the product and continuity key are unchanged. Legacy substrates without such notifications/bindings cannot claim this guarantee.

On Change wallet, the controller MUST stop admitting new calls to the old connection and show pending work. The user/application can either wait for all calls to settle or explicitly abandon the connection. Waiting MUST NOT impose a permission deadline. Abandoning rejects unresolved application promises with delivery certainty as below, closes the old connection, and MUST NOT claim that wallet-side effects were undone. Where a BRC-100 action reference is known, an application MAY explicitly call `abortAction` on the old wallet; there is no invented universal cancellation method. New work begins only on a separately resolved binding.

`signAction`/`abortAction` references, in-progress funding flows, and wrapper state MUST stay with the wallet/epoch that produced them. A wrapper MUST be recreated or explicitly reset on switching; changing the `base` of a live wrapper with pending work is prohibited. An adapter MUST NOT retry a wallet method automatically after uncertain delivery, reconnect it to another wallet, or replay a transaction because the chooser reopened. Re-delivery of identical encrypted transport records within one live mobile session is not re-invocation; section 10 prevents duplicate dispatch.

Connection-layer errors are distinct from wallet errors and MUST retain the following fields:

```ts
type ConnectionError = {
  domain: 'brc185'
  code: string
  message: string
  delivery: 'not-sent' | 'unknown'
  epoch?: string
}
```

Codes are `CONFIGURATION_ERROR`, `SELECTION_REQUIRED`, `USER_CANCELLED`, `DISCOVERY_BLOCKED`, `PROVIDER_CHANGED`, `PAIRING_EXPIRED`, `PAIRING_REJECTED`, `PROTOCOL_ERROR`, `RESOURCE_LIMIT`, `DISCONNECTED`, and `CONNECTION_CLOSED`. Before wallet dispatch, delivery is `not-sent`. If dispatch may have occurred and no authoritative wallet result exists, it is `unknown`. A network timeout cannot prove no transaction was created. An explicit BRC-100 error remains the original wallet error, not a connection error. Libraries MAY add a cause without replacing these fields.

Applications MUST be able to distinguish discovery, choosing, pairing, connected, locked/authentication required, waiting for wallet approval, suspended, disconnected, and closed. `isAuthenticated:false` MUST NOT be converted into “install a wallet.” Permission requests follow [BRC-219](./0219.md): the wallet presents/maintains the prompt or returns an error; connected pending prompts have no fixed permission timeout. Cancellation of a chooser or unapproved pairing sends no queued BRC-100 call.

### 7. Wrappers, onboarding, and commercial composition

The controller's output MUST be wrappable as an ordinary `WalletInterface`. Applications MAY place onboarding, funding, branded presentation, developer/platform fees, or other commercial policies above it. This BRC neither mandates nor removes those policies. A transport/controller MUST NOT edit transaction outputs, suppress a wrapper's fee, insert its own fee, or reroute funding. Wallet permissions remain authoritative for any resulting action.

The application MUST be able to replace the default no-wallet/onboarding UI, supply install and same-device handoff routes, and receive typed connection errors. One component must own a given connection/onboarding interaction: a controller and wrapper MUST NOT each open a competing missing-wallet modal for the same resolution. Integration documentation MUST explain how to disable or delegate overlapping UI while retaining funding and commercial behavior. A user-cancelled chooser MUST not be transformed into an indefinite missing-wallet wait.

Discovery and chooser entry MUST NOT require a vendor account, paid directory listing, referral agreement, sponsored auction, or approval by a central catalog. A separate onboarding catalog MAY contain disclosed commercial offers. It MUST be distinguishable from the neutral list of discovered wallets and MUST NOT hide, rank, or preselect those wallets because of payment. A wrapper cannot claim a conforming chooser while using commercial ranking inside it.

For example, a connection can be resolved once and supplied to `new BabbageGo(connection.wallet, options)`. Funding retries after a definite insufficient-funds result remain wrapper/application decisions against that same binding. They MUST NOT become retries after ambiguous transport failure or against a replacement wallet. This preserves the composition boundary without standardizing a vendor's fee amounts, business model, or UI.

### 8. Mobile pairing and trust boundaries

#### 8.1 Endpoints and relay

Mobile connections MUST use authenticated end-to-end encryption. HTTPS/WSS to a relay alone does not satisfy this requirement. The mandatory profile is `Noise_NNpsk0_25519_ChaChaPoly_SHA256`, using [Noise revision 34](https://noiseprotocol.org/noise.html), X25519, ChaCha20-Poly1305, and SHA-256. Implementations MUST use maintained implementations of these primitives/protocol processing, cryptographically secure randomness, and reject an all-zero X25519 shared secret. Implementations MUST NOT invent alternate nonce, key derivation, or cipher constructions under version 1. A future cryptographic profile requires a separately specified version; unsupported versions fail closed, with no plaintext fallback.

The application is the Noise initiator; the wallet is the responder. The invitation carries a random 256-bit preshared key (PSK), never a seed, spending key, account identity key, or password. Both sides generate fresh ephemeral X25519 keys for every invitation. The PSK and ephemeral private keys MUST be erased after a successful handshake or abandonment; only the resulting in-memory session state remains. In managed runtimes implementations MUST remove references and overwrite mutable buffers where supported, without claiming guaranteed erasure of garbage-collected copies. The displayed QR/link MUST be removed at that point. Sessions MUST NOT resume after a process loses its cryptographic state.

Two deployment modes use the same wire protocol:

| `mode` | Encryption endpoint and disclosure |
| --- | --- |
| `client` | Default. The actual application client, including a browser, encrypts/decrypts. A separately deployed application backend and relay receive no BRC-100 plaintext or session keys. |
| `backend` | Explicit configuration. The application's backend is the encryption endpoint and therefore can read the calls/results. Both connection UIs MUST say that the named application backend has this access before pairing is approved. Client-to-backend traffic MUST use authenticated HTTPS and application-session isolation. |

`backend` MUST NOT be selected automatically as a workaround for unavailable client cryptography. The mode is authenticated in the handshake. A relay is a replaceable ciphertext router and MUST NOT receive the PSK, ephemeral private keys, transport keys, decrypted payloads, or account keys in either mode. A backend that terminates the wallet encryption is an application endpoint, not a ciphertext-only relay. Self-hosted and vendor-operated relays use the same contract; no relay operator is privileged by this BRC.

This profile protects payloads from the relay and network intermediaries and provides forward secrecy through fresh ephemeral DH. It does not hide connection timing, approximate traffic volume, IP addresses, or the relay topic. It cannot protect plaintext from either authorized endpoint or compromised code running there. The QR/link is a short-lived bearer invitation: anyone who obtains it can attempt pairing, so explicit endpoint confirmation remains required.

#### 8.2 Invitation encoding

The vendor-neutral URI is exactly:

```text
brc-wallet://pair#<base64url(JCS(offer))>
```

There is no query, username, port, trailing path, or alternate host in this URI. Fragment transport avoids placing the invitation in an HTTP request or Referer. An offer has exactly the following fields, all required:

| Field | Value |
| --- | --- |
| `version` | Integer `1`. |
| `topic` | 16 independently random bytes, base64url. Single invitation/session identifier. |
| `relay` | Absolute `wss:` URL of the relay WebSocket endpoint; no credentials, query, or fragment; at most 2048 UTF-8 bytes. |
| `walletToken` | 32 random bytes, base64url; authorizes relay attachment as wallet, not wallet operations. Distinct from PSK and client token. |
| `psk` | 32 independently random bytes, base64url, produced by the application encryption endpoint. |
| `challenge` | 32 independently random bytes, base64url, for the wallet descriptor proof. |
| `origin` | Canonical HTTPS application origin, or a canonical HTTP loopback origin for explicit local development. |
| `originator` | ASCII hostname of `origin`, 1–250 bytes. |
| `mode` | Exactly `client` or `backend`. |
| `expires` | Integer Unix seconds, no later than 300 seconds after invitation creation. |
| `returnUrl` | `null`, or an absolute HTTPS URL with the same origin as `origin`, no credentials or fragment, at most 2048 UTF-8 bytes. |
| `returnState` | 16 independently random bytes, base64url; for same-device return correlation, even when `returnUrl` is null. |

The decoded offer MUST be at most 4096 bytes. Encoders MUST ensure the complete encoded URI fits their selected QR capacity and MUST reject oversize offers rather than truncate fields or lower cryptographic entropy. Wallets MUST accept the full 4096-byte decoded limit through paste/link intake even when a particular camera/QR renderer cannot carry it. A QR renderer MUST expose the equivalent link/intake alternative.

Version 1 mobile origins are web origins. A native or terminal application can use an application-controlled HTTPS origin and MUST explain its non-browser context; this does not prove the native program owns the domain. It MUST NOT impersonate another application's origin. Non-web origin authentication mechanisms can be specified separately without changing BRC-100.

Parsers MUST reject offers whose expiry is at or before their current time and MUST reject offers more than 330 seconds in the future (the extra 30 seconds accommodates a slightly slow receiving clock). The originating endpoint's 300-second deadline remains authoritative; clock disagreement can fail pairing but cannot extend it. The application MUST destroy an unused invitation at its expiry and generate new topic, PSK, tokens, challenge, and state for Refresh. Expiry applies to establishing a new session, not to an approved session's pending permission requests. The application MUST permit only one completed wallet pairing per invitation and MUST invalidate the invitation after approval or cancellation.

Offers MUST be produced from the actual application context, not a URL supplied by an untrusted frame or the relay. QR data, tokens, and fragments MUST NOT enter logs, analytics, crash reports, public clipboard history services, or third-party URL shorteners. A pairing page MUST not load third-party code with access to the fragment and MUST remove the fragment from visible browser history as soon as it has safely handed the offer to the local pairing component. Only explicitly user-initiated copying is permitted.

#### 8.3 Origin and user confirmation

Before any wallet method can be sent, both endpoints MUST complete this sequence:

1. Validate the offer, establish the Noise handshake, and compute the confirmation code below. Handshake message payloads are empty. No BRC-100 request is a handshake payload.
2. The wallet sends encrypted `HELLO`, containing the section 3 proof for `offer.origin` and `offer.challenge`. The application verifies it and displays the wallet name, instance label, and provenance, including whether it matches a remembered continuity key.
3. Both surfaces display the application origin and the same confirmation code. In `backend` mode both also display the backend-access disclosure. The wallet MUST identify the origin as a pairing claim, not an independently verified browser attestation. The user MUST confirm that it is the intended application and compare the code across the actual application and wallet surfaces. For same-device use, the UI MUST support switching between those surfaces to compare it.
4. Each endpoint requires its user's explicit confirmation and sends encrypted `APPROVE`. Once both local and peer approvals exist, the connection becomes usable. Until then, a requester MUST NOT send and a wallet MUST NOT dispatch any BRC-100 method. Reject/back sends `REJECT` and destroys the session. A relay event or URL callback never substitutes for encrypted approval.

Let `h` be the final Noise handshake hash. Compute SHA-256 over `UTF8("BRC-185 confirmation v1\n") || h`; interpret its first four bytes as an unsigned big-endian integer; take its value modulo 100000000 and display eight zero-padded decimal digits, grouped `1234 5678`. A refresh/retry MUST generate a new invitation, not repeatedly guess confirmation codes within one invitation. The code is an authenticated-channel comparison aid, not a password or wallet identity.

An origin claim is bound against modification by the relay through the prologue, but a malicious QR issuer can claim a false origin. The code comparison and user's verification of the actual application surface are mandatory; branding or an unverified origin label MUST NOT be represented as cryptographic website ownership proof. In a browser the controller MUST source the claim from the real document origin. Permissions MUST bind to the confirmed originator and MUST never be silently reused for another origin.

#### 8.4 Same-device links and return

Wallets MUST accept the vendor-neutral offer through an in-wallet scan or paste/intake route. They SHOULD also expose OS-verified HTTPS app/universal links. After the user chooses a wallet, the application MAY wrap the same offer as:

```text
https://<wallet-controlled-host>/<registered-path>#brc185=<base64url(JCS(offer))>
```

The wallet link endpoint is supplied by an application-configured adapter or an explicitly selected onboarding entry. The application MUST NOT follow a relay-supplied redirect to choose a wallet. The HTTPS route MUST use the platform's verified app-link association when opening a native wallet; a generic custom scheme MAY be offered as a disclosed fallback, never treated as authenticated app identity. Neither route changes the offer, encryption, or confirmation requirements. An OS's own app chooser is outside this BRC's ordering control; an application-owned list is subject to section 5.

After approval, rejection, or cancellation the wallet MAY open `returnUrl` after user action, appending `brc185_state=<returnState>` and `brc185_status=connected|rejected|cancelled` using normal URL query encoding. Existing occurrences of those two reserved parameters make an offer invalid. The wallet MUST NOT include tokens, keys, signatures, BRC-100 results, or permission grants in the return URL. The application MUST verify state against its locally outstanding invitation and take authoritative connection status only from the encrypted channel. It MUST consume the state once. A return link MUST NOT initiate/replay a wallet operation. A failed return MUST leave a visible manual Return to app path.

### 9. Relay wire profile

#### 9.1 Allocation and attachment

A version 1 relay exposes `POST /brc185/v1/sessions` over HTTPS. Request JSON is `{version:1, topic, expires}`. The relay MUST atomically reject an existing topic with HTTP 409 and expired/invalid requests with HTTP 400. On HTTP 201 it returns `{version:1, relay, clientToken, walletToken}`; tokens are distinct random 32-byte base64url values. The application validates fields and MUST refuse any relay URL that violates its configured relay-origin policy. The relay MUST NOT request the PSK or complete offer. Authentication, quotas, payment, and abuse controls for allocation MAY be deployment-specific; they cannot alter session semantics. No secret is transmitted in a URL query.

The WebSocket uses subprotocol `brc185.v1`. Its first message is UTF-8 JSON `{version:1, type:"attach", topic, role, token}`, with role `client` or `wallet`. The server responds `{version:1,type:"attached",peerPresent:boolean}`. It subsequently sends `{version:1,type:"peer",present:boolean}` on peer attachment changes. Invalid attachment closes with WebSocket code 1008. Expired, unapproved sessions cannot accept a first wallet attachment. At most one socket per role can be active; a valid replacement attachment closes that role's previous socket before accepting frames from the new socket. Client implementations MUST serialize their own reconnects.

The relay routes each binary message unchanged to the opposite role, in order, and never echoes it to the sender. It MUST NOT reinterpret the binary contents. When the other role is absent it MAY discard messages; endpoint replay, not relay storage, provides continuity. It MUST make peer presence changes visible. Text after attachment is restricted to the server control messages above and client `{version:1,type:"close"}`; unexpected text fails the session. Close erases tokens and ends the relay session. Either endpoint can close; this is transport closure, not proof of wallet-side rollback.

To preserve a successfully established session beyond invitation expiry, the client sends `{version:1,type:"established"}` after both encrypted approvals. This is the one additional permitted client text message. It MUST be sent before the invitation expires. The relay then accepts reattachments with the existing role tokens until explicit closure or actual resource/service failure; it MUST NOT impose a permission-response deadline. This relay notification is not authorization: endpoints still require encrypted approvals, and a malicious relay cannot grant them. Service policy MAY retire an idle session only when both peers have been absent for at least 24 hours, reporting it as disconnection on a subsequent attachment.

TLS certificate validation is mandatory. Redirects during allocation or attachment MUST NOT be followed automatically. A deployment MAY require a user-approved relay account or fee, but that is a relay service choice, not wallet-provider certification. Logs MUST omit tokens and payloads. The relay MUST enforce allocation/attachment resource limits and return a visible failure; none of these controls establishes trust in ciphertext contents.

#### 9.2 Handshake and transport records

The Noise prologue is:

```text
UTF8("BRC-185 mobile v1\n") || JCS(publicOffer)
```

`publicOffer` is the complete offer with only `psk` omitted; the PSK is supplied separately to the Noise `psk0` input. Both sides MUST use identical canonical bytes. Neither the prologue nor its fields need to be sent to the relay. The handshake starts after both roles are attached. The first binary message is byte `0x00` followed by the initiator's Noise handshake message; the second is `0x01` followed by the responder's. With this pattern, 32-byte public keys, and empty payloads, each message is exactly 49 bytes including its leading type byte. Unexpected direction, extra handshake payloads, failed authentication, or malformed lengths abort pairing. Each side MUST cache its exact sent and received handshake bytes for the session. On reconnect before approval, it retransmits any already-generated handshake message verbatim; a byte-identical previously processed handshake message is a duplicate, not another Noise state-machine step. A responder receiving the duplicate first message retransmits its cached second message. A different message in an already processed handshake position is fatal. Retained handshake state can survive socket loss until invitation expiry; it MUST never be restarted with reused ephemeral keys. Loss of that state requires a fresh invitation.

After Noise `Split`, the initiator's first cipher state sends client-to-wallet and its second receives wallet-to-client; the responder uses the inverse directions. Each binary transport record is:

```text
0x02 || sequence:uint64be || noiseCiphertext
```

Each direction starts sequence 0. Sequence MUST equal that direction's Noise cipher nonce. Additional authenticated data is `UTF8("BRC-185 record v1\n") || topicBytes || directionByte || sequenceBytes`, where direction is `0x00` client-to-wallet and `0x01` wallet-to-client. Use the Noise cipher state's normal `EncryptWithAd` / `DecryptWithAd` and monotonic nonce progression. Ciphertext is at most 65535 bytes, including its 16-byte authentication tag. Application plaintext is at most 65519 bytes. The nine-byte outer header is not part of that ciphertext limit. At 2^31 records in either direction, endpoints MUST stop admitting new requests and drain pending work before establishing a fresh approved session. They MUST never generate or accept a record with sequence 2^32 or greater; exhausting that remaining drain allowance is a resource failure with appropriate delivery uncertainty, never a nonce reset under an existing key.

Record plaintext is:

```text
kind:uint8 || requestId:16bytes || total:uint32be || offset:uint32be || payload
```

The header is 25 bytes; each payload fragment is at most 65494 bytes. `total` counts the entire unfragmented payload; `offset` is its zero-based byte position. Fragments for a given `(kind,requestId)` MUST be contiguous, start at offset 0, preserve total, and end exactly at total. Different requests MAY interleave. Empty payloads use one fragment with total 0 and offset 0. Reassembly MUST finish and validation succeed before a wallet method is dispatched. Partial requests cannot execute.

| Kind | Direction, ID, and payload |
| --- | --- |
| `0x01 ACK` | Either; zero ID; exactly 8 payload bytes containing highest contiguous authenticated sequence received, uint64be. |
| `0x02 HELLO` | Wallet to client; zero ID; JCS descriptor proof, at most 16384 bytes. |
| `0x03 APPROVE` | Either; zero ID; empty. |
| `0x04 REJECT` | Either; zero ID; empty. |
| `0x05 CLOSE` | Either; zero ID; empty. |
| `0x10 REQUEST` | Client to wallet; new random nonzero 16-byte ID; complete BRC-100 binary request including method call code, originator frame, and parameters. |
| `0x11 RESPONSE` | Wallet to client; matching ID; complete BRC-100 binary response including success/error code and existing response/error serialization. |
| `0x12 FAILURE` | Either; matching request ID, or zero for a session failure; JCS section 6 connection error, at most 4096 bytes. |

Controls other than HELLO MUST fit in one record with offset 0. Every request and response payload MUST be at most 67,108,864 bytes (64 MiB). Endpoints MUST support this limit for a single message, at least 16 outstanding dispatched calls, and at least 64 MiB of aggregate in-progress reassembly; greater aggregate use MAY return `RESOURCE_LIMIT`. This finite transport resource limit is not permission to omit methods. Oversize requests fail locally `not-sent`; oversize responses produce `RESOURCE_LIMIT` with `unknown` delivery because wallet effects may already exist. Implementations MUST bound length arithmetic and allocation before accepting fragments and never silently truncate a BEEF or other byte array.

The receiver MUST compare the BRC-100 originator frame with the approved offer's originator and reject mismatches before wallet dispatch. It MUST pass that originator to the wallet and MUST NOT substitute the relay hostname. Method codes, serialization, and results are exactly [BRC-100](./0100.md), with no method-name whitelist or rewritten fields. Unknown connection kinds or invalid control ordering terminate the connection with `PROTOCOL_ERROR`; an existing wallet error is returned as RESPONSE.

The endpoint state machine is fixed:

| State | Accepted transition/control |
| --- | --- |
| `offered` | Validate offer and attach; expiry/reject goes to `closed`. No wallet RPC. |
| `handshake` | Exactly the two directional handshake messages; success goes to `confirming`; authentication/state failure goes to `closed`; socket loss with retained state goes to `suspended`. |
| `confirming` | Wallet sends exactly one HELLO before its APPROVE. Client accepts/verifies HELLO before its own APPROVE. Each side sends at most one APPROVE after local confirmation. ACK, REJECT, CLOSE, or fatal FAILURE are permitted; REQUEST/RESPONSE are prohibited. |
| `connected` | Both local and peer approvals exist. REQUEST/RESPONSE, ACK, FAILURE, and CLOSE are permitted. A newly encrypted HELLO, APPROVE, or REJECT is a protocol error. |
| `suspended` | Prior handshake/confirmation/connection state survives but a socket/peer is absent. Reattach and replay cached handshake bytes and/or encrypted records to return to that prior state; no newly admitted application requests until connected. The invitation deadline still applies until approval. |
| `closed` | Terminal. No frame can reopen it; a new invitation is required. |

A socket loss while the user switches between same-phone surfaces MUST NOT by itself discard a retained handshake or confirmation. Before approval, the invitation expiry remains in force; after approval, no permission deadline is added. Duplicate cached handshake messages and duplicate ciphertext are handled as specified above, not as new controls. A terminal state change completes pending application promises according to section 6.

### 10. Delivery, mobile lifecycle, and revocation

Within a live session, each endpoint retains its send/receive cipher states, next sequence, unacknowledged ciphertext records, request dispatch table, and unfinished responses. Keys and role tokens MUST remain in endpoint memory or equivalently protected live-process storage and MUST NOT enter ordinary browser persistent storage. Loss of any state required to avoid nonce reuse or duplicate dispatch terminates the session. A new connection requires new pairing material; it MUST NOT replay old requests.

The receiver processes only its expected next sequence. Lower sequences are duplicates and MUST be discarded without decryption, nonce advancement, or wallet dispatch. A higher sequence is a gap: the receiver suspends application delivery, closes that socket, and reconnects to request peer retransmission through the attachment/presence transition. It MUST NOT decrypt out of order or invent missing results. Authentication failure on the expected sequence is fatal. Relays can disrupt availability; endpoints MUST never trade authenticity for reconnection.

After every successfully received non-ACK record, the receiver MUST enqueue an encrypted ACK for the highest contiguous received sequence, coalescing adjacent acknowledgements when possible. ACK records do not trigger ACKs by themselves. An ACK can acknowledge earlier ACK records. Only an authenticated peer ACK can release stored outbound ciphertext; relay presence, write completion, and attach responses cannot. ACK values beyond the largest sequence sent are protocol errors; older ACK values never move the acknowledged position backward. An implementation MUST retain at least 8 MiB of unacknowledged ciphertext; at its configured bound it applies backpressure to new data and continues processing incoming records/ACKs. It MUST reserve an additional 64 KiB for ACK/control output so two full send buffers cannot deadlock acknowledgements. It MUST NOT drop unacknowledged records to make space. Exhausted control capacity is an explicit resource failure, not permission to reuse a nonce.

On either role reconnecting, both endpoints retransmit their retained, unacknowledged records in original sequence order before sending new records. These MUST be the exact original bytes: do not re-encrypt, reset counters, rebuild requests, or dispatch an ID twice. After that replay batch, each endpoint that has received at least one peer record MUST send a fresh ACK for its current contiguous receive position, even if the batch contained only duplicates. This recovers a lost ACK without an ACK-to-ACK response loop. Reconnect replay happens only after attachment/peer-presence transitions, not on every ordinary ACK.

A terminal RESPONSE/FAILURE ID cannot be reused; the wallet retains dispatched IDs for the session even after acknowledging the response. Once a REQUEST has completed reassembly, that ID in a new REQUEST is `PROTOCOL_ERROR`, not a retry; correctly ordered continuation fragments of its original reassembly are not new requests. A second terminal response for one ID is also a protocol error. Response ciphertext retransmission is handled by sequence deduplication. These rules provide at-most-once dispatch within the surviving session, not durable exactly-once transactions after process loss. Implementations MAY bound session dispatch history, but MUST stop admitting new requests and drain/close before discarding IDs; they cannot silently forget them while keeping the session usable.

A request-specific FAILURE ends only its matching request. If failure occurs during reassembly, the receiver MUST discard subsequent payload fragments for that ID while continuing authenticated sequence processing through the declared total; it MUST never dispatch the partial request. A sender receiving that failure MUST still send any already encrypted records in sequence and MAY omit only fragments not yet encrypted. The receiver marks such an abandoned reassembly terminal on receiving the failure's authenticated ACK from the sender or on session closure. A zero-ID FAILURE is fatal to the session. Any failure that prevents reliable sequence/state retention MUST terminate the whole session and report possibly dispatched calls as `unknown`.

Ordinary backgrounding, screen lock, suspension, and foreground return MUST preserve the session and pending prompt while the process/state remain alive. A reconnecting UI shows `suspended`, retains the original request, and offers cancel/disconnect. It MUST NOT reissue the method or start a second permission prompt merely because the user returned through a link. There is no elapsed-time limit on a live permission decision. Implementations MUST honor BRC-219 prompt visibility and restoration. Actual process/state loss, unrecoverable relay failure, explicit disconnect, and service closure end the connection with `unknown` delivery for possibly dispatched calls. They are not permission timeouts.

Users MUST be able to see and revoke active mobile connections in the wallet and disconnect in the application. Revocation sends encrypted CLOSE when possible, closes relay attachment, erases keys/tokens and unresolved invitation material, and blocks future requests under that session. Receiving CLOSE has the same effect. Revoking transport access does not delete wallet data or retroactively revoke completed operations; wallet permission persistence is separately controlled by BRC-116. A future mobile connection requires a new invitation and explicit approval, even when a wallet preference is remembered.

### 12. Compatibility and rollout requirements

This proposal adds transport/control protocols alongside existing ones. It MUST NOT change BRC-100, its method wire codes, legacy BRC-5 routes, or the meaning of BRC-6/BRC-7 messages. Legacy wallets remain usable through compatibility adapters, with limitations honestly identified. They MUST NOT be labeled BRC-185 conforming merely because one readiness call succeeds.

New desktop listeners SHOULD retain the default port when it is available, making a lone new wallet reachable by legacy clients. When it is occupied, ascending allocation makes the additional wallet available to new discovery clients. A legacy client that probes only the default port cannot see every new listener; documentation MUST say so. A new client MUST NOT send a legacy JSON request to a binary listener based only on its port number.

Existing mobile-relay protocols and branded URI schemes MAY coexist through explicit legacy adapters. They MUST NOT be silently accepted as the encrypted version 1 profile, and version 1 MUST NOT downgrade to them after an authentication failure. A relay method subset cannot be made conforming by advertising optional capabilities. Migration requires implementing complete carriage, preserving request/error semantics, and the new pairing security contract.

Implementation work MUST preserve the layering in section 2. Public packages SHOULD release independent adapters/controller/UI components and document compatible version combinations. Reference UI/framework packages MUST NOT become transitive dependencies of the core SDK. Wallet-specific integration can supply an adapter; applications and wrappers MUST NOT need vendor-specific branches to call BRC-100.

## Design rationale and implementation guidance (non-normative)

### Source findings and proposed changes

At the September 25, 2026 capture, the TS stack's `WalletClient` used fixed default endpoints and priority among successful readiness probes. It could accept a supplied `WalletInterface`, but it did not enumerate ascending ports or choose among all wallets. BSV Desktop listeners used fixed ports. The proposed controller and descriptor are new; they are not descriptions of shipped discovery behavior.

The existing `ts-wallet-relay` provides useful pairing, mobile prompt, and modal experience. Its application backend is an encryption endpoint, whereas its WebSocket relay routes encrypted traffic. Its typed proxied-method list was a subset of BRC-100 at the captured revision. The new client endpoint mode, full method carriage, URI, wire protocol, and security requirements therefore require implementation work; compatibility must be explicit. The BSV Browser pairing route delegates to the shared mobile wallet-toolbox pairing UI, providing another concrete integration point.

`@babbage/go` version 0.1.20, commit `448505904367b8990e5493f68c419bebf06b88c7`, accepts `WalletInterface` in its constructor, defaults to `WalletClient` when none is supplied, handles wallet-unavailable UI, and wraps `createAction` with funding and monetization behavior. Its platform contribution and developer fee are distinct settings. Its existing modal/error handling can deliberately leave a promise pending; integration with typed selection cancellation needs specific attention. Its existing `base` and pending payment state make one wrapper per immutable connection the appropriate composition model. These are source observations, not execution tests or recommendations to change its commercial terms.

EIP-6963 supplies useful precedent for independent browser provider announcements without redefining the wallet API. WalletConnect's pairing specifications supply precedent for explicit pairing versions and expiry. This BRC does not adopt Ethereum methods, a WalletConnect network dependency, or a central wallet directory. Chrome's local-network access controls and Android/iOS app-link behavior are platform constraints that adapters must respect; a BRC cannot grant a browser permission or native-app association.

The bounded discovery window makes routine connection work finite. Ascending allocation remains valid above that window; the coverage report and explicit extension avoid pretending that a bounded scan is exhaustive. Signed, per-origin descriptors provide continuity and alias merging without asking every discovered wallet to reveal a user identity. They do not certify vendors.

Noise is selected as a documented protocol construction, rather than composing ad hoc encryption primitives. Fresh ephemeral keys and a random invitation PSK establish encrypted sessions without using wallet spending keys as transport identities. The extra confirmation and honest origin labeling address the fact that a QR payload alone does not attest a browser origin. The mandatory security review remains a release gate, not evidence that this newly composed profile is already secure in deployed implementations.

### Initial implementation and acceptance plan

The specification precedes implementation. Suggested work packages, in dependency order, are:

1. Build independent fixtures for descriptor signatures, origin normalization, allocation/discovery overlap, binary carriage, state transitions, and encrypted records. Produce deterministic cross-language test vectors for this BRC's envelopes in addition to upstream cryptographic vectors. Complete the protocol review before presenting the profile as production-ready.
2. Implement the external controller interfaces, storage, runtime checks, and neutral selection policy. Add the narrow optional WalletClient delegation hook with compatibility tests. Publish plain HTML, React, terminal, headless, and wrapper composition examples separately.
3. Add signed discovery and next-free-port allocation to desktop wallets; implement extension, window.CWI, XDM, and React Native adapters and their provider events. Test simultaneous independent wallets and alias deduplication before mobile integration.
4. Implement the complete encrypted relay/phone profile and its lifecycle/replay tests, then QR, same-phone links, return, revocation, and backend disclosure UIs. Retain legacy mobile adapters only as explicitly identified paths.
5. Exercise Babbage Go around the bound interface, including missing-wallet UI ownership, insufficient-funds retry, both fee settings, action signing and pending state, cancellation, and switching. Verify behavior from source and execution rather than assuming constructor compatibility proves every flow.
6. Run the published conformance matrix with BSVA reference wallets first, then independent vendor wallets. Candidate follow-on integrations include Metanet Desktop, Metanet Explorer, Peacock Wallet, PaperTrade, and Metanet Docs. This order is an implementation plan, not chooser ranking, certification, or a claim of commitments by those projects.

No package names, reference applications, or proposed rollout order grant a vendor special treatment in normative discovery or selection. Onboarding opinions such as BRC-110/BRC-137 and the separate sponsored-onboarding proposal are background inputs; their catalogs or business flows are not prerequisites for this connection protocol.
