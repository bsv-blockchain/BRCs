# BRC-214: Wallet Asset Profiles

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

A [BRC-100](../wallet/0100.md) wallet holds more than one kind of value: BSV, coins of other chains, items, open tokens and issuer-countersigned assets. Each kind has its own storage, its own proof of authenticity, and its own way of letting applications see and move it.

This document names those kinds as **asset profiles**. A profile is the unit of everything an application can be granted, and it fixes six things:

- where the value lives;
- what proves it;
- how an application views it;
- how an application moves it;
- which actions exist;
- which spending scope covers it.

Three rules make profiles safe to combine:

1. Every held asset belongs to exactly one profile, for life.
2. A grant in one profile never grants anything in another.
3. Only coin profiles share the payment budget.

The document registers six profiles (`bsv`, `coin:<chain>`, `1sat`, `p2pft`, `csft`, `csnft`) and defines one read method, `listAssetProfiles`, so applications can learn what a wallet holds and accepts before asking.

## Motivation

Each asset format so far has specified its own basket, permission scheme and actions in isolation. Wallets then have to decide on their own how these interact:

- Does Auto-pay cover a token transfer?
- Does permission to view items show tokens?
- Is a Litecoin balance a collectable?

Different answers in different wallets are a security problem, not a style choice. An application granted a payment budget must not be able to spend an item out of it.

Applications face the opposite gap. They cannot tell whether a wallet holds Litecoin or countersigned tokens without calling methods and handling failures.

## Terms

- **Profile:** a named kind of held value with the fields of §1.
- **Coin profile:** a profile whose value is a plain payment unit (`bsv`, `coin:<chain>`).
- **Asset profile:** every other profile: value with identity, issued by someone, proven back to an origin or deploy.
- **Grant:** anything a user gives an application that outlives one call: a view permission, a spend label scope, an automatic-payment budget, a BRC-73 `spendingAuthorization`.

## Specification

### 1. Profile fields

| Field | Meaning |
|---|---|
| `id` | Lowercase identifier. Coin profiles of other chains are `coin:<chain id>` |
| Holds | What one unit is |
| Custody | Where the value lives and whose key moves it |
| Authenticity | What proves a held unit is what it claims |
| View | How an application lists it, and which grant that needs |
| Move | How an application spends it, and which consent that needs |
| Actions | The application methods that act on it, each its own consent |
| Spending scope | `payment` (shares the per-application payment budget) or `per-action` (always its own prompt, never in a budget) |

### 2. Registered profiles

| `id` | Holds | Custody | Authenticity | View | Move | Spending scope |
|---|---|---|---|---|---|---|
| `bsv` | Satoshis | Wallet keys on BSV | BRC-67 SPV | `getBalance`, `listOutputs` on the application's own baskets | `createAction` | `payment` |
| `coin:ltc` | Litoshi | The wallet's coin key on Litecoin (BRC-213 §2) | Burial 6 deep on the wallet's own Litecoin header chain (BRC-213 §4) | `listCoins({ chain: "ltc" })` | `sendCoins({ chain: "ltc", … })` | `payment` |
| `coin:bch` | Satoshi | The wallet's coin key on Bitcoin Cash | Burial 6 deep on its own Bitcoin Cash header chain | `listCoins({ chain: "bch" })` | `sendCoins({ chain: "bch", … })` | `payment` |
| `coin:btc` | Satoshi | The wallet's coin key on Bitcoin | Burial 3 deep on its own Bitcoin header chain | `listCoins({ chain: "btc" })` | `sendCoins({ chain: "btc", … })` | `payment` |
| `coin:doge` | Koinu | The wallet's coin key on Dogecoin | Burial 20 deep on its own Dogecoin header chain | `listCoins({ chain: "doge" })` | `sendCoins({ chain: "doge", … })` | `payment` |
| `1sat` | One-sat ordinal items | Owner key on BSV | BRC-150 proof to the origin | Basket `p 1sat <scope>` (BRC-165) | `createAction` labeled `p 1sat input id <key>` | `per-action` |
| `p2pft` | Open fungible tokens | Owner key on BSV | BRC-176 lineage to the deploy | Basket `p p2pft <scope>` | `createAction` labeled `p p2pft input id <key>` | `per-action` |
| `csft` | Countersigned fungible tokens | Owner key, plus the issuer's key set for each transfer | The issuer's countersignature in each transfer | Basket `p csft <scope>` | Wallet methods only (BRC-253) | `per-action` |
| `csnft` | Countersigned items (supply 1) | As `csft` | As `csft` | Basket `p csnft <scope>` | Wallet methods only (BRC-253) | `per-action` |

`coin:<chain>` registers one profile per BRC-213 binding. A wallet lists only the chains it supports.

### 3. Rules

1. **One profile, for life.** A held asset belongs to exactly one profile from the moment the wallet records it. Nothing moves an asset between profiles. Even a countersigned asset whose issuer released it stays `csft` or `csnft`.
2. **Grants never cross.** A grant in one profile gives nothing in another. Permission to view `1sat` items shows no tokens, a `p2pft` spend label cannot select an item, and a payment budget never covers an asset profile.
3. **One payment budget.** All coin profiles share one budget per application: any automatic-payment budget the wallet keeps, and any BRC-73 `spendingAuthorization` grant. A payment in `coin:<chain>` counts at its BSV-equivalent fiat value (BRC-213 §10). An application cannot route around its budget by paying on another chain.
4. **Asset actions stay per-action.** A transfer, mint, issue, listing, purchase or offer that moves an asset profile is never approved automatically, even when it also pays satoshis. The satoshis it pays do not open a payment-budget path for the asset.
5. **Separate views.** A wallet shows each profile in its own place. Coins are balances, never collectables or tokens. Items are never mixed into token lists. A retired or migrated record of an earlier format is not shown as value in any profile.
6. **Refuse by profile.** A request that names one profile but would move value of another is refused, not partly executed.
7. **No profile, no value.** A wallet MUST NOT count, price or offer value it cannot place in a profile it supports.

### 4. `listAssetProfiles()`

Requires a connected application, with no further prompt. It tells the application which profiles this wallet supports and how to reach each. It reveals no balances.

```json
{
  "profiles": [
    { "id": "bsv", "scope": "payment", "spec": ["BRC-100"] },
    { "id": "coin:ltc", "scope": "payment", "spec": ["BRC-213"],
      "chain": "ltc", "decimals": 8, "minConfirmations": 6,
      "methods": ["getCoinAddress", "listCoins", "sendCoins"] },
    { "id": "1sat", "scope": "per-action", "spec": ["BRC-147", "BRC-150", "BRC-165"],
      "basket": "p 1sat", "spendLabel": "p 1sat input id" },
    { "id": "p2pft", "scope": "per-action", "spec": ["BRC-162", "BRC-176", "BRC-251"],
      "basket": "p p2pft", "spendLabel": "p p2pft input id" },
    { "id": "csft", "scope": "per-action", "spec": ["BRC-253"], "basket": "p csft" },
    { "id": "csnft", "scope": "per-action", "spec": ["BRC-253"], "basket": "p csnft" }
  ]
}
```

- `spec` lists the documents the wallet implements for that profile, so an application can tell a draft-level implementation apart.
- `basket` is the prefix of the view basket, and `spendLabel` the prefix of the spend label, where they exist.
- Coin profiles carry the BRC-213 binding facts an application needs to show amounts and waiting times.

A wallet MUST list only profiles whose full rule set it enforces. An application MUST treat a missing profile as unsupported, and MUST NOT probe for it with spending calls.

### 5. Registering a profile

A new profile is registered by a document that fixes every field of §1 and states how it satisfies §3. A profile whose units can pay for anything SHOULD be a coin profile and join the payment budget. A profile whose units have identity MUST be `per-action`.

## Security considerations

- **Budget escape.** Without rule 3, an application limited to $10 a day in BSV could pay unlimited Litecoin. Without rule 4, a budget sized for small payments could move a valuable item that happens to cost one satoshi to send.
- **Confused deputy.** Rule 6 prevents a request built for one profile from reaching inputs of another. An example is a `createAction` spend label that selects an output filed elsewhere.
- **Fingerprinting.** `listAssetProfiles` reveals which profiles a wallet supports, not what it holds. A wallet MAY answer it only after connection, as specified, to avoid exposing even that to unconnected sites.

## Rationale

- **The profile is the unit of consent.** Users reason about "my Litecoin" or "my items", not baskets or script templates. Grants that follow that line are the ones users can predict.
- **Format is not profile.** HCT shares filings with older formats of the same mode, because what a holder can do with an asset depends on its mode (open or countersigned), not on how its lock is encoded.
- **Coins share one budget, assets never do.** Coins are interchangeable at a price, so one fiat budget is meaningful. Assets are not interchangeable, so no budget can describe them.

## Open questions

1. **Per-profile budgets.** Some users may want a smaller budget for one chain. That would narrow rule 3 without breaking it: the shared budget stays an upper bound.

## Implementations

HandCash Desktop and Mobile (`@handcash/wallet-ui`) implement every profile in §2, with coin bindings `coin:ltc`, `coin:bch`, `coin:btc` and `coin:doge`. The code is in `src/wallet/assetProfiles.ts` (`listAssetProfiles`), and the profile table is in `docs/asset-actions-and-permissions.md` §0.
