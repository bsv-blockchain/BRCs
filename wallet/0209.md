# BRC-209: 1Color Minimal Resource Profile

Ty Everett (ty@projectbabbage.com)

## Abstract

This specification defines one required processing profile for [BRC-207](./0207.md)
resources whose applications do not require token provenance, conserved quantities,
issuer authorization or overlay admission. The wallet protects signing keys,
identified transaction outputs and satoshis. It makes no fungible-token validity,
scarcity or lineage claim for these resources. The profile uses the existing
[BRC-162](../tokens/0162.md) declaration, script prefix and module interfaces.

MUST, MUST NOT, SHOULD and MAY express conformance requirements. This profile is
optional. Unsupported wallets MUST fail rather than use ordinary token handling.

## Single mode declaration

The profile identifier is exactly `https://brc.dev/209`. Its descriptor is exactly
`{"version":1,"params":null}` in the original deploy's `req` map:

```json
{
  "req": {
    "https://brc.dev/209": {"version": 1, "params": null}
  }
}
```

This is one mode, not a collection of independent flags. Other versions or
parameters fail. BRC-162's immutable requirements, strict payload parsing,
binary-prefix precedence and legacy `colorPayload` carrier apply. Later outputs
cannot introduce the mode for an identifier whose original declaration lacks it,
or remove it by omitting payload data. This profile defines no `ext` state;
its own `ext` entry MUST be absent. Other required profiles remain enforceable,
including their history, identity or transition requirements. This profile
removes only the baseline obligations listed below, never another profile's
obligations. Incompatible requirements fail.

## Declaration evidence

For each resolved asset ID involved in a signature request, action plan or
receipt, the caller MUST supply this profile's asset-scoped `profileData` leaf
as exactly `{"declarationTx": "<lowercase raw transaction hex>"}`. Hex MUST be
nonempty, even-length and decode to exactly one complete serialized Bitcoin
transaction without trailing bytes. The wallet MUST:

1. Compute the transaction ID from the exact supplied serialized bytes, without
   normalization, and match the asset ID's TXID component.
2. Select the asset ID's actual output index and validate the encoding's deploy
   position, prefix and syntactic quantity/role rules.
3. Strictly decode the applicable payload and verify this exact descriptor and
   every other required profile. A display label or caller-supplied parsed map
   is not declaration evidence.
4. Match every involved source and destination's declared asset ID, and reject
   conflicting repeated `req` maps under BRC-162.

This authenticates bytes committed to by the identifier. The declaration
transaction need not be mined, broadcast or connected to the current resource.
No historical token path from it to that resource is required. The wallet MUST
NOT describe this check as confirmed issuance, issuer identity, supply validation
or proof that a current output descended from the declaration. Anyone can create
another output naming the same identifier. Applications needing origin,
uniqueness or continuity must establish those properties separately.

A new deploy uses `ISSUE` and an empty leaf `{}`; its declaration is read from
the proposed transaction itself. After finalization, the actual ID and full
transaction bytes replace the provisional record, retaining the original key
tuple. Subsequent requests for that resolved ID supply `declarationTx` normally.
An internalization request using an ISSUE remittance reads the declaration from
its completed subject transaction. ISSUE never identifies an existing input in plan/evidence metadata. The preserved
original ISSUE key-derivation tuple remains usable to sign that deploy output;
its resolved asset ID selects the declaration evidence.

Evidence is required for every involved ID using this profile, including foreign
resources and requested destinations. Repeated declaration evidence MUST agree.
A wallet MAY cache verified bytes by exact ID to avoid repeated verification,
but cache presence does not permit an omitted leaf in these requests.
`signAction` and continuation/processing of an existing action use its retained,
validated plan and evidence. Read queries use the record's authenticated
requirements; they do not infer support from a basket name.

### Transport and bounds

Evidence travels only in `profileData["https://brc.dev/209"][assetId]`, or its
ISSUE entry. It is not a BRC-176 packet or an extra transaction in ordinary
Atomic BEEF. URLs, proof references and automatic network retrieval are not
part of this profile. Duplicate or extra members, mismatched IDs, invalid hex
or missing declarations fail before signing or receipt acceptance.

For `internalizeAction` basket insertions into this profile's `p color` baskets,
the complete `customInstructions` string MAY exceed the ordinary 1000-byte
limit. It MUST NOT exceed 16 MiB (16,777,216 UTF-8 bytes); the sum of all `p color` receipt
instruction strings in one call MUST also fit that limit. This exception
requires a valid, supported declaration and valid module receipt instructions;
a basket label alone cannot establish eligibility. Count the actual encoded
strings, including repeated evidence and JSON/hex overhead. Enforce bounds
before large allocation or hex decoding. A smaller documented host or transport
limit MUST produce an explicit error, never truncation or partial acceptance.
Other receipts retain their ordinary limit. Signature envelopes and reconstructed
action plans retain BRC-207's existing 16 MiB limits. Binary string framing is
unchanged; codecs enforcing the earlier limit may explicitly reject the call.

## Processing contract

For an authenticated identifier using this profile, the following BRC-207
baseline checks and operations do not apply:

- Token ancestry or back-to-deploy validation, BRC-176 lineage packets, and
  historical admission of token inputs.
- Token overlays, SLAP discovery, bootstrap topics, topical membership, token
  spendability lookups, overlay preflight, submission and admission.
- Token quantity conservation, provenance, supply, minting authority and
  token mint/burn/transfer accounting, including authority continuity.

A wallet MUST NOT require these as prerequisites for this profile alone. It MUST
reject a `tokenProofs` item scoped to this profile's asset unless another
required profile explicitly requires or accepts it and validates it under
BRC-176. This profile alone never requires one; other assets retain their proofs. Ordinary BRC-161/162 indexers and BRC-176
validators remain unchanged: they may reject these outputs, and their base
validity results are not assertions made by this profile.

The asset ID, script encoding, exact uint64 field, deploy-position rules and
zero-versus-positive role discriminator remain syntactically meaningful. The
field is a declared quantity, not a verified conserved balance; zero is not proof
of an authorized minting capability. A resource may be created without a same-ID
input, change quantity, or disappear without a token mint/burn authorization.
Those facts do not waive consent for a protected key or resource being used.
Every encountered identifier is evaluated independently; this mode cannot
propagate through a transaction to ordinary assets.

### Bitcoin evidence, signing and completion

BRC-207's ordinary Bitcoin source authentication, BEEF/SPV requirements for the
subject transaction, exact source scripts and satoshi values, DSAP, signature
coverage, key isolation, script validation, reservations and exposure tracking
remain mandatory. The declaration-only exemption above applies only to the
configuration anchor; if that transaction also supplies an input or is the
receipt subject, it must independently meet the ordinary Bitcoin requirements
for that role. An arbitrary raw transaction is not proof of an available UTXO.

There is no additional token-level assertion of current unspentness. Wallets use
their ordinary Bitcoin conflict and processing policy, reject known spent or
conflicting resources, and describe pending or uncertain state accurately.
Successful processing requires normal Bitcoin acceptance; inclusion or local
possession alone is not a perpetual availability guarantee.

Wallets MUST support module-derived P2PKH resources. Arbitrary contract scripts
use BRC-207's verified signing-role and executed-script-path rules. No covenant
business semantics are added by this profile. The wallet may rely on supported
script analysis or validated execution to establish its actual signing role;
a public key appearing in a script or a supplied script-code offset alone is
insufficient. Wallets MUST NOT require asset-specific business validation when
ordinary script execution establishes the requested signing context. This
profile does not make an otherwise unresolved execution path knowable. If
missing material prevents determination of the signing context,
that signature fails until the material is supplied. Missing other unlocking
scripts may remain pending through `signAction` under BRC-207. A completed
transaction must pass all required script checks.

The wallet MUST authorize each exercise of a protected role and its actual
commitment, even when the declared quantity is unchanged. A user may grant an
application continuing authority for arbitrary updates of identified resources
or roles. Narrower permissions require facts the wallet can establish; unknown
application semantics cannot be presented as verified conditions. Claims of
ownership, entitlement, authenticity or contract success require additional
validation and do not follow from this declaration.

All BRC-207 signature modes and input/output position constraints remain
available. Partial, `noSend`, `sendWith` and two-phase flows retain their normal
meaning. The wallet's non-final processor coordination and higher-sequence
replacement responsibilities remain mandatory before non-final signature
release. Removing overlays does not remove that responsibility or make a
released signature revocable.

### Plans, custody and receipts

Each action plan MUST contain exactly one `{assetId, operation:"resource"}`
entry for each identifier using this profile, including ISSUE for a new deploy.
The ordinary token operation names MUST NOT be used for those IDs. Other assets
use their normal operation entries. This entry authorizes no operation by
itself: actual source/output changes and signing roles require user consent.
The wallet must preserve exact requested scripts and declared fields rather
than manufacture token change or repair apparent non-conservation.

Resources MUST be selected explicitly. Wallets MUST NOT automatically select,
merge, split or generate change for them as fungible funding. Ordinary satoshi
selection and change remain available. `createAction` may auto-sign a selected
resource only when it can construct and validate the unlock and has the required
resource and satoshi authorization. Arbitrary foreign scripts and mixed
transactions remain supported without automatic custody assumptions.

Managed resources use BRC-207's existing per-asset baskets and authenticated
remittance derivation. The zero/positive discriminator chooses the authority
or value basket for storage compatibility, without asserting base-token rights.
Receipts require completed, consensus-final transactions, normal Bitcoin source
and script validation, no known conflicting spend, verified wallet control and
all applicable profile checks. They require no token overlay or lineage.
Internalization does not itself broadcast a transaction.

A locally accepted unreserved resource is `spendable:false` with
`color_state_restricted`; reserved or pending status takes precedence. Both its
value and authority balance selectors return `"0"` for accessible existing
baskets because neither trusted units nor minting capabilities are available.
Inventory still exposes actual managed outpoints, scripts and declared fields
under ordinary read permissions. The wallet MUST distinguish these records from
validated fungible holdings and MUST NOT claim issuer-authorized supply or
provenance. Spent records leave held-resource inventory normally.

### Exchanges and other assets

These resources MUST NOT enter automatic amount-based netting or satisfy an
ordinary token balance/payment requirement. A user may authorize an exchange
of satoshis, normal tokens or other resources for a specified resource output.
The wallet must independently authorize those debits and describe the resource
consideration with only the facts it has validated. Incoming resource quantities
cannot reduce the stated debit of a normal asset or satisfy a quantitative
spending allowance. Actual incoming satoshis follow ordinary DSAP rules.

Conditional exchanges retain BRC-207's commitment requirements. The promised
resource must be identified by transaction/script conditions that remain binding
under the released signatures or another validated safeguard. A matching asset
ID and declared quantity alone cannot guarantee authenticity or a unique
resource. Additional required profiles may establish stronger conditions; this
profile never suppresses them.

## Discovery and failures

This profile requires BRC-207 capability revision `3` or a subsequently specified
compatible revision. Revision 3 does not itself advertise profile support:
the wallet MUST check this exact descriptor on each operation. Older or
unsupported implementations fail explicitly; applications MUST NOT retry by
stripping the profile or using ordinary token or generic signing fallbacks.

Failures use BRC-207's existing BRC-100 error channel. Missing or conflicting
evidence, unsupported requirements, resource limits, unavailable signing
context, denied consent and ordinary Bitcoin failures MUST be reported without
signature release, receipt acceptance or partial balance changes. After a
signature has already escaped, BRC-207's exposure rules still apply.
