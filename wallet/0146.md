# BRC-146: Vault Sub-Accounts (Named Account Roots)

Brandon Cryderman (brandongcryderman@gmail.com)

## Abstract

This standard defines how a single vault mnemonic (BRC-75 master root) derives multiple named **account roots**. Each account is a normal BRC-100 wallet identity with its own UTXO set, balance, and BAP identity. Recovery remains one unlock / one mnemonic. It does not introduce a parallel identity protocol.

## Motivation

Users need multiple on-chain personas (brands, websites, issuer roles) without managing ten seed phrases. Existing wallets already treat a BRC-75 root as the BRC-100 wallet root. Sub-accounts keep that primary root intact (no fund migration) and add deterministic sibling roots under the same vault.

## Specification

### Master root

The vault master private key is the BRC-75 root derived from the BIP39 mnemonic (or the existing vault root already stored for legacy wallets). Account index `0` **is** this master root. Implementations MUST NOT re-derive account 0; existing wallets remain account 0 without migration.

### Child accounts

For integer account index `n >= 1`, the account root private key is:

```
KeyDeriver(master).derivePrivateKey([2, "account"], `account-${n}`, "self")
```

- Protocol ID: security level `2`, protocol name `"account"` (BRC-42 / BRC-43 wallet protocol shape).
- Key ID: the UTF-8 string `account-${n}` (for example `account-1`).
- Counterparty: `"self"`.

The account’s identity key is the compressed public key of that private key. Each account root is thereafter a normal BRC-100 wallet root: baskets, BAP (`[1, "sigma"]` / `identity-{N}`), and BRC-247 issuer attestation (when used) all hang under that account root alone.

### Naming and metadata

Display names are local UX only. They MUST NOT affect derivation. Implementations SHOULD persist `{ index, name, identityKey }` per vault master so recovery on a new device can recreate the same account list after the user creates accounts again at the same indices (identity keys are deterministic; names may need backup as an optional future extension).

### Recovery

1. Restore the vault mnemonic → master root (account 0).
2. For each known index `n >= 1`, derive `account-${n}` as above.
3. Open each account as its own wallet database / UTXO set.

One password / device factor unlocks the vault; switching accounts does not require re-entry of the mnemonic.

### Non-goals

- This is not a second identity hierarchy and not a replacement for BAP.
- This does not move coins between accounts; each account’s balance is independent.
- This does not change BRC-246 session upgrade or other wallet-to-wallet delivery protocols.

## Implementations

- HandCash Desktop derives and switches vault sub-accounts using the protocol above; account 0 retains the historical toolbox database name, while `n >= 1` uses a distinct per-account database suffix.
