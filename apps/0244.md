# BRC-244: Pinned Builds for Connected Apps

Crumbs

## Abstract

A catalog under [BRC-241](./0241.md) can say that its curator read an app's client source. It cannot say that the code a host loads tomorrow is the code that was read, because whoever controls an app's domain can serve anything.

A **build manifest** lists every file of a client with its SHA-256 hash, under one **aggregate hash** computed as Nostr's NIP-5A computes one. A checking host loads the app only through a loader that checks every code response against a manifest, under a Content Security Policy the host enforces, and preferably serves the build from its content-addressed copies.

Two parties can name the build. A **curator-pinned** build is the one a curator reviewed, at BRC-241's review level `pinned`. An **author-pinned** build is the one the app's operator released, signed by a **release key** that the app's offline key appointed and that lives in the release pipeline, never on a web server. Author pinning catches hijacked domains, compromised hosting, injected third-party code and rollbacks, because none of them yields the release key.

Pinning binds only the client, and never blocks an app from opening.

## Motivation

BRC-241's review levels end at `source`: a curator read the client source at the app's `source` URL. The curator read what it was shown, and a server can serve different code to one user, or to everybody from tomorrow.

### What has actually happened

The attacks that have cost users of crypto web apps most came from somebody else taking control of what the browser loaded from a legitimate domain, while the operator's own servers and keys were untouched. MyEtherWallet's users were sent to an attacker's server in 2018 when the routes to its DNS provider were hijacked. Curve Finance's front end was replaced in 2022 after its registrar was compromised, and Balancer's in 2023 after its DNS provider was talked into a change. In 2024 the migration of domains to Squarespace let attackers take over the front ends of several DeFi projects, Compound and Celer among them. And in 2023 a compromised release of Ledger's Connect Kit library, loaded by many applications from a CDN, injected a drainer into front ends whose own code and domains were never touched.

An attacker who controls a domain's DNS can obtain a valid TLS certificate for it, and can relay BRC-241's possession check to the real servers, as BRC-241 section 3.7.6 says. What the attacker cannot do in any of these cases is sign a release with a key that lives only in the operator's release pipeline. Author-pinned builds make that signature the test a host applies before it runs any code served from the domain.

### What the web already has

**Subresource Integrity** binds by hash only the files a page names, and the page that carries the hashes is what an attacker replaces. **Content Security Policy** is set by the server whose code it restricts, so it guards against injected content and gives no protection from whoever controls the server. Neither lets a curator or an operator bind what a host loads to what was reviewed or released.

### What other ecosystems do

**F-Droid** publishes reproducible builds whose hash anybody can confirm came from the reviewed source, and Android refuses an update not signed by the key of the installed app, which is author pinning for native code. **Nostr's NIP-5A** names a static site version by one aggregate hash over its paths and file hashes. This document applies NIP-5A's construction to a connected app's client.

### Why a separate document

A checking loader, a host-enforced policy, content-addressed fetching and recorded release numbers are the most machinery a catalog host can need, and the least likely to be built first. BRC-241's Host Core profile needs none of it, and a host that implements BRC-241 alone shows a `pinned` review as `source`, the level it can actually vouch for.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

### 1. Terminology

- **Client**: the files a host loads to run a connected app, as distinct from the app's server and the data it serves.
- **Code response**: a response whose request destination is a document, a frame, a script, a style sheet or a worker of any kind, or whose content type is `application/wasm`.
- **Build manifest**: a JSON document listing every file of a client with its hash. Section 3.1.
- **Aggregate hash**: one hash naming a build. Section 3.2.
- **Checking loader**: a host's means of loading an app such that every code response is checked against a build manifest before it is used. Section 5.
- **Curator-pinned**: a build named by a catalog entry at BRC-241's review level `pinned`. Sections 3.3 and 4.
- **Release key**: a key named in an app's BRC-241 delegation that signs the app's releases, held by its release pipeline and never by its web servers. Section 6.1.
- **Signed release**: the app's own statement, signed by a release key, of the build it currently serves. Section 6.2.
- **Author-pinned**: an app whose delegation names release keys, loaded by a checking host only against its newest signed release. Section 6.

### 2. Scope

2.1 This document defines the build manifest, its aggregate hash, the `build` object of a [BRC-241](./0241.md) catalog entry, the signed release in `metanet.app.build`, what a host must do before it shows a review as `pinned`, and what a checking host does with an author-pinned app.

2.2 It does not bind an app's server, its API responses, or any data. It adds no [BRC-100](../wallet/0100.md) method, and changes no permission rule beyond what BRC-241 section 7.4.2 already says about an app that is not proven.

### 3. The build

#### 3.1 The build manifest

```json
{
  "metanetBuild": "1.0",
  "files": [
    ["/index.html", "..."],
    ["/app.js", "..."],
    ["/app.css", "..."],
    ["https://cdn.example/lib-4.2.1.js", "..."]
  ]
}
```

Hashes are elided because this document prints no value it cannot reproduce from bytes it also prints.

3.1.1 `files` lists every file of the client that a host loads as a code response, each as a two-element array of a path and a hash.

3.1.2 A path on the app's own origin begins with `/`, is written as it appears in a URL with no query or fragment, and is percent-decoded once. A file on another origin is listed by its absolute HTTPS URL, with no query or fragment, under the same decoding. Each path appears once.

3.1.3 A hash is the lowercase hex SHA-256 of the file's bytes as served, after any content coding such as compression has been removed.

3.1.4 A manifest MUST NOT list more than 4096 files or exceed 1 MiB.

3.1.5 Files that are not code responses, such as images, fonts and data, MAY be listed. A host is not required to check them, and their presence changes nothing in section 5.

#### 3.2 The aggregate hash

3.2.1 The aggregate hash of a manifest is computed as Nostr's NIP-5A computes one for a static site: for each entry, the line `<hash> <path>` followed by a line feed; the lines sorted in ascending byte order and concatenated; and the SHA-256 of the result, in lowercase hex.

3.2.2 Two manifests listing the same files with the same hashes have the same aggregate hash, whoever lists them and in whatever order. The aggregate names the build, not the document that describes it.

#### 3.3 The catalog's `build` object

3.3.1 A [BRC-241](./0241.md) catalog entry at review level `pinned` carries `build`:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `aggregate` | MUST | The aggregate hash of the reviewed build |
| `manifest` | MUST | A `uhrp://` reference under [BRC-26](../overlays/0026.md) to the build manifest |

3.3.2 Because the reference is content-addressed, the manifest it resolves to cannot differ from the one the curator reviewed. A host MUST check that the resolved manifest's aggregate hash equals `aggregate`, and treats a mismatch as no manifest.

3.3.2.1 **The pin is as unforkable as the catalog.** The `build` object is inside a catalog document committed to on chain under [BRC-241](./0241.md) section 6.6, so every host following the catalog sees the same pin, and no mirror can substitute an older one, since a host never accepts an earlier version under section 6.6.3 of that document. Nothing signs or expires a pin separately.

3.3.3 Every file a pinned manifest lists SHOULD also be published under UHRP. Section 5.3 depends on it, and it lets anybody audit exactly what was reviewed after the operator's server has moved on. A curator MUST NOT record a review as `pinned` unless every code file the manifest lists was available to it under UHRP when it made the review.

3.3.4 The app's own statement of its current build is the signed release of section 6.2. The two are compared under section 5.4.3.

#### 3.4 One build per entry

A catalog entry pins exactly one aggregate hash. A new build is `pinned` only once a curator reviews it and publishes a catalog version naming it; until then section 5.4 applies.

### 4. What a curator-pinned review says

4.1 `pinned` says that the curator reviewed the source, as at level `source`, and that the client a host loads is byte for byte the client the curator reviewed. It says nothing about the server.

4.2 A host MUST NOT show a review as `pinned` unless it loaded the app through a checking loader under section 5 and every code response in the session so far has matched the curator's manifest. In every other case it shows the review at level `source`, which [BRC-241](./0241.md) section 6.4.4 also requires of a host that does not implement this document.

4.3 The wording rules of BRC-241 section 7.3.3 apply: a pinned review is shown with its level and curator together, never as a mark or the word "verified".

### 5. The checking loader

One loader serves both kinds of pinning. In a session it checks against the newest signed release where the app is author-pinned under section 6, and otherwise the curator's pinned manifest.

#### 5.1 What is checked

5.1.1 For every code response in the app's session, the loader checks, before the response is used, that its URL's path, under the rules of section 5.1.2, is listed in the manifest and that the SHA-256 of its bytes equals the listed hash.

5.1.2 **Matching a path.** The loader takes the request URL, discards its query and fragment, and percent-decodes its path once. For a same-origin request it compares the decoded path with the listed paths; for a cross-origin request it compares the scheme, host and decoded path with the listed absolute URLs. A path ending in `/` matches the listed path formed by appending `index.html`. No other rewriting, redirection or case folding applies. A redirect is checked at its final URL.

5.1.3 A code response whose path is not listed is a mismatch.

#### 5.2 What may run

Code can also arrive as data and be turned into code by the page, so a checking loader enforces a Content Security Policy of its own on every document and worker of a checked session, in addition to any policy the app sets, and the stricter of the two applies.

5.2.1 The host's policy:

1. Forbids `unsafe-eval` and `unsafe-inline` for scripts, so that `eval`, `new Function`, string timers and inline script cannot run.
2. Forbids `blob:` and `data:` as sources of scripts, workers and frames, so that fetched bytes cannot be turned into code by a URL the loader never sees.
3. Permits scripts, workers, style sheets and frames only from the app's origin and from the absolute URLs the manifest lists.
4. Permits `wasm-unsafe-eval` only where the manifest lists at least one file served as `application/wasm`, and then only for listed modules.

5.2.2 An app that wants to be reviewable at `pinned`, or to be author-pinned, MUST run under this policy. A curator SHOULD test that it does before recording the level, and an operator before naming release keys, because an app that breaks under it breaks for every user of a checking host.

5.2.3 Style sheets are code responses because they can exfiltrate data and load further resources. Inline style is not restricted, because it cannot fetch code that section 5.1 does not see.

#### 5.3 Where the build comes from

5.3.1 A host MAY load listed files from the app's origin and check them as they arrive, or serve them from their UHRP copies, since the bytes are the same by construction.

5.3.2 **Serving from UHRP is RECOMMENDED.** The host fetches each listed file by its hash, serves it under a scheme or origin the host controls, and passes every other request, such as API calls, to the app's origin unchanged. This works where web views cannot intercept HTTPS responses, as on iOS; a file fetched by its hash is checked by the fetch; the client opens when the operator's server is down; and for an author-pinned app a hijacked domain never serves the client at all.

5.3.3 A host that serves the build under its own scheme or origin MUST present the app's domain as its identity everywhere [BRC-241](./0241.md) section 3.3 requires, and MUST make the app's requests to the wallet under that domain as originator, so that permissions and continuity are unaffected by where the client's files came from.

5.3.4 A host that can neither check responses from the origin nor serve from UHRP, such as an ordinary browser tab, MUST NOT show a review as `pinned`, and does not apply section 6. It shows the review at level `source`, and an author-pinned app is to it an ordinary app.

#### 5.4 A mismatch

5.4.1 **Against a curator's pin.** On any mismatch, or any code response the loader could not check, the host MUST stop describing the app as pinned for the rest of the session, MUST show the review as having been made of a different version, at level `source`, and SHOULD tell the user once, naming the curator and the date of the review.

5.4.2 A mismatch against a curator's pin usually means a release not yet reviewed. A host MUST NOT present such a mismatch in the manner of a threat, and MUST NOT block the app because of one.

5.4.3 **Two pins at once.** Where an app is author-pinned and also listed at `pinned`, the loader checks against the author's newest signed release, and compares that release's aggregate with the curator's. Where they are equal, the host MAY show both: "Reviewed by the curator (pinned, 3 Nov)" and "Released by its operator". Where they differ, the review is shown under section 5.4.1, in words such as "Running a newer release than Harbor reviewed". A mismatch against the author's release is governed by section 6.4.

5.4.4 **Rollback is a mismatch.** An older build has a different aggregate hash, so a server rolled back to a vulnerable release is caught by the same check as one rolled forward to a malicious one.

### 6. Author-pinned builds

An author's pin binds the code to a release: the operator says, with a key no domain or server holds, which build it serves, and a checking host treats nothing else as the app.

#### 6.1 Release keys

6.1.1 An app becomes author-pinned by naming, in the `releaseKeys` field of its [BRC-241](./0241.md) delegation under section 3.7.1 of that document, from one to eight release keys. A release key MUST NOT be the app key or a server key, and MUST NOT be held by any machine that serves the app.

6.1.2 A release key belongs in the operator's release pipeline, the one place that a domain hijack, a registrar breach, a hosting compromise or a CDN compromise does not reach.

6.1.3 Release keys are appointed by the offline app key, and so are rotated by a new delegation that no longer names a feared-stolen key. Under BRC-241 section 3.7.5 the newest delegation retires every older one, so a stolen release key stops working for every host that has seen the new delegation.

6.1.4 An app that names no release keys is not author-pinned, and this section does not apply to it.

#### 6.2 The signed release

6.2.1 An author-pinned app publishes `metanet.app.build`:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `aggregate` | MUST | The aggregate hash of the build the app serves |
| `manifest` | MUST | A `uhrp://` reference under [BRC-26](../overlays/0026.md) to its build manifest |
| `seq` | MUST | An integer from 1, strictly greater than in any earlier release of the app |
| `signature` | MUST | By one of the delegation's `releaseKeys`, over `{"aggregate", "domain", "manifest", "seq"}`, under [BRC-241](./0241.md) section 6.6.1, key ID `app release` |

6.2.2 The release names its domain, so a release signed for one domain is not a release for another. A host MUST check that the resolved manifest's aggregate hash equals `aggregate`.

6.2.3 Every file the manifest lists SHOULD be published under UHRP before the release is published, so that a host can serve the build without the app's server under section 5.3.2.

6.2.4 A signed release is the operator's statement of what it serves, and never raises a review level. An app that publishes `metanet.app.build` without naming release keys has made an unsigned statement, which a host MAY show and MUST NOT rely on.

#### 6.3 What a checking host does

6.3.1 A checking host that finds `releaseKeys` in the app's current delegation records, per domain, the highest `seq` it has accepted, and loads the app only against a signed release whose `seq` is at least that, whose signature verifies against a release key of the current delegation, and whose manifest resolves and matches its aggregate. A higher `seq` replaces the recorded one; the recorded one never goes down.

6.3.2 The host SHOULD fetch the app's manifest, and so its signed release, before the first code response of each session, and loads the client under section 5 against the release's manifest.

6.3.3 A host that synchronises recorded app keys under BRC-241 section 9.8 SHOULD synchronise recorded release sequence numbers with them.

#### 6.4 Code its operator did not release

6.4.1 Where the app is author-pinned and any of the following holds, the host MUST tell the user, on the surface of BRC-241 section 7.9.3, that **this app is serving code its operator did not release**:

1. The manifest carries no `metanet.app.build`, or one whose signature does not verify against a release key of the current delegation.
2. The release's `seq` is lower than the one the host recorded.
3. The release's manifest does not resolve, or does not match its aggregate.
4. Any code response in the session does not match the release's manifest under section 5.1.

6.4.2 For the rest of that session the app is not proven under BRC-241 section 7.4.2, where the wallet is itself the host that loaded it: the wallet honours none of its standing grants, and asks for each request as though none had been granted. A host that is not the wallet shows the warning of section 6.4.1 and cannot change what the wallet honours, because BRC-100 gives it no way to tell the wallet. The host MUST NOT block the app from opening, and MUST NOT revoke anything; the next session that loads a released build is proven again without the user's involvement.

6.4.3 Unlike a mismatch against a curator's pin, this one is a warning: an operator that names release keys has said every build it serves is signed. The honest cause, a deploy that went out before its release was published, is the operator's to prevent by publishing the release first.

#### 6.5 What author pinning catches, and what it does not

6.5.1 It catches:

1. **A hijacked domain or registrar.** The attacker can obtain a certificate and relay BRC-241's possession check, but cannot sign a release. A host serving from UHRP never loads the attacker's client; one loading from the origin finds the mismatch on the first code response.
2. **A compromised hosting or CDN account.** Replaced files do not match the release.
3. **Injected third-party code.** Cross-origin code runs only if listed by URL and hash, so a compromised CDN library, as in the Ledger Connect Kit case, is a mismatch once its bytes change.
4. **A rollback.** An older signed release has a lower `seq` than the one the host recorded.

6.5.2 It does not catch:

1. **A first visit after a takeover.** A host that has recorded no `seq` accepts any validly signed release. A modified build is still caught, because the release keys come from a delegation the offline app key signed, but an attacker can serve an older genuine release with a known flaw.
2. **A stolen release key**, until a new delegation retires it under section 6.1.3.
3. **A malicious release by the real operator.** That is what a curator's review, and BRC-242's labels, are for.
4. **Hosts that cannot check**, under section 5.3.4. Their users rely on every consequential call meeting the wallet's prompt under BRC-241 section 7.6, and on threat labels under BRC-242.

### 7. Not covered

7.1 Data the client fetches, such as API responses, is not code and is not checked. A pinned client can be asked by its server to request a payment, which the wallet confirms or refuses on its merits, as [BRC-241](./0241.md) section 7.6 provides.

7.2 A pinned build says nothing about who operates the app; that is BRC-241's app key and continuity, section 7.4. Author pinning adds only that whoever operates it released this code.

7.3 Native code, browser extensions and anything the host itself injects are outside the build.

### 8. Labels on builds

8.1 [BRC-242](./0242.md) section 4.3.3 allows a label whose subject is a build, named by its aggregate hash, so that a finding about malicious code follows that code to a new domain and a new key.

8.2 A host MUST apply a build label only to a build it has itself checked under section 5 and found to have that aggregate hash in the current session. A build the host did not check has no known aggregate. A signed release whose aggregate carries a threat label is shown with the label, whoever signed it.

### 9. Extension

9.1 The version discriminator `metanetBuild` is `"1.0"`. A consumer MUST reject a manifest whose major version it does not recognise and MUST ignore members it does not recognise.

9.2 A later version MAY add a hash algorithm. Version 1.0 has one, SHA-256, because a build named two ways is two builds.

### 10. Conformance

| Condition | Required behaviour |
| --- | --- |
| Curator records `pinned` | `build` with aggregate and UHRP manifest; every listed code file available under UHRP; app tested under the policy of section 5.2 |
| Host shows `pinned` | Checking loader; every code response matched by path rules of section 5.1.2; host policy enforced; otherwise `source` |
| Checked session | No `eval`, inline script, `blob:` or `data:` code; cross-origin code and WebAssembly only if listed |
| Mismatch against a curator's pin, including rollback | `source` for the session, user told once, never a threat, never a block |
| Served from UHRP | App's domain remains its identity and its originator |
| App names release keys | In the delegation, held by the release pipeline, never by a server |
| App publishes a release | `metanet.app.build` with aggregate, UHRP manifest, increasing `seq`, signed by a release key over its domain; never raises a review level |
| Checking host, author-pinned app | Loads only the newest signed release it has accepted; never goes back |
| Release missing, unsigned, older, or code not matching it | "Serving code its operator did not release", on one surface; app not proven for the session; never a block |
| Build label | Applied only to a build the host checked |

### 11. Surfaces that fail conformance

1. "Pinned build" shown in a browser tab that cannot check what it loaded.
2. A pinned app that fetches a file and runs it through `eval`, still shown as pinned.
3. "This app has been tampered with" shown because the operator shipped a release the curator has not reviewed.
4. An app served from UHRP under a host scheme, asking the wallet for permission as the host's scheme instead of its own domain.
5. An author-pinned app whose domain was hijacked, loaded from the attacker's server, with its standing spending authorisation honoured.
6. A host that accepts release 12 after having loaded release 14.

## What Is Checkable, and What Is Taken on Trust

| Fact | Who can check it | How |
| --- | --- | --- |
| The client a host loaded is the one a curator reviewed, or its operator released | A host with a checking loader | Every code response against the relevant manifest |
| The release was signed by the operator's process | Anybody | The signature against a release key in a delegation the app key signed |
| What was reviewed or released, after the server has moved on | Anybody | The UHRP copies of the listed files |

| Claim | Why it cannot be checked | What stands in for a check |
| --- | --- | --- |
| The reviewed or released source is benign | Review happens off the record; the operator signs what it chooses | The curator's name, level and date; BRC-242 labels |
| A release key is held only by the release pipeline | Key custody is not observable | Rotation by a new delegation |
| The manifest lists every code file | Only the app's author knows | An unlisted code response is a mismatch, so an incomplete manifest fails safe |

## What It Buys, and What It Costs

| Party | What they get | What it costs them |
| --- | --- | --- |
| User | Code that cannot change without their host noticing; standing grants a hijacked domain cannot use | Occasionally reading that an app runs a newer version than was reviewed |
| App author | The strongest review a catalog can give; and, without any curator, protection from domain, hosting and CDN takeovers | A manifest per release, files under UHRP, a client without `eval` or inline script, a release key in the pipeline |
| Curator | A review that means something after the day it was made | Reviewing per build, and testing under the host policy |
| Host vendor | A defence against the most common attack on web-app users | A checking loader, a policy it enforces, UHRP fetching, recorded release sequence numbers |

Curator pinning slows releases, so most apps will never be curator-pinned. Author pinning costs one release step and protects every release from publication, so for an app that holds or moves money it is the cheaper of the two.

## Security Considerations

**A pinned build binds only the client.** Its server can still send it data that leads it to request a payment, which the wallet confirms or refuses on its merits.

**Every route for code is closed or checked.** Code responses, cross-origin ones included, are checked by listed path or URL and hash, and code built from data is forbidden by the host's policy. A gap in either half would let code past the other, as an `eval` of fetched bytes would pass a path check that never sees it.

**Author pinning moves the target** from a registrar, DNS provider, hosting account or CDN to the release pipeline or the offline app key: a smaller, better-guarded target the operator already controls. Its limits, chiefly a first visit after a takeover and a stolen release key, are listed in section 6.5.2.

**UHRP copies are checked by their names**, so serving from UHRP introduces no party the host must trust.

**Two kinds of mismatch, two tones.** A mismatch against a curator's pin is the ordinary consequence of shipping and is stated as a fact; one against the operator's own release is a warning. Presenting the first as the second would teach users to dismiss the one that matters.

## Privacy Considerations

**Fetching from UHRP tells UHRP hosts which builds a user loads.** Hosts SHOULD cache fetched files, which are immutable by construction, so that a build is fetched once per device rather than once per session.

**Recorded release sequence numbers are part of the browsing profile** that BRC-241's Privacy Considerations describe, and are protected the same way.

## Implementations

No host implements this document.

On Android and desktop a web view can intercept and check responses. On iOS a host registers a URL scheme of its own and serves the build from UHRP under it, as section 5.3.2 recommends. In a browser, a service worker cannot check its own installation, so an ordinary tab shows `source` and does not apply section 6.

Building a manifest is a file walk and a hash per file over a static build output; common bundlers already avoid `eval` in production builds. Signing a release is one more pipeline step: compute the aggregate, upload the manifest and files under UHRP, sign with the release key, and publish the release before the deploy goes live.

## Failure Modes

| What went wrong | How it shows | Detected by | Attributable to |
| --- | --- | --- | --- |
| Operator served different code to one user, or rolled back | Mismatch; review shown as `source` | That user's host | The operator |
| Operator shipped an unreviewed release | Mismatch; "running a newer version" | Every checking host | Nobody. This is the system working |
| Domain, registrar, hosting or CDN compromised, author-pinned app | "Serving code its operator did not release"; no standing grants honoured | Every checking host | The attacker, and the compromised provider |
| Deploy published before its release | The same warning until the release is published | Every checking host | The operator |
| Release key stolen | Signed malicious releases until a new delegation | A labeler; the operator | The operator, for its pipeline |
| App needs `eval` | Breaks under the host policy | The curator or operator, when testing | The author |
| Host shows `pinned` without checking | Nothing visible | An auditor of the host | The host |

## Appendix A: Worked Example

Illustrative. `vault.example` is invented, and hashes, keys and signatures are elided because no real build is printed.

**Two pins.** `vault.example`, a finance app, publishes release 3.1, four files including `/sql.wasm`, with its manifest and files under UHRP. A curator reviews it, tests it under the policy of section 5.2, and lists it at `pinned`. The operator names a release key held by its build system in a new delegation, and publishes `metanet.app.build` for 3.1 with `seq` 31. A user's iOS host serves the four files from UHRP under its own scheme, permits `wasm-unsafe-eval` for the listed module, records `seq` 31, and shows "Reviewed by the curator (pinned, 3 Nov)" and "Released by its operator".

**A new release.** Release 3.2 is published as `seq` 32 and deployed. Checking hosts load it, record 32, and show "Running a newer release than the curator reviewed (source, 3 Nov)" until the curator reviews it.

**A registrar hijack.** An attacker takes over the domain's name servers, obtains a certificate, copies the manifest, release and delegation, relays the possession check to the real servers, and serves `/app.js` with a drainer added. A user's Android host loads from the origin, finds `/app.js` does not match the release, and shows "vault.example is serving code its operator did not release"; the wallet honours no standing grants for the session, so the drainer's first spend meets the ordinary prompt. The iOS host never loads the attacker's script, because it serves the client from UHRP. Serving the genuine release 3.1 instead would fail on every host that recorded `seq` 32.
