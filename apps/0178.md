# BRC-178: Federated Identity Bootstrap Proxy for Application Authorization

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft / Beta

## Abstract

This BRC defines a narrow HTTP protocol by which an application can use a
shared federated identity provider to bootstrap authorization with an
application platform without receiving provider credentials or tokens.

The application creates a one-time authorization key pair and state value,
asks an authorization proxy for a login URL, and opens that URL in the user's
browser. The proxy authenticates the user with a selected provider, resumes an
application-authorization page, and redirects to the application's registered
success URL. The application validates the returned state and authorization
credential before creating its own session.

The protocol standardizes the boundary between the application and proxy. It
does not standardize Google, Auth0, a particular application platform, or the
application's session format.

## Motivation

Applications often want to offer a familiar federated login before a user has
installed, unlocked, or understood a wallet. Requiring every application to
register and protect its own Google, Apple, or other OAuth client creates:

1. duplicated provider configuration and security review;
2. redirect-URI sprawl;
3. application access to provider tokens it does not need;
4. inconsistent transition from identity login to wallet/application
   authorization; and
5. pressure to treat a provider identity as a wallet identity.

A shared authorization platform can already authenticate users and authorize
registered applications. A small proxy endpoint lets applications enter that
flow while preserving an important separation:

- the **identity provider** authenticates a person to the proxy;
- the **authorization platform** grants an application credential;
- the **application** validates that credential and creates its own session.

The application never needs a provider access token, and a provider account is
not itself a Bitcoin identity key.

## Conformance language

The key words **MUST**, **MUST NOT**, **REQUIRED**, **SHOULD**, **SHOULD NOT**,
and **MAY** in this document are to be interpreted as described in RFC 2119 and
RFC 8174 when, and only when, they appear in all capitals.

## Specification

### 1. Roles

- **Application** — the relying application that wants an authorization
  credential.
- **Authorization proxy** — the HTTPS service that owns the federated identity
  integration and application-authorization UI.
- **Identity provider** — Google, Apple, GitHub, or another provider selected
  by the proxy.
- **Authorization platform** — the service that validates an application ID
  and issues an application credential.
- **User agent** — the browser or embedded browser carrying the login.

The authorization proxy and authorization platform MAY be one deployment.

### 2. Discovery

The proxy base URL is deployment-specific. An implementation MUST document an
HTTPS base URL and an application-login endpoint. This profile uses:

```text
GET {proxyBaseUrl}/api/auth/federated/app
```

Deployments MAY expose a provider-specific alias such as:

```text
GET {proxyBaseUrl}/api/auth/google/app
```

An application MUST NOT infer that the same path without `/app` implements
this protocol. A non-app path commonly starts the proxy's own login and can
return a redirect instead of JSON.

### 3. Application initiation

Before calling the proxy, the application backend MUST create:

1. a cryptographically random, single-use `state` value;
2. a one-time authorization key pair; and
3. a short-lived server-side or `HttpOnly` browser binding between the private
   key, `state`, and application login attempt.

For a secp256k1 authorization platform, `publicKey` MUST be a compressed SEC
public key encoded as lowercase or uppercase hexadecimal. The private key MUST
NOT be sent to the proxy, identity provider, authorization platform, or
browser JavaScript.

The binding SHOULD expire within 10 minutes and MUST expire within 30 minutes.

### 4. Login URL request

The application sends:

```http
GET /api/auth/federated/app?appId=<id>&returnTo=<encoded-path>&provider=<provider>
Accept: application/json
```

Parameters:

| Parameter | Required | Meaning |
|-----------|----------|---------|
| `appId` | yes | Identifier of the registered application |
| `returnTo` | no | Proxy-relative path to resume after provider authentication |
| `provider` | no | Requested federated provider; deployment default if omitted |
| `source` | no | Opaque analytics/source label; MUST NOT carry secrets |

The `returnTo` value MUST be a path on the proxy's own origin. It MUST NOT be
an external absolute URL or protocol-relative URL. The proxy MUST validate and
normalize it before use.

For an authorization platform accepting a public authorization key, the path
SHOULD include:

```text
/connect
  ?appId=<id>
  &autoAuthorize=true
  &publicKey=<compressed-public-key-hex>
  &state=<state>
```

`autoAuthorize=true` is a request to continue automatically after federated
authentication. It MUST NOT bypass authorization policy, consent, signing-key
requirements, multifactor authentication, or any other platform control.

### 5. Login URL response

On success, the proxy returns HTTP 200 and:

```json
{
  "authUrl": "https://proxy.example/api/auth/login?returnTo=...&connection=...",
  "appId": "example-app-id"
}
```

Requirements:

- `authUrl` MUST be an absolute HTTPS URL.
- `authUrl` MUST target the proxy or an identity-provider origin explicitly
  trusted by the proxy deployment.
- `appId` MUST equal the requested application ID.
- The response MUST use `Content-Type: application/json`.
- The response MUST NOT include provider access tokens, refresh tokens,
  authorization codes, client secrets, or the application's private key.

Errors SHOULD use JSON:

```json
{
  "error": "machine-readable-or-short-message",
  "details": "optional operator-facing detail"
}
```

Recommended status codes are:

| Status | Meaning |
|--------|---------|
| 400 | Missing or malformed request |
| 403 | Application or return path is not permitted |
| 429 | Initiation rate limit exceeded |
| 500 | Proxy identity-provider configuration unavailable |
| 502 | Upstream identity or authorization service returned an invalid response |

### 6. User-agent transition

The application opens `authUrl` as a top-level browser navigation.

Desktop applications MAY use a popup. They MUST fall back to top-level
navigation when popup creation is blocked. Mobile applications SHOULD use
top-level navigation unless their platform provides a secure system
authentication session.

The application MUST NOT load the identity provider in an iframe.

### 7. Provider return and application authorization

After provider authentication, the proxy resumes the validated `returnTo`
path. The authorization platform:

1. authenticates the proxy session;
2. resolves `appId` to a registered application;
3. applies ordinary application authorization policy;
4. binds the grant to `publicKey` when supplied; and
5. redirects only to that application's registered success URL.

The proxy MUST NOT accept an application-supplied success origin in place of
the registered success URL.

The success redirect MUST preserve `state`. If the platform returns the
application's public key, it MUST equal the key supplied during initiation.
An implementation MAY return an encrypted credential or use the one-time key
itself as the authorization credential.

### 8. Application callback

The application callback MUST:

1. require the short-lived login binding;
2. compare returned `state` to the bound value using constant-time comparison
   where practical;
3. reject missing, expired, mismatched, or already-used state;
4. validate the application authorization credential with the authorization
   platform;
5. issue a new application session only after validation;
6. delete or mark used the temporary private key and state; and
7. avoid placing the private key or long-lived application session in a URL.

Fetching the current authorized profile is a sufficient credential-validation
operation when the platform defines that endpoint as authenticated.

### 9. Privacy boundary

The application MUST NOT receive provider tokens through this protocol. The
proxy SHOULD disclose to the user:

- which identity provider is used;
- which application will be authorized; and
- what profile fields the application authorization platform will reveal.

The application MUST NOT claim that the provider account proves ownership of
a Bitcoin identity key unless a separate cryptographic binding establishes
that fact.

### 10. Security considerations

#### 10.1 Open redirects

The proxy MUST restrict `returnTo` to its own origin. The authorization
platform MUST select the final application origin from its registration
record, not from an arbitrary request parameter.

#### 10.2 Login CSRF and mix-up

`state` MUST be unpredictable, single-use, bound to the temporary
authorization key and app ID, and checked by the application. Provider state
used internally by the proxy is a separate concern; implementations MAY nest
or re-sign state but MUST preserve the application's value end to end.

#### 10.3 Key handling

The temporary private key is an application authorization credential. It MUST
be stored with the protections of a session secret, MUST NOT be exposed to
client JavaScript, and MUST be rotated for every initiation attempt.

#### 10.4 Origin consistency

The origin that creates the login binding MUST be the origin that receives the
success redirect. Differences in scheme, apex versus `www`, or cookie domain
can otherwise produce a callback without its key or state.

#### 10.5 Popup messaging

If a popup notifies its opener, the opener MUST verify `event.origin` and an
application-specific message type. Closing a popup alone MUST NOT be treated
as proof of successful authentication; the application must revalidate its
session.

#### 10.6 Logs

Logs MUST NOT contain provider tokens, application private keys, authorization
credentials, or complete session cookies. State values SHOULD be redacted or
truncated.

## HandCash deployment profile

HandCash currently deploys the provider-specific endpoint:

```text
GET https://handcash.io/api/auth/google/app
```

It returns `{ "authUrl", "appId" }`, uses Auth0 connection
`google-oauth2`, and resumes:

```text
/connect?appId=...&autoAuthorize=true&publicKey=...&state=...
```

The final redirect is the Connect application's registered
`authenticationSuccessUrl`.

This section documents one implementation profile; the normative protocol
above is vendor-neutral.
