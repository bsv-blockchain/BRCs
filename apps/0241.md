# BRC-241: Connected App Catalogs

Crumbs

## Abstract

This document specifies how a **connected app** describes itself, how a curator publishes a **catalog** of connected apps, and what a wallet or browser does with several catalogs at once.

A connected app is a web application used through a [BRC-100](../wallet/0100.md) wallet: identified by its domain, granted permissions under [BRC-116](../wallet/0116.md), and never installed.

**The app describes itself; the catalog only selects.** An app states its category, tags, the capabilities it needs beyond BRC-100 and its audience in a `metanet.app` object in its own `/manifest.json`. A catalog picks apps by domain, arranges them in sections and says how far its curator reviewed each; it cannot rename or redescribe them.

**A catalog is a chain of on-chain outputs, each spending the one before.** An output is spent once, so a catalog has one history that no curator can fork and that anybody can prove, with no counters, expiry or transparency log. Offline root keys appoint the keys that publish versions. Once added, a catalog is accepted from any source, so it survives its curator's server and domain.

An app publishes an **app key**, held offline, that appoints the keys its servers hold. **Standing grants follow proof**: a wallet honours them only while the app proves what its key promised, and after the key changes they wait for the user.

A host derives whether an app is **portable**, **enhanced** or **host-bound** and whether it will work there. It may ship its own catalog as the default and MUST let the user add others and turn any off. An app in three catalogs is shown once; two apps with one name are shown with their domains. Listing grants nothing. Labels (BRC-242), recommendations (BRC-243), pinned builds and signed releases (BRC-244) and "open with" (BRC-245) are specified separately and are not required.

## Motivation

A wallet that can pay, sign and prove is only as useful as the applications that ask it to. Every wallet vendor has built, or is building, a place to find those applications, and every one of them is a private list in a private format.

### What exists today

**The application already has a description file.** [BRC-116](../wallet/0116.md) section 3.2 has every application serve `https://{domain}/manifest.json`, whose `name`, `short_name` and `icons` wallets already show. It does not say what kind of application this is, what it needs beyond BRC-100, or who it is for.

**Every catalog is private.** This document calls three prototypes it studied by codenames: Harbor, a wallet, and Meadow and Lattice, two community networks. Harbor compiles six repositories into its wallet, Meadow and Lattice each hard-code one, and BSV Radar keeps a directory with its own categories and submitter-asserted compatibility badges. The apps overlay holds publisher-signed listings with free-text categories and no check that a publisher controls the domain it names. None of these reads any other, so an app listed in one is invisible to the users of every other wallet and network.

### Why the app must describe itself

The obvious design is a catalog that carries complete records for every app it lists. It fails twice. **The description drifts**, because a catalog holds a snapshot of somebody else's facts. **The curator can say anything**, because a record mixing an application's name with a curator's category and a curator's compatibility claim is the blend [BRC-184](../wallet/0184.md) section 3.2 forbids: "Never blend fields from different publishers into a falsely unified endorsement."

So the division is by authorship. What an application is, what it needs and who it is for are statements only its author can make, and they live at the author's domain. Which applications are worth showing, how far each was checked, and under what heading are statements only a curator can make, and they live in the curator's catalog.

### Why many catalogs, and why they need rules

A wallet's own catalog is its distribution. A food-systems network wants its members to see its tools first, a games studio wants a catalog of games, and a user in two networks wants both. The useful arrangement is many catalogs in every wallet, with the wallet's own as one default among them. F-Droid reached the same arrangement for Android: an official repository shipped by default, and third-party repositories, such as IzzyOnDroid, added by the user.

Many catalogs raise questions no single catalog has to answer: the same app listed twice, two apps with one name, an app that will not run in this wallet, a curator listing a lookalike, a catalog going offline, and a wallet deciding that its own listings may connect without asking. Each has an answer that protects users and an answer that is easier to build.

### Why a catalog belongs on chain

A signed list fetched from a server can be **frozen**, by a mirror that keeps serving an old version; **forked**, by a curator showing different users different versions; and **stopped**, by a lapsed domain or a hosting provider. The Update Framework answers the first with expiry, which kills a catalog whose curator goes quiet, and Certificate Transparency the second with a separate log and auditors. An output that each new version spends answers all three. It is spent once, so there is only ever one next version; anybody can prove it was spent, so a host learns of a newer version from whoever tells it first; and it lives on chain, away from the curator's server. What remains to trust is that somebody tells a host when a newer version exists, which section 6.6.5 handles by asking more than one party.

### What a listing can vouch for, and what it cannot

F-Droid lists files: an APK is immutable and hashed, and IzzyOnDroid refuses any later build signed by another key. A catalog of connected apps lists **domains**, which are neither.

**A domain changes hands.** Domains lapse and are re-registered, projects are sold, accounts are taken over and maintainers' email domains expire, and each compromise of this kind arrived as an ordinary update. Attackers re-registered expired publisher domains after the Snap Store's 2024 wave of fake wallets; a study of npm found 2,818 maintainers on expired email domains; and browser extensions sold from The Great Suspender onward pushed malicious updates to users who had trusted the old owners. A new owner can also copy every file the old one served, so a published statement proves nothing about who serves it now.

**A web app's code changes after review**, and can differ from one user to the next; Subresource Integrity binds only the scripts a page names.

So this document requires a catalog to say how far it checked, makes a change of owner visible by asking the app's server to prove a key the old owner appointed, and leaves binding the exact code to BRC-244. What remains, a malicious app run honestly by its real owner and never reviewed, is bounded by one rule that needs no review: **listing grants nothing**, so every consequential call still meets the wallet's own prompt.

### Why the capabilities have to be declared

Most applications need nothing beyond BRC-100, and [BRC-185](../wallet/0185.md) section 1 makes the complete core contract mandatory, so a portable application works in every conforming wallet. Some need more: a permission module reserved under [BRC-98](../wallet/0098.md), a capability advertised under [BRC-212](../wallet/0212.md), or an interface one vendor injects into the page, as Harbor injects `window.harbor`. Those applications are legitimate, and in every wallet but one they are broken. Telegram Mini Apps and WeChat Mini Programs show the end state of leaving this unstated: applications that exist only inside one host, with nothing to tell a user so. The fix keeps host-bound applications and makes the binding visible before the user taps.

### Why "connected app"

"Mini app" says an application is small, which is often false, and "web app" does not separate one that works with a wallet from any other website. **"Connected app"** names what distinguishes these applications: they connect to the user's wallet instead of being installed, which is what Harbor already calls them.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119. They are used where interoperability breaks or a user is misled; the rest of this document describes a mechanism.

**Versioning.** Each object this document defines carries a version discriminator. A consumer MUST reject an object whose major version it does not recognise, and MUST ignore fields and minor versions it does not recognise.

**Reserved words.** "Listed" means present in a catalog and implies nothing else. "Reviewed" means listed at a review level above `none`, and always appears with the level and the curator. A surface MUST NOT describe an application as verified, approved, endorsed, safe or official on the strength of a listing or a review.

**Signatures and time.** Every signature this document defines, other than a transaction's own, follows section 6.6.1. Clocks are compared only for a delegation's validity (section 3.7.5), the age of a proof of possession (section 7.4.2) and the time since a successful refresh (section 6.6.5), each tolerating a wrong clock; a catalog version is dated by its block.

### 1. Terminology

- **Connected app**: a web application, identified by its domain, that a user uses through a BRC-100 wallet. Section 3.
- **Native app**: an application installed from a platform store. Not governed here.
- **Host**: the wallet, or the browser bound to a wallet, that shows catalogs and opens connected apps.
- **App description**: the `metanet.app` object at an app's domain. Section 4.
- **App key**: the public key in an app domain's `metanet.trust` object, held offline by the app's operator. Section 3.5.
- **Server keys**: keys held by the app's servers, appointed by the app key for a short period. Section 3.7.
- **Delegation**: the app key's signed, expiring appointment of server keys for a domain. Section 3.7.
- **Possession**: a server's proof, at the time of asking, that it holds a server key. Section 3.7.3.
- **Requirement**: something an app needs from the host beyond the core BRC-100 interface. Section 4.3.
- **Audience**: who an app is built for, stated as certificates its users hold. Section 4.4.
- **Portability**: `portable`, `enhanced` or `host-bound`, derived. Section 5.1.
- **Verdict**: `works`, `reduced`, `unsupported` or `unknown`, computed by a host. Section 5.2.
- **Curator**: the domain that publishes a catalog.
- **Catalog**: a curator's selection of connected apps, published as a chain of outputs, each committing to a document. Section 6.
- **Start**: the outpoint of a catalog's first root output, which identifies the catalog on chain. Section 6.6.2.
- **Root keys**: a catalog's offline keys, which lock its root output. Section 6.6.4.
- **Signer keys**: the keys, named in the current root output, that lock its version outputs. Section 6.6.4.
- **Document hash**: the SHA-256 of the bytes of a catalog document file. Section 6.6.2.
- **Review level**: how far a curator checked an app before listing it. Section 6.4.
- **Home catalog**: a catalog a host enables by default. Section 7.1.
- **Pin**: a host's record that a user wants an app on their own surface. A pin is not a grant.
- **Proven**: the state of an app that currently shows what its app key promised. Section 7.4.
- **Changed owner**: the state of an app whose app key no longer matches the one recorded. Section 7.4.
- **Domain-confirmed**: a listing found outside catalogs whose domain's manifest confirms its publisher key. Section 7.10.

### 2. Scope

2.1 This document defines one object an application publishes, one document and two kinds of on-chain output a curator publishes, and the behaviour of a host that consumes them.

2.2 It adds no [BRC-100](../wallet/0100.md) method and changes no permission rule, except that section 7.4.2 has a wallet honour standing grants only while an app proves what its key promised, and section 7.4.4 has it reconfirm them with the user after a change of owner.

2.3 It does not govern native apps, how a host frames an application or injects a provider into it, or anything commercial. Safety labels are in BRC-242, recommendations in BRC-243, pinned builds in BRC-244 and "open with" in BRC-245. Section 9 lists the rest.

### 3. Identity of a connected app

3.1 A connected app is identified by its **domain**: the fully qualified domain name a BRC-100 wallet receives as the originator of its requests, normalised as [BRC-116](../wallet/0116.md) section 6.2 requires. Its manifest is retrieved from that origin and no other: a host MUST NOT accept a manifest reached through a redirect to another origin, and a catalog entry names the domain that serves the manifest, not one that redirects to it. `www.readings.example` and `readings.example` are two apps to a wallet, and a curator lists whichever one the application runs on.

3.2 One domain is one connected app. A grant under BRC-116 is made to a domain, so two applications on one domain share every permission either is given, and a catalog listing them separately would show a user two things that are, to their wallet, one.

3.3 A host MUST show an app's domain as text wherever it shows the app's name in a catalog, a search result or a pin or open prompt, and MUST NOT shorten it to a registrable suffix. A label of an internationalised domain is shown in Unicode only where it is in a single script and is not confusable with another domain under Unicode Technical Standard #39, and is otherwise shown in its ASCII form, as Chromium's IDN display policy does. A name is chosen by the party being named; the domain is the only part of a listing an attacker cannot make identical to somebody else's, and it must not be displayed in a way that undoes that.

3.4 An app MUST NOT be identified by its name in any object this document defines.

#### 3.5 The app key

3.5.1 An app SHOULD publish a `metanet.trust` object under [BRC-68](../peer-to-peer/0068.md) at its domain. Its `publicKey` is the **app key**. The domain says where the application is; the app key says who runs it, and survives what happens to the domain.

3.5.2 An app key MUST NOT be the key of a user. It SHOULD be held by the application's operator off every web server, because it signs only rotations (section 3.6), delegations (section 3.7) and moves (section 3.8), and an operator makes those a few times a month at most.

3.5.3 An app with no app key MAY be listed. Its continuity cannot be checked, which section 6.4.1 makes visible by keeping it at review level `none`.

3.5.4 One operator MAY use one app key for several domains. Each domain publishes its own delegation, naming server keys of its own, and sections 6.5.4 and 7.5.2 treat domains whose delegations are by one app key as one operator's.

3.5.5 **Who runs it.** A host MAY show who operates an app by asking its wallet to `discoverByIdentityKey` with the app key, and showing any certificates found, each attributed to the certifier that issued it: "Operated by Readings Ltd, according to certify.example". A certificate states what its certifier checked, and a host presents it as that and nothing more. An operator that has disclosed no certificate is shown as having disclosed none, which is not evidence against it. Metanet Apps resolves publishers the same way, and keeps names out of listings for the same reason: a name copied into a listing is the listing's claim, and a certificate is somebody else's.

#### 3.6 Rotation

3.6.1 An app that replaces its app key publishes `metanet.app.keyRotations`, an array of up to eight entries, oldest first, each:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `from` | MUST | The key being replaced, compressed, in hex |
| `to` | MUST | The key replacing it |
| `seq` | MUST | An integer from 1, strictly greater than the previous entry's |
| `signature` | MUST | By `from`, over `{"from", "seq", "to"}`, key ID `app key rotation` |

3.6.2 A key K' is **reached** from a key K when the array holds a chain of entries in which the first `from` is K, each later `from` is the previous `to`, the `seq` values increase, and the last `to` is K'. A host that recorded K with sequence number s accepts a current app key K' as a continuation only if K' is reached from K by a chain whose first `seq` is greater than s. It then records K' and the last `seq`. A key that was retired at a sequence number the host has already passed cannot start a new chain, so a key that leaks after retirement cannot sign one.

3.6.3 A new key without such a chain is a change of owner under section 7.4. The party who lost the old key and the party who bought the domain cannot be told apart by any other means.

3.6.4 A rotation is a statement about a key, so it names no domain: the same entries serve every domain the key speaks for, and survive a move under section 3.8. An app SHOULD keep entries for at least two years, so that a host that has been offline that long can still follow them.

#### 3.7 Delegation and possession

A key held offline cannot answer a challenge, and a statement published at a domain can be copied by whoever serves that domain next. The app key therefore appoints, for a limited time, the keys the servers hold, and says whether the servers will prove it. TLS delegated credentials, RFC 9345, take the same shape for the same reason: a credential copied from a server is worth only the time it has left.

3.7.1 An app with an app key publishes `metanet.app.delegation`:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `keys` | MUST | 1 to 8 server keys, compressed, in hex. None may be the app key, and none may appear in a delegation for another domain. Several servers behind one domain each hold one, or share one |
| `possession` | MUST | `true` if the app's servers answer the handshake of section 3.7.3, otherwise `false` |
| `releaseKeys` | MAY | 0 to 8 keys, compressed, in hex, held by the app's release pipeline and never by its web servers. None may be the app key or a server key. They sign the app's releases under BRC-244 |
| `issued` | MUST | RFC 3339 UTC timestamp |
| `expires` | MUST | After `issued`, and no more than 90 days after it where `possession` is `true`, or 30 days where it is `false` |
| `signature` | MUST | By the app key, over `{"domain", "expires", "issued", "keys", "possession", "releaseKeys"}`, key ID `app key delegation`, with `releaseKeys` as an empty array where the field is absent |

3.7.2 **The key vouches for the domain, as the domain vouches for the key.** A domain can name any key in its `metanet.trust`, including somebody else's, and so borrow continuity and reviews that belong to another operator. A current, valid delegation is the app key's statement that it speaks for this domain, which is [BRC-169](../peer-to-peer/0169.md) section 5.5's two-way rule applied to an app and its key, and the form Zapstore uses to bind a signing certificate to a key. A curator MUST NOT record an app key in an entry above `none` unless it observed a current delegation by that key for the app's domain.

3.7.3 **Possession.** An app whose delegation says `possession: true` answers a [BRC-104](../peer-to-peer/0104.md) handshake at `/.well-known/auth` with one of the delegation's `keys` as its [BRC-103](../peer-to-peer/0103.md) identity key, and SHOULD allow that endpoint to be called from other origins, since a host running in a web page must reach it across origins. A party checking possession sends an `initialRequest` from a key of its own choosing, and has **proof of possession** only if the `initialResponse` carries one of `keys` as its identity key and a valid signature over the nonces of that exchange. Any other outcome, including a refusal, an error, a timeout or a dropped connection, is not proof.

3.7.4 **Why the flag is in the delegation.** Whether a server is expected to prove possession is stated by the app key itself, which leaves the host nothing to infer. A party that copies the manifest copies `possession: true` with it and cannot answer the handshake. An operator that moves to hosting that cannot answer the handshake signs a new delegation saying `false`, and no host mistakes the move for a change of owner.

A copied delegation without possession is good for at most 30 days, which is shorter than the time a lapsed generic domain normally takes to become available to anybody else.

3.7.5 **Validity.** A delegation is **current** when it verifies, its `issued` is no earlier than the newest `issued` the checking party has accepted for that domain, its `issued` is no more than 24 hours after the checker's clock, and the checker's clock is no more than 24 hours past its `expires`. A newer delegation therefore retires every older one at once, so a server key that was stolen and then replaced cannot be put back with the delegation that named it. A wrong clock can at most make an app look unproven.

3.7.6 **What possession does and does not stop.** It stops a party that holds the domain and a copy of what the old operator served: a lapsed domain re-registered, a project sold with its servers switched off, a hosting account taken over. It does not stop a party that takes over the domain's name resolution while the real servers keep running and relays the handshake to them, because [BRC-103](../peer-to-peer/0103.md) signs nonces and not the origin; keeping server keys to one domain stops such a relay borrowing another domain's servers. What that attacker controls is the code users run, and BRC-244's signed releases catch it in any host that checks what it loads. In an ordinary browser tab the hijack remains open, bounded by the wallet's prompts and by BRC-242's labels.


#### 3.8 Moving to a new domain

3.8.1 An app that moves publishes, at its old domain, `metanet.app.movedTo`: the new domain as `to`, and a signature by the app key over `{"from", "to"}`, key ID `app moved`, with the two domains as values. The new domain publishes the same app key, or one reached from it under section 3.6, with a current delegation of its own server keys.

3.8.2 A host that holds a pin of, or a recorded key for, the old domain, and finds a valid move, MAY offer once to pin the new domain in its place, and carries the recorded key and rotation sequence to the new domain, so that continuity does not reset. It MUST NOT carry over any grant: a grant under [BRC-116](../wallet/0116.md) is to a domain, and the user grants the new domain afresh. Catalog listings are by domain and do not move; a curator lists the new domain.

3.8.3 A move to a domain that does not publish the old app key, or a reached one, with a current delegation is not a move, and a host ignores it.

### 4. The app description

An application describes itself in a `metanet.app` object in the `/manifest.json` that [BRC-116](../wallet/0116.md) section 3.2 already places at its domain's root, alongside `metanet.groupPermissions` and `metanet.trust`.

```json
{
  "name": "Readings",
  "short_name": "Readings",
  "description": "Record and share refractometer readings from your own fields.",
  "start_url": "/",
  "icons": [{ "src": "/icon-512.png", "sizes": "512x512", "type": "image/png" }],
  "metanet": {
    "schemaVersion": 1,
    "app": {
      "version": "1.0",
      "category": "productivity",
      "tags": ["farming", "soil", "measurement"],
      "audience": {
        "certificates": [
          { "type": "Jsnn82gKqqpWg++XYXCykap1FbiJ/ZMloZQizdER1pw=", "certifiers": ["lattice.example"] }
        ],
        "description": "Members of the Lattice network"
      },
      "source": "https://git.example/readings",
      "support": "https://readings.example/help"
    }
  }
}
```

The certificate type above is the base64 SHA-256 of the ASCII string `lattice membership v1`, derived in the manner of [BRC-169](../peer-to-peer/0169.md) section 4.5. It illustrates the construction; no network has deployed it. The `metanet.trust` object and the delegation are omitted because this document prints no key or signature it cannot reproduce.

| Field | Requirement | Meaning |
| --- | --- | --- |
| `version` | MUST | `"1.0"` |
| `category` | MUST | One value from section 4.1 |
| `tags` | MAY | Up to eight, section 4.2 |
| `requires` | MAY | Up to sixteen requirements, section 4.3. Absent means none |
| `audience` | MAY | Section 4.4. Absent means anyone |
| `source` | MAY | HTTPS URL of the application's client source code |
| `support` | MAY | HTTPS URL at which the author answers users |
| `keyRotations` | MAY | Section 3.6 |
| `delegation` | SHOULD, where `metanet.trust` is present | Section 3.7 |
| `movedTo` | MAY | Section 3.8 |
| `build` | MAY | Defined by BRC-244 |
| `handles` | MAY | Defined by BRC-245 |

The display fields are the W3C manifest's own and are not repeated. A host takes the name from `name`, falling back to `short_name`; the summary from `description`; artwork from `icons`; pictures of the application from `screenshots`; and the page it opens from `start_url`, which MUST resolve to the application's own origin and is otherwise replaced by the root. A host that does not implement a companion document ignores the field that document defines.

#### 4.1 Category

An application states exactly one category, from a closed set.

| Value | Covers |
| --- | --- |
| `communication` | Messages, mail, calls and contact books |
| `productivity` | Documents, signing, calendars, notes, records and measurement |
| `finance` | Payments, invoicing, exchange, on and off ramps, accounting |
| `marketplaces` | Buying and selling goods and services between people |
| `collectibles` | Tokens, inscriptions, digital collectibles, and the tools for them |
| `media` | Publishing, music, video, podcasts and reading |
| `social` | Feeds, groups, forums and communities |
| `learning` | Courses, reference and research |
| `games` | Games |
| `identity` | Certificates, attestations, handles, credentials and reputation |
| `developer` | Block explorers, transaction tools and developer utilities |
| `other` | An application none of the above describes |

4.1.1 The set is closed. A host MUST treat an unrecognised value as `other`.

4.1.2 **One category, not several.** An application allowed several will claim every one in which it might be seen, and a category every application claims sorts nothing. What else an application is goes in its tags.

4.1.3 **The set is closed because it is compared.** A category exists so that a host can put applications from twelve curators on one shelf, which works only if every author means the same thing by the same word. The W3C manifest's `categories` member is free-form and was written for consumer platform stores, with `weather` and `kids` and no word for an identity tool or a block explorer. A host MAY read it and MUST NOT substitute it for `category`. New values arrive by revision of this document.

4.1.4 A network keeps its own taxonomy. A curator who wants "Circles", "Field labs" or "Studio" has them as sections of its catalog under section 6.3, where they govern that catalog and nothing else.

#### 4.2 Tags

4.2.1 A tag is 1 to 24 characters of lowercase ASCII letters, digits and hyphens. An application MAY state up to eight.

4.2.2 Tags are the author's words, offered for search. They are never normative and MUST NOT be presented as categories.

#### 4.3 Requirements

A requirement is something the application needs from the host that the core [BRC-100](../wallet/0100.md) interface does not supply. A core method is never a requirement, because [BRC-185](../wallet/0185.md) section 1 makes the complete core contract mandatory.

```json
"requires": [
  { "kind": "feature", "value": "brc177-nosend=2", "fallback": "reduced", "why": "Batches several payments into one" },
  { "kind": "module", "area": "basket", "scheme": "app", "fallback": "none", "why": "Keeps readings in their own basket" },
  { "kind": "host-api", "ecosystem": "harbor.example", "name": "harbor", "fallback": "none", "why": "Opens your Harbor vault", "docs": "https://harbor.example/docs/host-api" }
]
```

| Kind | Fields | Met when |
| --- | --- | --- |
| `feature` | `value`: a [BRC-205](../wallet/0205.md) attribute as it appears in a `getVersion` result, `key=value`; or `brc212:` and a decimal flag index from [BRC-212](../wallet/0212.md) section 4 | The bound wallet's `getVersion` result carries that attribute or sets that flag |
| `module` | `area`: `protocol`, `basket` or `label`; `scheme`: a scheme identifier under [BRC-98](../wallet/0098.md), [BRC-99](../wallet/0099.md) or [BRC-111](../wallet/0111.md) respectively | The bound wallet implements that scheme for that area |
| `host-api` | `ecosystem`: the domain that defines the interface; `name`: its name as that domain documents it; `docs`: SHOULD, an HTTPS URL of that documentation | The host implements the interface the named ecosystem defines under that name |

Every requirement also carries `fallback` (MUST): `reduced` if the application still runs without it, or `none` if it does not. It SHOULD carry `why`, up to 80 characters, telling a user what the requirement is for.

4.3.1 A host MUST treat an omitted `fallback` as `none`. The difference between losing a feature and not opening is the whole of what a user needs to know before choosing.

4.3.2 **A `host-api` requirement is labelled by its ecosystem**, and a host MUST show that domain when it explains a verdict that depends on one. This is [BRC-218](./0218.md) section 8 rule 3 applied to a page interface: an interface one vendor defines is that vendor's.

4.3.3 `why` is unattested. A host renders it as text, attributed to the application, and never lets it alter a verdict.

4.3.4 Kinds are closed and extended under section 8. Two requirements with the same kind and the same identifying fields are one requirement, and a host uses the first.

#### 4.4 Audience

4.4.1 `audience.certificates` lists [BRC-52](../peer-to-peer/0052.md) certificate types, each with the certifiers whose certificates of that type the application accepts. A user is in the audience if they hold any one. `audience.description`, up to 60 characters, says who that is in words.

4.4.2 A certifier is named by domain and resolves to the `publicKey` of that domain's `metanet.trust` object under [BRC-68](../peer-to-peer/0068.md).

4.4.3 **Audience is not a requirement.** Any conforming wallet can hold any certificate, so an application built for members of one network is still portable. A host MUST NOT derive portability from audience; a description that conflated the two would make every membership network look like a walled garden.

4.4.4 **Audience is a hint, not a gate.** An application that admits only members enforces that itself, with [BRC-103](../peer-to-peer/0103.md) and the certificates the user chooses to prove.

#### 4.5 What the description is not

4.5.1 An app description is the author's statement about the author's own application. It is not a review, a rating or a safety claim, and a host MUST NOT present it as one.

4.5.2 It MUST NOT carry prices, plans or payment terms. Section 9.1 gives the reason.

#### 4.6 Relation to `groupPermissions`

`metanet.groupPermissions` under [BRC-73](../wallet/0073.md) declares what an application will ask the user for; `metanet.app.requires` declares what it needs the host to be. They MUST NOT be merged. A wallet that supports every module in existence still asks before granting any of them, and a user who would grant everything cannot make a wallet support a module it lacks.

#### 4.7 Absence

4.7.1 An application with no `metanet.app`, or one that cannot be parsed, MAY still be listed and opened.

4.7.2 A host MUST treat its category as `other` and its verdict as `unknown`, and MUST present that neutrally. An application that has not described itself has not described itself as dangerous, which is [BRC-184](../wallet/0184.md) section 3.2's rule that "unregistered" is not evidence of danger.

4.7.3 An application that carries `metanet.app` without `requires` has stated that it needs nothing beyond BRC-100, which an application with no `metanet.app` at all has not.

4.7.4 An application with no `metanet.groupPermissions` has not said what it will ask for, and may ask for anything at runtime. Sections 6.4.3 and 7.9.2 treat it accordingly.

### 5. Portability and the verdict

Two values are derived from the app description, and neither is ever accepted from anyone. Portability is a property of the application; the verdict is a property of the application in one host, at one moment.

#### 5.1 Portability

| Portability | Derived when |
| --- | --- |
| `portable` | `requires` is absent or empty |
| `enhanced` | Every requirement has `fallback: "reduced"` |
| `host-bound` | At least one requirement has `fallback: "none"` |

5.1.1 No host, catalog or application may state a portability other than the derived one. "Works with every wallet" is a claim; `portable` is a computation.

5.1.2 This document allows host-bound applications, and forbids presenting one without the word.

#### 5.2 The verdict

A host evaluates each requirement against itself and its bound wallet as **met**, **unmet** or **undetermined**:

1. A `feature` requirement is met if the bound wallet's `getVersion` result carries the attribute or sets the flag, and otherwise **undetermined**, never unmet. [BRC-212](../wallet/0212.md) section 3: a clear flag "MUST NOT be treated as proof of non-support."
2. A `module` requirement is met or unmet where the host is the wallet or the wallet has told it, and otherwise undetermined. [BRC-185](../wallet/0185.md) section 1: "A missing advertisement is not proof of non-support."
3. A `host-api` requirement is met or unmet. A host knows what it implements.
4. A requirement of an unrecognised kind is undetermined.

The verdict is the first that applies:

| Verdict | When | A presentation says |
| --- | --- | --- |
| `unsupported` | A `fallback: "none"` requirement is unmet | It will not work here, what is missing, and for a `host-api` which ecosystem defines it |
| `unknown` | A `fallback: "none"` requirement is undetermined, or there is no description | The host could not tell whether it will work |
| `reduced` | A `fallback: "reduced"` requirement is unmet or undetermined | It works here; something it can use is missing or could not be confirmed |
| `works` | Every requirement is met, or there are none | Nothing. This is the ordinary case |

5.2.1 **`unknown` MUST NOT be presented as `unsupported`.** One is a reason to look elsewhere and the other a reason to try, which is [BRC-190](./0190.md) section 3.1's distinction between "you do not qualify" and "I could not check".

5.2.2 A host MAY hide `unsupported` apps from default views. If it does, it MUST say so, MUST provide a way to show them, and MUST show the reason on each. It MUST NOT hide `unknown` apps.

5.2.3 A host MUST NOT prevent a user from opening an app because of its verdict. BRC-100 then answers each call as it would have anyway, with [BRC-326](../wallet/0326.md)'s `unavailable` where a capability is missing.

5.2.4 The verdict is recomputed when the bound wallet changes.

### 6. The catalog

#### 6.1 Where catalogs are declared

A curator declares its catalogs in a `metanet.catalogs` array in the `/manifest.json` at its domain.

```json
{
  "metanet": {
    "catalogs": [
      {
        "id": "catalog:harbor.example/signature",
        "start": "<txid>.<vout>",
        "url": "https://apps.harbor.example/catalog.json",
        "steps": "https://apps.harbor.example/catalog.beef"
      }
    ]
  }
}
```

The outpoint is shown as its form, not a value, because this document prints no transaction it cannot reproduce.

| Field | Requirement | Meaning |
| --- | --- | --- |
| `id` | MUST | The catalog identifier, section 6.2 |
| `start` | MUST | The catalog's start, section 6.6.2: a transaction ID in lowercase hex, a full stop, and an output index in decimal |
| `url` | SHOULD | HTTPS URL at which the current document is served. MAY be on a host the curator does not control |
| `steps` | SHOULD | HTTPS URL at which the curator serves the chain's steps as BEEF, section 6.6.5 |
| `mirrors` | MAY | Up to eight further HTTPS URLs for the document |

6.1.1 **Both directions, once.** When a user adds a catalog, it is accepted only if its `id` names the domain whose manifest declares it, that manifest declares the same `id` with the same `start`, and the root output at `start` names the same `id`. This is [BRC-169](../peer-to-peer/0169.md) section 5.5's bidirectional rule applied to a new pair. After the catalog is added, section 6.7.3 governs, and the domain is not consulted to accept a version.

6.1.2 A domain without `metanet.catalogs` publishes no catalog, and a host MUST NOT probe other paths for one. A host MUST ignore manifest keys it does not recognise, as [BRC-180](../overlays/0180.md) requires. A manifest that declares one `id` twice declares neither, and a host refuses both.

#### 6.2 The catalog document

```json
{
  "metanetCatalog": "1.0",
  "id": "catalog:harbor.example/signature",
  "name": "Harbor Signature Apps",
  "description": "The apps Harbor builds and maintains",
  "policy": "https://harbor.example/catalog-policy",
  "mirrors": ["https://mirror.example/harbor-signature.json"],
  "sections": [
    {
      "id": "studio",
      "title": "Studio",
      "description": "Read, write, keep",
      "apps": [
        { "app": "mail.harbor.example", "key": "...", "review": { "level": "used", "date": "2026-10-20" } },
        { "app": "calendar.example", "review": { "level": "none" } }
      ]
    }
  ],
  "withdrawn": [
    { "app": "board.example", "at": "2026-10-12", "reason": "defunct", "ref": "https://harbor.example/catalog-log#2026-10-12" }
  ]
}
```

The app key is elided for the reason above. The document carries no signature, counter, date or expiry: the chain of section 6.6 supplies the first three, the date of a version being the time of the block that holds it, and makes expiry unnecessary.

| Field | Requirement | Meaning |
| --- | --- | --- |
| `metanetCatalog` | MUST | `"1.0"` |
| `id` | MUST | `catalog:<domain>/<local>`, the local part 1 to 32 lowercase ASCII letters, digits and hyphens |
| `name` | MUST | 1 to 48 characters |
| `description` | SHOULD | 1 to 140 characters |
| `policy` | MUST | HTTPS URL of the curator's published policy, section 6.9 |
| `mirrors` | MAY | Up to eight HTTPS URLs from which the document may also be fetched |
| `sections` | MUST | 1 to 64 sections, section 6.3 |
| `withdrawn` | MAY | Section 6.5 |

6.2.1 The identifier carries its domain because two curators will both have a catalog called `signature`. [BRC-190](./0190.md) section 2.2 reached the same form for rooms. The identifier is what a person reads; the start is what a host trusts.

6.2.2 Mirrors change where a document is fetched, never what is accepted: a document from a mirror is accepted only if its hash is the one the chain commits to. F-Droid lists its mirrors inside its signed index for the same reason, so that the list cannot be altered by whoever serves it.

6.2.3 A document MUST NOT exceed 1 MiB or list more than 1024 entries across all sections, and a host MUST reject one that does without reading past the bound.

#### 6.3 Sections and entries

6.3.1 A section has an `id` (1 to 32 lowercase ASCII letters, digits and hyphens, unique in the catalog), a `title` (1 to 32 characters), an optional `description` (up to 140), and `apps`, 1 to 256 entries in the order the curator intends.

6.3.2 **A section is the curator's taxonomy**: Meadow's "Hives", Lattice's "Circles", Harbor's presets. A host MUST NOT merge sections from different catalogs because their titles match.

6.3.3 An entry has:

| Field | Requirement | Meaning |
| --- | --- | --- |
| `app` | MUST | The app's domain, the one that serves its manifest, section 3.1 |
| `key` | SHOULD | The app key the curator observed, with a current delegation, when it reviewed the app, sections 3.5 and 3.7.2. Required at review levels above `none` |
| `review` | MUST | Section 6.4 |
| `build` | MAY | Defined by BRC-244. Required at review level `pinned` |
| `note` | MAY | Up to 140 characters, the curator's own words about the app |
| `snapshot` | MAY | Section 6.3.5 |

6.3.4 **An entry selects; it does not describe.** Nothing in an entry states the app's name, category, requirements or audience except a snapshot, which is a copy. A `note` is the curator's and MUST be presented as the curator's.

6.3.5 A snapshot lets a host draw a catalog without contacting every listed domain. It copies `name`, `short_name`, `description`, one icon reference and `metanet.app` from the app's manifest, with the time taken in `fetched`. The icon reference follows [BRC-185](../wallet/0185.md) section 3.1: HTTPS, `uhrp://` or `chirp://`, at most 256 bytes, no data URIs, resolved as an untrusted image.

6.3.6 **The app's own manifest governs a snapshot.**

1. A snapshot is the curator's report of what the app said, not what it says. Before a host pins an app or opens it for the first time, it MUST fetch the app's own manifest, and where the two differ the manifest governs. A verdict computed from a snapshot is provisional until then.
2. Where the host holds a manifest it fetched itself, it shows that manifest's name and artwork. Otherwise, where several catalogs carry snapshots of one app with different names, it shows the one with the latest `fetched`, and never shows the app twice because its snapshots disagree.
3. Wherever a host shows a snapshot's name it shows the app's domain beside it, and the check of section 7.5 runs on every snapshot name as well as the manifest's, so that a curator cannot dress a listing as somebody else's app in a browse view the live fetch never reaches.

6.3.7 **One answer per app.** A domain MAY appear in several sections of one catalog, and every appearance MUST carry the same `key`, `review` and `build`. A domain MUST NOT be both listed and withdrawn in one document. A host MUST treat a document that breaks either rule as invalid under section 6.6.6.

#### 6.4 Review levels

6.4.1 Every entry states how far the curator checked the app, as one of five cumulative levels, with the `date` the check was made and an optional `ref` to the curator's public record of it.

| Level | The curator | Requires |
| --- | --- | --- |
| `none` | Listed the app without checking it | Nothing |
| `identity` | Established who operates the domain, and recorded their app key with a current delegation and, where it promises possession, proof of it | `key` |
| `used` | Did the above, and used the app as its description says | `key` |
| `source` | Did the above, and reviewed the client source at the app's `source` URL | `key`, and a `source` URL in the app description |
| `pinned` | Did the above, and bound the review to the exact client a host loads, under BRC-244 | `key`, `build` |

6.4.2 **A review level states what was checked, never that an app is safe.** Users read Flathub's domain verification and Farcaster's signatures as safety; the levels say precisely what somebody did, and section 7.3.3 governs how. Control of a domain, by DNS record or otherwise, is not `identity`, because the domain's next owner passes that check too.

6.4.3 **Review in proportion to reach.** A curator MUST NOT list at level `none` an app whose `metanet.groupPermissions` declares `spendingAuthorization` or `certificateAccess`, or whose category is `finance` or `identity`. An application that can ask to move money or reveal credentials is the kind impersonators build, and a catalog that lists one unexamined has lent its name to whoever registered the domain. MetaMask Snaps applies the same principle: what an extension may do decides how much review it needs. An application that declares no `groupPermissions` escapes this rule by saying nothing, which is why section 7.9.2 puts the friction at its first request instead.

6.4.4 **A pinned review needs BRC-244.** A host that does not implement BRC-244 MUST show a review at level `pinned` as `source`, because only a host that checks what it loads can say that it loaded what was reviewed.

#### 6.5 Withdrawals

6.5.1 A curator that removes an app MAY record it in `withdrawn` with the domain, the date `at`, a `reason`, a `ref` to a dated public explanation (MUST for `unsafe` and `owner-changed`, SHOULD otherwise), and the app `key` it last observed (SHOULD).

| Reason | Means |
| --- | --- |
| `unsafe` | The curator believes using the app may harm its users |
| `owner-changed` | The app's key or possession changed without a valid rotation, and the curator has not re-established who operates it |
| `defunct` | The app no longer works or no longer exists |
| `requested` | The app's author asked to be removed |
| `editorial` | The curator chose to stop listing it, for no reason above |

6.5.2 A withdrawal SHOULD remain in the document for at least one year, so that a host offline when it happened still learns of it.

6.5.3 A withdrawal is the curator's statement about its own catalog, and a host MUST attribute it to that curator.

6.5.4 **A withdrawal follows the key.** Where a withdrawal for `unsafe` names an app key, a host that meets that key with a current delegation on another domain, in any catalog or none, MUST treat that domain as section 7.7.4 treats the withdrawn one. A domain that merely names the key, without a delegation by it, is not that operator's, and is not affected. This includes the other domains of an operator that uses one key for several, which is intended, since a curator that finds an operator harmful has found the operator behind all of them. A publisher removed for harm otherwise returns the next day under a new name, as replacement accounts did after the Snap Store removals.

#### 6.6 The chain

Each version spends the output of the one before, and an output is spent only once, so a catalog has a single history that nobody, the curator included, can fork, and anybody can prove which version is the newest. It is a single-use seal.

6.6.1 **The signing rule.** Every signature this document defines other than a transaction's own, and every signature a companion document defines by reference to this section, is a [BRC-3](../wallet/0003.md) signature made through `createSignature`, whose `data` is the canonical bytes of a JSON object under RFC 8785, restricted to ASCII member names and to integers between minus and plus 2^53 minus 1, which is the profile BRC-239 proposes. The protocol ID is `[2, "app catalog"]` unless a section names another, the counterparty `anyone`, and the key ID the one each section names. Where a section lists member names in braces, the object signed has exactly those members, with the values the section gives. A signature is carried in JSON as the lowercase hex of its DER encoding, and in an output's field as the raw DER bytes, with a low S value in either case, and a verifier MUST reject one with a high S value. Where a signed object has a member naming a domain, such as `domain`, `from` or `to`, its value is the domain normalised as section 3.1 requires, in lowercase ASCII, with internationalised labels in their ASCII form.

6.6.2 **Two outputs.** Each is a one-satoshi output whose locking script pushes its fields and drops them, as in [BRC-48](../scripts/0048.md), and then locks with the keys that hold it:

1. **One key**, the default: the lock is BRC-48's own, `<key> OP_CHECKSIG`, so the output is an ordinary PushDrop token. Any BRC-100 wallet creates and spends it through `createAction`, as it does every overlay token, with the `PushDrop` template of `@bsv/sdk`.
2. **Several keys with a threshold**, for a curator that wants one: a bare multisignature of [BRC-47](../scripts/0047.md), `<m> <key 1> ... <key n> <n> OP_CHECKMULTISIG`, the keys compressed and in the order given.

The **root output** is locked by the root keys and their threshold. Its fields are:

| Field | Content |
| --- | --- |
| 1 | `app-catalog` |
| 2 | `1` |
| 3 | `catalog`, or a kind another document defines, such as BRC-242's `labels` |
| 4 | `root` |
| 5 | The catalog `id` |
| 6 | The signers threshold, as ASCII decimal; `1` for a single signer key |
| 7 onward | The signer keys, 1 to 8, each 33 bytes compressed |

The **version output** is locked by the signer keys and threshold that the root output beginning its run names. Its fields are:

| Field | Content |
| --- | --- |
| 1 | `app-catalog` |
| 2 | `1` |
| 3 | The kind, as above |
| 4 | `version` |
| 5 | The catalog `id` |
| 6 | The document hash: the SHA-256 of the bytes of the document file, 32 bytes |

The catalog's **start** is the outpoint of its first root output. The transaction that creates it MUST also create the first version output.

**Encoding.** Each field is pushed as data with the shortest push opcode for its length, never as a small-number opcode, so field 2 is the single byte `0x31`; text fields are their ASCII bytes and hashes and keys their raw bytes. The pushes are followed by `OP_2DROP` for each pair of fields and one `OP_DROP` for an odd one left, then the lock. Root and signer keys MAY be any keys their holders choose. A keyholder whose key lives in a BRC-100 wallet SHOULD derive it under protocol `[2, "app catalog"]`, key ID the catalog `id` followed by a space and `root` or `signer`, counterparty `self`, so that the wallet can find it again and spend the output with nothing but `createAction` and `signAction`. Root keys are offline in the sense that their wallet is: a curator keeps its root key in a wallet on a separate device used for nothing else. A threshold lock needs signatures from several wallets, and BRC-100 defines no exchange of partly signed transactions: the curator's tool computes each input's signature hash, asks each keyholder's wallet for a signature through `createSignature` with `hashToDirectlySign`, and assembles the unlocking script. This document does not define that tool, and a curator that uses one key per role never needs it.

6.6.3 **Following the chain.** A host holds the start it pinned, the current root output, and the current version output, and moves forward from there:

1. **Root steps.** A transaction that spends the current root output is judged only as a root step, whatever else it spends. It is a root step if it creates exactly one root output and exactly one version output with the same kind and `id`, the version output locked as the new root output names. The new root output MAY be locked by different root keys, which is a root rotation, and MAY name different signer keys. Its version output begins a new **run** and becomes the current version, and no later step of the previous run counts, whichever block it is in.
2. **Version steps.** A transaction that spends the current version output, and does not spend the current root output, is a version step if it creates exactly one version output with the same kind and `id`, locked by the same signer keys and threshold. Its output becomes the current version.
3. **Ends.** A spend of the current version output that is not a version step ends the run, and a spend of the current root output that is not a root step ends the catalog. In either case the host keeps the last version and shows the catalog as **ended at a spend that did not continue it**, naming neither cause nor culprit, since the host cannot know which. A run that has ended resumes at the next root step; a catalog whose root output has ended cannot resume, and its curator starts another. A curator's tool SHOULD check every transaction against these rules before it is broadcast, because a mistaken root step is permanent.
4. **Proof.** A host accepts a step only when it holds the transaction with a merkle path under [BRC-74](../transactions/0074.md) to a block header on the best chain it knows, checked as [BRC-67](../transactions/0067.md) describes. Steps travel as [BRC-62](../transactions/0062.md) or [BRC-95](../transactions/0095.md) BEEF from any source. An unmined step is not yet a version. Two steps in one block are ordered by spending: a step that spends another's output is the later.
5. **Never backwards, except with the chain.** A host MUST NOT accept, from any source, a version earlier along the chain than the one it holds. Where the block holding a step it accepted leaves the best chain, the host returns to the last step it holds that is still on the best chain, and moves forward again from there.

Because each output can be spent once, two different next versions cannot both exist, and no rule about counters, rollback or equivocation is needed. A curator cannot show one user one catalog and another user another: there is one chain, and every host that follows it reaches the same output.

6.6.4 **The keys.**

1. The **root keys** are held offline and used only in root steps: to rotate themselves, to appoint new signer keys, to begin a new run after signer keys are lost or stolen, or to end the catalog under section 6.6.3 item 3.
2. The **signer keys** publish versions. A thief of the signer threshold can publish versions in the current run, or end it, until the curator's next root step begins a new run with new signer keys, after which nothing the thief does to the old run is part of the chain. A thief of fewer root keys than the root threshold gets nothing. The root output is a separate output for exactly this reason: no signer key can spend it, so no theft of signer keys can end the catalog.
3. No root or signer key may be the curator domain's `metanet.trust` key, or a key used for anything but this catalog. The keys of one catalog are in that catalog's outputs and nowhere else, so they are scoped to it by construction; Debian's `signed-by` reached the same scoping by rule.
4. A curator MAY name the same keys as root and signers. It then gives up recovery under item 2, and its policy SHOULD say so. A curator SHOULD use a root key that is not a signer key, held in a separate wallet. The curator of a home catalog SHOULD use a root threshold of at least two keys held apart.

This is The Update Framework's division of keys, without the rest of its machinery, which a spent output makes unnecessary.

6.6.5 **Freshness by asking.** A spent output can be proved; an unspent one cannot. A host therefore learns that its version is the newest by asking.

1. A host refreshes each catalog on a schedule by asking sources for whatever spent the current outputs: overlay hosts under section 6.8, the curator's `steps` URL, and any other service that reports spends with their merkle paths. It accepts any valid step any of them shows. A source can withhold a step; it cannot invent one.
2. A refresh **succeeds** when at least two sources under different registrable domains answer, and every step they show is valid. One source alone, however honest, cannot show that nothing is being withheld. A host whose last successful refresh of a catalog is more than 31 days old, by elapsed time on its own clock, MUST show the catalog as out of date under section 7.7.2.
3. A catalog whose newest version is old is not out of date. A host SHOULD show the date of a version more than a year old, so that a quiet curator is visible, and keeps using it: a curator that has stopped publishing has left its catalog as it last was, and nothing about that is stale.

6.6.6 **Verify before use; invalid is not empty.** A host MUST check that a document's hash is the one the current version commits to, that its `id` is the chain's, and that it satisfies sections 6.2.3 and 6.3.7, before using it. Where the current version's document cannot be found, the host keeps the document it holds and says that a newer version exists and could not be fetched. Where the document is found and is invalid, the host keeps the one it holds and says that the curator published an invalid version. Neither is ever presented as an empty catalog: an empty catalog is a statement a curator can make, and a document that cannot be found or does not parse is a statement nobody has made.

6.6.7 **What this costs.** Each version is a transaction of a fraction of a cent, so every curator needs a funded wallet, and each root step needs the root keyholders. A host needs a source of block headers to check merkle paths, which every BRC-100 wallet already keeps. A version takes effect when it is mined.

#### 6.7 A catalog without its server

A version's authority is the chain, which the host follows from a start it pinned, so it does not matter who serves the chain or the document.

6.7.1 **Any source.** A host MAY fetch steps from any overlay host or service, and a document from `url`, from any mirror named in the manifest or in a document it holds, from a [BRC-26](../overlays/0026.md) UHRP host by the document hash, from another host, or from a file the user was given. Nothing about the source affects acceptance. A host SHOULD try every source it knows before treating a refresh as failed.

6.7.2 A curator SHOULD publish every document under UHRP, so that the hash in each version output resolves to it without the curator's server.

6.7.3 **The domain is needed once.** After a catalog is added under section 6.1.1, a host accepts its versions on the chain alone, and MUST NOT require the curator's domain to be reachable, or still registered, in order to accept a version. A domain that lapses, a server that goes offline and a hosting provider that withdraws service do not switch a catalog off.

6.7.4 **When the domain stops agreeing.** A host SHOULD read the curator's manifest again on its refresh schedule when the domain is reachable. Where the manifest no longer declares the catalog, or declares the same `id` with a different `start`, the host MUST NOT switch chains or drop the catalog, and MUST tell the user once, naming the domain and the date, that the domain no longer confirms the catalog they added. It MAY offer the newly declared catalog as a separate catalog to add under section 7.2. The domain may have been sold or compromised, or its curator may have lost its root keys; the host cannot tell which, and the chain the user chose is the one it keeps.

6.7.5 **What does not survive.** A host cut off from every source for 31 days shows its catalogs as out of date, because it cannot know what it has missed. A curator that loses both its root keys and its signer keys cannot change the catalog again, and starts a new one; section 6.7.4 tells its users. Nothing else stops a catalog.

#### 6.8 The overlay

6.8.1 Root and version outputs are submitted under [BRC-22](../overlays/0022.md) to topic `tm_appcatalog`, and found under [BRC-24](../overlays/0024.md) through lookup service `ls_appcatalog`. As [BRC-87](../overlays/0087.md) establishes no registry, these names are claimed rather than reserved, and carry no document number.

6.8.2 The topic manager admits a root output whose transaction creates a first version output with it, and any output whose transaction is a root step or version step under section 6.6.3 from an output it has admitted. It retains spent outputs, because a host that pins a catalog late needs the steps that came before, and it records the transaction that spent each admitted output whether or not that transaction was a step, because an end is news a host needs as much as a step. An overlay host MAY decline to keep chains that nobody has looked up.

6.8.3 The lookup service is queried by start, optionally with the outpoint of the newest step the asker holds, and returns the steps after that point as BEEF, oldest first, at most 64 to a response, with a continuation for more, followed by any transaction that spent the last output and did not continue the chain. The curator's `steps` URL serves the same BEEF, from the start, so that every catalog has a second source that needs no overlay.

6.8.4 Anybody can begin a chain with any `id`. A host follows only chains it pinned under section 6.1.1, so a chain that copies somebody else's `id` is noise, and is never confused with the catalog, because the host asks by start.

6.8.5 The overlay is federated in the sense of [BRC-183](../overlays/0183.md): any host may run it, any host may check its answers against the chain, and an overlay host can withhold a step but cannot invent one. Section 6.6.5 asks more than one.

6.8.6 **Eviction is public.** An overlay host will sometimes have to stop serving an output, for spam, for unlawful material or under legal compulsion, as Metanet Apps does under what it calls Topical Eviction. An overlay host that declines to serve an output it has admitted SHOULD publish an eviction record naming the outpoint, the basis and the date, and SHOULD let the publisher ask for reconsideration. Eviction changes nothing on chain and nothing on any other overlay host, and to a host it is withholding: section 6.6.5's rule that a refresh needs two independent answers is what keeps one operator's eviction from becoming every user's.

#### 6.9 The curator's policy

6.9.1 `policy` is a public HTTPS document. It SHOULD state, and a home catalog's curator MUST state:

1. What the curator lists and what it will not.
2. What the curator checks at each review level it uses.
3. Its **removal ladder**: what it does first when a listed app misbehaves, when it removes, and when it records `unsafe`.
4. How an author or a user asks for a correction, a listing or a removal, and an **appeal** route by which a decision is reconsidered by somebody not involved in making it, or a statement that no such person is available.
5. Any relationship the curator has with an app it lists, commercial or otherwise.
6. Who holds its root and signer keys, in what number, and whether they are the same keys.
7. A dated history of changes to the policy itself.

6.9.2 This is [BRC-184](../wallet/0184.md) section 5 applied to app catalogs, and the shape F-Droid and IzzyOnDroid already publish. Its content is the curator's; this document requires only that it exists, says these things, and can be found. A host that holds a catalog whose policy URL no longer answers shows that, and keeps the catalog.

6.9.3 A curator SHOULD separate the ability to edit a catalog from the ability to publish it, and SHOULD NOT let any pipeline place an app in a section before it has passed the review the policy promises. An app that reaches a featured position through a gap between a publishing pipeline and a curation layer was featured by the catalog, whatever the catalog intended.

### 7. What a host does

#### 7.1 Home catalogs

7.1.1 A host MAY enable one or more catalogs by default. These are its home catalogs. A host that calls the apps in its own catalog its signature apps has chosen a name for its own list.

7.1.2 A host MUST indicate which enabled catalogs are home catalogs.

7.1.3 A host MUST let the user turn any catalog off, including a home catalog. It MAY keep a turned-off home catalog in its list so that it can be turned on again.

7.1.4 A fork that ships a different home catalog is doing what this document is for. Home catalogs are each host's own choice, as [BRC-184](../wallet/0184.md) section 3.3 says of defaults.

7.1.5 A host that ships a home catalog SHOULD ship its start, the steps up to a recent version, and that version's document, so that the catalog works on first run without any server. Shipping it in the host's own build is the host vendor's confirmation of the catalog, in place of the two-way declaration of section 6.1.1, and the host completes section 6.7.4's check at its first refresh with a network.

#### 7.2 Adding a catalog

7.2.1 A host MUST let the user add a catalog by entering a curator's domain or a **catalog link**:

```abnf
catalog-link = "catalog:" domain "/" local "?start=" txid "." vout
domain       = label 1*( "." label )
label        = ( ALPHA / DIGIT ) *61( ALPHA / DIGIT / "-" ) [ ALPHA / DIGIT ]
local        = 1*32( %x61-7A / DIGIT / "-" )
txid         = 64( DIGIT / %x61-66 )
vout         = 1*10DIGIT
```

7.2.2 A catalog link carries the start the sharer expects, as F-Droid's repository links carry a fingerprint. The start commits to the root keys, because they lock the output it names. A host given one MUST compare it with the start the curator's manifest declares, and MUST refuse to add the catalog on a mismatch, saying so at that moment. Failing at the add step rather than at a later use is the lesson of F-Droid clients that surfaced fingerprint failures only at install.

7.2.3 Before the catalog is enabled, the host MUST show, on one surface: the domain from which the manifest was actually retrieved, as text; the catalog's `name`; the curator's `metanet.trust.name`, attributed to the curator; the review levels the catalog uses and how many of its apps are at each; a link to its `policy`; and whether the host has reviewed this catalog. Where it has not, the host MUST say so. Where the catalog's `name` has the same skeleton under section 7.5.1 as an enabled catalog of another curator, the host MUST say so on that surface, naming both domains.

7.2.4 **No catalog without its domain.** A host MUST NOT enable a catalog the user adds whose two-way declaration under section 6.1.1 it has not completed. A link the user scanned on a network that blocks the curator's domain is exactly what an attacker controls, and a catalog that cannot be confirmed now can be added when it can.

7.2.5 A host MUST NOT refuse to add a catalog on the ground of who curates it. A host that its distribution platform prevents from offering added catalogs MUST say so where the control would be.

7.2.6 **One catalog, one chain.** A catalog is the same catalog wherever it was added from if its start is the same, and a host adds it once. Two catalogs with the same `id` and different starts are two catalogs, which happens after section 6.7.4, and a host shows each with a fingerprint of its start: the first eight characters of its transaction ID.

7.2.7 For each enabled catalog a host SHOULD show its curator, when it last refreshed successfully, which sources answered that refresh and which did not, the date of the block holding the version it holds, and how many apps it lists. A refresh in which some sources failed is shown as partial, and a source that did not answer is never shown as having reported an empty catalog.

#### 7.3 One app, many catalogs

7.3.1 An app listed in several enabled catalogs is one app. A host MUST NOT show it twice in any view not organised by catalog: all apps, a category, search.

7.3.2 Every enabled catalog listing it MUST be inspectable, each with its review level and date, in words such as "Listed by Harbor (used, 20 Oct) and Lattice (not reviewed)". A host MUST NOT summarise listings as an endorsement count or a score.

7.3.3 A host stating a review MUST state its level and curator together, and MUST NOT reduce it to a mark, a colour or the bare word "reviewed". Where catalogs disagree, the host states each.

7.3.4 Curator notes are shown attributed, separately, and never combined.

7.3.5 In a view organised by catalog, the app appears where that catalog places it.

7.3.6 Pinning is a union. An app pinned from two catalogs, two sections or two sets is pinned once.

7.3.7 Where one catalog lists an app and another withdraws it, the host shows both, each attributed.

#### 7.4 Continuity

7.4.1 **The wallet keeps the record.** The party that holds grants is the party that must notice a change of owner. A wallet MUST record, for each app for which it holds a standing grant or which the user has pinned, the app key, the last rotation `seq` it accepted, the newest delegation `issued` it accepted, and the delegation's `possession` flag. An app for which the wallet held grants before it implemented this document is recorded at the first fetch afterwards. A host that is not the wallet SHOULD keep the same record for what it displays. Where the two records differ, the wallet's governs grants and the host's governs only the host's own displays, and no BRC-100 channel is needed between them. For the same reason the release check of section 7.4.2 governs grants only where the wallet is itself the host that loaded the app, as in a wallet's built-in browser; a separate host that finds code its operator did not release shows that, and cannot change what the wallet honours.

7.4.2 **Standing grants follow proof.** An app with a recorded key is in one of three states:

| State | When | Standing grants |
| --- | --- | --- |
| Proven | The current app key is the recorded one, or reached from it under section 3.6; its delegation is current under section 3.7.5; where the delegation says `possession: true`, the wallet has proof of possession from this session or the last 24 hours; and, where the delegation names `releaseKeys` and the wallet is itself the host that loaded the app and checks builds under BRC-244, the code it loaded matches the newest release signed by one of them | Honoured |
| Unproven | The current app key is the recorded one, or reached from it, and anything else in the row above is missing: no current delegation, no proof of possession, code its operator did not release, or no answer at all | Not honoured: the wallet prompts for each request as though none had been granted, and honours them again as soon as the app is proven, without asking the user |
| Changed owner | A manifest fetched and parsed shows an app key that is not the recorded one and is not reached from it, or shows none where one was recorded | Not honoured until the user reconfirms them, section 7.4.4 |

A wallet checks before the first use of a standing grant in each session, and at least daily while an app is open. Because the rule asks for proof, deleting the delegation, serving an expired one, refusing the handshake or dropping the connection all leave the app unproven; and an honest operator whose delegation lapses, or a wallet with no network, only makes the app ask per request until proof returns.

7.4.3 An unproven app is shown as such in its details, and is otherwise used as normal. A changed owner is shown as section 7.4.4 says.

7.4.4 **Standing grants do not pass to a new owner unasked.** For an app in the **changed owner** state:

1. A wallet MUST NOT honour any standing [BRC-116](../wallet/0116.md) grant, including spending authorisations and remembered protocol, basket and certificate grants, until the user reconfirms it after being told of the change. The grant was made to whoever operated the domain at the time, and the user has not been asked about whoever operates it now. This, with section 7.4.2, is the one place this document reaches into BRC-116, because every documented account-transfer attack worked by inheriting exactly this trust.
2. A host MUST show, wherever the app is listed, that its owner has changed since each curator whose recorded `key` it no longer matches reviewed it, and MUST NOT show those reviews as current. A review whose `key` the current key is reached from under section 3.6 is shown as current, with "key rotated since review".
3. A host MUST tell the user before the app is next opened, naming what changed and when it was first observed.
4. A host MUST NOT pin the app as part of a set while it is in this state.

7.4.5 **Only the user restores grants after a change of owner.** The suspension under section 7.4.4 item 1 ends only when the user reconfirms. A curator recording the new key above `none` makes its own review current again in the host's displays and does nothing else, since a new owner can pass some curators' checks. Where the recorded key returns, as after a recovered hijack, the display clears and suspended grants still wait for the user.

7.4.6 An app that never published a key has none of these states, and so none of their protection. Section 6.4.1 makes that visible by keeping such an app at review level `none`.

7.4.7 Where catalogs record different keys for one domain, each curator's review is compared with the current key on its own. A catalog whose key matches, or from whose key the current key is reached, shows its review as current; one whose key does not shows its review as made of another operator.

#### 7.5 Impersonation

Impersonation of a known wallet or exchange is the attack that has taken the most money from users of every app store examined in preparing this document: fake Exodus and other wallets in the Snap Store, dozens of fake wallet extensions in the Chrome Web Store, and fake hardware-wallet companions in Apple's.

7.5.1 A host MUST compute a **skeleton** for each app's name, for each snapshot name of it, and for the label of each app's domain immediately left of its registrable suffix under the Public Suffix List, converted from its ASCII form to Unicode. The skeleton is computed, using Unicode 16.0 data or later, by applying normalisation form NFKC; then the skeleton function of Unicode Technical Standard #39 section 4, which applies NFD, replaces each character by its prototype in `confusables.txt`, and applies NFD again; then full case folding; then removing every character whose General Category is not a letter (`L`) or a decimal digit (`Nd`); then folding the sets of [BRC-169](../peer-to-peer/0169.md) section 2.3. A skeleton of fewer than three characters matches nothing. Hosts using different versions of the Unicode data may disagree about rare characters; the folds that matter, between Latin, Cyrillic and Greek letters and between ASCII lookalikes, have been stable for many versions.

7.5.2 **The trusted set.** Before pinning or first opening an app, and again whenever an app the user has pinned or granted changes its name, a host MUST warn the user where that app's name skeleton or domain skeleton equals that of a **different app** in the trusted set, naming both domains. The trusted set is the apps listed in a home catalog, pinned by the user, or holding a grant from the user, because that is what an impersonator imitates. Two apps whose domains both carry a current delegation by one app key are one operator's, and do not warn. Naming another app's key proves nothing; only a delegation by it does.

7.5.3 A curator SHOULD apply the same check against its own catalog and against the home catalogs of the hosts its users use before listing an app, and SHOULD NOT list one that collides, at any level above `none`, without first establishing that the two are the same operator.

7.5.4 A host MUST NOT silently substitute one app for another because their names are similar.

7.5.5 **Two apps, one name.** Where two or more apps a host shows in one view have equal name skeletons and are not one operator's under section 7.5.2, the host MUST show each with its domain given equal prominence to its name, and SHOULD mark them as sharing a name. When the user pins one of them, the host SHOULD name the others' domains on the pin surface. This applies whether the apps come from one catalog or several. It is a display rule, because two developers may honestly choose one name and the user only needs to tell them apart.

#### 7.6 Listing is not permission

7.6.1 A host MUST NOT grant, pre-approve, enlarge or renew any permission under [BRC-116](../wallet/0116.md) because an app is listed, listed in a home catalog, reviewed at any level, or pinned. "A manifest declaration or registry description alone never creates a grant" is BRC-116's own sentence, and a catalog is a registry description.

7.6.2 A host MUST NOT connect to an app automatically because it is listed. The Harbor prototype currently treats "listed in the catalogue" as its test for connecting without asking, and under this document that test is not available.

7.6.3 A host MUST NOT apply a lighter confirmation under BRC-328 to a listed or reviewed app than to an unlisted one.

7.6.4 A host MUST NOT block, warn against or add friction to an app because no enabled catalog lists it. Unlisted is the state of every application before its first curator.

7.6.5 The exceptions are sections 7.4, 7.5 and 7.7.4, and the threat labels of BRC-242. None of them blocks anything; each tells the user something specific and lets them decide.

#### 7.7 Sets, changes and absence

7.7.1 A host MAY offer a section as a set: one action that pins every app in it. **Adding a set pins; it does not connect.** Each app asks for its permissions on first use, as it would had it been pinned alone. A host SHOULD compute verdicts first, and SHOULD NOT pin an `unsupported` app as part of a set without saying so.

7.7.2 A catalog is **out of date** when section 6.6.5 item 2 says so. A host MUST then keep the last version it accepted, MUST show the catalog as out of date and since when, MUST NOT present its review levels as current, and MUST NOT present it as empty. Out-of-date review information is shown with its date. A catalog is not out of date because its curator's server is down, or because its curator has been quiet.

7.7.3 Turning a catalog off, or a catalog removing an app, removes that catalog's listings from the host's views. It MUST NOT unpin anything, revoke any grant, or delete any data. A catalog decides only what it shows.

7.7.4 Where an enabled catalog withdraws an app as `unsafe` or `owner-changed`, and the user has it pinned or holds grants for it, the host MUST tell the user once, naming the curator, the date and the `ref`, and MUST offer to unpin it and to open the review surface of BRC-329. It MUST NOT unpin it, revoke its grants or refuse to open it without the user's decision. For `owner-changed`, section 7.4 also applies.

#### 7.8 Labels

A host that implements BRC-242 shows the labels of the labelers its user subscribes to alongside every listing, and a threat label from any of them is shown even where a home catalog lists the app at its highest review level. Catalogs say what a curator chose and checked; labels say what anybody has found. Neither replaces the other, and this document does not require BRC-242.

#### 7.9 Where friction belongs

Warnings that are frequent, generic or overstated teach users to dismiss them. Apple's warning screens for alternative marketplaces in the EU were criticised by Spotify, Epic Games and others as overstated, and early installs took about a dozen steps. The warnings this document requires are few, specific, and placed at the moment they matter.

7.9.1 **Browsing carries no dialogs.** While a user browses, a host shows the domain, the verdict where it is not `works`, the portability where it is not `portable`, a shared name under section 7.5.5, and threat labels. Nothing else interrupts.

7.9.2 **Friction scales with reach.** A host SHOULD show, once, who has reviewed an app and at what level, or that no catalog the user has enabled has reviewed it: at the first open of an app that declares `spendingAuthorization` or `certificateAccess`, and otherwise at an app's first request to spend or to reveal a certificate where it declared neither or declared no `groupPermissions` at all. An app that never asks for either needs no such step.

7.9.3 **One surface per decision.** A host that owes the user several things at one moment, such as a changed owner, a name collision, a withdrawal and a threat label, MUST present them on one surface, not as a sequence of dialogs.

7.9.4 **Every warning names a fact**: who said it, about what, and when. "This app may be unsafe" is not a warning this document permits; "Lattice withdrew this app on 4 December 2026 as unsafe" is.

7.9.5 **Nothing here is a gate.** Every warning in this document ends in the user's choice. A host that turned any of them into a block would have made the curator, or itself, the gatekeeper the plurality of catalogs exists to prevent.

#### 7.10 Listings found outside catalogs

The apps overlay of `@bsv/overlay-topics`, under `[1, "metanet apps"]`, holds listings that anybody may publish, each signed by a publisher key and naming a `domain`. Metanet Apps shows them as its catalogue. Nothing admits a listing on the ground that its publisher controls the domain it names, so a listing can claim any domain, with any name and icon, and link to somewhere else.

7.10.1 A host or curator MAY read the apps overlay, or any similar index, as a source of candidate apps.

7.10.2 A listing is **domain-confirmed** when the manifest at the domain it names carries a current delegation, under section 3.7, by the listing's publisher key as its app key, or by an app key from which the publisher key is reached under section 3.6. Confirmation is checked by fetching that manifest, and lapses with the delegation.

7.10.3 A host MUST NOT show a listing that is not domain-confirmed as the app at the domain it names. It MAY show it, if at all, as an unconfirmed claim by the publisher key, with the domain marked as not confirming it.

7.10.4 A host showing a domain-confirmed listing takes the app's name, description, artwork, category and requirements from the app's own manifest under section 4, never from the listing, and opens the app at its domain, never at a URL the listing gives. The listing tells a host that an app exists; the app says what it is.

7.10.5 A listing is not a catalog entry and carries no review level. An index that wants to say how far it checked an app publishes a catalog under section 6.

### 8. Extension

8.1 The twelve categories, five review levels and five withdrawal reasons are closed, and change only by revision of this document. The level `pinned` is defined here and given its meaning by BRC-244.

8.2 The three requirement kinds are closed. A future specification MAY define another at a reserved dispatch point in the manner of [BRC-98](../wallet/0098.md), [BRC-99](../wallet/0099.md) and [BRC-111](../wallet/0111.md): the value `p `, a space-free scheme identifier, and the scheme-defined remainder.

8.3 A host MUST treat an unrecognised kind as undetermined under section 5.2.

8.4 An extension MUST NOT redefine the three kinds, and MUST NOT be a means of stating a portability or a verdict directly.

8.5 Another document MAY define a further kind for field 3 of section 6.6.2, and BRC-242 does; the chain rules of section 6.6 apply to it unchanged. Another document MAY define a further field of `metanet.app`, as BRC-244 and BRC-245 do, and a host that does not implement it ignores it.

### 9. Not Specified Here

Recorded so that the next author does not rediscover them or ship them incompatibly.

9.1 **Anything commercial.** Prices, plans, revenue shares, payment through a catalog and paid placement are business terms that vary by jurisdiction and platform, and are left out deliberately. Nothing here prevents or reveals a charge for inclusion; section 6.9.1 item 5 requires a curator to disclose its relationships with what it lists, and a later document could start from [BRC-300](./0300.md) section 3.5.

9.2 **User ratings, user reviews, and scores.** Section 7.3.2 forbids synthesising a score from listings. A system of user reviews has its own failure modes and deserves its own document. A fee paid to the developer per review, as Metanet Apps charges, fails as a defence, because a developer reviewing its own app pays itself.

9.3 **The content of a curator's criteria.** Section 6.9 requires a policy and what it covers, not what it decides.

9.4 **An app signing its own description.** A server key of section 3.7 could sign `metanet.app`, which would let section 6.3.6's live fetch be skipped. It is left for a revision that finds it worth the cost.

9.5 **Server behaviour.** No review level binds what an app's server does.

9.6 **How a host opens an app.** Framing, tabs, provider injection and whether an app opens inside the host are host decisions, bounded by the app's `frame-ancestors` policy and, on some platforms, by distribution terms such as Apple's App Review Guideline 4.7.

9.7 **Native apps**, which are not connected apps and are not to be listed as though they were.

9.8 **Synchronising pins, enabled catalogs and recorded app keys between devices.** A sync service may do so, and the format is not specified. A host that synchronises anything SHOULD include catalog starts and recorded app keys, since continuity that resets on a new device protects nobody who gets one.

9.9 **Catalogs of catalogs.** A catalog lists apps. A curator that wants to suggest other catalogs does so in its policy or on its site; BRC-243 lets a person recommend one.

9.10 **Apps without a domain.** An application served by content hash, such as a UHRP URL, with no domain of its own, has no originator a wallet can grant to, and is not a connected app under section 3. A host that opens one from a gateway grants to the gateway's domain. BRC-244's loader, which can serve a client from its UHRP copy under a domain's identity, is where a future document would start.

9.11 **The companions.** Safety labels (BRC-242), recommendations from people the user knows (BRC-243), pinned builds (BRC-244) and "open with" (BRC-245) are specified separately, and this document requires none of them.

### 10. Relationships

10.1 [BRC-116](../wallet/0116.md) and [BRC-73](../wallet/0073.md) are unchanged except by sections 7.4.2 and 7.4.4, which honour standing grants only for an app that is proven, and hold them after a change of owner until the user reconfirms.

10.2 [BRC-184](../wallet/0184.md) governs descriptions of protocols, baskets and certificate types; this document applies its consumption and stewardship rules to applications.

10.3 [BRC-169](../peer-to-peer/0169.md) identifies an ecosystem by domain, and a curator may be the same domain in both roles. Section 7.5 extends its skeleton to names in any script.

10.4 [BRC-137](../opinions/0137.md) section 3 defines a catalog endpoint for wallets, whose governance [BRC-300](./0300.md) leaves open. This document lists apps, not wallets; what carries over are sections 6.5 to 6.9.

10.5 The apps overlay of `@bsv/overlay-topics` is a source of candidates under section 7.10.

10.6 [BRC-326](../wallet/0326.md)'s `unavailable` is the failure that the verdict `unsupported` foretells.

10.7 [BRC-103](../peer-to-peer/0103.md), [BRC-104](../peer-to-peer/0104.md), [BRC-47](../scripts/0047.md), [BRC-48](../scripts/0048.md), [BRC-62](../transactions/0062.md), [BRC-67](../transactions/0067.md), [BRC-74](../transactions/0074.md) and [BRC-95](../transactions/0095.md) are used unchanged.

10.8 BRC-242 publishes label feeds as chains of kind `labels`, and meets catalogs at this document's section 7.8.

10.9 BRC-243 recommends apps, catalogs and label feeds, naming a catalog by its start.

10.10 BRC-244 defines build manifests, curator pins, and the signed releases that this document's sections 3.7.6 and 7.4.2 rely on.

10.11 BRC-245 defines `handles`, and how a host opens what a wallet holds with a connected app.

### 11. Conformance

| Condition | Required behaviour |
| --- | --- |
| App describes itself | `metanet.app` in its own manifest, retrieved from its own origin, with one category |
| App needs anything beyond BRC-100 core | A requirement with `fallback`; a vendor's page interface as `host-api` naming its ecosystem |
| App built for a network's members | `audience`, never a requirement |
| App publishes an app key | Held offline; a delegation to its own server keys of at most 90 days with possession or 30 without; `keyRotations` when the key changes; `movedTo` on a move, which never carries grants |
| Standing grant about to be used | Honoured only while the app is proven (section 7.4.2); otherwise each request prompts, and grants return by themselves on proof |
| App key differs without a rotation chain, or is removed | Changed owner: reviews shown as stale, user told before the next open, grants wait for the user whatever any curator does |
| Curator publishes a catalog | `metanet.catalogs` with `id` and `start`; root and version outputs, single-key PushDrop by default; each version mined before it counts |
| Signer keys lost or stolen; root keys change | A root step, beginning a new run |
| A run or the root spent into anything that is not a step | Ended; last version kept |
| User adds a catalog | Two-way declaration completed first; link start compared; curator, levels and policy on one surface; any curator allowed; one catalog per start |
| Catalog after adding | Accepted on the chain alone, from any source; never backwards except with a reorganisation |
| Freshness | A refresh succeeds only with answers from two sources under different registrable domains; out of date after 31 days without one, never for being quiet; partial refreshes shown as partial |
| Curator's domain later declares another start or none | Catalog kept; user told once |
| Document | Hash matches the version; `id` matches; size bounds; one answer per app; if missing or invalid, the previous kept with the reason, never empty |
| Entry above `none` | App `key` observed with a current delegation; money-moving, credential, `finance` and `identity` apps never at `none` |
| Review shown | Level, curator and date together, never a bare mark; `pinned` only by a host implementing BRC-244 |
| Withdrawal for `unsafe` or `owner-changed` | Dated `ref`; `unsafe` follows the key to domains it has delegated for |
| Names | Skeleton warning against the trusted set before pin, first open or rename; two apps with one name shown with domains equally prominent |
| App in several catalogs | Shown once in merged views; every listing and withdrawal inspectable and attributed |
| Listing found outside catalogs | Used only when domain-confirmed, and described by the app's own manifest |
| Portability or verdict | Derived by the host; absent feature flags undetermined; `unknown` never shown as `unsupported` or hidden |
| Any verdict, label or warning | Never prevents opening; several at once on one surface |
| Home catalog | Marked; can be turned off |
| Listing, review, pin or home catalog | No permission granted or lightened; no automatic connection; no friction for being unlisted |
| Catalog turned off or entry removed | Pins, grants and data untouched |

### 12. Surfaces that fail conformance

1. A catalog card whose name and icon came from a curator's snapshot, with no domain beside them.
2. "Verified", a green tick or "Endorsed by 3 catalogs" standing for a listing or a review level.
3. A connection opened without a prompt, or a first-run preset granting permission to sign, because an app is in a catalog.
4. The same app twice in search results, or two apps called "Readings" side by side with only one domain shown.
5. "Not compatible with your wallet" for an app whose only requirement is an unadvertised feature flag.
6. A home catalog that cannot be turned off, or an "Add catalog" control limited to the host's own list.
7. A catalog shown as having no apps because its newest document could not be fetched or one source timed out.
8. A catalog marked out of date because its curator's server is down while the chain and a UHRP copy are available.
9. A catalog switched to another chain because its curator's domain was sold.
10. A spending allowance honoured for a domain whose new owner serves the old manifest and cannot answer the handshake.
11. Grants restored without asking because a curator re-listed an app after its owner changed.
12. An app named "Exodus Wallet" at an unknown domain pinned without a word while the home catalog lists Exodus elsewhere, or a granted app renaming itself to match the user's bank.
13. An apps-overlay listing claiming `harbor.example`, with Harbor's name and icon, shown as Harbor's app.
14. A finance app in a home catalog at review level `none`.
15. Five dialogs in a row on first open, or "This app may be unsafe" with no source, date or reason.

## What Is Checkable, and What Is Taken on Trust

| Fact | Checked by | How |
| --- | --- | --- |
| A catalog is the curator's | Anybody, when it is added | The two-way declaration of `id` and `start` |
| A version belongs to it, and is the only one at its step | Anybody | The chain of spends from the start, with merkle paths |
| What it said at a past step, and when | Anybody, where the document was kept | The document hash under UHRP, and the block's time |
| An app's server holds a key its app key appointed | A wallet, where possession is promised | The delegation and the handshake |
| The code loaded is a release the operator signed | A wallet that checks builds, where release keys are named | BRC-244 |
| An app's operator is the one a curator reviewed | A host | The app key against the entry's `key`, with rotation |
| Portability; that listing granted nothing | Anybody | Recompute it; open a listed app and watch for the prompt |

| Taken on trust | Because | What stands in |
| --- | --- | --- |
| The version held is the newest | Unspent cannot be proved | Two independent sources; out of date after 31 days |
| A curator did what its review level says | Review is off the record | The `ref`, the policy, and the curator's name on every review |
| An app is safe, or its server behaves | Nothing establishes it | Section 7.6, and BRC-242's labels |
| An app's requirements are complete | Only its author knows | `unavailable` at runtime under [BRC-326](../wallet/0326.md) |
| A curator applies its policy evenly | A policy is prose | Its appeal route and the user's freedom to turn it off |
| An app is still run by the party first trusted | A copy lasts until its delegation expires; a sale of every key is invisible | The 30-day limit; curators' disclosure rules, withdrawals and labels |

## What It Buys, and What It Costs

| Party | Gets | Pays |
| --- | --- | --- |
| User | Many networks' apps in one wallet, shown once; catalogs that survive their curators' servers; warnings before a host-bound app fails, an owner changes or a lookalike is pinned; reviews that say exactly what was checked | Reading a domain beside a name; occasionally reconfirming a grant |
| App author | One description every host reads; no curator can misdescribe it; protection from hijacks in hosts that check builds | A manifest entry, an offline app key, a delegation renewed every one to three months, a handshake if it promises possession, release keys if it signs releases |
| Curator | A catalog every host reads that survives its servers and needs no re-signing | A funded wallet and a fraction of a cent per version, a root key kept apart, a policy with an appeal route, real review of anything that moves money |
| Host or wallet vendor | Every other network's catalog for nothing, and its own as the default | Following chains, verdicts, skeletons, key and possession checks, and giving up trusting its own listings |

**The chain's trade-off.** A signed file with an expiry bounds how long colluding servers can hide a newer version; a chain cannot, because nothing proves an output unspent, so a host asks more than one party. In exchange a curator cannot fork its history, and a catalog outlives a curator who goes quiet, with no counters or log to maintain.

## Security Considerations

**A listing vouches for less than it appears to.** It says that a curator chose a domain on a date and checked it to a stated level, and section 7.6 keeps a listed app to exactly what an unlisted website could do.

**The change of owner is the attack that has worked everywhere.** Sold extensions, hijacked publisher accounts, expired maintainer domains and re-registered publisher domains all delivered malicious code as a valid update. A new owner can copy every file, so section 3.7 checks a key the server must hold, and section 7.4.2 honours standing grants only while that proof is present, so removing or blocking it achieves nothing. Three gaps remain: an app whose delegation says `possession: false` can be impersonated with a copy for at most 30 days; a takeover of a domain's name resolution can relay the handshake, which BRC-244's signed releases close in hosts that check builds (section 3.7.6); and an app with no key has no protection, which section 6.4.1 keeps visible.

**A project sold with its keys cannot be told from its old self.** The buyer is the operator in every sense a key can express, as with the sold browser extensions that motivated section 3.5. Curators' disclosure policies, `owner-changed` withdrawals, dated reviews and labels stand in for detection.

**Impersonation is the attack that has taken the most money.** Section 7.5 compares names, across scripts, with the apps the user already trusts, and section 3.3 keeps a confusable domain from displaying as its lookalike. A name and domain that fold differently pass; the domain shown and the labels of BRC-242 are the remaining defences.

**A home catalog is a high-value target.** Once a host has pinned the start, neither the curator's server nor its domain can change what the host accepts. Stolen signer keys yield versions in one run, public and permanent, until a root step; fewer root keys than the threshold yield nothing. Section 6.9.3 covers the curator's own pipeline.

**Forks, rollbacks and freezes.** A catalog cannot fork, and a host never moves backwards. A freeze needs two sources under different registrable domains to withhold the same step, and after 31 days without a successful refresh the user is told. Sources under one operator can collude; asking more sources makes that harder.

**Untrusted input.** Documents are bounded (section 6.2.3), text is rendered as text and icons as untrusted images. Section 7.2.3 shows the domain the manifest actually came from, after F-Droid's 2018 audit found that a redirect could change the URL in its add prompt, and section 7.2.4 adds no catalog its domain has not confirmed. A chain that copies another catalog's `id` misleads nobody, because hosts follow the start they pinned.

## Privacy Considerations

**Fetching a catalog tells its source who is browsing.** Hosts SHOULD refresh catalogs on a schedule rather than per view, and MAY fetch documents from UHRP hosts and mirrors rather than the curator, which tells the curator less.

**Fetching an app's manifest tells the app who is looking.** Snapshots let a host draw a catalog without contacting every listed domain. Section 6.3.6 requires the live fetch only before a pin or first open, when the user has chosen to contact that app anyway. The possession check of section 3.7.3 is made at the same fetch, and tells the app nothing it did not already learn from it. A wallet makes the handshake from a key of its own choosing, and SHOULD NOT use the user's identity key.

**Audience is evaluated locally.** A host MUST NOT send the result, or the user's certificates, to a curator or an app in order to decide what to show.

**The set of enabled catalogs is a profile**, and so is the set of recorded app keys. Hosts MUST NOT disclose either to any curator or app, and SHOULD treat them as browsing history if they synchronise them.

**Telemetry.** A host that measures its own use SHOULD NOT send search text, the user's identity key, app domains, catalog starts, outpoints or amounts to any analytics service, which is the rule Metanet Apps publishes for itself. Search text and app domains together amount to the browsing profile that the rest of this section protects.

**Chain lookups reveal interest in a catalog.** A host refreshing a catalog asks overlay hosts by its start, which tells them which catalogs its user has enabled. Hosts SHOULD batch these lookups with the refresh schedule rather than issue them per view.

## Implementations

No host implements this document.

**Harbor** has the host side in prototype: toggleable repositories (section 7.1.3), user-added ones behind a warning (section 7.2.3), and presets that compose as a union (section 7.3.6). To conform it would follow catalog chains instead of compiling catalogs in, stop connecting automatically to listed sites (section 7.6.2), move per-app records into the apps' manifests (section 6.3.4), and add key recording, possession checks and skeleton checks.

**Meadow and Lattice** become catalogs whose organisation scopes are sections and whose steward-only apps are a steward catalog; their membership certificates become `audience`. **BSV Radar**'s compatibility badges become verdicts a host computes, and its DNS TXT verification supports level `identity` only once an app key and delegation are recorded beside it (section 6.4.2).

**Metanet Apps** already queries several overlay hosts and merges them, as section 6.6.5 asks. Under section 7.10 a publisher that uses its identity key as its domain's app key makes its listings domain-confirmed with no change to the overlay; Metanet Apps could filter on that, and publish its Topical Eviction records under section 6.8.6.

**The chain** needs no new tooling: with one key per role both outputs are ordinary PushDrop tokens that any BRC-100 wallet creates and spends through `createAction`, and steps travel as BEEF. **Possession** uses BRC-104's `/.well-known/auth`, which `@bsv/auth-express-middleware` already serves.

### Conformance levels

Each party conforms to its own part of this document, since "supports BRC-241" alone tells a counterparty nothing it can check.

**Application.** Serves `metanet.app` with a category and a complete `requires`; publishes an app key held offline, a current delegation and, when the key changes, `keyRotations`; and answers the handshake where its delegation promises it.

**Curator.** Declares `id` and `start`; publishes versions and key changes as steps; states a review level on every entry and records the app key above `none`; never lists a money-moving or credential app at `none`; and publishes its documents under UHRP and a policy.

**Wallet.** Records app keys, rotation sequence, newest delegation and possession flag for apps it holds grants for, and honours standing grants only while an app is proven.

**Host Core.** Most Nostr clients publish handler records and reports and few read them, so the reading half here has a small core. A Host Core implementation confirms a catalog's domain when it is added; follows its chain from any source with merkle paths; refreshes from two sources; checks document hashes and keeps the last good document; merges by domain and shows the domain; shows the changed-owner state; runs the skeleton check; lets the user add and turn off any catalog; grants nothing for a listing; and puts its warnings on one surface. It MAY omit verdicts, review display and labels, and where it omits review display it MUST NOT show any substitute for it.

**Host.** Host Core, plus verdicts, review display, section 7.5.5's shared names, section 6.7.4's notice, moves under section 3.8, and section 7.10 where it reads listings from outside catalogs. A host that offers no way to add another catalog conforms at neither level.

**Verification.** Transactions are checked as any SPV client checks them, other signatures as BRC-3 signatures over canonical JSON, and the rest against section 11's table: for instance with two catalogs sharing an app, two apps sharing a name, a chain served by one source that withholds a step, a curator manifest that changes its start, a signer run ended and resumed, a copied manifest whose server cannot answer the handshake, a rename that collides with a granted app, and a device clock a day wrong.

| --- | --- | --- | --- |

## Appendix A: Worked Example

Illustrative. Harbor, Meadow and Lattice are codenames, and every domain except `bsvblockchain.org` is invented; no organisation named has published these objects, and no transaction, key or hash is printed because none has been made.

A Harbor user has two home catalogs, `catalog:harbor.example/signature` and `catalog:bsvblockchain.org/apps`, whose starts and recent steps shipped with the wallet, and scans a QR code at a Lattice event. It carries a catalog link for `catalog:lattice.example/apps` with its start.

**Adding.** The host fetches `https://lattice.example/manifest.json`, finds the catalog in `metanet.catalogs` with the same start as the link, and asks two overlay hosts for the chain from that start. It checks the root output names `catalog:lattice.example/apps`, follows three version steps with their merkle paths, takes the document hash from the third, fetches the document from `url`, and checks its hash. It then shows one surface: "Lattice Apps, from lattice.example. Lattice describes itself as: a growers' research network. 2 apps used by Lattice, 9 not reviewed. Policy. Harbor has not reviewed this catalog." The user turns it on.

**Merging.** Lattice lists `readings.example` (invented) and `brix.example` in a section titled "Field tools". BSVA lists `brix.example` in "Science". In the category view `brix.example` appears once, with "Listed by BSV Association (identity, 2 Sep) and Lattice (used, 14 Oct)" on inspection, and each curator's note shown under its name.

**Two apps, one name.** BSVA also lists an unrelated app called "Readings" at `meterreadings.example` (invented), for utility meters. In search, both appear as "Readings", each with its domain in the same type as its name, marked as sharing a name. When the user pins the Lattice one, the pin surface adds "Another app called Readings is at meterreadings.example." Nothing warns.

**First open.** The wallet fetches the readings app's manifest, records its app key, checks its delegation, which says `possession: true`, and completes the handshake at `/.well-known/auth` with one of the delegated keys. The app is proven. The app declares no spending or certificate permissions, so its first open shows nothing beyond the ordinary BRC-116 prompt when it first asks to sign. A finance app from the same catalog would first show, once: "Reviewed by Lattice (used, 14 Oct). Not reviewed by Harbor or BSV Association."

**Impersonation.** A week later the user adds a catalog from a stranger's link. It lists an app named "Rеadings", with a Cyrillic `е`, at `readlngs.example` (invented). Its name skeleton equals that of the app the user pinned from `readings.example`, and its domain label folds `l` to the same representative as `i` and so collides too. Before pinning, the host shows one surface: "Another app you use is called Readings, at readings.example. This one is at readlngs.example." Had the stranger called it "Field Notes" at `fieldnotes.example`, nothing would have fired, and the user would have had only the domain shown and any labels from their labelers. That is the limit of section 7.5.

**The curator's server goes down.** In January `lattice.example` is offline for three weeks. The host's refresh asks two overlay hosts, finds one new version step with its merkle path, fetches the document from a UHRP host by its hash, and checks it. The user notices nothing, because both the step and the document came from sources other than the curator's own server.

**A change of owner.** In March `readings.example` lapses and is re-registered, and the new owner copies the old manifest byte for byte. The new server cannot answer the handshake the delegation promises, so the app is unproven and its remembered signing grant is not honoured. When the new owner publishes a key of its own, the app enters the changed owner state: the host says so wherever it is listed and before the next open, the grant waits for the user, and Lattice withdraws the app as `owner-changed`.

**A registrar hijack.** In April somebody takes over `mail.harbor.example`'s name resolution through its DNS provider, obtains a certificate, and serves a modified client while relaying the possession handshake to Harbor's real servers. The handshake passes. But Harbor's delegation names release keys, and the user's Harbor browser checks builds under BRC-244: the modified script matches no release Harbor signed, so the host shows that the app is serving code its operator did not release, and the app is unproven for the session. Its standing spending allowance is not honoured; each request prompts, and the user closes the tab.

**A stolen signer key and a recovery.** In May a Lattice signer key is stolen and the thief publishes a version listing a drainer. Hosts follow it, and labelers flag the drainer. Lattice's root keyholders take a root step with a new signer key and a version withdrawing the drainer as `unsafe`; every host moves to the new run, and the thief, who cannot touch the root output, cannot end the catalog.
