# BRC-243: Recommendations from People You Know

Crumbs

## Abstract

This document specifies a **recommendation**: a small on-chain token in which a person, under their own identity key, recommends a connected app, a catalog or a label feed, as defined in [BRC-241](./0241.md) and [BRC-242](./0242.md). A wallet shows a user the recommendations of the people in their [BRC-169](../peer-to-peer/0169.md) address book, by name, and of nobody else.

A recommendation is a one-satoshi [BRC-48](../scripts/0048.md) PushDrop output locked to its author and bound by its signature to the transaction that created it, so nobody can copy it. **Spending it withdraws it.** It names the subject's key where there is one, so it does not pass to the next owner of a domain. It grants and ranks nothing, and is counted only as the names of people the user knows.

## Motivation

### What catalogs and labels leave out

A catalog under [BRC-241](./0241.md) is an institution's selection, and a label under [BRC-242](./0242.md) a security service's finding. Neither is the statement people rely on most when choosing what to use: that somebody they know uses it.

It is also the statement most easily faked: the fake-wallet extensions found in the Chrome Web Store in 2020 came with fake five-star reviews. A recommendation is useful only if its author is a person the user knows, so this document shows nobody outside the address book.

### What Nostr learned

**NIP-89** has users publish which application they recommend, and clients look those recommendations up among the people the user follows; it warns that unfiltered lookups invite malicious handlers. **NIP-87** applies the pattern to ecash mints, pointing at the mint's own description. **NIP-85** had providers publish trust scores, which drew the objections that they are easily gamed and relative to the viewer. This document takes NIP-87's shape and NIP-89's filter, and replaces Nostr's deletion request, which relays may ignore, with spending; section 6.3 explains why it leaves out NIP-85's scoring.

### Why on chain

A person has no domain at which to publish a document. A token they hold is theirs: created from any wallet, verified by anybody against their identity key, withdrawn only by them, for a fraction of a cent.

### Why the token names the transaction that made it

A signature over a token's fields proves who wrote them, and says nothing about who put them in a particular output, so a copy would outlive the recommender's withdrawal. The recommendation therefore signs the outpoint its creating transaction spends first, and a copy would have to spend that same, already spent, outpoint.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119. Terms defined in [BRC-241](./0241.md) section 1 and [BRC-242](./0242.md) section 1 are used as defined there.

### 1. Terminology

- **Recommendation**: the token of section 3.
- **Recommender**: the person whose identity key signs a recommendation.
- **Subject**: what is recommended: a connected app, a catalog or a label feed.
- **Subject key**: what identifies the subject's operator at the time of the recommendation. Section 3.2.
- **Contact**: an entry in the user's address book under [BRC-169](../peer-to-peer/0169.md) section 10.

### 2. Scope

2.1 This document defines one token a person creates and the behaviour of a host that shows them.

2.2 It adds no [BRC-100](../wallet/0100.md) method and changes no permission rule. A recommendation never grants, lightens or renews a permission, never changes a verdict, review or label, and never suppresses a BRC-242 threat label.

### 3. The recommendation

#### 3.1 The token

A recommendation is a one-satoshi [BRC-48](../scripts/0048.md) PushDrop output whose fields are:

| Field | Content |
| --- | --- |
| 1 | `app-recommendation` |
| 2 | `1` |
| 3 | The subject kind: `app`, `catalog` or `labels` |
| 4 | The subject: an app's normalised domain, a catalog identifier `catalog:<domain>/<local>`, or a label feed identifier `labels:<domain>/<local>` |
| 5 | The subject key, section 3.2; or empty where the subject is an app with no app key |
| 6 | The recommender's note, UTF-8, at most 280 bytes, possibly empty |
| 7 | The recommender's identity key, 33 bytes compressed |
| 8 | The outpoint spent by input 0 of the creating transaction, as ASCII: the transaction ID in lowercase hex, `.`, and the output index in decimal |
| 9 | The signature of section 3.3 |

Fields are pushed and dropped, and field 2 encoded, exactly as the encoding paragraph of [BRC-241](./0241.md) section 6.6.2 requires: the shortest data push for each field, never a small-number opcode, so field 2 is the single byte `0x31`.

The output is locked to a key the recommender's wallet derives under protocol `[2, "app recommendation"]`, key ID `1`, counterparty `self`, so that only the recommender can spend it.

3.1.1 Field 5 pins what was recommended. A user who recommended an application recommended its operator, and section 6.2 makes sure the recommendation does not pass to the next one.

3.1.2 Field 6 is the recommender's words, shown attributed to them, and is rendered as text.

3.1.3 A recommendation carries no rating or category; section 6.3 says why.

3.1.4 One transaction MAY create several recommendations. They share field 8, which is still unique to that transaction.

#### 3.2 The subject key

| Subject kind | Field 5 |
| --- | --- |
| `app` | The app key of [BRC-241](./0241.md) section 3.5, 33 bytes compressed, as the recommender's wallet observed it with a current delegation under section 3.7 of that document; or empty if the app publishes no app key |
| `catalog`, `labels` | The start of the catalog or feed under [BRC-241](./0241.md) section 6.6.2, as ASCII: the transaction ID in lowercase hex, `.`, and the output index in decimal, as the recommender's host has pinned it |

3.2.1 A catalog's or feed's start never changes and cannot be transferred: key rotations continue the same chain, and a curator who starts again has a new start.

#### 3.3 The signature

Field 9 is a signature made under [BRC-241](./0241.md) section 6.6.1, by field 7's key, with protocol ID `[2, "app recommendation"]`, key ID `1` and counterparty `anyone`, over the object `{"input", "kind", "note", "recommender", "subject", "subjectKey", "version"}`, whose members are:

| Member | Value |
| --- | --- |
| `input` | Field 8, as a string |
| `kind` | Field 3 |
| `note` | Field 6, as a string |
| `recommender` | Field 7, lowercase hex |
| `subject` | Field 4 |
| `subjectKey` | For an app, field 5 in lowercase hex, or the empty string; for a catalog or label feed, field 5 as a string |
| `version` | The integer 1 |

It is carried, as section 6.6.1 of that document requires for an output's field, as the raw DER bytes with a low S value. A verifier MUST reject one with a high S value.

#### 3.4 One per subject

A recommender has at most one current recommendation per subject. A wallet updating one MUST spend the previous output in the transaction that creates its replacement. A host that finds more than one unspent recommendation by one recommender for one subject MUST show only the one in the latest block, and among those in one block, the one latest in block order. Because a recommendation cannot be copied into a new transaction under section 4.2, a replaced recommendation cannot be posted again to override its replacement.

#### 3.5 Withdrawal

A recommendation is withdrawn by spending it, with or without a replacement. Withdrawal is final and observable: anybody can verify that the output was spent, and section 4.2 ensures that nobody can re-create it.

### 4. The overlay

4.1 Recommendations are submitted under [BRC-22](../overlays/0022.md) to topic `tm_apprecommend` and found under [BRC-24](../overlays/0024.md) through lookup service `ls_apprecommend`. As [BRC-87](../overlays/0087.md) establishes no registry, these names are claimed rather than reserved, and carry no document number.

4.2 The topic manager admits an output only if its fields parse, field 9 verifies against field 7 under section 3.3, and input 0 of the transaction that contains it spends exactly the outpoint in field 8. It retains the output until it is spent. A host that obtains a recommendation from anywhere other than a topic manager MUST apply the same three checks. The overlay is federated in the sense of [BRC-183](../overlays/0183.md).

4.3 The lookup service answers two queries: by subject kind and subject, returning every unspent recommendation of that subject; and by recommender identity key, returning every unspent recommendation by that recommender.

### 5. Whose recommendations are shown

5.1 **A host MUST show recommendations only from recommenders in the user's address book**, matched by the identity key of [BRC-169](../peer-to-peer/0169.md) section 10, and MUST NOT show any recommendation from anybody else, in any form, including as a count. A thousand recommendations from keys the user has never met cost an attacker a few cents and are worth nothing.

5.2 An address book entry whose identity key has changed under BRC-169 section 4.4 is not a match until the user has accepted the change. A recommendation from a contact's old key is that contact's only if the address book says so.

5.3 A host MAY additionally let the user choose particular people outside their address book whose recommendations they want to see, for example a reviewer they trust, provided the user chooses each one by identity key and the host shows them as chosen rather than as contacts. Everything this document says of contacts applies to chosen people.

### 6. Presentation

#### 6.1 Where, and when to look

6.1.1 A host looks up recommendations of a subject **on demand**: when the user opens an application's detail view, when the user is adding a catalog or subscribing to a label feed, or when the user asks to open an object with an application under BRC-245 and the host is finding candidates. A host MUST NOT look up recommendations for each listing in a list, browse or search view, because a lookup per listing would tell the overlay host everything the user scrolls past.

6.1.2 On a detail view, a host SHOULD show the contacts who recommend the application, by the names in the user's address book: "Recommended by Alice and Bob". It MAY show a contact's note when the user opens it.

6.1.3 A host MAY offer a view of one contact's recommendations, opened at the user's request: "Apps Alice recommends". It looks those up by that contact's identity key, at that moment.

6.1.4 A host MAY show contacts' recommendations of catalogs and label feeds when the user is adding one.

#### 6.2 When the subject has changed

6.2.1 Where field 5 differs from the subject's current key, a host follows the subject's history before deciding: for an app, the rotation chain of [BRC-241](./0241.md) section 3.6; for a catalog or label feed, nothing: its start never changes, so field 5 either equals the start the host has pinned for that identifier or names a different chain, as when a domain declares a new start under section 6.7.4 of that document, and a host keeps the two apart as section 7.2.6 of that document does. Where no accepted chain leads from field 5 to the current key, or a catalog's field 5 is not the start the host follows, the recommendation was made of a different operator. A host MUST NOT show it as current, and SHOULD show it, if at all, as "Alice recommended this app before its owner changed".

6.2.2 A recommendation of an app with an empty field 5 is shown only while the app still publishes no app key, with the date of its block, because nothing ties it to an operator. Once the app publishes an app key, a host MUST NOT show the recommendation as current, and SHOULD show it, if at all, as "Alice recommended this app before it published a key".

6.2.3 A recommendation of an application in the changed owner state of [BRC-241](./0241.md) section 7.4 MUST NOT be shown as current, and MUST NOT be offered as a reason to reconfirm its grants.

6.2.4 **A recommendation follows a move.** Where an app has moved under [BRC-241](./0241.md) section 3.8, and the new domain publishes the key in field 5 or one reached from it, a host MAY show recommendations of the old domain on the new one, and MUST show them as made under the old domain: "Alice recommended this app under its old domain, readings.example". A host looks them up by the old domain, which the move names. A move that is not valid under that section carries nothing.

#### 6.3 No scores

6.3.1 A host MUST NOT turn recommendations into a score, a rank, a star rating or a count of anybody but named contacts. Where more contacts recommend a subject than it can name, it MAY name some and say "and three others in your contacts", which is a count of people the user knows and nothing else.

6.3.2 A host MUST NOT order applications in any catalog view by recommendations. It MAY offer a separate view, chosen by the user, of what a contact recommends.

6.3.3 Names cannot be inflated from outside the user's address book, and are relative to the user by construction, which answers both objections to NIP-85's scores.

#### 6.4 What a recommendation is not

A recommendation is shown as what it is, a contact's statement that they use and vouch for something. A host MUST NOT describe a recommended application as safe, reviewed, verified or trusted on the strength of recommendations, and MUST show BRC-242 threat labels on a recommended application exactly as on any other.

### 7. Creating one

7.1 A wallet MUST NOT create a recommendation except by the user's explicit action on that subject. It MUST NOT recommend automatically on use, on pinning, or in exchange for anything the wallet offers.

7.2 Before creating one, a wallet MUST tell the user, on the same surface: that the recommendation is public, signed with their identity key and visible to anybody; that withdrawing it stops it being shown but does not erase the record that it existed; and what it will cost.

7.3 A wallet creating a recommendation of an app MUST fetch the app's manifest at that moment and use the app key it finds with a current delegation, and of a catalog or label feed MUST use the start it has pinned. A wallet that has recorded the app in the changed owner state of [BRC-241](./0241.md) section 7.4 MUST tell the user so before creating one.

7.4 A wallet SHOULD offer the user a list of their own current recommendations, each with a control to withdraw it.

### 8. Relationships

8.1 BRC-245 offers "open with" candidates from applications recommended by the user's contacts, looked up under section 6.1.1.

8.2 [BRC-242](./0242.md) labels and [BRC-241](./0241.md) reviews are unaffected by recommendations, and recommendations are unaffected by them. A contact can recommend an application a labeler has flagged, and the user sees both.

8.3 [BRC-169](../peer-to-peer/0169.md) section 10's address book is the only source of whose recommendations count, apart from the people a user chooses under section 5.3.

8.4 [BRC-241](./0241.md) section 6.6.1 supplies the signing rule, applied here under this document's own protocol ID.

### 9. Not Specified Here

9.1 **Recommendations of anything else**: handles, content, people or merchants. The token's subject kinds are closed to the three of section 3.1, and extend only by revision.

9.2 **Paid recommendations.** A recommendation made in exchange for payment is an advertisement, and no host can detect one. The protection is that only people the user chose are shown.

9.3 **Private recommendations** shared with particular contacts rather than published. They would need encryption to each recipient, and are left for a later document.

9.4 **Looking up recommendations without telling the overlay host what is looked up.** Section 6.1.1 limits what it learns; a private lookup scheme is left for a later document.

### 10. Conformance

| Condition | Required behaviour |
| --- | --- |
| Recommendation created | Only by the user's explicit action, after being told it is public and lasting |
| Output admitted or accepted | Fields parse, signature over section 3.3's object verifies, input 0 spends the outpoint in field 8 |
| Update or withdrawal | Previous output spent; a withdrawn recommendation is not shown and cannot be re-created |
| Subject key | App key with a current delegation; a catalog's or feed's start |
| Recommender not in address book or chosen | Never shown, not even as a count |
| Subject changed owner, key appeared, or start differs | Not shown as current; a valid move carries recommendations, shown as made under the old domain |
| Lookups | On demand, by subject or by one contact; never per listing; never the address book |
| Display | Names of contacts; no score, rank, order or count of strangers; threat labels shown as usual |

### 11. Surfaces that fail conformance

1. "Recommended by 1,204 people", or "Trusted by your network" in place of names.
2. A recommendation from a key the user has never met.
3. A recommendation still shown after its author spent it, because somebody copied it into another output.
4. A recommendation carried over to the new owner of a lapsed domain.
5. A wallet that recommends every app the user pins.
6. A browse view that queries the overlay for every app on the screen.

## What Is Checkable, and What Is Taken on Trust

| Fact | Who can check it | How |
| --- | --- | --- |
| A contact made a recommendation | Anybody | The signature against the identity key, and the key against the address book |
| It is the original, not a copy | Anybody | Field 8 against the creating transaction's input 0 |
| It is current | Anybody | The output is unspent |
| It was made of the current operator | A host | Field 5 against the app's current key, through its rotations, or against the catalog's start |

| Claim | Why it cannot be checked | What stands in for a check |
| --- | --- | --- |
| The contact actually uses the app | Use is not observable | That the user knows the contact and can ask |
| The recommendation was not paid for | Payment is not observable | Section 9.2 |
| The contact's wallet was not compromised | Compromise looks like the contact | BRC-169's key-change rules, and the fact that a recommendation grants nothing |
| A keyless app is still run by whoever was recommended | There is nothing to compare | Section 6.2.2 drops the recommendation once a key appears |

## What It Buys, and What It Costs

| Party | What they get | What it costs them |
| --- | --- | --- |
| User | The one kind of discovery people trust, from people they chose, that cannot be inflated by strangers | A detail view that names a few contacts, and a public record of anything they recommend |
| Recommender | A way to vouch for an app, catalog or feed that is theirs to withdraw | A transaction fee of a fraction of a cent, a satoshi held until withdrawal, and a public link between their identity key and the subject |
| App author, curator, labeler | Reach through users' own contacts, at no cost to them | Nothing, and nothing they can buy |
| Host vendor | Social discovery without running a review system | An address book match, on-demand lookups, and rotation checks |
| Overlay operator | A small, self-checking topic | Storing unspent outputs, and learning which subjects users look at |

**This will show little at first.** A user whose contacts recommend nothing sees nothing until they do. **And a recommendation is permanent in a way people do not expect**: withdrawal does not erase the transaction, which section 7.2 makes the wallet say.

## Security Considerations

**A copied recommendation cannot exist**, because section 4.2 admits one only in the transaction whose first input it names.

**A compromised contact can recommend a malicious app.** Recommendations are only as trustworthy as the wallet that signs them. The damage is bounded by the wallet's own permission prompt, which section 2.2 leaves untouched, and by BRC-242's threat labels, which a recommendation never suppresses.

**A Sybil attack has nowhere to land.** Section 5.1 shows only contacts, so creating recommendations from many new keys achieves nothing unless the user adds those keys to their address book, which is the social-engineering attack BRC-169 already addresses.

**A recommendation does not follow a domain.** Field 5 binds it to the app's key or the catalog's start, so the attack in which a lapsed domain inherits its predecessor's reputation does not reach recommendations. An app with no key has no binding until one appears, and section 6.2.2 then drops its recommendations.

**Spam costs the overlay.** Anybody can fill the topic with recommendations of anything, and none of them reaches a user who has not put the author in their address book.

## Privacy Considerations

**A recommendation is a public, permanent record linking a person's identity key to an application.** Section 7.2 requires the user to be told so before they create one.

**What the overlay host learns.** A lookup by subject tells it that somebody is looking at that application, catalog or feed, at about the moment they open it; a lookup by recommender, interest in that person. Section 6.1.1 confines lookups to moments the user chose. A host MUST NOT send the user's address book, or any list of contacts, to a lookup service, and MAY run or choose its own overlay host to keep both queries local.

**Field 8 reveals nothing new.** The outpoint input 0 spends is already public in the transaction that carries the recommendation.

## Implementations

No host implements this document. The token is an ordinary PushDrop output and can be created and spent with `@bsv/sdk` and any BRC-100 wallet; the wallet chooses which of its outputs to spend as input 0 and signs the outpoint before it builds the PushDrop. The overlay can be deployed with existing overlay tooling; its topic manager checks field 8 against the transaction it is already given.

### Conformance levels

**Recommender's wallet.** Creates, updates and withdraws recommendations only on the user's action, after the disclosure of section 7.2, with field 8 naming the outpoint its input 0 spends.

**Overlay operator.** Admits only outputs that pass the three checks of section 4.2, and stops returning them when spent.

**Host.** Meets every row of section 10's table.

**Verification.** Field 9 is a BRC-3 signature over canonical JSON, checkable with any implementation of both, and field 8 is checked against the transaction itself. Everything else is behaviour against section 10's table.

## Failure Modes

| What went wrong | How it shows | Detected by | Attributable to |
| --- | --- | --- | --- |
| A contact's wallet was compromised and recommended a drainer | "Recommended by Alice" on a malicious app; threat labels still shown; prompts still asked | The contact, labelers, the user | The compromised wallet's owner |
| App's domain changed hands, new key | Old recommendations shown as made before the owner changed | The host, by key comparison | Nobody. This is the system working |
| Keyless app changed hands | Old recommendations shown as current until a key appears | Nobody, until then | The app, which published no key |
| Catalog lost its keys and started again under a new start | Old recommendations do not carry over | The host | The curator |
| Overlay host withholds a recommendation | A contact's recommendation missing | The contact, if they look | The overlay host; another host shows it |
| Overlay host serves a spent recommendation | Shown until the host checks spent status | Anybody, against the chain | The overlay host |

## Appendix A: Worked Example

Illustrative. People and domains are invented; no keys or signatures are printed because this document prints none it cannot reproduce.

**Creating.** Alice recommends `readings.example`. Her wallet fetches the app's manifest, finds its app key with a current delegation, and tells her the recommendation is public, signed with her identity key, and survives withdrawal as a record, for less than a cent. She writes "Use it for every field walk" and confirms. The wallet picks one of its outputs to spend as input 0, signs section 3.3's object naming that outpoint, builds the PushDrop and submits it to `tm_apprecommend`, which checks the fields, the signature and input 0, and admits it.

**Seeing it.** Bob has Alice in his address book. Browsing a catalog, his host queries nothing. When he opens `readings.example`'s details, it looks up that subject's recommendations, discards every one not from his address book, checks field 5 against the app's key, and shows "Recommended by Alice".

**A copy.** Mallory copies Alice's fields into her own output. Its input 0 is not the outpoint in field 8, and the topic manager refuses it.

**A change of owner.** In March `readings.example` is re-registered and its new owner publishes a new app key with no rotation. Bob's host shows "Alice recommended this app before its owner changed".

**A move.** Had the app instead moved to `fieldreadings.example` under BRC-241 section 3.8, with the same key, Bob's host would show "Alice recommended this app under its old domain, readings.example".
