# BRC-245: Opening What a Wallet Holds with Connected Apps

Crumbs

## Abstract

A [BRC-100](../wallet/0100.md) wallet holds things that are more useful opened in an application than shown as rows: a collectible in a basket, a membership certificate, a room identifier, a signing envelope. This document lets a connected app, as defined in [BRC-241](./0241.md), declare which kinds of object it opens, and lets a wallet offer "open with".

An app declares **handlers** in `metanet.app.handles`: a match on a basket, a certificate type or an identifier scheme, and a same-origin URL template. A wallet offers handlers only from apps the user already has a reason to trust: apps the user has pinned, apps listed in a catalog the user has enabled, and apps recommended under [BRC-243](./0243.md) by somebody in the user's address book. It opens an object only on the user's action or a default the user chose, and passes the app only the values its template names, never anything [BRC-116](../wallet/0116.md) would gate. **Being chosen to open something grants nothing.**

## Motivation

A wallet can show a collectible's outpoint and basket, but what it is and what can be done with it is known to the application that made it. Today a user must know which application to visit and find the object in it.

Nostr's NIP-89 lets an application publish which event kinds it handles, with URL templates, and records the lesson: handler records gathered from anybody invite malicious handlers. It answers with recommendations from people the user follows.

This document applies both halves to what a BRC-100 wallet holds. The declaration is the app's own, under BRC-241's rule that the app describes itself. The choice of whose declarations to offer is the user's, through what they have already pinned, enabled or been recommended.

### Why it is a separate document

It was split out of BRC-241 because it is optional for every party and carries its own privacy question: which values reach the app.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

### 1. Terminology

- **Object**: something a wallet holds that a handler can match: an output in a basket, a certificate, or an identifier.
- **Handler**: an app's declaration that it opens objects of one kind. Section 3.
- **Candidate**: an app whose handler matches an object and which section 4.2 allows a wallet to offer.
- **Default**: a handler the user has chosen to open every object of one kind without being asked. Section 4.4.

### 2. Scope

2.1 This document defines one field of `metanet.app` and how a wallet, or a host bound to it, offers to open an object with a connected app.

2.2 It adds no [BRC-100](../wallet/0100.md) method and changes no permission rule. It requires [BRC-241](./0241.md)'s app description and does not require catalogs, labels or recommendations, though section 4.2 uses them where present.

### 3. Handlers

An app declares handlers in `metanet.app.handles`, an array of up to sixteen.

```json
"handles": [
  { "match": "basket", "value": "collectibles", "url": "/item/{outpoint}" },
  { "match": "certificate", "value": "Jsnn82gKqqpWg++XYXCykap1FbiJ/ZMloZQizdER1pw=", "url": "/member?type={type}" },
  { "match": "scheme", "value": "room", "url": "/room/{id}" }
]
```

The certificate type above is the base64 SHA-256 of the ASCII string `lattice membership v1`, as in BRC-241 section 4.

| `match` | `value` | Matches | Placeholders |
| --- | --- | --- | --- |
| `basket` | A [BRC-46](../wallet/0046.md) basket name | An output the wallet holds in that basket | `{outpoint}`, `{txid}`, `{vout}` |
| `certificate` | A [BRC-52](../peer-to-peer/0052.md) certificate type, base64 | A certificate of that type the wallet holds | `{type}` |
| `scheme` | A lowercase identifier scheme, without its colon | An identifier of the form `<scheme>:...` the wallet holds, such as a [BRC-190](./0190.md) `room:` identifier | `{id}`, the whole identifier |

#### 3.1 Values

3.1.1 `{txid}` is the transaction ID in lowercase hex, `{vout}` the output index in decimal, and `{outpoint}` the two joined as `<txid>.<vout>`.

3.1.2 `{type}` is the certificate type as the wallet holds it, in base64.

3.1.3 `{id}` is the identifier exactly as the wallet holds it, scheme included.

#### 3.2 The URL template

3.2.1 `url` is a path on the application's own origin, beginning with `/`, optionally with a query. Placeholders are expanded under RFC 6570 simple string expansion, which percent-encodes reserved characters.

3.2.2 A wallet MUST resolve the expanded URL against the app's origin and MUST ignore a handler whose result is not on that origin. An app opens objects on its own domain or not at all, so that the domain a user sees in "open with" is the domain that receives the object.

3.2.3 A wallet MUST NOT expand a placeholder the table does not list for that `match`, MUST NOT expand one the template does not contain, and MUST NOT add any other data to the URL.

#### 3.3 What a handler learns

3.3.1 Opening an object discloses to the app exactly the placeholder values its template names. For a basket, that is where the output is on chain; for a certificate, only its type; for an identifier, the identifier.

3.3.2 **A certificate's serial number and certifier are never placeholders.** Both are what BRC-116 certificate access exists to gate, and an app that needs them asks under BRC-116.

3.3.3 An outpoint is public on chain, but disclosing it links the user's session with the app to an output the user holds. A wallet MUST show, before the first open of each kind with each app, which value will be sent.

#### 3.4 Rules

3.4.1 **Being chosen to open something grants nothing.** The handler receives the values in its URL. To read the output's contents, prove the certificate or act on the room, it asks under [BRC-116](../wallet/0116.md) like any other application, and the user answers like any other prompt.

3.4.2 A basket, type or scheme an application names does not become its own. Any number of applications may handle the same one, and section 4 says how a wallet chooses among them.

3.4.3 `match` values are closed. A wallet MUST ignore a handler whose `match` it does not recognise. A future specification MAY define another at a reserved dispatch point in the manner of [BRC-241](./0241.md) section 8.2: the value `p `, a space-free scheme identifier, and the scheme-defined remainder.

3.4.4 A handler is the app's statement about itself, under BRC-241's rule that the app describes itself. A catalog cannot add, remove or alter one.

3.4.5 **One handler per kind per app.** Where an app declares two handlers with the same `match` and `value`, the first is its handler for that kind and a wallet ignores the rest, as [BRC-241](./0241.md) section 4.3.4 treats a duplicated requirement.

### 4. Open with

#### 4.1 Offering

4.1.1 A wallet MAY offer to open an object it holds with an application that declares a matching handler. A host bound to the wallet MAY offer the same, under the same rules.

#### 4.2 Whose handlers

4.2.1 **Handlers come only from applications the user already has a reason to trust.** A wallet MUST NOT offer a handler from any application that is not:

1. pinned by the user, under [BRC-241](./0241.md);
2. listed in a catalog the user has enabled, under BRC-241; or
3. recommended under [BRC-243](./0243.md) by somebody in the user's address book under [BRC-169](../peer-to-peer/0169.md) section 10, where the recommendation is current under BRC-243.

4.2.2 An "open with" menu filled by whoever registered a basket name first is a phishing surface; under section 4.2.1 a stranger's handler is never offered.

4.2.3 **Recommendations are looked up on demand.** A wallet MUST NOT look up recommendations by sending the user's address book or any list of contacts to an overlay host. An app that is neither pinned nor listed becomes a candidate through a recommendation only if the wallet already holds that recommendation, found by an earlier lookup by that app, such as when the user opened the app's details. When the user invokes "open with", a wallet MAY look up recommendations for candidates it already has, by each app, to show who recommended them.

4.2.4 A wallet MUST NOT offer a handler from an app in BRC-241's changed owner state, under section 7.4 of that document, until the user has reconfirmed the app.

4.2.4.1 A wallet MAY offer a handler from an app in BRC-241's unproven state, under section 7.4.2 of that document, and MUST mark it as unproven beside its domain. An app that has not proven itself today may still be run by its original operator, and being chosen grants it nothing it would not have to ask for.

4.2.5 A wallet SHOULD check a candidate's manifest before offering it, and MUST check it before opening an object with it, under the rules for a first open in BRC-241 section 6.3.6.

#### 4.3 Presenting and ordering

4.3.1 A wallet MUST show each offered handler with the app's name and its domain, under BRC-241 section 3.3.

4.3.2 Where several handlers match, a wallet orders them by whether the user has pinned the application, then by name. It MUST NOT order them by any payment, and MUST NOT present one as recommended by the wallet on the strength of a payment.

4.3.3 A wallet SHOULD show, for a handler offered because of a recommendation, who recommended it, by the name the user gave them, as BRC-243 provides.

4.3.4 **Two handlers, one name.** Where two offered handlers come from apps whose names share a skeleton under [BRC-241](./0241.md) section 7.5.1 and are not one operator's, the wallet shows each with its domain given equal prominence to its name, as section 7.5.5 of that document requires in any view, and never collapses them into one entry.

#### 4.4 Opening and defaults

4.4.1 A wallet MUST NOT open an object with any handler without the user's action, unless the user has chosen that handler as the default for its `match` and `value`.

4.4.2 A default is the user's choice, made on the "open with" surface, and is shown and removable wherever defaults are managed.

4.4.3 A default is cleared when its application enters BRC-241's changed owner state, when its application stops declaring the handler, or when the reason it could be offered under section 4.2.1 lapses. An application that is merely unproven under BRC-241 section 7.4.2, for whatever reason, keeps its default; being chosen to open something grants it nothing.

4.4.4 Opening an object with a default still applies section 3.3.3 the first time.

4.4.5 **A default and a move.** Where the default's application moves under [BRC-241](./0241.md) section 3.8, the default does not move by itself. A wallet that finds a valid move MAY ask the user, once, whether to make the new domain's matching handler the default; until the user agrees, the default is cleared.

### 5. Relationships

5.1 [BRC-241](./0241.md) defines connected apps, `metanet.app`, pins, catalogs and the changed-owner state this document relies on. Its section 4 lists `handles` as defined here.

5.2 [BRC-243](./0243.md) defines the recommendations of section 4.2.1 item 3.

5.3 [BRC-116](../wallet/0116.md) is unchanged. Every permission a handler needs is asked for under it.

### 6. Conformance

| Condition | Required behaviour |
| --- | --- |
| App declares a handler | `metanet.app.handles`, closed `match` value, same-origin URL template |
| Certificate handler | `{type}` only; serial number and certifier asked for under BRC-116 |
| Wallet offers "open with" | Only pinned, listed or contact-recommended apps; name and domain shown |
| Recommendation used | Looked up by candidate app on demand; address book never sent |
| App in changed owner state | Not offered; its defaults cleared |
| App in unproven state | Offered, marked unproven; default kept |
| Same `match` and `value` declared twice | First used; rest ignored |
| Two offered apps share a name | Each with its domain given equal prominence |
| Default's app moves | Default cleared until the user moves it |
| Several handlers | Pinned first, then by name; never by payment |
| Opening | User's action or the user's default; listed values only; first disclosure shown |
| Handler chosen | Nothing granted |

### 7. Surfaces that fail conformance

1. An "Open with" menu listing an app nobody the user knows recommends, no enabled catalog lists and the user never pinned.
2. A collectible opened automatically in an app that registered the basket name first.
3. A membership card opened at `/member/` followed by its serial number.
4. A handler that opens an object at another domain from the one shown.
5. "Sponsored" first in the "open with" list.
6. A wallet that sends its user's contact list to an overlay to find out which handlers their friends recommend.

## What Is Checkable, and What Is Taken on Trust

| Fact | Who can check it | How |
| --- | --- | --- |
| The handler opens on the app's own domain | The wallet | Resolving the template against the origin |
| What the app was told | The user | The values shown at first open |
| Why a handler was offered | The user | Pin, catalog or the name of the recommender shown |
| Opening granted nothing | Anybody | Watch for the BRC-116 prompt when the app reads the object |

| Claim | Why it cannot be checked | What stands in for a check |
| --- | --- | --- |
| The handler displays the object faithfully | It is the app's code | The app's catalog reviews, and BRC-242 labels where implemented |
| The handler does not misuse the outpoint | It is public data in the app's hands | Section 3.3.3 tells the user before the first disclosure |

## What It Buys, and What It Costs

| Party | What they get | What it costs them |
| --- | --- | --- |
| User | What they hold, opened where it means something, in one step | Choosing a handler, or a default, once per kind |
| App author | Users arriving at the right object | A few lines of manifest |
| Wallet vendor | A reason for objects in its vault to be more than rows | Matching, filtering by trust, and a default store |

## Security Considerations

**The handler list is a phishing surface.** An app that claims a popular basket is the first thing an attacker would publish. Section 4.2 confines the list to apps the user already has a reason to trust, so an attacker must first get pinned, listed or recommended by a contact, and each of those leaves a name attached.

**A handler gets nothing it could not ask for.** The values in its URL are public or are the kind of thing the user is choosing to share; everything else goes through BRC-116.

## Privacy Considerations

**Opening discloses a holding.** An outpoint links the user's session to an output; a certificate type tells the app the user holds one. Section 3.3 limits what is sent to the values the template names, and shows them before the first open of each kind.

**Recommendation lookups disclose interest in an app.** A lookup by candidate app tells the overlay host that somebody considered opening something with that app. Sending the address book would tell it who the user knows, and section 4.2.3 forbids it.

**The set of defaults is a profile** of what the user holds and which apps they use, and a wallet MUST NOT disclose it to any app or curator.

## Implementations

No wallet implements this document.

Harbor's Vault lists outputs by basket and is the natural place for "open with". A wallet that already reads app manifests under BRC-116 has the handler declarations of every app it has met.

## Failure Modes

| What went wrong | How it shows | Detected by | Attributable to |
| --- | --- | --- | --- |
| Stranger declares a popular basket | Not offered | Nobody needs to | Nobody. This is the system working |
| Listed app's handler misdisplays an object | User sees a wrong rendering | The user | The app; its curators |
| Contact recommends a bad handler | Offered, with the contact's name | The user | The contact |
| App changes owner | Not offered; default cleared | The wallet | The former operator |

## Appendix A: Worked Example

Illustrative. Harbor and Lattice are codenames, and every domain is invented.

A user's wallet holds an output in the `collectibles` basket. Two pinned apps, `gallery.example` and `frames.example`, declare a handler for that basket, and a third, `tokens.example`, listed in a catalog the user has enabled, does too. A fourth, `free-nfts.example`, declares the same handler; no catalog the user enabled lists it, the user never pinned it, and nobody in their address book recommends it.

The user opens the output in the wallet's Vault and chooses "Open with". The wallet offers three: `gallery.example` and `frames.example` first, as pinned, then `tokens.example`, each with its domain. `free-nfts.example` is not offered.

The user chooses `gallery.example`; the wallet says, the first time, that the app will be told which output this is, and opens `https://gallery.example/item/` followed by the outpoint. Reading the output's fields meets an ordinary BRC-116 basket prompt. The user ticks "Always open collectibles with Gallery".

The user also holds a Lattice membership certificate. `directory.example` declares a handler for its type and is recommended by Bob, who is in the user's address book. The user had opened `directory.example`'s details the week before, when the wallet looked up its recommendations and found Bob's. When the user chooses "Open with", the wallet offers it as "Recommended by Bob". It opens `/member?type=` followed by the type, and the directory asks under BRC-116 to see the certificate's fields.

In June `gallery.example` lapses and is re-registered. The new owner cannot answer the possession check, so the app is unproven and its default is kept; when the new owner then publishes an app key of its own, the app enters the changed owner state. The default for collectibles is cleared, and the next "Open with" offers the remaining two.
