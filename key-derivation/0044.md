# BRC-44: Admin-reserved and Prohibited Key Derivation Protocols

Ty Everett (ty@projectbabbage.com)

## Abstract

We define a set of reserved protocol namespaces that can be employed by clients utilizing the [BRC-43](../key-derivation/0043.md) invoice numbering scheme to be set aside for administrative and internal use by the client software itself. This enables client software to manage its own internal state without the risk that application software will utilize the same internal protocols.

## Motivation

[BRC-43](../key-derivation/0043.md)<sup>[1](#footnote-1)</sup> defines an open-ended way to create protocols and systems of interaction within a [BRC-42](../key-derivation/0042.md)<sup>[2](#footnote-2)</sup> key derivation architecture. However, client software implementing the [BRC-43](../key-derivation/0043.md)<sup>[1](#footnote-1)</sup> invoice numbering scheme needs a way to manage its own internal state, encrypt data and perform administrative tasks like permissions management without interference from applications.

This specification distinguishes fully internal namespaces from payment namespaces with operation-specific restrictions. Public derivation can remain available while private-key operations remain internal.

## Specification

The uppercase terms MUST, MUST NOT, SHOULD and MAY indicate normative
requirements for implementations adopting this specification.

### Fully internal namespaces

Any protocol ID that starts with `admin` is reserved for administrative and
internal use, regardless of security level. Wallets MUST reject application
requests involving these protocols. This rule is unchanged.

### BRC-29 payment namespace

The exact normalized protocol name `3241645161d8` is reserved for
wallet-internal private-key operations, regardless of security level. It is
an operation-specific reservation, not an `admin` prefix alias. Its
[BRC-29](../payments/0029.md) derivation remains unchanged.

| Application operation | Rule in `3241645161d8` |
| --- | --- |
| `getPublicKey` | Permitted subject to ordinary derivation permissions, including `self`, `anyone` and public-key counterparties. |
| `verifySignature` | Permitted subject to ordinary verification permissions. |
| `createSignature` | MUST reject both `data` and `hashToDirectlySign` requests. |
| `encrypt`, `decrypt`, `createHmac`, `verifyHmac` | MUST reject. |
| `revealSpecificKeyLinkage` | MUST reject requests for this protocol. |
| `revealCounterpartyKeyLinkage` | MUST reject disclosure of a root linkage that covers protected payment keys for that counterparty pair. |

A root linkage is not limited to the protocol named in another request.
[BRC-69](./0069.md) disclosure must therefore be evaluated for its full
scope. Wallets MUST NOT release protected payment derivation secrets through
an auxiliary method, another module, or a renamed protocol.

The wallet MUST enforce these restrictions before ordinary protocol grants
or policy defaults can authorize the operation. `privileged: true`, an
existing grant and `seekPermission: false` MUST NOT bypass them. Applications
cannot become wallet-internal callers by choosing an originator string.

Trusted wallet transaction signing remains available via [BRC-100](../wallet/0100.md)
`createAction` and `signAction`, with normal spending authorization. Payment
receipt via `internalizeAction` remains available. The wallet MUST NOT rename
existing payment keys or require senders to derive a different invoice.

### Other asset keys and alternative modules

Wallet designers SHOULD isolate balance and asset signing from ordinary
application data signing. A permission to sign opaque data is not a
transaction spending permission. [BRC-207](../wallet/0207.md) proposes a
transaction-context module in a separate [BRC-98](../wallet/0098.md) key domain;
its module authorization is mandatory even when generic protocol-signing
prompts are disabled.

This revision does not reserve every asset protocol, allocate an ordinal
namespace, or define a runtime protected-protocol registry. Additional
reservations and their migration contracts require public specification and
review. The module proposal's open questions distinguish these possible
extensions from the BRC-29 rule above.

## Compatibility and migration

This draft adds an application-operation restriction to an existing payment
namespace; it is a behavioral change for applications that used it for
arbitrary signatures or other private-key operations. It preserves payment
key derivation, public verification and the transaction interface. Such
applications MUST move new data signatures to a domain not used for spendable
assets, or adopt an appropriate transaction module for asset signing.
Existing assets and historic signatures do not change keys merely because a
wallet updates its policy. See BRC-207's migration and recovery requirements.
Wallets SHOULD publish release notes and establish replacement support before
applications mint new assets. A raw-signing compatibility window is not a
conforming migration mechanism.
