# BRC-236: Paymail Public Profile Registration

Deggen (deggen@kschw.com)

## Abstract

[BRC-235](./0235.md) lets anyone look up the identity key behind `handle@domain`, and the handle behind an identity key, from self-signed profile certificates that a Paymail host serves. It leaves out how a profile reaches the host. This document fills that gap with two more Paymail capabilities. **Public profile registration** (`eb3df9208b8e`) accepts a profile certificate with `PUT` to register, update or release a handle. **Public profile availability** (`5854609359e2`) is optional and advisory: it says whether a handle can be registered and, if not, which rule refuses it.

The certificate is the authorisation. The holder signs it, and it names the handle and the domain, so registration needs no account, session or password. Any wallet that can sign a BRC-235 profile can register at any host that advertises this capability. Pricing, reserved names, how similar two handles may be, cooldown length and lost-key recovery stay host policy. A host that refuses names the rule it applied with a fixed code.

## Motivation

A domain-scoped name is only as portable as the way you get one. If every host has its own sign-up flow, a wallet has to be written for each host, and users can only pick from the hosts their wallet already knows. That is the silo BRC-235 exists to avoid on the read side.

The holder already has what a host needs to accept a registration: a signing key and the ability to produce a BRC-235 profile. A signed statement "key K takes `alice@example.com`, as of time T" authenticates itself, and only K could have made it. The host checks it, applies its own policy, and stores it. Advertising the endpoint in `.well-known/bsvalias` lets a wallet find it at any domain the same way it finds lookup.

This is a separate document from BRC-235 because the two are deployed separately. Many hosts will fill their directory from their own on-boarding and never accept registrations from outside wallets. Those hosts can implement BRC-235 alone. Registration also carries the replay, release and policy rules that a read-only directory never needs.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY are to be interpreted as described in RFC 2119. Terms are as in BRC-235, section 1. **Profile certificate** means a certificate that follows BRC-235, section 5.

### 1. Capability identifiers

Both identifiers are BRFC ids, computed as in BRC-235, section 2.

```yaml
brfcid: eb3df9208b8e
title: public profile registration
author: Deggen
version: v1.0.0
```

```yaml
brfcid: 5854609359e2
title: public profile availability
author: Deggen
version: v1.0.0
```

### 2. Discovery

Discovery is BRC-235, section 3, with one difference. Client rule 3 there requires a placeholder in the capability's URL. That rule applies to availability, whose placeholder is `{handle}`. Registration has no placeholder: its value is an absolute `https://` URL that the client uses as it stands.

A host that advertises registration MUST also advertise BRC-235 reverse lookup (`43dcf83ddc5f`) for the same domain. It SHOULD also advertise BRC-235 lookup, so that a registered profile can be found. A complete document:

```json
{
  "bsvalias": "1.0",
  "capabilities": {
    "0ace65da5987": "https://paymail.example.com/api/handle/{query}",
    "43dcf83ddc5f": "https://paymail.example.com/api/identityKey/{pubkey}",
    "eb3df9208b8e": "https://paymail.example.com/api/handle",
    "5854609359e2": "https://paymail.example.com/api/handle/available/{handle}"
  }
}
```

Paths are the host's choice.

### 3. Request

The client sends `PUT` to the registration URL with `Content-Type: application/json`. The body is one of:

1. a profile certificate, as a JSON object; or
2. an envelope: a JSON object with a `certificate` member that holds the profile certificate, and other members that the host defines (a payment, for example; see section 7).

A host tells the two forms apart by the presence of a `certificate` member. A host MUST accept both forms, and MUST ignore envelope members it does not define. A client SHOULD send the bare form unless the host has asked for something more (section 7).

Registration needs no other authentication. A host MUST NOT require a session, login or [BRC-103](../peer-to-peer/0103.md) handshake for the bare form, and SHOULD rate-limit by client.

### 4. What the host checks

Before it looks at any stored state, the host MUST check that:

1. the certificate meets rules 1 to 7 of BRC-235, section 5, signature included;
2. `fields.paymail` is `handle@domain`, all lowercase, where `domain` is one the host serves and advertises this capability for;
3. `fields.issuedAt` is no further ahead of the host's clock than a bound the host chooses. The bound MUST NOT be more than one hour, and five minutes is RECOMMENDED.

When the certificate is not released (`fields.released` is not `"true"`), the host MUST also check that the handle meets the syntax of BRC-235, section 4, and is not on the host's reserved list. These two checks apply only to claims. They MUST NOT stop a holder from releasing a handle that was valid when it was claimed, for example after the reserved list grows.

The host MAY store and serve the certificate re-serialized. The BRC-52 signature covers the certificate's binary form, not its JSON text, so a re-serialized certificate still verifies.

### 5. Outcomes

Each handle has at most one **holder** at a time: the `subject` of its stored profile. Each identity key holds at most one handle at a host. The host keeps, for every handle it has ever stored, the highest `issuedAt` it has accepted for it. That value survives release.

For an accepted certificate the host MUST apply the first row of this table that matches. Every row after the first also requires that `issuedAt` is strictly later than the stored value. A certificate that fails that is stale (section 6).

| Situation | Certificate | Effect | Status |
|---|---|---|---|
| Same document as the stored one (same `serialNumber`, `issuedAt` and content) | either | Nothing changes. | `200` |
| No record of the handle | not released | **Register**: the key becomes the holder. | `201` |
| Handle held by the same key | not released, fresh `serialNumber` | **Update**: the new profile replaces the stored one. | `200` |
| Handle held by the same key | released, fresh `serialNumber` | **Release**: the handle has no holder; the host serves it from neither BRC-235 capability. | `200` |
| Handle released, cooldown over or never set | not released | **Reclaim** by any key. | `201` |
| Handle released by its holder, inside the cooldown | not released, `subject` is the key that released it | **Reclaim** by the former holder. | `201` |

Retrying a request whose response was lost MUST be safe. The first row exists for that, and it covers a tombstone the host already stored as well as a live profile.

A key that holds a handle and wants a different one MUST release the first. A claim of a second handle is refused (`ERR_KEY_HAS_HANDLE`).

**Success body.** On `200` or `201`, the host returns the certificate it stored, exactly as it will serve it. The client SHOULD check that it has the `serialNumber` the client sent.

**Cooldown.** After a release, a host MAY bar other keys from the handle, and from handles confusable with it, for a period the host chooses. The former holder MAY reclaim during that period. A release that the host itself carries out, for lost-key recovery for example, is host policy. It need not allow the former key to reclaim.

**Confusables.** A host SHOULD refuse a claim whose handle is confusable with one already held, or still in cooldown, under a skeleton such as the one in BRC-235, section 4.

### 6. Errors

An error is a non-2xx status with a JSON object body whose `code` member is one of the codes below. The body MAY carry other members, such as a human-readable `description`. A client MUST act on `status` and `code`, and MUST NOT parse `description`.

| Status | `code` | Meaning |
|---|---|---|
| `400` | `ERR_INVALID_CERTIFICATE` | Section 4 rules 1 or 3 failed, or the body is not a certificate. |
| `400` | `ERR_WRONG_DOMAIN` | `fields.paymail` is at a domain this host does not serve. |
| `400` | `ERR_INVALID_HANDLE` | The handle fails the syntax of BRC-235, section 4. |
| `402` | `ERR_PURCHASE_REQUIRED` | This handle costs something, and no payment came with the request (section 7). |
| `404` | `ERR_HANDLE_NOT_FOUND` | A release of a handle that has no holder. |
| `409` | `ERR_HANDLE_TAKEN` | Another key holds the handle. This includes a release whose `subject` is not the holder. |
| `409` | `ERR_HANDLE_TOO_SIMILAR` | The handle is confusable with one held or in cooldown. |
| `409` | `ERR_HANDLE_RESERVED` | The host reserves this handle. |
| `409` | `ERR_KEY_HAS_HANDLE` | The key already holds another handle here. |
| `409` | `ERR_HANDLE_COOLDOWN` | The handle was released recently and is barred to this key. |
| `409` | `ERR_STALE_CERTIFICATE` | `issuedAt` is not later than the stored value, or the stored `serialNumber` is reused with a different document. |
| `413` | `ERR_BODY_TOO_LARGE` | The body is larger than the host accepts. That limit MUST be at least 16384 bytes for the bare form. |
| `429` | any | Rate limited. |
| `5xx` | any | Host failure. The request may be retried unchanged. |

A host MAY use other codes for refusals that come from its own extensions (section 7), with statuses from the same classes. A client that meets a code it does not know MUST treat the request as refused and SHOULD show the description, if there is one.

On `ERR_STALE_CERTIFICATE`, a client that is updating its own handle SHOULD fetch its current profile by reverse lookup, then sign again with a fresh serial and an `issuedAt` later than that profile's.

### 7. Host policy

The following are the host's to decide. This document requires only that a refusal under any of them uses the matching code from section 6, or a code of the host's own:

- Price. A host MAY charge for some handles, for example by length. When a claim needs payment and none was sent, the host answers `402 ERR_PURCHASE_REQUIRED`. How payment travels, as envelope members or by another route, is a host extension and is outside this document. An update or release of a handle the key already holds SHOULD NOT need a new payment.
- The reserved list, and any minimum handle length above BRC-235's.
- The confusable skeleton, and whether it applies across cooldowns.
- The length of the cooldown.
- Recovery after a holder loses its key, and other releases by the host. A host that offers recovery SHOULD say how it decides who to give the handle to.

### 8. Public profile availability (`5854609359e2`)

**Request.** The client replaces `{handle}` with the URL-encoded, lowercase handle and performs `GET`.

**Response.** `200` with:

```json
{ "available": false, "reason": "taken" }
```

`reason` is absent when `available` is `true`. Otherwise it is one of:

| `reason` | Refusal it predicts |
|---|---|
| `invalid` | `ERR_INVALID_HANDLE` |
| `reserved` | `ERR_HANDLE_RESERVED` |
| `taken` | `ERR_HANDLE_TAKEN` |
| `too_similar` | `ERR_HANDLE_TOO_SIMILAR` |
| `cooldown` | `ERR_HANDLE_COOLDOWN` |
| `stale` | `ERR_STALE_CERTIFICATE`: the stored `issuedAt` of a released handle is not yet in the past, so a certificate dated now cannot claim it. |

The answer does not depend on who asks. It cannot say whether the former holder may reclaim during a cooldown, nor whether a claim needs payment. It is advisory: another claim can arrive between the check and the `PUT`, and the `PUT` decides. A client MUST NOT treat `available: true` as a reservation.

### 9. Client procedure

To register `handle` at `domain`:

1. Discover the host (section 2). Optionally check availability (section 8).
2. Sign a profile certificate (BRC-235, section 5) with the identity key that will hold the handle. Use a fresh 32-byte random serial, `fields.paymail` = `handle@domain` in lowercase, and `fields.issuedAt` = the current time.
3. `PUT` it (section 3).
4. On `201` or `200`, verify the returned certificate as in BRC-235, section 8, and check its `serialNumber`. On an error, act on `code` (section 6).

To update, the client follows the same steps with a fresh serial and an `issuedAt` later than the current profile's. To release, it adds `fields.released = "true"`. A client SHOULD keep the fields it has no reason to change.

## Security Considerations

**The host cannot claim for a key.** A claim carries a signature by the key it claims for. A third party that obtains a holder's fresh certificate, by intercepting or replaying it, can only register exactly what the holder signed, for the holder. A host can register a handle to a key of its own, as BRC-235 already notes; this document does not change that.

**Replays.** A certificate already stored is accepted again as a no-op. An older certificate is stale. After a release, the release's `issuedAt` is stored and survives, so neither the old profile nor any certificate signed before the release can bring the handle back. A certificate for `@example.com` names that domain, so a different host cannot accept it (`ERR_WRONG_DOMAIN`), and lookups of other domains will not return it (BRC-235, section 8).

**Why the clock bound is a MUST.** `issuedAt` decides every later contest for a handle. If a host accepted a certificate dated far in the future, no other certificate could be later than it. The handle would be frozen, and so would every handle confusable with it, for all keys, its holder included, until that date. A short bound limits the damage to that window and costs an honest client with a fast clock no more than a retry.

**Squatting and look-alikes.** Free, unauthenticated registration lets anyone claim names first. Prices, reserved lists, confusable checks and rate limits are how a host answers that, and section 7 leaves them to it. Clients still rely on BRC-235's exact-match and key-pinning rules, not on a host's registration policy, to avoid paying the wrong key.

**Privacy.** Registering links an identity key to a public name at that domain, from then on. A holder who wants separate contexts SHOULD register separate identity keys (BRC-235, Security Considerations).

**Resource bounds.** Section 4's checks need no stored state, and include one signature verification. A host SHOULD run them before reading storage, and SHOULD bound the body size before parsing.

- [go-message-box-server](https://github.com/bsv-blockchain/go-message-box-server) implements this behaviour at `PUT /api/handle` and `GET /api/handle/available/{handle}` (`pkg/handlers/lookup.go`), including a paid-handle envelope (`{certificate, purchase}`, for app-store subscriptions). It does not yet advertise these two capabilities in its `.well-known/bsvalias`.
