# BRC-175: 1Color Offline Peer-to-Peer Payments

Deggen (d.kellenschwiler@bsvassociation.org)

## Abstract

This BRC specifies how one wallet pays [1Color (BRC-162)](../tokens/0162.md) tokens to another wallet when either party, or both, may be offline. The payer hands the payee one **payment bundle**: a signed transaction, the data the payee needs to recognize its output, and enough evidence to show that every token the payer spends traces back to outputs an overlay has already admitted. The payee checks the bundle without any network access, credits the payment, and settles it with the overlay later.

The evidence is an **admission attestation**: an overlay operator's signature over the outputs it admitted. The payee walks back through the transaction graph until every token input ends at an attested output. It applies the asset's declared BRC-207 trust mode: personal trusted entities by default, or a declared fixed identity.

Offline acceptance carries counterparty risk: the payer could spend the same input twice before the payee settles. This BRC states that risk and, for regulated assets, how it is contained. For assets with the required ownership-disclosure and identity-registration companion profile, the overlay records owners, permitting the attribution described below even when sender blinding is used. The default attestation profile alone makes no personal-identity claim.

The bundle has one binary encoding. Bindings are given for a nearby session (QR pairing, sealed frame, air-gap QR) and for a [BRC-33](../peer-to-peer/0033.md) message box.

## Motivation

A token payment today is accepted when its overlay admits it. That needs a network connection at the moment of payment. Many real payments happen without one: in a shop with poor signal, between two phones on a train, at a market stall. A stablecoin that only works online is a weaker substitute for cash.

The rules needed to accept a payment offline safely are subtle. The payee must know which ancestors to check, what signature stands in for the overlay, whose signature to believe, what to do when settlement later fails, and why it is reasonable to take the risk at all. Until now these rules existed only in one wallet's source code. This document states them so that other wallets, overlays and issuers can interoperate.

[BRC-207](../wallet/0207.md) requires a current overlay answer before a wallet spends or accepts a token. This BRC carries the **deferred admission** evidence selected by [BRC-207's attested-admission profile](../wallet/0207.md#attested-admission-and-offline-token-graphs). A wallet chooses whether to offer it. The asset MUST opt in through that profile in its original BRC-162 `req`; neither enabling a wallet setting nor receiving a bundle opts an undeclared asset in.

## Roles

| Role | Does | Is trusted for |
|---|---|---|
| Payer | Builds, signs and hands over the bundle | Nothing. Every claim is checked. |
| Payee | Checks the bundle, credits it, settles it | Its own trust choices |
| Overlay operator | Admits transactions to `tm_color_<assetId>` and signs attestations | Having admitted the attested outputs, if the payee trusts its key |
| Identity registrar | For regulated assets, binds identity keys to real-world persons | Identity of a key's owner, outside this protocol |

One organization MAY hold several roles. An issuer commonly runs the overlay and the registrar.

## Admission attestation

An attestation is an overlay operator's statement: "the topic `tm_color_<assetId>` admitted these outputs of this transaction."

### Message

```text
1color-admit:v1:<topic>:<txid>:<outputs>
```

- `topic` is `tm_color_<assetId>` per BRC-207, using the canonical asset ID `<64 lowercase hex>_<decimal vout>`.
- `txid` is 64 lowercase hex characters, in display order.
- `outputs` is the admitted output indices as decimal integers without leading zeroes, unique, ascending and joined by `,`. It MUST NOT be empty.

The topic is part of the message so an attestation for one asset cannot be replayed as evidence for another.

### Signature

The signer computes `e = SHA-256(UTF-8(message))` and signs `e` with ECDSA over secp256k1 using the BRC-42 child of its identity for protocol `[2, "color admission attestation"]`, key ID `"1"`, counterparty `"anyone"`, as specified in BRC-207. The published signer key remains the identity key; verifiers derive its child independently. A raw identity-key signature is not this construction. `e` is not hashed again. Signers SHOULD use RFC 6979 deterministic nonces, so re-signing the same message gives the same bytes and settlement retries are idempotent. The signature is DER encoded. Verifiers MUST accept any valid `S` value and MUST NOT require low-S.

An overlay MUST sign only outputs its topic has admitted. It returns the attestation for each topic in its BRC-22 submission response as `admissionSignature` (lowercase DER hex) and `admissionIdentityKey` (compressed public key, 66 hex), next to that topic's `outputsToAdmit`.

### Meaning and limits

An attestation proves admission at signing time. It does **not** prove the output is still unspent. That gap is the counterparty risk discussed below.

### Trust

A verifier MUST authenticate the deploy's `req` and apply BRC-207's exact
attested-admission policy. Default `any` mode requires one BRC-189-listed entity
per anchor; different anchors may use different entities. `same` requires a
common listed entity across the complete asset frontier, `all` requires every
listed entity for every anchor, and `identity` requires the deploy's fixed key
without a list-membership check. Each signature verifies against the child of
that identity under the fixed tuple, never against an arbitrary bundled key.
Wallet defaults are proposals subject to the user's accepted trust policy.
Trust changes apply at each new acceptance/spending decision and may restrict
pending offline value, without retracting released signatures or past decisions.
Future evidence replacements use their own declared carriers/contracts; this
version-1 bundle carries the default construction only.

## Payment bundle

### Encoding

All integers marked VarInt use Bitcoin CompactSize encoding in its minimal form. A non-minimal VarInt MUST fail. `str` is a VarInt byte length followed by strict UTF-8. `bytes` is a VarInt length followed by raw bytes. A `txid` field is 32 bytes in display order: the bytes of the hex string as written. A decoder MUST reject trailing bytes.

```text
u8      version            = 0x01 or 0x02
33B     senderKey
VarInt  outputIndex
str     derivationPrefix
str     derivationSuffix
str     assetId
VarInt  nSubmissions
        nSubmissions × { 32B txid ; bytes offChainValues }
VarInt  nAttestations
        nAttestations × { 32B txid ; VarInt nOutputs ; nOutputs × VarInt output ;
                          bytes signature ; 33B signerKey }
str     note
bytes   transaction
// Version 2 only:
bytes   lifecycle          // UTF-8 JSON array of BRC-177 portable lifecycle objects
```

Version 1 retains its exact framing and is suitable when no unresolved protected
root requires lifecycle evidence. Version 2 appends `lifecycle`, a strict UTF-8
JSON array of the exact [BRC-177](../wallet/0177.md#portable-lifecycle-statements)
objects. Bound the entire bundle before decoding; reject duplicate JSON members,
invalid statements, unsupported versions and trailing bytes. An empty array is
valid only when no unresolved protected root requires a statement. A bundle for
such a root MUST use version 2, including for `never`. Version 1 cannot assert
a protected root's `never` status. The display-only note cannot carry policy.

The receiver verifies and persists each original root wallet's signature and
policy under BRC-177, matches it to the actual ancestry, and forwards the records
unchanged with subsequent payments. Token attestations do not replace these
statements. Authentication of a promise does not prove that the signer will
honor it; acceptance still uses the recipient's counterparty/risk policy. Unknown
upstream lifecycle is disclosed as unknown, not treated as non-reclaimable.

### Why each field is sent

| Field | Why the payee needs it |
|---|---|
| `version` | Lets a decoder refuse a format it does not implement. |
| `senderKey` | The counterparty for deriving the payee's output key under BRC-42. It is the blinded key `A′` for a blinded payment, or the payer's identity key `A` otherwise. The payee treats both the same way. |
| `outputIndex` | Which output of the tip pays the payee. Output order is randomized, so the payee cannot guess it. |
| `derivationPrefix`, `derivationSuffix` | The remittance strings that select the payee's key in the BRC-207 namespace. On the nearby rail the payee chose them, which binds the bundle to one session. |
| `assetId` | Which asset is being paid. It fixes the topic, the attestation message and the per-asset basket. |
| submissions | For the tip and every unattested token ancestor, the exact off-chain values the overlay needs to admit that transaction. The payee must be able to settle without the payer, so it carries what the payer would have sent. For an asset without ownership disclosure the value MAY be empty. |
| attestations | Where the walk-back stops. Each entry lets the payee confirm, offline, that the overlay already admitted the named outputs. |
| `note` | Optional message from payer to payee. Display only. Empty means absent. |
| `transaction` | A [BRC-233](../transactions/0233.md) Subject BEEF whose subject is the tip. It MUST contain the full body of every transaction the walk-back will require. The payee needs these bodies to validate scripts, check conservation and settle. |

There is deliberately no amount field: the amount is read from the payee's output script, so the bundle cannot claim a different one. There is also no overlay URL and no trusted key: the payee uses its own configuration for both, so a payer cannot steer it to a server or signer of the payer's choosing.

### Structural rules

- `senderKey` and each `signerKey` MUST be valid compressed secp256k1 points.
- `assetId` MUST be canonical as defined in BRC-162.
- Submission txids MUST be unique. Attestations are unique by `(txid, signerKey, outputs)`; multiple signers or disjoint output sets for one txid are allowed. A transaction may have attested outputs and a submission entry for other required outputs. No duplicate entry adds trust coverage.
- Attestation outputs MUST be ascending and unique, and the list MUST NOT be empty.
- `derivationPrefix` and `derivationSuffix` MUST satisfy BRC-207's remittance rules: nonempty strict UTF-8 without whitespace. The resulting protocol name MUST fit BRC-43's 280-character bound.
- `transaction` MUST parse as a BRC-233 Subject BEEF whose subject is the tip. Like a [BRC-176](../tokens/0176.md) packet, it MUST NOT be validated, stripped or round-tripped as BRC-95 Atomic BEEF: BRC-95 handling may drop the ancestor bodies the walk-back needs.

A bundle that breaks any rule fails as `decode_failed`.

## Walk-back

The walk-back decides whether every token in the payment traces to attested outputs, and which transactions the payee must settle. It runs without network access.

The authoritative walk is BRC-207's complete token-frontier validation. Start
at the payment's required inputs (or requested receipt output); authenticate the
source body and stop a branch only at exact-output attestation coverage. Otherwise
validate the producing transaction's complete same-asset transition and recurse
through all its same-asset value and authority inputs. A mined parent is not
an admission anchor. Every branch must terminate at covered outputs, with
`same`/`all` coverage evaluated across the entire frontier. Missing bodies,
invalid transitions, incompatible known spends or incomplete coverage fail.

The output list in a signature asserts admission of those outputs, not rejection
of every unlisted output. For an unlisted output the wallet needs other qualifying
coverage or a complete validated walk. An actual known rejection cannot be
bypassed. Non-token inputs are outside token lineage, but their source bytes,
scripts and Bitcoin/SPV evidence remain mandatory. An attestation never supplies
a missing amount or locking script and never substitutes for a Merkle proof.

The result is the tip and all unattested token ancestors requiring settlement,
ordered parents before children. Every such transaction MUST have a submission
entry with the exact off-chain data required by the asset's declared profiles;
empty bytes suffice only where those profiles permit them. The bundle MUST also
provide the deploy body needed to authenticate `req`. The adapter maps these
bodies, attestations and submissions into BRC-207's asset-scoped `profileData`
carrier, independently preserving the ordinary Bitcoin evidence. It does not
put this Subject BEEF in BRC-100's Atomic BEEF `tx` field.

Wallets MAY impose documented work/size bounds; exceeding them fails as
`limit_exceeded`, never a shortened graph or partial balance. This single-asset
bundle cannot assert completion of unrelated asset legs. A multi-asset action
must independently satisfy BRC-207 for every asset and satoshi leg.

## Payee acceptance

The payee runs these checks and stops at the first failure. Each failure maps to an ack code. A payee that declines MUST NOT have saved or credited anything.

1. **Decode and policy.** Decode under the structural rules, else `decode_failed`. Then authenticate the deploy and supported `req`, resolve the complete dependency graph and apply all companion/lifecycle rules. Unsupported or missing policy or evidence fails as `not_covered`; an exceeded bound is `limit_exceeded`.
2. **Output.** `outputIndex` names a tip output that is a BRC-162 value output of `assetId` with a P2PKH remainder. Else `invalid_tx`.
3. **Ownership.** The payee computes its key with BRC-100 `getPublicKey`. The arguments are `protocolID` `[2, "p color <assetTag> <prefixTag> <suffixTag>"]` and `keyID` `"color"` per BRC-207, with `counterparty: senderKey` and `forSelf: true`. The HASH160 of that key MUST equal the output's public key hash. Else `session_mismatch`. This proves the payee alone can spend the output.
4. **Scripts.** Every input of the tip and of each `mustSubmit` transaction MUST pass consensus script validation against its source output. Required source bodies MUST be available, and Bitcoin/SPV evidence for all Bitcoin inputs MUST validate under the wallet's chain policy. Attestations waive neither. The tip MUST be consensus-final. Else `invalid_tx`.
5. **Token rules.** The tip and each `mustSubmit` transaction MUST satisfy BRC-162 conservation and authority rules for `assetId`, with all inputs counted from walked or attested sources. Else `invalid_tx`.
6. **Walk-back.** It succeeds. Else `not_covered`.
7. **Session or request.** On the nearby rail the prefix, suffix, asset and any requested amount equal the session's. Else `session_mismatch`. A session already paid fails as `already_paid`, here or atomically at step 9.
8. **Policy.** The amount and depth fit the payee's deferred-admission limits. Else `limit_exceeded`.
9. **Save.** The payee durably stores the bundle and marks the session spent. This is one atomic step. Else `save_failed`.
10. **Ack and credit.** The durable commit includes the validated credit or its idempotently recoverable pending application. The payee then sends a positive ack and exposes the output with `color_offline`. A crash before or after the ack cannot lose or duplicate credit. No ack asserts Bitcoin confirmation or current global unspentness.

## Settlement

Settlement turns an offline credit into an admitted one. Either party MAY settle under its applicable authorization, and both MAY try. Protected `noSend` actions require BRC-177's explicit publication authorization; internalization or a received ack alone is not such a request. Submission is idempotent, so a duplicate does no harm.

1. Submit each `mustSubmit` transaction, then the tip, in order. Each goes to the settling party's configured provider for `tm_color_<assetId>` with its submission entry's off-chain values.
2. Accept an admission only when it carries fresh processing results under the configured overlay policy and attestation coverage satisfying the asset's declared trust mode for the expected outputs. An unsigned or unverifiable answer is a retryable failure, never an admission.
3. Store each attestation. It becomes evidence for later bundles.
4. Broadcast only after the overlay has admitted the transaction and required ancestors, under BRC-207's publication and partial-settlement rules. Broadcasting the tip's BEEF also broadcasts its unmined ancestors. If a transaction were mined before admission and the overlay then refused it, its token inputs would be destroyed on-chain.
5. Remove `color_offline` only after actual current admission and all required dependency, asset and companion-profile checks pass. Preserve unresolved related legs and any restricted/reserved state; one positive answer is not graph-wide settlement.

Outcomes:

| Outcome | Payee action |
|---|---|
| Retryable (unavailable, rate-limited, unverifiable answer) | Keep state and retry with backoff. |
| Final refusal of the tip or an ancestor | Mark it refused and its descendants orphaned. Remove the credit and correct the balance. Keep the bundle. |
| Conflict: an input already spent by another transaction | As for a final refusal. Also record the competing txid the overlay reports. Keep the bundle as evidence. |

A wallet SHOULD tell the user when settlement has not finished within its stale threshold. A threshold of three days is suggested.

The payer MUST keep its spent inputs reserved, and the exposure recorded, until it sees the tip admitted or a conflict established, as BRC-207 requires.

## Deferred admission policy

This section applies BRC-207's declared attested-admission policy. A wallet MAY offer it only for assets whose immutable `req` selects it, with every companion requirement enforced. Undeclared assets retain baseline admission.

- **Accepting.** An eligible, unreserved output accepted under this BRC has BRC-207 state tag `color_state_available` and additional tag `color_offline`, and counts toward the asset's token balance. Companion-profile restrictions and reserved/pending states take precedence and exclude unavailable value. Applications cannot set or remove `color_offline`. This extends BRC-207, which otherwise reserves `color_state_available` for admitted outputs.
- **Spending offline.** A `color_offline` output MAY be spent in a new bundle. The payer forwards the evidence: its own bundle's submission entries and attestations for every still-unattested ancestor.
- **Spending online.** Authorized offline construction may release signatures while connected too. Before actual publication, reconcile and settle required ancestors under BRC-207; a known refusal prevents new descendant publication. Connectivity alone does not convert a `noSend` handoff into publication.
- **Limits.** The wallet sets per-asset amount caps, maximum walk depth, retention/exposure limits and accepted counterparties. The default signature has no authenticated timestamp, so local first-seen time is not proof of attestation age. The user consents to the policy when enabling it, and may authorize later settlement, subject to BRC-177's explicit publication rules where applicable.
- **Capability.** A wallet that accepts bundles MAY advertise BRC-205 attribute `brc175-offline=2` for this revision, including both bundle versions, derived-key verification and declared trust/lifecycle rules. Value `1` does not establish this support. A payer that cannot tell whether the payee accepts bundles SHOULD settle online first.

## Bindings

### Nearby session

The payee starts a payment by showing a session QR:

```text
bsvpay1:<base64url, unpadded, of UTF-8 JSON>
```

| Member | Type | Why |
|---|---|---|
| `v` | integer `2` | Session format version. |
| `s` | base64url of 16 random bytes | Session ID. It names the radio rendezvous and is burned after one payment, so a bundle cannot be replayed. |
| `k` | base64url of 32 random bytes | Pre-shared key that seals the bundle, so only this payee can read it. |
| `i` | compressed key, 66 hex | Payee identity key `B`. The payer derives the payee's output key toward it. |
| `p`, `x` | strings | Payee-chosen derivation prefix and suffix. They make the output key fresh and tie the bundle to this session. |
| `a` | decimal string, optional | Requested amount in token base units, up to uint64. Absent means the payer chooses. |
| `t` | object | `i`: asset ID. Optional `k`: array of attester keys the payee trusts, as a hint so the payer can choose evidence the payee will accept. Optional `n`, `s`, `d`: display name, ticker, decimals. |
| `c` | integer, optional | Transport capability bits, so the payer picks a radio both phones support. |

The payer replies with one sealed frame:

```text
0x01 ‖ IV (32 bytes) ‖ AES-256-GCM ciphertext of the bundle ‖ tag (16 bytes)
```

The key is the session PSK. A wrong key or any tampering fails authentication, which maps to `decode_failed`. The frame travels by whichever radio both sides support. Radio link details are implementation-specific. If no radio works, the payer shows the sealed frame as a [BRC-141](../peer-to-peer/0141.md) animated QR; 1024-byte blocks are suggested. A sealed frame MUST NOT exceed 65,536 bytes.

The payee answers over the radio with a UTF-8 JSON ack of at most 4,096 bytes:

```json
{ "ok": true }
{ "ok": false, "error": "not_covered" }
```

`error` is one of `decode_failed`, `invalid_tx`, `session_mismatch`, `already_paid`, `not_covered`, `limit_exceeded` and `save_failed`. A negative ack reports refusal; it does not prove that released signed bytes were destroyed or cannot be used. The payer MUST retain reservations/exposure until a verified winning spend or safe finite-root reclamation resolves them. A released BRC-177 `never` payment remains permanently sent and MUST NOT be reclaimed, even after a negative ack. The QR fallback has no return path. The payer then treats the payment as delivered but unconfirmed, and keeps its reservation until it observes settlement.

### Message box

For payments to a remote payee, the payer sends the bundle through a BRC-33 message box named `color-payments`. It may first resolve a [BRC-169](../peer-to-peer/0169.md) handle to the payee's identity key. The message body is:

```json
{ "v": 1, "bundle": "<standard base64 of the bundle>" }
```

With no session, the payer chooses the derivation prefix and suffix. They MUST be fresh random values. The payee runs the acceptance checks, skipping step 7. It acknowledges the message only after step 9, or after a decline. A payee that declines MAY send the decline code back to the payer's `color-payments` box.

## Sender blinding

A payer MAY hide its identity from the payee. It picks a fresh random scalar `r` and sends `senderKey = A′ = A + r·G`. It derives the payee's key from the shared secret `S′ = S + r·B`, where `S` is its BRC-42 shared secret with `B`. Because `b·A′ = S′`, the payee derives the same key with an unchanged `getPublicKey` call and `counterparty: A′`. The payee cannot tell a blinded payment from an unblinded one, or from a [BRC-228](./0228.md) ephemeral key. Unblinded payment, with `senderKey = A`, is equally valid.

The payer keeps `r` privately, against the payment's outpoint. Revealing `r` later proves that the payer built the payment: anyone can check `A′ − r·G = A`. `r` never appears in a bundle, in an overlay submission or in BRC-100 metadata.

A protected version-2 bundle also discloses the lifecycle signer's identity and
its association with a root transaction. That identity may be the payer's wallet
identity. Sender blinding does not conceal these lifecycle records. Wallets MUST
disclose this additional exposure before choosing protected delivery, and MUST
NOT promise the same identity hiding as an unprotected bundle. The records are
not published on-chain by this protocol, but a recipient can retain or disclose
them. A later explicitly declared construction may provide different privacy
semantics; the default must not omit required records to claim privacy.

For an unprotected bundle, what each party learns:

| Party | Payer identity | Payee identity |
|---|---|---|
| Payee | `A′` only | itself |
| Overlay of a regulated asset | `A` | `B` |
| Public chain | neither | neither |

Blinding gives privacy from counterparties and the public. It deliberately gives none from a regulated overlay.

## Counterparty risk and double-spend attribution

### The risk

An attestation shows that an output was admitted, not that it is still unspent. Until the payee settles, the payer can spend the same input to someone else. Whoever settles first wins; the other payee's credit is removed. Deferred admission puts that risk on the payee who accepted it. Issuer supply is never affected, because the overlay admits only one spend of each output.

The payee's limits bound the exposure. For regulated assets, attribution makes cheating traceable and therefore deterrable.

### Regulated assets

A regulated asset is one whose overlay admits an output only when the submission discloses the output's owner and that owner is registered with the asset's identity registrar. Those admission controls belong to an optional issuer-controls profile declared in the asset's BRC-162 `req` map. This BRC does not define that profile; it states what attribution needs from it.

- **Ownership disclosure.** For each token output, the submission carries a BRC-69 specific linkage, encrypted to the overlay key under BRC-72. The linkage lets the overlay recompute the output key as `owner + k·G` and match it to the script. For a blinded output, the payer discloses the offset `k` it derived from `S′`.
- **Owner record.** The overlay MUST keep the owner identity key of every admitted output. It MUST keep that record after the output is spent, and record the txid of the spend it admitted.
- **Conflict record.** The overlay SHOULD keep the bytes of any refused submission that tried to spend an already spent output.

Only the owner can spend an output: its private key is `b + k`, and the payer knows `k` but not `b`. So the identity key recorded as the owner of a double-spent outpoint is the identity that signed both spends, unless that key was stolen or shared.

### Reporting a double spend

1. The victim's wallet reports the double-spent outpoint, the bundle it holds and the competing txid from settlement. The bundle contains the second spend, signed by the offender's key.
2. The overlay operator looks up the outpoint's owner record. That gives the owner identity key and the transaction the overlay admitted.
3. The registrar maps the identity key to the person who registered it.

The outpoint is enough to start the lookup. The victim's bundle is the proof. Blinding does not hinder either step, because the overlay saw the real keys. Access to owner records, and the legal process for disclosure, are governed by the operator's and registrar's terms. Those terms are outside this BRC.

For assets without ownership disclosure, attribution stops at the overlay's view of the transactions. There is no person behind a key.

## Security considerations

- **PSK exposure.** Anyone who photographs the session QR can open the sealed frame. They learn the payment but cannot redirect it, because the output pays the payee's key. Payees SHOULD show session codes only briefly.
- **Replay.** A session is burned when its payment is saved. A message-box bundle is unique by tip txid, and saving it twice MUST be idempotent.
- **Attester compromise.** A stolen attester key can attest outputs that were never admitted, and wallets trusting it would accept them. Settlement would then fail, and those payees lose the credited value. Wallets SHOULD let users remove a trust anchor quickly, and overlays SHOULD rotate keys under BRC-189's rules for trust changes.
- **Eviction.** If an admitted transaction is later evicted, for example because it never confirmed, its outputs are no longer admitted. A settled payment can then be reversed. Wallets SHOULD show an evicted credit as reversed, not silently hide it.
- **Stale trust.** Removing a trust anchor does not revoke attestations already relied on. Wallets MUST re-check `color_offline` outputs against the current declared trust policy before a new acceptance or spend, and restrict affected value when that policy no longer holds.
- **Size.** Decoders MUST bound allocation by the received length before reading counts. Walk depth and BEEF size MUST be bounded.

## Implementations

A prior version of this protocol is implemented in the BSV wallet (`bsv-wallet`, `packages/expo-wallet-toolbox/core/localpay` and `core/mandala`) with the `@bsv/mandala` library and its Go overlay. That implementation predates the 1Color names and this bundle encoding, and is being migrated to this specification.
