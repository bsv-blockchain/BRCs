# BRC-182: Mandala Extension for BSV-21 Compatibility

David Case (david.case@shruggr.cloud)

This specification extends Mandala so that a BSV-21 token can be issued on Mandala outputs, and an existing BSV-21 token can be converted to them. Holder outputs and authority remain Mandala. This document adds a fixed supply on the deploy, an admission profile, and CBOR metadata.

[BRC-162](./0162.md) is withdrawn. Its prefix was never implemented.

## Forward path

A token created under [BRC-161](./0161.md) keeps the outpoint of its deploy as its token id. A later output of that token may be a Mandala output of that same id. The token is the same token.

## Fixed supply

A fixed-supply deploy is a Mandala deploy followed by the supply amount.

```
<metadata> <amount> OP_2DROP <lock>
```

The output's own outpoint is the token id. The amount is the entire supply, a positive minimally encoded script number. This specification does not cap the amount. Spending this output moves that supply. It does not mint.

An authority deploy carries no amount. It is a Mandala deploy. Spending it mints onto ordinary holder outputs. The minted amount is the script number on those outputs.

## Admission

Deploy metadata may contain `admission`. The value is `mandala` or `bsv21`. If the field is absent, the value is `mandala`.

`mandala` requires three checks. The output carries exactly 1 satoshi. The locking script is P2PKH. Authority is a key derived from the hash of the admin action JSON. The amounts must match. A spend that does not match is not admitted, and the inputs are gone. There is no partial burn.

`bsv21` does not run those checks. By convention, token outputs often hold 1 satoshi. That is ecosystem practice for indexing and wallet UX, not a protocol rule. Validators MAY apply a 1-satoshi policy when admitting outputs. The locking script is not required to be P2PKH. Authority is the spend of the authority output. Inputs must cover outputs, and any surplus is burned. A payment that exceeds the inputs is not admitted, and those inputs are burned.

An indexer that sees `bsv21` runs those rules. It does not apply the Mandala checks and then ignore the failures.

Identity linkage, pause, freeze, and sanctions are not selected by this field. A Mandala overlay may still enforce them.

## Metadata

A contract cannot cheaply write JSON. An outpoint or an identity key would have to be reversed and hex-encoded. CBOR takes the raw bytes. The fields are the same as the JSON metadata. The encodings are not interchangeable byte for byte.

JSON remains valid.

A CBOR map is valid in any key order. A decoder MUST accept the pairs in the order written. Writers SHOULD use deterministic encoding so the same fields produce the same bytes. A reader MUST NOT require that order.

An outpoint or an identity key in CBOR is a byte string: `0x58`, the length, and the raw bytes.

## Compatibility

A fixed-supply deploy and a CBOR deploy are not scripts an existing Mandala indexer accepts. An indexer that does not read `admission` still requires P2PKH. Tokens deployed before this specification are unchanged.
