# BRC-303: 1Sat Collectables in BRC-100 Wallets

David Case / b-open-io (david.case@shruggr.cloud)  
Luke Rohenaz / b-open-io  
Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

## Abstract

This BRC defines how **1Sat collectables** (inscribed 1-satoshi tokens held as NFTs) are tracked in a [BRC-100](../wallet/0100.md) wallet under the [P1Sat scheme](./0302.md).

It specifies the basket name, eligibility, display tags, and the mint / list / transfer / import shapes for this asset class. Chain rules and inscription bytes are defined elsewhere; this document only covers wallet filing and actions.

## Motivation

Users hold inscribed 1-satoshi outputs as collectables. Wallets need one basket, shared tags for filtering and UI, and enough structure that transfers are approved as “send this item,” not as opaque scripts.

This document **supersedes** [BRC-147](./0147.md) for new implementations. BRC-147 recorded an earlier basket profile (`1sat` without `p `); this is the P1Sat-aligned successor used by 1sat-sdk.

## Specification

### Basket

```
p 1sat ordinals
```

All P1Sat rules apply (scheme gating, `id:`, origin tag, action labels, spend `customInstructions`, fixed output order).

### Eligibility

File an output in this basket only when:

1. `satoshis === 1`
2. It is the current (or mint origin) 1-satoshi output on a 1Sat chain ([BRC-300](./0300.md))
3. It is treated as a collectable inscription asset for this wallet (typically a valid inscription envelope on the origin; see [BRC-301](./0301.md))

Do not place ordinary payment change or non-1-sat outputs here. Application-specific 1-sat assets that have their own baskets (e.g. OpNS, BSV21) use those baskets instead, even if they also carry inscriptions.

### Tags

The P1Sat **`id:`** and **origin** tags are required on every output in this basket ([BRC-302](./0302.md)). The tags below are additional and **all of them are conditional** — write one only when its value applies to the asset and is known. None is required, and a missing tag means the value was unavailable, not that it is absent from the asset.

| Tag | Write it when | Meaning |
|-----|---------------|---------|
| `type:<type>/<subtype>` | The content type is known | Content type with any parameters removed — everything before the first `;` (e.g. `type:image/png` from `image/png; charset=binary`) |
| `collection:<origin>` | The item is a collection member | Collection origin outpoint, so a wallet can list one collection ([BRC-304](./0304.md)) |
| `app:<id>` | An issuing application is known | Lets a user filter by where an item came from |
| `creator:<id>` | A creator identity is known | Same, by who made it |

Rules:

* `type:` describes the **origin** inscription — envelope field 1 at the chain origin ([BRC-300](./0300.md)) — not whatever the current output's locking script contains. A transfer output commonly carries no envelope at all, and a re-inscription later in the chain does not change the tag.
* Self-keep transfers MUST therefore copy `type:…` forward with the origin tag ([BRC-302](./0302.md) origin rules) rather than re-deriving it from the new output.
* A tag value MUST survive case normalization, since wallet storage commonly lowercases tags. Values that do not — display names, for instance — belong in `customInstructions` instead.

**Open question — where these values come from.** This document does not yet fix the canonical source of the display-oriented values. The working assumptions are below; most map to fields of the `ord` MAP schema on the inscription ([BRC-301](./0301.md)), and `creator:` to the Sigma signer.

| Value | Assumed source | Status |
|-------|----------------|--------|
| `collection:` tag | `subTypeData.collectionId` under `subType=collectionItem` | Defined — see [BRC-304](./0304.md) |
| `type:` tag | Content type of the **origin** inscription, envelope field 1 | Defined — see [BRC-301](./0301.md) |
| `name` in `customInstructions` | MAP `name` | Assumed; MAP defines the field |
| `app:` tag | MAP `app` | Assumed; MAP defines the field |
| `creator:` tag | Sigma signer — of the collection origin for a collection item, or of the inscription itself for a standalone one | Assumed; no MAP field exists |

### Custom instructions

Spend fields follow P1Sat (`protocolID`, `keyID`, `counterparty`).

When a display **name** is defined for the asset (from on-chain metadata; see a future MAP / metadata BRC based on [1sat-ordinals metadata](https://docs.1satordinals.com)), writers SHOULD include it as a case-preserving `name` string in the JSON. Do not rely on tags for name — wallets may lowercase tags.

### Operations

Wallets classify a collectable operation from the output locking scripts and the templates of the spent inputs ([BRC-302](./0302.md)). The operations a wallet is expected to recognize:

| Operation | Shape |
|-----------|-------|
| Inscribe | No collectable input; an output carrying an `ord` envelope filed into the basket |
| Transfer | A held collectable in, a 1-satoshi output to a key the wallet does not hold |
| Burn | A held collectable in, no collectable out |
| List | A held collectable in, a marketplace-lock output (script out of scope here) |
| Cancel listing | A marketplace-lock input the wallet can cancel, a held collectable back out |
| Purchase | A marketplace-lock input the wallet does not own, a collectable filed into the basket |

An output whose template the wallet does not recognize is described as unrecognized.

Input labels use class `ordinals` (basket suffix): `p 1sat input ordinals <id>`.

Collection mints: see [BRC-304](./0304.md), same basket.

### List ordinals

To list ordinals in the wallet, call BRC-100 `listOutputs`:

```json
{
  "basket": "p 1sat ordinals",
  "includeTags": true,
  "includeCustomInstructions": true
}
```

Optional `tags` / `tagQueryMode` filter on exact tag values, e.g. `type:image/png` or `origin:<outpoint>`. Tag matching is exact; there is no prefix or wildcard form.

### Mint (inscribe)

Create a 1-sat output with lock + inscription envelope, basket `p 1sat ordinals`, tags:

* bare `origin` (this output is the origin)
* `type:…` from content type
* `id:<actionId>_<outputIndex>` per P1Sat

### Transfer

Spend the held 1-satoshi output under core sat ordering into a new 1-satoshi output.

**Self-keep** (still held in this wallet): new output in `p 1sat ordinals` with promoted/copied origin tag, copied `type:…`, new `id:`, and fresh spend `customInstructions` under the `p 1sat` protocol (SHOULD carry `name` when defined).

**To an external recipient:** 1-sat output to their lock; basket/tags/CI on that output are for the **receiver’s** wallet when they internalize (sender need not file the remote output in a local basket).

One `p 1sat input ordinals <id>` label per spent output.

### Import

`internalizeAction` with `basket insertion` into `p 1sat ordinals`, P1Sat tags (`id:`, origin, and `type:` as known), and spend `customInstructions` for the lock the wallet will use.

### Out of scope

* OrdLock / marketplace script templates (only the operations that touch them are named)
* Full MAP beyond [BRC-301](./0301.md) basics; collections — [BRC-304](./0304.md)
* Provenance proofs (current outpoint → origin packages)
* Content delivery (OrdFS)
* BSV21, OpNS, and other non-collectable baskets
