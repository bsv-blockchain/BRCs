# BRC-252: Compact Lineage Evidence for P2P-FT

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

BRC-252 keeps the proof of a [BRC-251](./0251.md) token short as the token trades. It does not change when a token is valid. The recipient still walks the history back to the deploy, or stops at an output it has already checked itself. No host decides that the token is valid.

## What this adds

[BRC-251](./0251.md) already says a wallet may stop at a check it recorded earlier. That record stays on the wallet that made it. The next payment to someone else still carries every ancestor that person has not checked.

Four rules shrink that package.

1. **A transaction is named by its txid.** Anyone may hand over the body. The recipient keeps it only when the body hashes to that txid.
2. **Leave out history the recipient has already checked.** Once they acknowledge a payment, the next payment to them may omit the ancestors behind those outputs. If they no longer have that check, they fetch the missing transaction, or the tokens stay unverified.
3. **Spend the coins that leave the shortest remainder.** When several inputs cover the amount, the sender should choose the set that leaves the least new history for that recipient. Spending an older branch is still a valid payment.
4. **A shorter proof counts only when the recipient can check it.** This draft registers no such proof. An overlay's signature does not qualify. A proof the recipient cannot check is ignored, and the recipient walks the bodies.

HandCash already records its own checks and fetches a missing transaction by txid. Rules 2, 3 and 4 are specified here.

## Specification

### 1. A transaction is named by its txid

Any party MAY store or serve the body of a same-token transaction: the wallet, another device of the same vault, the counterparty, or a public host.

The recipient MUST accept a served body only when the body hashes to the txid it asked for. A body that does not hash to the txid is a different transaction. A host that refuses to serve a txid delays the walk. It cannot put a different body in its place.

A wallet MAY keep one cache of these bodies, shared across tokens, payments and its own devices. Copying a body to another device copies bytes. That device still hashes them, and it still runs the BRC-251 walk.

### 2. Leave out history the recipient has already checked

A wallet's **frontier** for a token is the set of outputs of that token for which it holds a recorded BRC-251 check.

When a recipient acknowledges a BRC-251 payment, the sender MAY record that recipient as holding a check for each value output of that payment which the sender itself has checked. The record says what a later package may omit. It is not a check for the sender, and the recipient cannot use the sender's record as its own check.

To cover a spent output for a recipient, the sender walks same-token inputs back toward the deploy. It includes each body until every branch reaches either the deploy, or an output on that recipient's frontier. Bodies behind the frontier MAY be omitted. With no frontier recorded for the recipient, the package carries the full walk BRC-251 already requires.

The recipient resumes at the new outputs:

1. It stops if it already holds a recorded check for that output.
2. Otherwise it takes the body from its cache or fetches it by txid, checks the hash, and checks that transaction under BRC-251.
3. It continues into each same-token input.

A package that arrives already cut off is complete only when step 1 applies to the missing parent. If the recipient has no check there, it fetches that parent and continues. A fetch that fails leaves the output unverified. Omitting a body never makes the output valid.

### 3. Spend the coins that leave the shortest remainder

When more than one set of checked inputs covers the amount, the sender SHOULD choose the set that minimizes the number of bodies rule 2 includes for that recipient. Ties SHOULD go to the inputs this wallet checked most recently.

The choice does not change validity. A payment that spends an older branch is still valid. The recipient walks whatever remainder arrives.

### 4. A shorter proof counts only when the recipient can check it

A compressed proof claims that a BRC-251 walk already succeeded for one output, so a later wallet can skip the bodies behind it.

The proof is bound to an **evidence root**. The root is SHA-256 over the txid of every same-token transaction in that walk, including the deploy and the transaction that created the output. Each txid is its 32 display-order bytes. Those txids are sorted as raw bytes, then concatenated, then hashed.

A proof type is registered by a revision of this document or by a companion document. The registration gives the proof bytes and a verification procedure. The procedure MUST accept or reject with no trusted signer. It MUST reject a proof whose evidence root, token id, output or amount is not the one presented.

This document registers no proof type.

A proof of an unregistered type, or a proof the verifier rejects, MUST be ignored. The wallet then walks the bodies. A proof the verifier accepts MAY end the walk at that output. The new payment, from the spent inputs forward, is still walked in bodies. The proof covers the token rules for the skipped history. It does not say whether the new transaction has been mined.

## Security considerations

- A sender can omit a body the recipient still needs. The recipient fetches it, or the output stays unverified.
- A host can refuse a txid. It cannot substitute a body, because the hash would fail.
- One recipient's acknowledgement says nothing about a different recipient, and nothing about a reinstall that lost its checks. That wallet fetches what it no longer holds.
- A proof that checks for one evidence root fails for another. Until a type is registered, no proof skips a walk.
- Spending an older branch changes the size of the package, not the result of the walk.
- A checked output that is not yet mined is still unconfirmed, as BRC-251 says.

## Implementations

- **HandCash Desktop and Mobile**, from version 1.3.555, records BRC-251 checks and fetches a missing ancestor by txid. After a recipient's box accepts a payment, the next payment to that recipient omits ancestors behind those outputs. When several checked inputs cover the amount, it spends the set whose remaining walk for that recipient is shortest. It ignores a compressed proof: this document registers none, so the wallet walks the bodies.
