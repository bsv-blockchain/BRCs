# BRC-302: 1Sat Assets in BRC-100 Wallets (P1Sat Scheme)

David Case / b-open-io (david.case@shruggr.cloud)

## Abstract

This BRC defines the **P1Sat** permission and tracking scheme for holding and spending [BRC-300](./0300.md) assets inside a [BRC-100](../wallet/0100.md) wallet.

It specifies:

* The BRC-98 / BRC-99 scheme id **`1sat`**
* How asset outputs are filed in **baskets**
* How **tags** and **custom instructions** record identity and spend keys
* How **action labels** identify the held assets an action spends
* How wallets classify an operation from the transaction rather than a declared verb

Asset-specific rules (collectables, BSV21, OpNS, locks, …) are separate documents that build on this one. They do not redefine the scheme prefix, tracking ids, or spend-instruction shape.

## Motivation

BRC-100 wallets track application UTXOs with baskets, tags, labels, and `customInstructions` ([BRC-46](../wallet/0046.md), [BRC-37](../outpoints/0037.md), [BRC-65](../wallet/0065.md)). Plain baskets only support coarse grant/deny access. [BRC-98](../wallet/0098.md) and [BRC-99](../wallet/0099.md) reserve the `p ` prefix so a named **scheme** can apply richer permissions.

1Sat needs that richer path: many discrete asset UTXOs, structured dApp prompts (“transfer this ordinal”, “send these tokens”), and scheme-mediated access instead of a blank basket dump.

P1Sat is the scheme id **`1sat`**: one protocol family, one basket prefix, shared tracking and label conventions, implemented today by the 1Sat permission module and `@1sat/*` actions.

## Specification

### Scheme identifier

* **Scheme id:** `1sat` (no spaces).
* **BRC-98 protocol name:** `p 1sat`
* **BRC-99 basket prefix:** `p 1sat ` (trailing space before the asset-class suffix)

Wallets that do not implement this scheme MUST reject operations under these identifiers per BRC-98/99. Wallets that implement P1Sat MUST route matching protocol, basket, and label operations through the 1Sat permission path (see [Permissions](#permissions)) instead of the default basket/protocol prompts alone.

### Protocol

Key derivation and signing for P1Sat-managed asset outputs use the BRC-43 protocol name `p 1sat`, which is what causes BRC-98 to dispatch to the scheme:

```
protocolID = [<security level>, "p 1sat"]
```

The name is fixed. The security level is not fixed by this document, and it governs exactly one thing: **key derivation**. When an application requests a public key under this protocol, the wallet MUST apply the standard [BRC-43](../key-derivation/0043.md) semantics for the declared level — level 0 open, level 1 a grant per application, level 2 a grant per application and counterparty. Wallets therefore persist protocol grants alongside basket grants.

The level does **not** govern spending. Signing and action creation go through the scheme, which presents an approval for every action that creates or spends basket outputs, whatever the level says. That is stricter than any standing grant, so the level neither relaxes nor tightens it.

Implementations record the level they used in the output's `customInstructions`, so each held output remains spendable under the protocolID it was created with, whatever later outputs use.

Asset actions (hold, transfer, list, mint into a P1Sat basket, etc.) derive and sign under this protocol unless a later asset-class BRC defines an additional template.

### Baskets

Each asset class has one or more baskets of the form:

```
p 1sat <class>
```

Examples (informative; normative names live in the asset-class BRCs):

| Basket | Role |
|--------|------|
| `p 1sat ordinals` | General 1-sat inscription / collectable outputs |
| `p 1sat bsv21` | BSV21 token outputs |
| `p 1sat opns` | OpNS name outputs |
| `p 1sat lock` | Time-locked outputs |
| … | Further classes as those BRCs define |

Only outputs that belong to that asset class belong in its basket. `listOutputs`, `internalizeAction` (basket insertion), and spends of basketed outputs are scheme-gated (see [Permissions](#permissions)).

Baskets outside this prefix (e.g. `default` funding, or non-P application baskets) are not part of P1Sat.

### Output tags

Tags are wallet-local BRC-46 metadata on a basketed output. They are **not** on-chain.

#### Tracking id (`id:`)

Every output filed into a P1Sat asset basket MUST carry a stable tracking tag:

```
id:<actionId>_<outputIndex>
```

* `actionId` is a unique hex id for the wallet action that created or re-filed the output.
* `outputIndex` is the index of that output in the action’s `outputs` list (and in the final transaction — see [Output order](#output-order)).

Purpose:

* Address a specific held asset without scanning the whole basket (`listOutputs` + tag query).
* Correlate permission prompts and later spends with the same row.

When an action spends a held asset, it MUST refer to that asset by its `id:` value (not only by outpoint), loading BEEF and metadata from wallet storage.

#### Origin tag

Every P1Sat-held output on a 1Sat chain MUST carry an **origin** tag naming that chain’s origin ([BRC-300](./0300.md)). One tag, two forms:

| Form | When |
|------|------|
| `origin` | This output **is** the origin (mint / chain start) |
| `origin:<outpoint>` | This output is a later link in the chain; `<outpoint>` is the chain origin |

Rules:

* `<outpoint>` is `txid.vout` (64 hex chars, `.`, decimal vout). Never use an empty `origin:` suffix.
* On self-keep transfer or re-file:
  * If the source has `origin:<outpoint>`, copy that tag unchanged onto the new output.
  * If the source has bare `origin`, the spent outpoint **is** the origin — write `origin:<spent outpoint>` on the new output.
* Tags are set when the output is created or internalized; they are not updated in place afterward.
* The origin tag is a wallet **claim**, not proof of chain membership. Verification is out of scope here.

#### Template tag

```
template:<name>
```

Names the script template that locks the output. Its absence means the default pay-to-public-key-hash path.

* The wallet MUST determine the template from the output's locking script and stamp the tag itself. A caller-supplied value is not authoritative and MUST NOT be trusted.
* `<name>` values are defined by the asset-class BRC that introduces the template.
* Signing paths read this tag to select how the output is unlocked.

#### Other tags

Asset-class BRCs define additional tags (`type:…`, token ids, etc.).

### Output order

Actions that create or transfer P1Sat basket outputs MUST keep a fixed output order from build through broadcast. Wallets MUST NOT shuffle or randomize those outputs (e.g. `randomizeOutputs` MUST be off).

Reordering would break 1Sat sat ordering on transfers and would desynchronize `id:…_<outputIndex>` from the on-chain output index.

### Custom instructions (spend metadata)

For a P1Sat-held output the wallet can spend, `customInstructions` MUST be a UTF-8 JSON object string. The **spend** fields are:

| Field | Type | Meaning |
|-------|------|---------|
| `protocolID` | BRC-43 protocol (e.g. `[0, "p 1sat"]`) | Derivation / signing protocol |
| `keyID` | string | Key id under that protocol |
| `counterparty` | string (optional) | Counterparty for Type-42 derivation when not self |

Example:

```json
{
  "protocolID": [0, "p 1sat"],
  "keyID": "<key id>",
  "counterparty": "self"
}
```

Rules:

* These fields tell the wallet how to derive the key that unlocks the output. They are **not** a substitute for on-chain origin proofs.
* Asset-class specifications MAY add further JSON keys. Readers MUST ignore keys they do not understand.
* Display-only fields that duplicate tags MAY exist; tags are often lowercased by wallet storage, while JSON can preserve case.

### Action labels

Labels on `createAction` use the BRC-111 `p ` form so the wallet dispatches to P1Sat. Two label kinds are part of this scheme:

#### Input

```
p 1sat input <class> <id>
```

* `<class>` — basket suffix after `p 1sat ` (e.g. `ordinals`, `bsv21`)
* `<id>` — bare tracking id of the held output (**same value** as in that output’s `id:` tag, without the `id:` prefix)

When the action spends one or more tracked P1Sat assets, it MUST include one input label per spent asset. This does **not** invent a second identifier: it points at the inventory row already tagged `id:<id>` so the permission path can load name, origin, and other metadata from **wallet storage** (not from dApp-supplied description text).

#### Action id

```
p 1sat action-id <actionId>
```

Every `createAction` that creates or spends P1Sat basket outputs MUST include exactly one action-id label. `<actionId>` is a unique id for this **entire** action (not per input or output).

Wallets MUST reject an action carrying no action-id label or more than one.

New basket outputs from the action MUST use that same value in their tracking tags: `id:<actionId>_<outputIndex>`. The label is how the scheme handler and the action share one action id for the transaction.

### Permissions

P1Sat is enforced by a **scheme handler** registered with the wallet’s permission manager. Conforming behavior:

1. **Basket access** — `listOutputs` / `internalizeAction` into `p 1sat …` baskets require user (or prior) grant for that basket under the scheme.
2. **Protocol** — signing and action creation under `p 1sat` go through the scheme rather than an open-ended protocol grant. Key derivation follows the declared security level per [BRC-43](../key-derivation/0043.md), with grants persisted the same way basket grants are.
3. **Transactions** — each P1Sat `createAction` gets a single user-facing approval that is **structured**, not a raw script dump:
   * The operation is derived from the output locking scripts and the templates of the spent inputs, not from a verb declared by the caller.
   * **Input labels** say which held assets are spent; the handler resolves those rows from the wallet.
   * Outputs are described from locking scripts, baskets, and tags on the args.
   * An output whose locking script the wallet cannot classify is described to the user as unrecognized. Nothing in this scheme requires refusing such an action; whether to proceed is wallet policy.
   * The user approves or rejects that package.

Grant storage and exact UI chrome are implementation details.

### Placeholder signatures

An action MAY build an output whose locking script carries a signature that does not exist yet: the field is present at its final length with every byte zero. This reserves the space so the fee is known before the signature can be computed, which is necessary whenever the signature covers the script it sits in.

An all-zero signature can never verify, so a zero-filled signature field is an unambiguous marker for an output that still needs sealing.

* Wallets MUST seal a placeholder only when they recognize the template that owns it. A wallet MUST NOT compute a signature for a zero-filled field in a script it cannot classify — that would let a caller obtain a signature over data of its choosing.
* For a recognized template, the wallet MUST seal before broadcast: compute the signature and overwrite the placeholder in place, leaving every other byte of the script unchanged and the script length identical.
* Wallets MUST NOT broadcast an output that still carries an unsealed placeholder.
* No label or other declaration is required to trigger sealing; a placeholder in a recognized template is the signal.

This does not conflict with describing unrecognized outputs rather than refusing them. A wallet may show the user an output it cannot classify and let them approve it; what it must not do is sign into one.

Where the placeholder sits in the script, how long it is, and how its value is computed belong to the template that owns it. The templates recognized under this scheme are:

| Template | Placeholder | Signature covers | Defined by |
|----------|-------------|------------------|------------|
| Sigma tape | Zero-filled signature field in the tape | Script bytes before the tape, plus the outpoint of the referenced input | [BRC-307](./0307.md) |
| Signed PushDrop | Zero-filled final pushed field | Byte-concatenation of every preceding field, in order | [BRC-48](../scripts/0048.md) template; signature construction per [BRC-35](../overlays/0035.md) |

Note that the two differ in what they bind. A Sigma signature is tied to a specific input outpoint, so it cannot be replayed onto another output. A PushDrop field signature covers only the field bytes, so an identical set of fields carries an identical valid signature wherever it appears.

### Import and internalize

To adopt an external output into a P1Sat basket:

* Use BRC-100 `internalizeAction` with protocol `basket insertion`.
* Set `insertionRemittance.basket` to the correct `p 1sat <class>` basket.
* Supply tags (including `id:` and origin as required above) and `customInstructions` for how the wallet will spend the lock.

### What this document does not define

* Which basket name each asset class uses beyond the `p 1sat ` prefix pattern  
* Collectable display tags, BSV21 amounts, OpNS covenants, marketplace scripts  
* Inscription or MAP byte formats  
* On-chain proofs that a current outpoint descends from an origin  
* Remote indexer APIs  

Those cite this scheme where they file outputs into a BRC-100 wallet.

## Security considerations

* **Tag spoofing** — Tags and CI display fields are local claims. Do not treat `origin:…` as proof without a separate verification mechanism.
* **Tracking id reuse** — `actionId` / `id:` values must be unique per wallet row; collisions break spend and prompt resolution.
* **Scheme bypass** — Filing 1Sat assets into a non-`p ` basket loses P1Sat permission routing.
