# BRC-251: Peer-to-Peer Fungible Tokens (P2P-FT)

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

Peer-to-Peer Fungible Tokens (P2P-FT) is a wallet profile for holding, sending and receiving [BRC-162](./0162.md) tokens peer to peer, with no overlay and no trusted party deciding whether a token is valid. The recipient verifies each received output by walking its history back to the deploy ([BRC-176](./0176.md)) from transaction bodies the sender delivers.

It uses merged documents for the token encoding ([BRC-162](./0162.md)), the walk ([BRC-176](./0176.md)), and delivery (a [BRC-169](../peer-to-peer/0169.md) envelope over a [BRC-33](../peer-to-peer/0033.md) message box). The [BRC-100](../wallet/0100.md) interface is unchanged. This profile reserves the filing name `p2pft`.

## Motivation

A BRC-162 output commits its token id and amount in its locking script, and BRC-176 proves an output descends from its deploy under the token rules. Two wallets therefore need nothing beyond transaction bodies to agree that a transfer is valid. What they lack is a shared contract for the rest: which script layout to write, where held outputs live, what the sender delivers, and when the recipient may count the tokens.

This profile fixes those choices and nothing else. It defines no new BRC-100 method or response type. It reserves the filing name `p2pft`.

## Specification

### Scope

A conforming wallet:

- holds BRC-162 value outputs under the filing name `p2pft`;
- verifies each received output by a complete lineage walk;
- sends value with BRC-100 `createAction` and records receipts with `internalizeAction`;
- delivers each transfer with the evidence the recipient needs to verify it offline.

It does not define swaps, partially signed transactions, authority operations, issuance policy or overlay admission. A wallet MAY implement those under other documents.

### Encoding

1. New outputs MUST use the BRC-162 wire format exactly: canonical token id (32 bytes for a deploy at output 0, 36 bytes otherwise), minimally encoded amount, the optional payload with its `OP_DROP`, then the remainder. A new deploy MUST be output 0.
2. Readers MUST decode a payload as strict DAG-CBOR, as BRC-162 requires. A payload that is not a valid DAG-CBOR map carries no display fields. An `icon` is read only in BRC-162's `[mediaType, bytes]` shape.
3. The amount is always read from the output script, never from `customInstructions` or a message.

### Custody

- **Recipient output.** The value output for a recipient is locked, after the BRC-162 prefix, with P2PKH to the address of the recipient's identity key.
- **Change.** Change is locked with P2PKH to a key the sender controls. When that key is derived, its BRC-43 derivation triple is recorded in the output's `customInstructions` as specified below.

The identity address lets a sender pay a recipient known only by identity key. It reuses one address per recipient (see Security considerations).

### Filing and remittance

This profile reserves the filing name `p2pft`. After the BRC-46 normalization of trim and lowercase, conforming use MUST be exactly `p2pft`. New outputs are filed under that name.

- Tag `p2pft:<tokenId>` SHOULD be present. The token id is the deploy outpoint in `txid_vout` form.
- Tag `p2pft:auth` MAY mark an authority output. Authority outputs MUST NOT count toward a value balance.

When present, [BRC-37](../outpoints/0037.md) `customInstructions` MUST be a UTF-8 JSON object serialized as a string. Writers SHOULD include `id` (the token id in `txid_vout` form), `amt` (integer units as a decimal string), `op`, `sym`, `dec`, and `icon` when known. When this wallet derived the locking key, it SHOULD also include the BRC-43 derivation triple `protocolID`, `keyID`, and `counterparty`. Unknown members MUST be preserved and ignored by readers that do not understand them.

The script is authoritative. Balances are sums of BRC-162 script amounts per token id, never carrier satoshis, tags, `customInstructions`, or message claims.

### Verification

A received output is **verified** when the wallet holds a complete BRC-176 walk from it to the token's deploy:

1. Every same-token ancestor body is present and satisfies the BRC-162 validation rules, and every path ends at the deploy whose outpoint is the token id.
2. Every input on the walk that spends a same-token output passes script validation against that output. A wallet MAY skip this check for an ancestor whose merkle path it has verified against block headers per BRC-67. A merkle path that is only present in a BEEF does not replace it.

Other inputs of an unmined ancestor decide whether it can be mined, which is a question of finality (see Security considerations), not of token validity.

A walk MAY stop at an output this wallet verified in an earlier walk and recorded with its verdict. It MUST NOT stop at an output because it is mined, because an indexer lists it, because a host signs an attestation for it, or because it is filed under `p2pft`. [BRC-252](./0252.md) keeps a later package short. Bodies are fetched by txid. A sender omits history only behind checks the recipient recorded. Inputs should be chosen to leave the shortest remainder. A compressed proof is accepted only when the recipient can check it.

A wallet MUST NOT present an output, or a balance containing it, as verified until its walk verifies. It SHOULD keep unverified outputs out of the spendable balance and list them separately with the reason. An output whose walk fails MUST NOT be sent to another party.

### Required processing

BRC-162 ignores unknown payload keys for validity.

- When a deploy's payload is a valid DAG-CBOR map with key `req`, and its value is anything other than an empty array or an empty map, the token is **unsupported** by this profile.
- A wallet MUST NOT count an unsupported token in a balance, select it for a send, or accept it as a receipt. It MAY display it as unsupported.

`req` marks processing that a later document requires before holders may spend. A wallet that implements the named processing applies that document instead.

### Sending

A send is one BRC-100 `createAction`:

1. Inputs are verified outputs of one token.
2. Outputs are the recipient output and, when needed, one change output, each written in the token's layout (see Compatibility). Output amounts sum to exactly the input amount. A wallet MUST refuse a send that would burn value unless the user asked for a burn.
3. The user approves the action with the token, the amount and the recipient shown. A satoshi payment grant, an auto-pay limit or a generic basket grant MUST NOT authorize it.

The sender broadcasts through its ordinary transaction path. Delivery never gates broadcast, and a failed delivery never becomes a second transfer.

### Delivery

The sender delivers each transfer as a BRC-169 §7 envelope to box `inbox` at the recipient's messagebox, resolved per BRC-169 §5. `payment` is `null`. `content` is encrypted to the recipient per BRC-78. Its plaintext is a UTF-8 JSON object, optionally preceded by an implementation tag of ASCII letters, digits and `-`, ending in `:`. Receivers strip a tag before parsing.

```json
{
  "version": 1,
  "kind": "tip",
  "text": "Sent you 100 GOLD",
  "meta": {
    "txid": "<transfer txid, hex>",
    "item": true,
    "asset": {
      "kind": "fungible",
      "tokenId": "<deploy txid>_0",
      "amount": "100",
      "sym": "GOLD",
      "dec": 0
    },
    "beefB64": "<Atomic BEEF of the transfer, base64>",
    "tokenLineage": "<BEEF of same-token ancestors, base64>"
  }
}
```

| Member | Meaning |
|---|---|
| `version`, `kind`, `item` | Fixed: `1`, `"tip"`, `true` |
| `text` | Display summary. Not used for validation |
| `meta.txid` | The transfer transaction |
| `meta.asset.tokenId` | The token id in BRC-162 display form |
| `meta.asset.amount`, `sym`, `dec`, `icon` | Display claims. The recipient reads amounts from scripts and display fields from the deploy |
| `meta.beefB64` | BRC-95 Atomic BEEF with the transfer as subject |
| `meta.tokenLineage` | BRC-62 BEEF of the same-token ancestors of the transfer, back to the deploy, with the deploy's merkle path when mined |

Receivers ignore unknown members.

The sender MUST attach `beefB64`. It SHOULD attach `tokenLineage`, omitting it only when the envelope would exceed the box's size limit. The recipient then fetches each missing ancestor body by txid from any source. A body must hash to its txid, so a source can withhold lineage but not forge it.

The sender keeps each undelivered transfer in durable wallet state and retries delivery. A repeat message for a transfer already received is the same transfer.

### Receiving

A recipient processes a transfer message in this order:

1. finds the transfer's value outputs of `meta.asset.tokenId` locked to its identity address;
2. runs the verification above and the required-processing check;
3. records the outputs under the filing name `p2pft` with `internalizeAction`;
4. only then acknowledges the message.

A recipient MUST NOT acknowledge a message it has not durably recorded or declined. It MAY broadcast the transfer's BEEF itself; broadcasting is idempotent.

## Security considerations

- **Evidence grows with history.** A walk covers the token's history since the deploy, less what the recipient has verified before. Tokens traded through long chains produce large lineage, which a sender may omit and a recipient then fetches.
- **Unconfirmed transfers.** Lineage proves validity, not finality. A recipient handles an unmined transfer under its ordinary rule for unmined receipts and shows it as unconfirmed.
- **Claims.** `customInstructions`, tags and every display member of the message are forgeable. Amounts come from scripts and validity from the walk.
- **Unsupported tokens.** Refusing a non-empty `req` stops a token that needs extra processing from showing as an ordinary balance.
- **Address reuse.** Every transfer to a recipient lands on the same identity address, which links that recipient's receipts on chain.
- **Privacy of lineage.** Delivered lineage shows the recipient the token's history, which is already public on chain.

## Implementations

- **HandCash Desktop and Mobile** (`@handcash/wallet-ui`, source `src/wallet/token/` in [HandCash/HANDCASH-DESKTOP](https://github.com/HandCash/HANDCASH-DESKTOP)), from version 1.3.555:
  - BRC-162 deploys and sends in the current layout;
  - files outputs under `p2pft`, with tags `p2pft` and `p2pft:<tokenId>` and the remittance fields defined here;
  - delivery and receipt as above (tag `handcash-message:`), with lineage up to 96 KB, offline proving with recorded verdicts, and missing bodies fetched by txid;
  - refusal of tokens with a non-empty `req`;
  - script validation of every same-token input on the walk, mined or not;
  - unverified outputs kept out of the spendable balance and shown as checking until a walk verifies them.
