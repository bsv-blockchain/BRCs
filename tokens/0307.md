# BRC-307: Sigma — Transaction-Bound Script Signatures

David Case / b-open-io (david.case@shruggr.cloud)  
Luke Rohenaz / b-open-io

## Abstract

This BRC defines **Sigma**: a way to attach a digital signature to a transaction **output script** so that the signature is bound to (1) a chosen **input outpoint** and (2) the **script bytes before the Sigma tape**. The signature cannot be copied onto a different inscription or script unchanged.

1Sat uses Sigma for issuer-bound mints (e.g. [BRC-304](./0304.md) user-minted collections). This document specifies on-output layout, the signed message, and verification.

## Motivation

Detached signatures over metadata alone can be replayed onto counterfeit outputs. Sigma signs a hash derived from transaction context and the output script **excluding** the signature itself, so the seal moves only with that script and the referenced input.

## Specification

### Placement on the output

Sigma is appended to the **locking script** of the signed output as a bitcom-style protocol tape:

```
<script-before-sigma>
OP_RETURN          // or "|" if OP_RETURN already present
  "SIGMA"
  <algorithm>
  <signer>
  <signature>
  <vin>
```

Rules:

* Sigma MUST live in the **`OP_RETURN` data path** of the locking script (bitcom-style protocol after return).  
* If the script has **no** prior `OP_RETURN`, the tape **MUST** begin with `OP_RETURN` then `"SIGMA"`.  
* If the script **already** has `OP_RETURN` (e.g. MAP), the Sigma tape is appended with a **`|`** separator push (ASCII `0x7c`), then `"SIGMA"` — not a second `OP_RETURN`.  
* Protocol id is the UTF-8 string **`SIGMA`**.  
* Multiple Sigma instances on one output are allowed; they appear as successive `|` / `SIGMA` segments after the initial `OP_RETURN`. Instance index is 0-based in order of appearance.

### Fields (after `"SIGMA"`)

| Order | Field | Encoding | Meaning |
|-------|--------|----------|---------|
| 1 | algorithm | UTF-8 push | Signature scheme id (see below) |
| 2 | signer | UTF-8 push | Signer identity for the algorithm. For **`BSM`**: Bitcoin address string. For other algorithms: as defined by that algorithm. |
| 3 | signature | binary push | Signature bytes (see below) |
| 4 | vin | UTF-8 push of decimal digits | Input index used for the input hash |

**Algorithm.** Implementations used for 1Sat collection mints use **`BSM`** (Bitcoin Signed Message). Other algorithm strings MAY appear; verifiers that do not implement them MUST treat those instances as invalid for rules that require a valid Sigma.

**Signature (BSM).** 65-byte **compact** recoverable signature: 1 recovery byte + 32-byte `r` + 32-byte `s` (same shape as common BSM compact signatures).

**vin.** Decimal string of the transaction input index whose outpoint is hashed (e.g. `"0"`). This selects which input binds the signature.

### Signed message (transaction-bound Sigma)

Verification builds a message hash from the transaction and the target output, then checks BSM against the **signer** field (for `BSM`, the address).

#### Input hash

Let `I` be the transaction input at index `vin` (from the Sigma field).

```
outpoint_bytes = txid_bytes(32) || vout_uint32_le(4)
input_hash     = SHA256(outpoint_bytes)
```

`txid_bytes` is the 32-byte transaction id as used in Bitcoin outpoints (implementation byte order MUST match the signer and the 1Sat reference verifiers).

#### Data hash

Let `S` be the full locking script of the **target output** (the output that carries this Sigma tape).

Find the `OP_RETURN` or `|` separator immediately before the `"SIGMA"` push for **this** Sigma instance (0-based among Sigma tapes on that script). Let `prefix` be the script bytes **strictly before** that separator.

```
data_hash = SHA256(prefix)
```

If no Sigma separator is found, `data_hash = SHA256(S)` (entire script). The signature tape itself is never included in `prefix`.

#### Message hash

```
message_hash = SHA256( input_hash || data_hash )
```

(32-byte input hash concatenated with 32-byte data hash, then SHA256.)

#### BSM verify

Treat `message_hash` as the **message bytes** for Bitcoin Signed Message verification with the **signer** field (address) and the compact signature (i.e. apply the usual BSM magic/hashing as in Bitcoin Signed Message, with those 32 bytes as the message payload).

The instance is **valid** if and only if BSM verification succeeds.

### What is bound

A valid Sigma asserts that the holder of **signer** authorized:

* spending (or committing to) the **specific input outpoint** at `vin`, and  
* the **script content before the Sigma tape** on the target output (inscription, MAP, lock prefix, etc.).

Changing the inscription, MAP, or parent field, or moving the tape onto another script, invalidates the signature. Changing only bytes after the separator (the Sigma fields themselves) is outside the signed prefix by design.

### Target output

Unless otherwise specified by the application, the **target output** is the output whose locking script contains the Sigma tape being verified. Collection rules in [BRC-304](./0304.md) use that output’s valid Sigma signer as the item issuer.

### Informative: wallet mint flow

1Sat wallet Sigma inscribes often:

1. Build the inscription (+ MAP) script with a **placeholder** Sigma tape (fixed-length zero signature) so fees are stable.  
2. Create an **anchor** input outpoint (or use a known input).  
3. Compute the real signature over that outpoint + script prefix and replace the placeholder.

That flow is implementation detail; only the final on-chain tape and verify rules are normative here.

* AIP or other detached metadata signatures  

## Security considerations

* **Replay** — Without input + script binding, metadata signatures can be copied; Sigma exists to prevent that for the signed prefix.  
* **vin choice** — Signers MUST use an input they control; verifiers MUST use the `vin` field in the tape.  
* **Instance index** — When multiple Sigma tapes exist, each is verified with its own instance index for locating `prefix`.  
* **Signer format** — for `BSM`, signer must be the address string BSM verify expects; mismatched network or encoding fails verification.
