# BRC-259: Address-Bound Ownership Proof with Bitcoin Signed Message

RexStarBSV (RexStarBSV@protonmail.com)

## Abstract

This BRC specifies how the holder of a pay-to-public-key-hash (P2PKH) address proves, to a verifier who asks, that they control the key of that address. The verifier issues a short plain-text challenge with a fixed first line, `BSV address ownership challenge v1`, followed by named fields in a fixed order: an optional purpose, verifier name and address, the network, a 128-bit nonce, the time of issue and an optional expiry. The holder signs the challenge text exactly as it stands with the Bitcoin Signed Message (BSM) construction, using the key of the address, and returns the text, the address and the 65-byte compact signature, either as three separate values or in one armoured block. The verifier then applies an ordered list of fail-closed rules, each with a named result code: the proof must parse, the address must be P2PKH and for the verifier's network, the signature must recover a key whose hash in the form the signature's header names equals the address, the text must be a well-formed challenge whose address and network lines agree, the challenge must be fresh, and, when the verifier issued it, its nonce must not have been used before.

The signature layer is the existing BSM scheme, unchanged, so any wallet that can verify a signed message can check the signature. This document pins that scheme down byte for byte, closes the compression-flag and network gaps that make one wallet's proof fail in another, and adds the challenge and freshness layer above it.

## Overview: what this BRC does

**The problem.** Someone tells you an address is theirs, and you want to be sure before you pay to it, credit a deposit from it, or return coins to it. The usual answer is "sign a message with it", but nobody says which message. The signature you get back may be months old, may have been made for someone else, and may pass in your wallet and fail in the next one.

**The idea.** The party who asks, the verifier, writes the message. It is a short text with a fixed first line and a few named lines: who is asking, why, which address, which network, a random number used once (the nonce), when it was issued and when it expires. The owner signs that exact text with the key of the address, using the Bitcoin Signed Message scheme that wallets already have. The verifier checks the signature strictly, checks that the text is a well-formed challenge for its network, that it is still current, and that its nonce has not been used before. If every check passes, someone holding the key signed the verifier's own question after it was asked. Nothing goes on chain and no coins move.

**A worked example.** Test vector V1 is this exchange in bytes.

1. *The verifier asks.* Example Exchange wants to pay a withdrawal to `194sjtY7LtC3P886FTepA5Q42VGqrwTK86` for account 4471. Its server draws a 128-bit random nonce, writes the challenge shown in section 3.2 with an expiry 15 minutes after issue, stores the nonce and the text as unused, and shows the text to the customer.
2. *The owner signs.* The customer pastes the text into their wallet. The wallet parses it, finds it current and for mainnet, and shows who asks (Example Exchange), why (a withdrawal check for account 4471), which address will sign and when the challenge expires. The customer approves. The wallet signs the text with the key of that address and returns the armoured block of section 5.2: the text, the address and an 88-character signature, 490 bytes in all.
3. *The verifier checks.* The exchange recovers a public key from the signature, hashes it in the form the signature's first byte names, and gets the address back. The text is a well-formed mainnet challenge, it names the same address, the check time is before `Expires`, and the nonce is one the exchange issued and has not used. The exchange marks the nonce used and reports `proven`.

What each side sees: the customer sees only the challenge and their own address. No secret leaves the wallet; the signature reveals the public key of the address, which the first spend from that address reveals anyway. The exchange sees the text, the address and the signature, and learns that someone able to use the key signed its challenge between the moment it issued the nonce and the moment it checked. Anyone either side later shows the proof to can check the signature too, but only the exchange can tell whether the nonce had been used before.

**What it does not do.** It does not show that the address holds coins, who the signer is, that nobody else has the key, or that the signer will still have it tomorrow. It does not cover P2SH, multisig or other script addresses, or keys derived under BRC-42. It defines no login session and no transport, and it needs no server, overlay or transaction.

**Who implements what.**

- A verifier (an exchange, payment processor, auditor, escrow agent or support tool) implements challenge issuing (section 3), the checks (sections 4.3, 5 and 6) and, if it acts on proofs, the record of issued nonces (section 6.5).
- A wallet or signing device implements the signer rules (section 7): parse the challenge, show it, sign the exact text with the right key form, and check its own proof.
- Software that only displays a proof someone pasted implements sections 4.3, 5 and 6 without a nonce record, and shows `NONCE_UNCHECKED`.
- A library that already verifies signed messages needs one change at the signature layer to be usable here: honour the key form the header byte names (section 4.3).

## Motivation

Exchanges, payment processors, auditors, escrow agents and support desks regularly need to know that a person controls a given address: before sending a withdrawal to it, before crediting a deposit claimed by a customer, when a customer asks for coins sent to a wrong address to be returned, or when a counterparty asks for proof of funds. The common practice in BSV and in Bitcoin generally is to ask for a signed message. That practice has three weaknesses, and each one shows up as a dispute or a false result.

1. **No fixed text.** The verifier asks for "a signed message" and the holder signs whatever they are told or whatever they choose. Nothing in the text says who asked, for what, or when, so the same signature can be replayed to a second verifier, or reused months later, and nobody can tell. A signature over a bare address or the word "test" proves control at some unknown time to nobody in particular.
2. **Lenient checks that do not agree.** BSM signatures carry a header byte that says whether the signing key was compressed. Some libraries ignore it and accept a match on either key form; others honour it. A proof made by a wallet that sets the flag wrongly passes in the first kind and fails in the second, so two honest verifiers reach different verdicts on the same bytes. Testnet, regtest and the scaling test network also share one address prefix, and a library that compares only the 20-byte hash will accept a test-network address where a mainnet one was asked for.
3. **No freshness or single use.** Without a nonce, an issue time and an expiry inside the signed text, a verifier cannot tell a proof made today from one captured last year.

The BRC series has no standard for this. [BRC-3](../wallet/0003.md) and [BRC-77](./0077.md) sign with keys derived under [BRC-42](../key-derivation/0042.md) and [BRC-43](../key-derivation/0043.md) from an identity key, so they cannot show control of the key behind a particular P2PKH address. BRC-77 names BSM in its motivation as the scheme it improves on, without specifying it. [BRC-138](./0138.md) defines single-use, expiring proofs, but for identity keys under derived-key signatures. [BRC-137](../opinions/0137.md) requires an application to "verify control of the connecting account" with "a SIWE-style (or chain-equivalent) message" against a single-use nonce, and [BRC-189](../wallet/0189.md) puts "Who controls this key now?" first among five questions that must remain distinct, to be established "through a fresh authenticated exchange or other applicable proof of control". Neither says what the BSV form of that message is for an address. This document is one concrete answer for P2PKH addresses.

BSM itself is old and widely implemented, and this document does not invent it. [BRC-217](../tokens/0217.md) section 4.3 already states the BSM preimage byte for byte for one use, and [BRC-248](./0248.md) uses BSM compact signatures with a recover-and-compare-address rule for another. This document makes the same move for address ownership and adds only what that use needs.

## Scope and conformance

**Layer.** This is an **Interface** standard: it fixes the bytes that cross between a verifier and a wallet (the challenge, the signature and the proof) and the checks that give both sides the same verdict. Section 6.4 carries a **Policy** part, the freshness defaults, which a verifier may set differently and must then state.

**Conformance targets.** A MUST in this document binds one of two parties and nobody else:

- *a verifier that claims this profile*: software that issues challenges, checks proofs, or both, and says it follows this document;
- *a signer that claims this profile*: a wallet or signing device that produces proofs from challenges and says it follows this document.

A wallet that offers generic message signing without claiming this profile is not bound by it. Such a wallet "does not follow this BRC"; it is not thereby wrong, and its signatures are not invalid BSM signatures.

**What a proof shows.** A proof that passes every rule shows that, at some time between the challenge's issue and the moment the verifier checked it, someone able to use the private key of the named P2PKH address signed that exact challenge. It does not show that the address still holds coins, that nobody else also holds the key, who the signer is in any real-world sense, or that the signer will control the key tomorrow.

**Non-goals.** This document does not cover:

- P2SH, bare multisig, threshold or guarded scripts, or any address that is not P2PKH. A script with more than one key has no single key whose signature proves control, and proving one cosigner's key would mislead.
- Keys derived under BRC-42 or identity keys. BRC-77 and BRC-138 serve those.
- Proof of funds. A verifier that wants to know the balance looks it up; the proof binds a person to an address, not to coins.
- Login sessions, cookies or tokens issued after a proof. What a verifier does after a proof passes is its own affair.
- Transport. The challenge and proof are plain text and may travel by web form, file, e-mail, chat or QR code.

**What is not required.** Storage of issued challenges is required only of a verifier that relies on single use (section 6.5), and its form is the verifier's choice. User-interface layout, languages, how a signer chooses among its keys, how the challenge reaches the signer and how the proof comes back are all left to the implementer. Nothing here needs a network connection, a server, an overlay or a transaction.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be read as in RFC 2119 and RFC 8174 when, and only when, they appear in capitals.

### 1. Terminology

- **Challenge**: the text a verifier issues, in the grammar of section 3.
- **Normalised text**: a text after the normalisation of section 5.1. Signatures are made and checked over the normalised text only.
- **Proof**: a normalised challenge together with an address and a signature, in either form of section 5.
- **Header byte**: the first byte of the 65-byte compact signature.
- **Network**: one of `mainnet`, `testnet`, `regtest` or `stn` (the scaling test network).
- **Verifier network**: the one network a verifier is checking for. A verifier that serves more than one network runs the rules once per proof with the network it expects for that proof.
- **Check time**: the verifier's clock reading, in whole seconds since 1970-01-01T00:00:00Z without leap seconds, when it runs the rules.

### 2. Networks and addresses

An address in this document is a P2PKH address: the Base58Check encoding of one version byte followed by the 20-byte HASH160 (RIPEMD-160 of SHA-256) of a public key.

| Version byte | Address class | Networks |
|---|---|---|
| `0x00` | main | `mainnet` |
| `0x6f` | test | `testnet`, `regtest`, `stn` |

Every other version byte, including the P2SH bytes `0x05` and `0xc4`, and every decoded payload that is not exactly 21 bytes, is not a P2PKH address for this document.

The three test networks share one version byte, so an address alone cannot say which test network it belongs to. The `Network` line of the challenge is signed and is therefore the authoritative statement of the network (section 6, rule 7).

### 3. The challenge

#### 3.1 Layout

A challenge is UTF-8 text made of lines separated by a single line feed (`0x0a`). The first line is exactly:

```
BSV address ownership challenge v1
```

Each further line is one field, written as the field name, a colon, exactly one space (`0x20`), and the value. The fields, in the only order allowed, are:

| Field | Required | Value |
|---|---|---|
| `Purpose` | no | free text (section 3.3), what the proof will be used for |
| `Verifier` | no | free text, the name of the party asking |
| `Address` | no | a P2PKH address of either class (section 2); when present, the proof must be for this address |
| `Network` | yes | `mainnet`, `testnet`, `regtest` or `stn` |
| `Nonce` | yes | exactly 32 lower-case hexadecimal characters (`0` to `9`, `a` to `f`), 128 bits |
| `Issued` | yes | a time (section 3.4) |
| `Expires` | no | a time (section 3.4) |

Each field appears at most once. Field names are case-sensitive. A value has no white space at either end, and an `Address` value is base58 characters only, so `Address:` followed by two spaces is not a field line. There is no blank line, no comment, no line other than the header and these fields, and no line ending after the last field. Unknown fields are not allowed; a later layout will have a different header line (for example `... v2`), and a verifier that claims this profile treats such text as not a challenge.

The whole normalised challenge is at most 1,000 bytes in UTF-8, so that a proof fits in one QR code.

A verifier that claims this profile MUST generate the nonce from a cryptographically secure random source, MUST NOT issue two challenges with the same nonce, and MUST emit only text that its own parser accepts.

#### 3.2 Example

The first valid test vector's challenge:

```
BSV address ownership challenge v1
Purpose: Withdrawal check for account 4471
Verifier: Example Exchange
Address: 194sjtY7LtC3P886FTepA5Q42VGqrwTK86
Network: mainnet
Nonce: 9f2c1e7a0b5d4c3e8a7f6b1c2d3e4f50
Issued: 2026-11-13T10:00:00Z
Expires: 2026-11-13T10:15:00Z
```

#### 3.3 Free text

`Purpose` and `Verifier` values are 1 to 120 Unicode code points. The first and last code points MUST NOT be white space (Unicode `White_Space`). No code point may have the general category `Cc` (control, including tab), `Cf` (format, including the bidirectional overrides and zero-width characters), `Cs`, `Co`, `Cn`, `Zl` or `Zp`. No Unicode normalisation is applied, by either side: the bytes are what they are.

The set of unassigned code points (`Cn`) shrinks with each Unicode version, so two verifiers on different Unicode versions can disagree about a code point assigned between them. A verifier SHOULD NOT put recently assigned code points in these fields.

#### 3.4 Times

A time is `YYYY-MM-DDTHH:MM:SSZ` in UTC with ASCII digits only (`0x30` to `0x39`; other Unicode digits, such as full-width ones, are refused): a valid Gregorian date with a year from 0001 to 9999, hours 00 to 23, minutes and seconds 00 to 59, no fractional seconds, no offset other than the literal `Z`.

#### 3.5 Grammar

The grammar in ABNF (RFC 5234, with RFC 7405 `%s` for case-sensitive strings). Free-text characters, white space at the ends and the address check are stated in prose above, because ABNF cannot express them in a useful way.

```
challenge     = header
                [LF purpose-line] [LF verifier-line] [LF address-line]
                LF network-line LF nonce-line LF issued-line
                [LF expires-line]
header        = %s"BSV address ownership challenge v1"
purpose-line  = %s"Purpose: " free-text
verifier-line = %s"Verifier: " free-text
address-line  = %s"Address: " p2pkh-address
network-line  = %s"Network: " network
nonce-line    = %s"Nonce: " 32lhex
issued-line   = %s"Issued: " utc-time
expires-line  = %s"Expires: " utc-time
network       = %s"mainnet" / %s"testnet" / %s"regtest" / %s"stn"
lhex          = DIGIT / %x61-66
utc-time      = 4DIGIT "-" 2DIGIT "-" 2DIGIT %s"T"
                2DIGIT ":" 2DIGIT ":" 2DIGIT %s"Z"
free-text     = 1*120text-char   ; section 3.3
text-char     = %x20-7E / %x80-10FFFF  ; less the categories of section 3.3
p2pkh-address = 25*34base58char  ; must decode as in section 2
base58char    = %x31-39 / %x41-48 / %x4A-4E / %x50-5A / %x61-6B / %x6D-7A
LF            = %x0A
```

### 4. The signature

#### 4.1 Preimage and digest

Let `M` be the normalised challenge as UTF-8 bytes. The preimage is

```
VARINT(24) || "Bitcoin Signed Message:\n" || VARINT(len(M)) || M
```

where the magic string is the 24 ASCII bytes shown, the last of which is a single line feed (`0x0a`), so `VARINT(24)` is the one byte `0x18`. `VARINT(x)` is `x` as one byte when below `0xfd`, else `0xfd` and two little-endian bytes. A challenge of at most 1,000 bytes always uses the one-byte or three-byte form. The digest is SHA-256 applied twice to the preimage. This is the construction of BRC-217 section 4.3.

#### 4.2 Compact signature

The signature is an ECDSA signature over the digest on secp256k1, in 65 bytes:

```
header (1 byte) || r (32 bytes, big-endian) || s (32 bytes, big-endian)
```

The header byte is `27 + recid` when the signing key's public key is used in its 65-byte uncompressed form, and `31 + recid` when it is used in its 33-byte compressed form, where `recid` (0 to 3) is the recovery id. A header byte outside 27 to 34 is invalid. As text, the 65 bytes are written in standard Base64 (RFC 4648 section 4) with padding: 88 characters, the last of which is `=`.

A signer that claims this profile MUST write canonical Base64 (pad bits zero) and SHOULD produce a low-S signature with an RFC 6979 deterministic nonce. A verifier that claims this profile MUST accept a high-S signature: the proof is an off-chain message where malleability does no harm, and a signer that does not normalise `s` produces a high-S signature about half the time. The high-S twin of a valid signature, with `s` replaced by `n - s` and the low bit of `recid` flipped, is therefore also valid, and a verifier MUST NOT treat signature bytes as a unique identifier of a proof.

#### 4.3 Recovery and the strict address check

To check a signature against an address, a verifier that claims this profile:

1. decodes the Base64 text strictly (only the Base64 alphabet and padding, after removing white space at the two ends) and requires exactly 65 bytes with a header byte from 27 to 34;
2. takes `compressed = (header >= 31)` and `recid = (header - 27) mod 4`;
3. recovers the public key from `r`, `s`, `recid` and the digest of section 4.1, and verifies the signature under that key;
4. computes HASH160 of the recovered key **serialised in the form the header names** (33 bytes when `compressed`, 65 bytes otherwise) and requires it to equal the 20-byte hash of the address.

Step 4 is stricter than some existing libraries, which try both key forms and accept either. A verifier that claims this profile MUST NOT accept the other form. A signer that claims this profile MUST set the header to the form whose hash is the address being proven: an uncompressed-key address (common among old imported keys) needs header 27 to 30. Without this rule, a proof that one wallet accepts fails in another, which defeats a proof meant to be shown to someone else.

### 5. The proof

#### 5.1 Normalisation

Before signing and before verifying, a text is normalised: every CR LF pair becomes LF, then every remaining CR becomes LF, then white space is removed from the two ends. Nothing else changes: no Unicode normalisation, no change inside lines, no change to letter case.

A conforming challenge already has no CR and no white space at its ends, so for a challenge made by a verifier that claims this profile, normalisation changes nothing; it exists so that a proof that passed through a system that rewrote line endings, or added a final line feed, still checks. Implementations differ in which code points they count as white space when trimming. A signer MUST sign the normalised text, and a verifier MUST check the normalised text, so a proof made from a conforming challenge is not affected by those differences.

#### 5.2 The armoured block

A proof as one text is:

```
-----BEGIN BITCOIN SIGNED MESSAGE-----
<the normalised challenge, one or more lines>
-----BEGIN SIGNATURE-----
<the address>
<the Base64 signature>
-----END BITCOIN SIGNED MESSAGE-----
```

with lines separated by LF and no line ending after the last line. A verifier that claims this profile parses it after normalising the whole block (section 5.1) and MUST refuse it with `PARSE` unless all of the following hold:

- the first line is exactly `-----BEGIN BITCOIN SIGNED MESSAGE-----` and the last line exactly `-----END BITCOIN SIGNED MESSAGE-----`, so nothing comes before or after the block;
- each of the three marker lines occurs exactly once;
- at least one line lies between the first line and `-----BEGIN SIGNATURE-----`;
- exactly two lines lie between `-----BEGIN SIGNATURE-----` and the last line, neither of them empty after removing white space at its ends.

The message is the lines between the first line and `-----BEGIN SIGNATURE-----`, joined with LF and normalised. The address and the signature are the two following lines, each with white space removed from its ends. A challenge cannot contain a line equal to a marker line, so the split is unambiguous.

The same bytes serve as text, as a file and as a QR code payload.

The first valid test vector as an armoured block:

```
-----BEGIN BITCOIN SIGNED MESSAGE-----
BSV address ownership challenge v1
Purpose: Withdrawal check for account 4471
Verifier: Example Exchange
Address: 194sjtY7LtC3P886FTepA5Q42VGqrwTK86
Network: mainnet
Nonce: 9f2c1e7a0b5d4c3e8a7f6b1c2d3e4f50
Issued: 2026-11-13T10:00:00Z
Expires: 2026-11-13T10:15:00Z
-----BEGIN SIGNATURE-----
194sjtY7LtC3P886FTepA5Q42VGqrwTK86
IF8m3ia3adct/Uii1ZvbT7+uTB5/wgsJvzcp+Akbg9I9Tdpnuw17H6PnTWIU4vrOjjaJs6tHnzExdnpFsril128=
-----END BITCOIN SIGNED MESSAGE-----
```

#### 5.3 The three-part form

Generic message-signing screens commonly take a signed message as three separate fields: message, address and signature. A verifier that claims this profile MUST also accept a proof given that way. It normalises the message, removes white space from the ends of the address and the signature, and runs section 6 from rule 2. The three-part form and the armoured block carry the same proof and give the same result.

Because the signature layer is unchanged BSM, a person who has no software that claims this profile can still check the signature alone by pasting the three parts into any wallet that verifies signed messages, provided that wallet does not alter the message. That check says nothing about freshness, network or single use, and a lenient wallet may also accept a wrong compression flag.

### 6. Verifier rules

#### 6.1 The rules in order

A verifier that claims this profile runs these rules on every proof, in this order, and fails closed: a rule that cannot be evaluated, for any reason, fails.

| # | Code | Rule | On failure |
|---|---|---|---|
| 1 | `PARSE` | The armoured block parses (section 5.2). Not run for the three-part form. | stop, `not-proven` |
| 2 | `ADDRESS_TYPE` | The address is a P2PKH address of either class (section 2). | `not-proven` |
| 3 | `ADDRESS_NETWORK` | The address class is the class of the verifier network. Skipped if rule 2 failed. | `not-proven` |
| 4 | `SIGNATURE` | The signature checks against the address under section 4.3, over the normalised message. Skipped if rule 2 or 3 failed. | `not-proven` |
| 5 | `NOT_CHALLENGE` | The normalised message is a challenge under section 3, including the 1,000-byte limit. | see 6.2; rules 6 to 11 are skipped |
| 6 | `ADDRESS_LINE` | If the challenge has an `Address` line, its value equals the proof's address, character for character. | `not-proven` |
| 7 | `NETWORK_LINE` | The `Network` line equals the verifier network. | `not-proven` |
| 8 | `FUTURE` | `Issued` is not more than 300 seconds after the check time. | `valid-not-fresh` |
| 9 | `EXPIRED` | If `Expires` is present, the check time is before `Expires`. If it is absent, the check time is not more than the maximum age (section 6.4) after `Issued`. | `valid-not-fresh` |
| 10 | `WINDOW` | If `Expires` is present, `Expires - Issued` is more than 0 and at most 2,592,000 seconds (30 days). | `valid-not-fresh` |
| 11 | `NONCE` | Section 6.5. | `not-proven` |

Rule 7 is how a verifier tells the three test networks apart (section 2): a regtest address in a challenge whose `Network` line says `testnet` fails at a regtest verifier and at a testnet verifier alike.

A verifier SHOULD evaluate and report every rule, not only the first failure, so that a person can see which ones passed.

#### 6.2 The result

The result is exactly one status, and for every status but `proven` the code of the rule that decided it:

1. If rule 1, 2, 3 or 4 failed, the status is `not-proven` with the code of the first of them that failed.
2. Otherwise, if rule 5 failed, the status is `not-a-challenge`. The signature is a valid BSM signature by the address's key over some text, but that text is not a challenge, so the proof says nothing about who asked, for what, or when. A verifier MUST NOT present `not-a-challenge` as `proven` and SHOULD say plainly that the text is not an ownership challenge.
3. Otherwise, if rule 6, 7 or 11 failed, the status is `not-proven` with the code of the first of them that failed.
4. Otherwise, if rule 8, 9 or 10 failed, the status is `valid-not-fresh` with the code of the first of them that failed. The signature and the challenge are good but the proof is not current, and a verifier MUST NOT present this as `proven`.
5. Otherwise the status is `proven`. If rule 11 passed only because the verifier holds no record of the nonce (section 6.5), the result also carries the note `NONCE_UNCHECKED`, and the verifier MUST show that reuse was not checked.

Status words in this document mean only these verdicts of a verifier on its own clock. None of them means that anything was broadcast, recorded on chain or accepted by any other party.

#### 6.3 Freshness

Times are compared as whole seconds. A challenge's `Issued` may be up to 300 seconds ahead of the verifier's clock (rule 8), to allow for the issuing clock and the checking clock to differ when they are not the same machine. There is no tolerance after `Expires`: a check at exactly the `Expires` second fails.

#### 6.4 Defaults (Policy)

| Parameter | Value in this profile |
|---|---|
| Clock skew allowed on `Issued` (rule 8) | 300 seconds |
| Maximum age when there is no `Expires` line (rule 9) | 86,400 seconds (24 hours), configurable |
| Longest `Expires - Issued` window (rule 10) | 2,592,000 seconds (30 days) |

A verifier MAY configure a different maximum age. If it does, it SHOULD say so to the people it asks for proofs, because a signer that claims this profile warns its user on the assumption of 24 hours (section 7). A verifier that issues challenges SHOULD include an `Expires` line, and SHOULD keep the window short (minutes, not days) when the proof gates an action such as a withdrawal.

#### 6.5 Nonce single use

A verifier that issues challenges and relies on single use keeps a record of each challenge it issued: at least the nonce, the exact normalised text, and whether it has been used. When rule 11 runs:

- If the verifier holds a record with this nonce, then the record's text MUST equal the normalised challenge exactly, and the record MUST NOT be marked used; otherwise rule 11 fails.
- If every other rule has passed, the verifier MUST mark the record used, durably and atomically with respect to other checks of the same nonce, before it reports `proven`. If that write fails, rule 11 fails. Two concurrent checks of one proof MUST NOT both report `proven`.
- If the verifier holds no record with this nonce, it cannot check reuse. Rule 11 passes with the note `NONCE_UNCHECKED` (section 6.2). This is the normal case for a third party who checks a proof issued by someone else.

A verifier that issued a challenge for its own use, such as a login or a withdrawal check, SHOULD treat `NONCE_UNCHECKED` as insufficient, because it means the record that would stop a replay is missing.

Records MAY be deleted once the check time is past the record's `Expires`, or past `Issued` plus the maximum age when there is no `Expires`; after that, rule 9 refuses the proof anyway.

### 7. Signer rules

A signer that claims this profile, when asked to produce an ownership proof:

1. MUST parse the text as a challenge under section 3 before anything else, and MUST NOT produce an ownership proof from a text that does not parse. It MAY point the user to a generic message-signing function, which is outside this profile.
2. MUST refuse a challenge that, on its own clock, would fail rule 8, 9 or 10.
3. MUST refuse a challenge whose `Network` line is not the network its key and wallet are on.
4. MUST, when the challenge has an `Address` line, sign only with the key of that address, and refuse if it holds no usable key for it. It MUST NOT substitute another address.
5. MUST sign only with the private key of a P2PKH address, and MUST refuse for a watch-only key, a multi-signature or other script address, or any account that has no single P2PKH key for the address.
6. MUST, before asking the user to approve, display: the `Purpose` and `Verifier` values when present; the address that will sign; the `Issued` time; and the `Expires` time, or the fact that there is none and the challenge is treated as stale 24 hours after `Issued`. It MUST either display the `Network` value or refuse every challenge whose `Network` is not its own (rule 3 above), It SHOULD label the `Purpose` and `Verifier` values as statements made by whoever sent the challenge, not checked by the signer, and SHOULD state how long remains before expiry.
7. MUST sign the normalised challenge exactly (section 5.1), with the header byte naming the key form whose hash is the address (section 4.3).
8. SHOULD check the proof it made with the rules of section 6 (without rule 11) before showing it, and MUST NOT show a proof that it has found not to verify.
9. SHOULD NOT treat the request as a spend. Signing a challenge moves no coins and needs no transaction.

A signer that cannot display the whole of the `Purpose` and `Verifier` values, such as a device with a very small screen, SHOULD refuse rather than truncate them silently, or SHOULD at least tell the user that part of the text is hidden.

#### 7.1 Domain separation

Two separations protect a signer that signs challenges:

- **From transactions.** The BSM preimage begins with the byte `0x18` and the magic string, and is hashed as a whole. A transaction signature digest is computed over a different preimage, so a BSM signature over a challenge cannot be used as a transaction signature unless SHA-256 fails. BRC-77 notes the same purpose of the magic string.
- **From other uses of BSM.** BSM uses one prefix for every application, so the prefix alone does not stop a signature made for one BSM application from being shown to another. The fixed header line `BSV address ownership challenge v1` is the first line of every signed challenge, and the grammar of section 3 leaves no room for other content. A verifier of another protocol that requires its own first line, or its own structure, will not accept a challenge as one of its messages, and a verifier that claims this profile will not accept another protocol's message as a challenge (`NOT_CHALLENGE`). A protocol that accepts any text at all as its signed message has no such protection, from this document or from anything else. Other BSM protocols SHOULD NOT start their messages with this header line.

### 8. State and exit

A signer keeps no state for this profile. The only state is the verifier's record of issued challenges (section 6.5). It contains nonces, challenge texts and used flags, nothing secret, and nothing that a third party needs. If a verifier loses it, proofs of challenges issued before the loss carry `NONCE_UNCHECKED`, and a replay is possible until those challenges expire. A verifier that moves to new software needs to carry over only unexpired records; expired ones can be dropped. Nothing in this document depends on a provider, a server or the chain, so there is nothing else to recover.

### 9. Summary of requirements

**A verifier that claims this profile**

- issues challenges only in the grammar of section 3, with a random 128-bit nonce never reused, and SHOULD include `Expires`;
- accepts both the armoured block and the three-part form;
- normalises as in section 5.1 and nothing more;
- checks the signature strictly, honouring the header's key form, and accepts high-S;
- runs the rules of section 6 in order, fails closed, and reports one of `proven`, `not-proven`, `valid-not-fresh` or `not-a-challenge` with the deciding code;
- compares the `Network` line with its own network, not only the address class;
- marks a nonce it issued as used, durably, before reporting `proven`, and shows `NONCE_UNCHECKED` when it holds no record.

**A signer that claims this profile**

- signs only parsed, fresh, same-network challenges, only with a single P2PKH key, and only for the named address when one is named;
- shows purpose, verifier, address, issue and expiry before approval;
- signs the normalised text with the header naming the right key form, in canonical Base64;
- SHOULD check its own proof before showing it.

## Cryptographic basis

### Primitives

| Primitive | Use here | Defined in |
|---|---|---|
| The curve secp256k1 | keys and signatures | SEC 2 section 2.4.1 |
| ECDSA signing and verifying | the signature over the digest | SEC 1 sections 4.1.3 and 4.1.4 |
| ECDSA public key recovery | the verifier gets the public key from the signature | SEC 1 section 4.1.6 |
| Point encoding, 33 bytes (compressed) or 65 bytes (uncompressed) | the key bytes that are hashed into the address | SEC 1 section 2.3.3 |
| SHA-256, applied twice | the message digest (section 4.1) | FIPS 180-4 |
| HASH160: RIPEMD-160 of SHA-256 | the 20-byte hash inside a P2PKH address | RIPEMD-160 (Dobbertin, Bosselaers and Preneel), FIPS 180-4 |
| Base58Check | the address as text, with a 4-byte checksum | the original Bitcoin client (`base58.cpp`); there is no RFC |
| Base64 | the signature as text | RFC 4648 section 4 |
| Deterministic nonce | the per-signature secret `k` (SHOULD) | RFC 6979 |

### Assumptions

- **ECDSA on secp256k1 is existentially unforgeable** under chosen-message attack: without the private key, nobody can produce a valid signature on a digest the key holder did not sign. This needs the elliptic-curve discrete logarithm problem (ECDLP) on secp256k1 to be hard. SEC 2 rates the curve at 128-bit strength. No proof reduces ECDSA's unforgeability to ECDLP alone; the known proofs use idealised models of the group or of the hash, and this document assumes no more than the usual assumption.
- **Double SHA-256 is collision resistant and second-preimage resistant.** The generic costs are about 2^128 evaluations for a collision and 2^256 for a second preimage.
- **HASH160 is second-preimage resistant** for an address the attacker did not make: finding another key with the same 20-byte hash costs about 2^160 generically. Its collision resistance is only about 2^80, which matters to nobody here, because a collision gives its finder two keys that they hold themselves.
- **The header byte is a hint, not a secret and not signed.** The signature does not cover it, so anyone can change it. That is safe because of step 4 of section 4.3: for any recovery id that yields a point, the recovered key satisfies the verification equation (see the next section), so a changed recovery id gives a different key that fails the address comparison, and a changed key-form bit gives a different hash that fails it too. The binding of a proof to an address is the HASH160 comparison, not the verification step.
- **The nonce is unpredictable.** It comes from a cryptographically secure random source (section 3.1).

### What a valid proof establishes

At the verifier that issued the challenge, a `proven` result establishes, under the assumptions above: a party able to compute ECDSA signatures with the private key whose public key, in the form the header names, hashes to the address signed exactly the normalised challenge, at some time after the nonce was drawn and before the check. "Able to compute signatures" includes a device or service that signs on request; the proof cannot tell a person holding the key from a signing oracle they can reach.

A third party that holds no record of the nonce gets less. The signature still binds the key to the text, but the signer could have written the text, with any `Issued` time, so nothing bounds the signing time from below.

No valid proof establishes that the address holds funds, who the signer is, that the signer is the only holder of the key, that the signer still controls the key after signing, or that the signer is the party who handed the proof to the verifier (see relay under Security Considerations).

### Separation from transaction signatures

A challenge signature is an ECDSA signature over `D_m = SHA256d(P_m)`, where `P_m` is the preimage of section 4.1. A transaction input signature is an ECDSA signature over `D_t = SHA256d(P_t)`, where `P_t` is the transaction digest preimage. One signature could serve as both only if `D_m = D_t`, which can happen in two ways.

**Equal preimages.** Laid over the two transaction digest layouts a node may use, `P_m` puts fixed bytes where the transaction needs a hash:

- *Fork-id digest* ([BRC-215](../scripts/0215.md) section 1 lists the layout): bytes 0 to 3 are the version and bytes 4 to 35 are hashPrevouts. In `P_m`, bytes 0 to 3 are `18 42 69 74`, and bytes 4 to 35 are the last 21 bytes of the magic string, the one or three bytes of `VARINT(len(M))`, and the first 10 or 8 bytes of the header line. Since a signer signs only texts that start with that header line (section 7), all 32 bytes are fixed by this document. In a transaction they are either 32 zero bytes (with `SIGHASH_ANYONECANPAY`), which they are not, or the double SHA-256 of the transaction's outpoints, so a match needs outpoints whose double hash is a given 256-bit value.
- *Original digest*: bytes 0 to 3 are the version, byte 4 is the input count and bytes 5 to 36 are the first input's previous transaction id. In `P_m`, byte 4 is `0x63` (the letter `c`), so 99 inputs (with `SIGHASH_ANYONECANPAY` the count is 1, which does not match), and bytes 5 to 36 are again fixed: the last 20 bytes of the magic string, the length bytes and the first 11 or 9 bytes of the header line. A match needs a real previous transaction whose id, a double SHA-256, is a given value. The quirk in which this digest is the constant 1 (`SIGHASH_SINGLE` with no matching output) would need `D_m = 1`, which is a preimage of double SHA-256.

`M` has 885 possible lengths (116 to 1,000 bytes, see the next section), so there are at most 885 target values. Either route costs about 2^256 / 885, roughly 2^246 hash evaluations.

**Different preimages with equal digests.** A verifier writes the challenge and could also write a transaction, so it controls both sides: the nonce and the free-text fields give it far more than 128 free bits. A match is then a double SHA-256 collision, about 2^128 evaluations by the birthday bound, which is the security level of the curve itself.

So a signed challenge is not usable as a transaction signature at any cost below the 128-bit level of the whole scheme. The byte positions above were checked by running code against the two preimage builders of the bitcoinX library.

### Why the key-form check is strict

One private key `d` gives one point `Q = dG` but two encodings: 33 bytes (`02` or `03`, then `x`) and 65 bytes (`04`, then `x` and `y`). They hash to two different HASH160 values and so to two addresses. The test key K1 has the compressed-form address `194sjtY7LtC3P886FTepA5Q42VGqrwTK86` and the uncompressed-form address `1KS4q93gbPXxSD52Q3sH7toomJyh2a3cXo`. The signature `(r, s)` commits to neither; only the header byte says which was meant.

A verifier that tries both forms accepts one signature as a proof for two addresses, and a verifier that honours the header accepts it for one. That leniency is not a forgery, since whoever holds `d` controls both addresses, but it makes two honest verifiers disagree about the same bytes, and it lets a proof asked for one address pass for another. With the rule of section 4.3, each signature proves exactly one address per address class.

### Why the freshness fields stop replay

- **Nonce.** It is unpredictable, so no signature made before the challenge was issued can match it, except with probability `q / 2^128` for `q` signatures prepared in advance. Once the issuing verifier marks it used, durably and atomically, a second use at that verifier fails with certainty.
- **Issued, Expires and the maximum age.** They give every proof a bounded life even at a verifier with no record, so a captured proof stops working at that verifier within the window of section 6.4.
- **Network.** It is inside the signed text, so a proof made for one test network cannot be replayed at a verifier for another, although all three share the address version byte.
- **Address.** When present, it binds the challenge to one address, so a challenge sent out for one address cannot come back signed by another.
- **Verifier and Purpose.** They are free text that no machine authenticates. They defend against relay only through the signer's display (section 7, rule 6).

### Malleability

Three things about a valid proof can change without the key:

- **High-S.** If `(r, s)` with recovery id `i` is valid, so is `(r, n - s)` with recovery id `i XOR 1`, for the same key and message. All four valid vectors were checked this way.
- **Base64 pad bits.** 65 bytes leave 2 spare bits in the last Base64 character, so one signature has 4 Base64 spellings, of which only the one with zero bits is canonical.
- **Text normalisation.** Line endings and white space at the two ends of the text can change in transit; section 5.1 maps every such version to the one normalised text that is signed.

None of these yields a proof for a different key, address, network or challenge. Single use is keyed on the nonce, so a changed signature is still the same challenge, and section 4.2 already forbids treating signature bytes as an identifier.

### Limits

- **Reused addresses.** Proving an address ties it, and its history, to the person; the proof is transferable, so the verifier can show that tie to others. The proof also publishes the public key of an address that may not have spent yet; that matters only to an attacker who can solve ECDLP.
- **Key compromise.** A stolen or shared key proves exactly as well as the owner's. Proofs signed before a compromise stay valid signatures, and nothing revokes them.
- **Phishing of the Verifier field.** `Verifier` and `Purpose` are what the verifier chose to write. An attacker can relay a genuine challenge to a victim, or write one that names a party the victim trusts, using confusable letters if need be. The signer's display is the only defence, and a person has to read it.
- **Signing oracles.** A wallet, device or service that signs any challenge put to it without a person reading it gives a proof to whoever asks. Section 7 narrows what a conforming signer signs, but cannot help a key that is also exposed to unrestricted message signing.
- **Clocks.** Freshness is only as good as the verifier's clock (Security Considerations).

## Mathematical basis

### Curve and keys

The curve is `y^2 = x^3 + 7` over the field of integers modulo `p = 2^256 - 2^32 - 977`, with base point `G` of prime order

```
n = FFFFFFFF FFFFFFFF FFFFFFFF FFFFFFFE BAAEDCE6 AF48A03B BFD25E8C D0364141
```

and cofactor `h = 1` (SEC 2 section 2.4.1, which writes `p` as `2^256 - 2^32 - 2^9 - 2^8 - 2^7 - 2^6 - 2^4 - 1`, the same number). A private key is an integer `d` with `1 <= d <= n - 1`, and its public key is `Q = dG`.

### Message digest

For the normalised challenge `m` as UTF-8 bytes:

```
H(m) = SHA256(SHA256(0x18 || "Bitcoin Signed Message:\n" || VARINT(len(m)) || m))
e    = H(m) read as a 256-bit big-endian integer
```

`VARINT(len(m))` is one byte for `len(m) <= 252` and three bytes (`0xfd` then two little-endian bytes) for `253 <= len(m) <= 1,000`, so the preimage is `len(m) + 26` or `len(m) + 28` bytes long. V1's message is 264 bytes, so its preimage is 292. `n` is 256 bits long, so SEC 1's truncation of the hash to the bit length of `n` changes nothing.

### Signature

The signer picks `k` with `1 <= k <= n - 1` (by RFC 6979 when following the SHOULD of section 4.2), computes `R = kG = (x_R, y_R)` and

```
r = x_R mod n
s = k^-1 (e + r d) mod n
recid = (y_R mod 2) + 2 * [x_R >= n]
header = 27 + recid + 4 * c        (c = 1 for the 33-byte key form, 0 for the 65-byte form)
```

restarting with a new `k` if `r = 0` or `s = 0`. The header is therefore 27 to 34. The 65 bytes `header || r || s` are written in Base64 as 88 characters ending in one `=`.

`x_R >= n` needs `x_R` in the range `n` to `p - 1`. That range holds `p - n`, about 2^128.35, of the roughly `p` possible x-coordinates, so for an honest signature `recid` is 2 or 3 with probability about 2^-127.65. A verifier still has to handle those values.

### Recovery

Given `(r, s, recid)` and `e`, the verifier:

1. requires `1 <= r <= n - 1` and `1 <= s <= n - 1` (SEC 1 section 4.1.4, step 1);
2. sets `x = r + (recid >> 1) * n` and requires `x < p`;
3. computes `y` as a square root of `x^3 + 7` modulo `p`, which, since `p mod 4 = 3`, is `(x^3 + 7)^((p + 1) / 4) mod p`, and requires `y^2 = x^3 + 7`; if the low bit of `y` differs from `recid & 1`, it replaces `y` by `p - y`; this gives `R = (x, y)`;
4. computes `Q = r^-1 (sR - eG)`, with `r^-1` taken modulo `n`.

This is SEC 1 section 4.1.6 for a curve with cofactor 1, where the two bits of `recid` replace the search over `j` and over the sign of `R`. The recovered key always satisfies the verification equation: `sR - eG = (e + rd)G - eG = rQ`, so with `u1 = e s^-1` and `u2 = r s^-1`, `u1 G + u2 Q = s^-1 (eG + rQ) = s^-1 sR = R`, whose x-coordinate reduces to `r`. This is why verification after recovery says nothing on its own, and why step 4 of section 4.3 compares the hash with the address.

### Address

```
address = Base58Check(v || HASH160(ser_c(Q)))
HASH160(x) = RIPEMD160(SHA256(x))
Base58Check(b) = Base58(b || first 4 bytes of SHA256(SHA256(b)))
```

where `v` is `0x00` or `0x6f` (section 2), `ser_c` is the 33-byte encoding when `c = 1` and the 65-byte one when `c = 0`, and each leading zero byte of the input to Base58 becomes the character `1`. A `0x6f` address is always 34 characters, because the 25-byte value lies between `58^33` and `58^34`. A `0x00` address is at most 34 characters; the all-zero hash gives `1111111111111111111114oLvT2`, 27 characters.

### Freshness

Write `I` for `Issued`, `E` for `Expires`, `c` for the check time and `A` for the maximum age (86,400 seconds by default), all in whole seconds. Rules 8 to 10 accept exactly when

```
I - c <= 300
and, if E is present:  c < E  and  0 < E - I <= 2,592,000
and, if E is absent:   c - I <= A
```

so the check times that accept a proof are `I - 300` to `E - 1` (at most 2,592,300 seconds, a little over 30 days) or `I - 300` to `I + A` (86,701 seconds with the default). The vectors N3, N4, N5, T1, T2 and T3 sit on each edge.

The nonce is 128 bits from a secure random source, so:

- a proof signed before the challenge was issued matches its nonce with probability at most `q / 2^128` for `q` such proofs;
- among `N` nonces drawn by one verifier, the chance that any two are equal is at most `N(N - 1) / 2^129`, which is below 2^-65 for `N = 2^32`; a verifier MUST NOT issue a repeated nonce anyway (section 3.1), and its record lets it check;
- single use at the issuing verifier does not depend on these numbers: with a durable, atomic record a second use fails every time.

### Sizes

| Item | Bytes |
|---|---|
| Shortest challenge (header, `Network: stn`, `Nonce`, `Issued`) | 116 |
| Longest challenge the field limits alone would allow (both free-text fields at 120 four-byte code points, a 34-character address, `testnet`, `Expires`) | 1,175 |
| Longest challenge that is all ASCII | 455 |
| Challenge limit (section 3.1) | 1,000 |
| Compact signature / as Base64 | 65 / 88 |
| Armour marker lines | 38, 25 and 36 |
| Longest proof: 1,000 + 38 + 25 + 36 + 34 (address) + 88 + 5 line feeds | 1,226 |
| V1's proof | 490 |

The 1,000-byte cap binds only when the free text uses multi-byte characters. In QR byte mode the capacity of the largest symbol, version 40, is 2,953, 2,331, 1,663 and 1,273 bytes at error correction levels L, M, Q and H. The longest proof, 1,226 bytes, therefore fits version 25 at L, 29 at M, 34 at Q and 40 at H, and V1's proof fits version 15 at L. These versions were found by encoding with a QR library; no symbol was printed and scanned.

### Bounds

Under the assumptions of the previous section, these are the costs for someone who does not hold the key:

| Attack | What it needs | Generic cost |
|---|---|---|
| Make a proof for an address from scratch | an ECDSA forgery for its key, or its private key | about 2^127.8 group operations for the best known attack on the key (Pollard's rho, `sqrt(pi n / 4)`) |
| Make a proof with some other key | a second preimage of HASH160 for that address | about 2^160 |
| Reuse the owner's signature on another BSM message the attacker did not choose | a second preimage of double SHA-256 | about 2^256 |
| The same, for a message the attacker chose and got the owner to sign | a collision of double SHA-256, plus the owner signing the attacker's text | about 2^128 |
| Use a challenge signature as a transaction signature | see "Separation from transaction signatures" | about 2^128 |
| Replay a proof at the verifier that issued it, with a record | | not possible |
| Replay a proof to a third party with no record | only a proof that is still fresh | possible until the proof expires; the result carries `NONCE_UNCHECKED` |
| Relay a genuine challenge to the owner | the owner approving a challenge from a verifier they do not deal with | not bounded by cryptography; see Limits |

These are costs of the best known generic attacks under the stated assumptions, not proofs of security.

## Implementations

A reference implementation exists, in Python, built on the bitcoinX library. It produced every vector above and passes them.

A second implementation exists, in Kotlin: the core library of a mobile wallet. It uses the Bouncy Castle library (1.78.1) for the curve arithmetic and the ECDSA primitives, with its own BSM and recoverable-signature code. It verifies the four valid vectors, reproduces their signatures byte for byte from the keys, verifies one further proof signed by the second library described under Test Vectors, and passes its own negative tests for the armour, address, signature, field, time and network rules. It was written by the same author from the same design, and it reads the same vector file as the reference, so it shares fixtures but no code with it. It is a second implementation, not an independent one in the sense of a different author.

The case file that holds the four valid vectors and all 47 cases in machine-readable form (SHA-256 `9d43a4649cd5bf41813fa94c5d54841e3d38af2b950e6288fcc57d7071c13772`, generated from the reference by this document's generator) was run through that Kotlin implementation and through a second Kotlin codebase. The case file can be made available.

*The mobile wallet's Kotlin core, the second implementation above.* Its verifier ran the whole file. All four valid vectors verify as `proven` from both the armoured form and the three-part form, and signing again with the test private key reproduces the signature, the header byte and the proof bytes exactly. Of the 47 cases, 45 agree with the reference on the headline and on the first failing rule. The other two, S2 and S3, need a stored record of a challenge the verifier issued; they are not applicable, because this implementation issues no challenges and keeps no issued-challenge store (it reports `proven` with the nonce rule in the warn state and says that nonce reuse is not checked). There were no disagreements.

*The challenge parser and key recovery code of a separate signing-device application written in Kotlin.* This application has no verifier. Its test code composes the order of rules in this document and tags each rule as run by the application's own functions or by test code on top of their primitives. For the four valid vectors, the signatures and header bytes (32, 28, 32 and 32) match byte for byte, and the address derived from each key matches in both key forms and on regtest. Of the 47 cases, 32 were fully checked and 15 were partly checked. In the partly checked cases the nonce rule is not applicable, because the application keeps no issued-challenge store; the age rule is not applicable where there is no `Expires` line, because its clock is advisory with no maximum age; cases T4 and T5 are not applicable, because its window rule runs only on requests without an address line; and the test's own splitter, not the application, decides how armour is parsed. There were no disagreements.

Both Kotlin codebases are by the same author as the reference, so neither is independent in the sense of a different author, and they share their key recovery code, so they are not independent of each other either. The signature layer alone was also checked with the second, independently written library described under Test Vectors.

No other wallet or verifier is known to implement this profile. This document makes no claim of adoption.

### Not tested

- Nonce reuse at the issuing verifier (cases S2 and S3) was run only in the reference: neither Kotlin implementation issues challenges or keeps an issued-challenge store.
- No implementation in Go, Rust, Java or C++ was tried, and no implementation by another author.
- No hardware wallet or other small-screen signer was tried; section 7's display rules are untested on such devices.
- Base64 text with non-zero pad bits is not covered: the reference accepts it, and this document does not require a verifier to reject it.
- No proof was checked in a third-party wallet's generic "verify message" screen, so the claim in section 5.3 that such a screen can check the signature alone rests on the signature layer being plain BSM, checked here with two libraries, not on a trial of any wallet's user interface.
- The armoured cases (N1, R1 to R4) and the network case R6 were run in the reference and in the mobile wallet's Kotlin verifier, both written by the same author; the second-library check covered the signature layer, not armour parsing or network rules, and the signing-device code left armour parsing to its test's own splitter.
- Concurrency of the single-use rule (two checks of one proof at the same moment) is required by section 6.5 but not exercised by a vector.
- No vector covers a verifier configured with a maximum age other than 24 hours.
- Unicode edge cases beyond those listed (combining marks, confusable characters, code points assigned in the newest Unicode versions) are not covered.
- No mainnet proof was made with a funded key; all keys here are test keys and nothing touches the chain.

## Security Considerations

**What is proven.** A `proven` result shows control of the key at signing time, by someone, for a challenge the verifier can tie to a request. It is not proof of funds, of exclusive control, or of identity. A key that has been stolen or shared proves just as well as one that has not. A verifier that needs more than key control needs another mechanism, such as [BRC-52](./0052.md) certificates for identity.

**Replay across verifiers.** A proof is a public signature: anyone who sees it can show it to someone else. The `Verifier` and `Purpose` lines are free text that the verifier writes and nobody authenticates, so they help a human, not a machine. The defence against replay is the nonce: a verifier that acts on a proof needs to have issued the challenge itself and to check the nonce against its own records (section 6.5). A third party who did not issue the challenge gets `NONCE_UNCHECKED` and should weigh the proof accordingly.

**Relay and phishing.** An attacker who wants to claim someone else's address can request a genuine challenge from a verifier and pass it to the victim under some pretext, then hand the victim's proof back to the verifier. The proof will pass, because the victim really signed the verifier's challenge. The only defence inside this profile is the signer's display (section 7, rule 6): the victim sees which verifier asked and for what, and can refuse a challenge that names a party they are not dealing with. A verifier SHOULD therefore put its own recognisable name in `Verifier` and a specific purpose in `Purpose` (for example, the account the proof will be attached to), and a signer SHOULD present those values as claims, not as facts it has checked. The 120-code-point limit and the ban on format characters (which include the bidirectional overrides) make it harder to hide text in those lines, but confusable letters remain possible, and a signer cannot detect them in general.

**Clock skew.** Rules 8 to 10 depend on the verifier's clock, and the signer's checks (section 7, rule 2) on the signer's. A verifier whose clock runs slow accepts challenges for longer than intended; one that runs fast refuses fresh challenges as expired. The 300-second skew covers ordinary drift between machines, not a clock that is wrong by hours. Nothing in this profile uses network time, so an attacker who can set a verifier's clock can extend a challenge's life. A verifier SHOULD keep its clock synchronised and SHOULD use short `Expires` windows for proofs that gate actions.

**Address reuse and privacy.** Proving an address links it, and every transaction it has made or will make, to the verifier's record of the person. Because the proof is a transferable signature, the verifier can also show that link to others, and the proof stays checkable as a signature after the challenge expires. A holder who wants to keep other addresses unlinked SHOULD prove only the address the verifier already knows (for example a deposit or withdrawal address), and SHOULD NOT reuse a proven address for unrelated payments. BRC-77's verifier-specific signatures avoid this transferability, at the cost of not being tied to an address.

**Hardware and small-screen signers.** A device that shows only part of a long message, or only a hash of it, cannot let its user check the `Purpose` and `Verifier` lines, which removes the main defence against relay. Section 7 asks such a signer to refuse or to say that text is hidden. The 1,000-byte cap and the 120-code-point field limit keep a challenge short enough for most screens, but neither guarantees that a given device can show it.

**Network confusion.** Testnet, regtest and the scaling test network share the address version byte `0x6f`. A verifier that compares only the address class would accept a regtest proof where a testnet proof was asked for. Rule 7 compares the signed `Network` line with the verifier's own network, and rule 3 compares the address class, so both must agree. Because the `Network` line is inside the signed text, an attacker cannot change it without breaking the signature.

**Key form.** A lenient verifier that accepts either key form will pass proofs that a strict verifier refuses. Section 4.3 makes strictness mandatory so that a proof that passes one verifier that claims this profile passes all of them. A verifier that also wants to accept old proofs with a wrong flag can do so only outside this profile, and SHOULD label such a result differently.

**Signature bytes are not unique.** A high-S twin of a valid signature is also valid (section 4.2). Single use is enforced on the nonce, not on the signature bytes, so this does not open a replay. A verifier MUST NOT use signature bytes as a database key for spent proofs.

**Signing oracle.** Any BSM signer that signs text it is handed with a key that holds coins is an oracle for that key over arbitrary text. This profile narrows what a signer signs in this flow to texts that parse as challenges and that the user has seen, and the header line keeps those texts apart from other BSM protocols that check their own structure (section 7.1). It cannot protect a protocol that accepts any signed text as meaningful, or a wallet that also offers unrestricted message signing to whoever asks.

**Parser differences.** Two verifiers that parse the challenge differently can reach different verdicts. The grammar of section 3.5 leaves no optional white space, no case folding, no Unicode normalisation and no unknown fields, and the 1,000-byte cap bounds the work. The one known source of possible disagreement is the set of unassigned code points (section 3.3).

**No revocation and no rotation.** A proof cannot be withdrawn. Once its challenge expires a verifier that claims this profile refuses it as not fresh, but the signature remains valid evidence that the key once signed that text.
