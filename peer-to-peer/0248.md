# BRC-248: Offline BAP Issuer Identity Packages

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

[BRC-247](./0247.md) stamps a 1Sat or BSV-21 issuance with the issuer's [BAP](https://github.com/BitcoinSchema/bap/blob/master/PROTOCOL.md) identity: a Sigma signature by the current BAP signing key over metadata naming the BAP ID. This BRC lets a holder turn that stamp into a name and an image from transaction data alone, without an indexer or a web server.

* An **identity package** is a minimal BEEF ([BRC-62](../transactions/0062.md)) of the BAP records a verifier needs: the ID key chain, the chosen `ALIAS` profile, its [B://](https://github.com/unwriter/B) image file, and any revocation. Records carry merkle proofs once they are mined.
* A **signer verdict** decides, from block heights in the package, whether the key that signed an asset spoke for the identity when the asset was mined. Key rotation does not disown older assets, and revocation is honoured.
* Wallets store one package per BAP ID and attach it to item deliveries only when the receiver needs it. Assets carry only the BAP ID.

This BRC adds no identity format. Identities, profiles, rotation and destruction are BAP.

## Motivation

A bare public key means nothing to a person, so wallets want a name and a picture for each issuer, and each common source of one falls short:

* A URL icon binds a location, not bytes. The image can change or disappear after signing.
* A self-signed JSON profile copied into every mint duplicates bytes in each asset, has no rotation, and leaves every wallet to invent freshness rules.
* An indexer lookup of the issuer's BAP profile brings back the trust dependency that [BRC-150](../tokens/0150.md) removes for item provenance.
* An identity ordinal (an inscription holding the profile) puts the profile on a satoshi that can be sold or moved, and moving it carries no authority.

BAP already separates a stable identity (the BAP ID) from rotating signing keys, 1Sat-ecosystem wallets already publish BAP `ALIAS` profiles, and BRC-247 names the BAP ID in each asset. Offline use still needs three rules: how a verifier decides from proofs alone which keys spoke for an identity and when, which of several profiles to show, and how the proof travels and is stored.

## Relationship to other documents

* [AIP](https://github.com/BitcoinSchema/aip): BAP records are signed with `BITCOIN_ECDSA`.
* [B://](https://github.com/unwriter/B): the profile image is a B file.
* [BRC-247](./0247.md): the asset-level issuer stamp this BRC verifies, and the BAP key derivation.
* [BRC-163](../tokens/0163.md) and [BRC-160](../tokens/0160.md): BSV-21 and 1Sat issuer attestation, which BRC-247 profiles.
* [BRC-52](./0052.md): certifier-signed identity certificates. They attest attributes of a key; they do not order key rotations, so they are not used here, and they can be used alongside.
* [BRC-62](../transactions/0062.md): BEEF, the package's carrier.
* [BRC-150](../tokens/0150.md): item provenance, which carries the asset's genesis transaction.
* [BRC-77](./0077.md) and Sigma: the stamp's signature, bound to a funding input.
* [BRC-37](../outpoints/0037.md): compact claims in `customInstructions`.
* [BRC-33](./0033.md): store-and-forward delivery.

## Specification

The key words MUST, SHOULD and MAY are used as in RFC 2119.

### 1. Records

An issuer identity is a BAP identity. Every record below is an `OP_FALSE OP_RETURN` data output, so it is unspendable. Writers SHOULD create these outputs with 0 satoshis.

```text
ID     OP_FALSE OP_RETURN 1BAPSuaPnfGnSBM3GLV9yhxUdYe4vGbdMT ID <bapId> <address>
       | 15PciHG22SNLQJXMoSUaWVi7WSqc7hCfva BITCOIN_ECDSA <signer address> <signature>
ALIAS  OP_FALSE OP_RETURN 1BAPSuaPnfGnSBM3GLV9yhxUdYe4vGbdMT ALIAS <bapId> <profile JSON>
       | 15PciHG22SNLQJXMoSUaWVi7WSqc7hCfva BITCOIN_ECDSA <signer address> <signature>
B      OP_FALSE OP_RETURN 19HxigV4QyBv3tHpQVcUEQyq1pzZVdoAut <image bytes> <content type> binary
```

**AIP signature**

* It signs the `OP_RETURN` byte (`0x6a`), then the data of every push before the `|` separator, concatenated without their push opcodes, then the `|` byte (`0x7c`).
* It is a [BSM](https://en.bitcoin.it/wiki/Message_signing) compact signature. Writers MUST carry it as 65 raw bytes, as 1Sat wallets do. Readers MUST also accept the 88-character base64 text of those bytes, which the AIP specification and earlier BAP libraries write.
* A reader MUST recover the public key from the signature and check that its address equals `<signer address>`. A record whose signature does not verify MUST be ignored.
* A record MUST contain exactly two protocols: BAP and AIP.

**BAP ID and root address**

* `bapId` is `base58(ripemd160(sha256(utf8(rootAddress))))`, as BAP defines.
* The root address is the signer of an ID record whose signer address hashes to `bapId`. Readers MUST NOT accept a root address that does not hash to the BAP ID.

**Profile**

* The `ALIAS` body is a JSON object using schema.org `Person` or `Organization` attributes.
* `name` MUST be 1 to 80 characters, with no control characters and no leading or trailing whitespace.
* `description` is OPTIONAL, at most 280 characters. Readers MUST drop an invalid `description` and keep the rest of the profile.
* `image` SHOULD be `b://<txid>`, naming a B output in the package.

**Image**

* `content type` MUST be `image/webp`, `image/png` or `image/jpeg`, and the image MUST be 1 to 65,536 bytes.
* Writers SHOULD re-encode the source image, removing EXIF and other metadata, and SHOULD use a square image of at most 512 px.
* Readers MUST NOT fetch an `image` that is an `http(s)` URL. They MAY accept an inline `data:` image within the same limits.

Key derivation is as [BRC-247](./0247.md) specifies for a wallet's own identity: key `N` is the [BRC-42](../key-derivation/0042.md) child at protocol `[1, "sigma"]`, key ID `identity-N`, counterparty `self`, and key 0 is the root. Verification in this BRC does not depend on derivation.

### 2. Key chain

From a set of records for one BAP ID, a reader builds the chain of signing keys:

1. Find the root address (section 1).
2. Let `current` be the root. Among ID records signed by `current` that declare a valid address other than `0`, take the **first on chain** (defined below). That address is the next signing key. Set `current` to it and repeat.
3. Stop when there is no candidate or when an address repeats. Readers MUST follow at least 64 keys and MAY stop after that.
4. The last key in the chain is the **current key**. A chain with no declared key is not an identity.

Following BAP, each rotation is an ID record signed by the outgoing key that declares the next one. The root address declares only the first signing key. It SHOULD sign nothing else except a revocation.

**First on chain.** A record has a mined height when the package proves it with a merkle path. Otherwise it is unmined.

* If any candidate is mined, the candidate with the lowest height wins.
* If two mined candidates share the lowest height, there is no winner and the chain stops there.
* If no candidate is mined, a single unmined candidate wins. Two or more unmined candidates have no winner.

**Revocation.** As BAP defines, an ID record signed by the root address that declares the address `0` destroys the identity. Readers use the first-on-chain revocation, or any revocation when none wins. ID records not signed by the root that declare `0` are ignored.

### 3. Signer verdict

A reader decides whether a key spoke for an identity in a block at height `h`. `h` is unknown when the asset is unmined or its proof is not available. The verdict is the first row that applies:

| Verdict | When |
|---|---|
| `unknown-key` | The key is not in the chain. |
| `revoked` | A revocation exists, and it is unmined, `h` is unknown, or `h` ≥ the revocation's height. |
| `active` | The key is the current key, its successor is unmined, or `h` is known and lower than its successor's height. |
| `retired-key` | Otherwise. |

Only `active` attributes an asset to the identity. A rotation therefore does not disown assets signed before it was mined, and an unconfirmed rotation disowns nothing yet. An unconfirmed revocation takes effect at once.

### 4. Profile selection

An identity can have many `ALIAS` records. Readers consider only those whose signer is `active` at the `ALIAS`'s own height, and rank them with these rules, applied in order:

1. An `ALIAS` signed by a later key in the chain ranks above one signed by an earlier key.
2. For the same key, an unmined `ALIAS` ranks above a mined one.
3. Between two mined records, the higher block ranks first.
4. In the same block, an `ALIAS` in the same transaction as the ID record declaring its signer (the key's first profile) ranks lower.
5. Otherwise, the higher transaction offset within the block ranks first.

If the top `ALIAS` has no valid `name`, the reader tries the next one. BEEF serialization may reorder transactions, so readers MUST NOT use package order to choose a profile.

Wallet-local tags such as `publishedAt:` (section 9) MAY order a wallet's own records, but they are not part of the package and MUST NOT override these rules for anyone else's identity.

Readers SHOULD still show a revoked identity's profile, together with the revocation.

### 5. Identity package

```json
{ "v": 1, "bapId": "<BAP ID>", "beefB64": "<base64 BEEF>" }
```

`beefB64` is a BEEF of at most 163,840 bytes. It contains:

* every transaction holding an ID record in the key chain;
* the selected `ALIAS`;
* the B file that `ALIAS` names;
* the revocation, if any.

Each mined transaction MUST carry its merkle path. For an unmined transaction, the writer SHOULD include its inputs' parents as txid-only entries. The AIP signature, not the ancestry, is what makes a record a claim by its key.

A reader verifies a package in these steps:

1. Parse the package and check the size limit.
2. Decode the BEEF and require BEEF validity, allowing txid-only parents.
3. Build the key chain (section 2) for `bapId`.
4. Select the profile (section 4).

The result is the identity: its BAP ID, root address, key chain with heights, revocation, profile and image.

**Header check.** Heights decide rotation and revocation. Before storing a package received from someone else, a reader MUST check every merkle root in it against block headers, for example with an SPV chain tracker. A reader that cannot check a root MUST NOT store the package.

### 6. Asset stamps

Asset stamps are [BRC-247](./0247.md) issuer attestations: a MAP tape naming `issuer` (the signing public key) and `bapId`, followed by a Sigma signature. BRC-247 defines the layout.

A reader MAY show the identity's name and image as the asset's issuer only when all of the following hold:

1. The asset's Sigma signature verifies, bound to a concrete funding input, and its signer equals `issuer`.
2. A verified package (section 5) for `bapId` is available.
3. The signer verdict (section 3) for `issuer` is `active` at the asset's mined height. That height comes from the merkle path of the asset's genesis transaction, for example in its BRC-150 provenance. If there is no such path, the height is unknown.

Otherwise the reader MUST NOT show the identity as the issuer's. It MAY show the signing key.

The stamp sits inside the signed genesis script, so it survives transfers. A later holder reads it from the origin transaction in the item's BRC-150 provenance.

Writers MAY copy `issuer` and `bapId` into the output's [BRC-37](../outpoints/0037.md) `customInstructions` as compact claims. These are hints only.

### 7. Store once

The package is the only large object, because it holds the image.

* Wallets SHOULD store one package per BAP ID and resolve every asset stamp through that store.
* Wallets MUST NOT copy a package into an item's remittance or Atomic BEEF.
* When a package arrives for a BAP ID already stored, a wallet SHOULD merge them: take the union of both packages' records, re-run sections 2 and 4 on it, and keep the records section 5 lists for the result. A peer that leaves out the real rotation then cannot displace it.
* Wallets SHOULD keep packages for identities they control indefinitely and include them in the user's identity backup.
* Wallets MAY cap the number of packages stored from peers, evicting the oldest-stored first.

### 8. Delivery beside an item

No BRC defines the message a wallet sends with an item or token over a [BRC-33](./0033.md) messagebox. When that message body is a JSON object, its `meta` object (created if absent) MAY carry packages for the BAP IDs the delivered assets name. Receivers that do not implement this BRC ignore the member.

```json
{ "meta": { "identities": [ <identity package>, … ] } }
```

* A sender MUST NOT attach more than 2 packages to one envelope.
* Within the box size cap, the Atomic BEEF and the item's BRC-150 provenance come first. A sender adds packages last and omits any that do not fit.
* The receiver header-checks, verifies and stores packages (sections 5 and 7). Packages MUST NOT gate item ingest, payment internalization or message acknowledgement, and MUST NOT be stored in a chat transcript.
* Packages MUST NOT be placed inside an item's Atomic BEEF. [BRC-95](../transactions/0095.md) Atomic BEEF holds only the subject transaction's ancestry, and BAP records are not part of it.

### 9. Wallet basket profile

A wallet's own identity — the key tree under its BRC-100 root — keeps its records in basket `bap`, as BRC-247 and 1Sat wallets do:

| Record | Tags | `customInstructions` |
|---|---|---|
| ID | `type:id`, `bapId:<id>`, `seq:<N>` | `{"protocolID":[1,"sigma"],"keyID":"identity-<N>"}` |
| ALIAS | `type:alias`, `bapId:<id>`, `publishedAt:<ms>` | — |
| B file | `type:image`, `bapId:<id>` | — |

An ID record's `seq:<N>` and `keyID` name the key it declares, `identity-<N>`. `publishedAt` is Unix milliseconds. 1Sat wallets take the ID record with the highest `seq:` in `bap` as declaring the wallet's current key. A wallet that also issues under another master key, such as an imported issuer key, MUST store that identity's records in a basket other than `bap`, with the same tags and no `customInstructions`.

Tags are filters, not records. Reference BRC-100 clients lowercase tags, and a BAP ID is case-sensitive base58, so readers MUST match `bapId:` case-insensitively and MUST take the BAP ID from the record script.

These are data outputs, not collectables, and wallets MUST NOT list them in a collectable view.

A wallet MAY rebuild its package from these baskets. When it does, it MUST merge them with its stored package, and it MUST continue an existing chain rather than declare a new first key from the root.

Before signing a stamp, a wallet merges the records other apps added to `bap` as [BRC-247](./0247.md) requires, so it never signs with a key that another app has already rotated away.

## Rationale

**BAP, not a new identity object.** BAP already gives a stable identity with rotating keys and a destruction path, and 1Sat-ecosystem wallets already publish `ALIAS` profiles under the same derivation.

**Revocation before confirmation.** An unconfirmed revocation takes effect at once because withdrawing trust cannot attribute an asset to the wrong issuer. An unconfirmed rotation waits, because acting on it early would disown valid assets.

**Not an ordinal.** Authority belongs to the key chain. A spendable identity satoshi could be moved or sold without any effect, which would mislead holders. Data outputs cannot be transferred, so there is nothing to misread.

**Package beside items, not inside them.** Copying up to 64 KB of image into each item wastes space, and putting the package inside Atomic BEEF is forbidden by BRC-95.

**Image reuse.** A profile update that keeps its image points at the existing B file. Updates cost a few hundred bytes, and a package holds only one image.

## Security considerations

* **Permanence and privacy.** The image, name and bio are public and permanent. Writers SHOULD warn the user before publishing and SHOULD strip image metadata such as GPS location.
* **No real-world identity.** A valid chain proves control of keys, not a legal name, a brand or a handle. Wallets MUST NOT present it as such.
* **Key compromise.** If the current key leaks, the issuer SHOULD rotate; assets mined before the rotation keep their attribution. If the root key leaks, or an unrecoverable fork appears, the issuer SHOULD revoke. A leaked retired key cannot fork the chain for a reader that holds the earlier-mined rotation (section 2).
* **Forks outside the package.** A reader with no prior package for an identity sees only the records it receives, so a fork the sender leaves out is invisible to it. Merging packages over time (section 7) narrows this gap. Full fork detection needs every BAP record for the ID, which only an indexer offers.
* **Unmined records.** Until proofs exist, rival claims cannot be ordered and have no winner. Publishers SHOULD replace unmined records in their packages with mined copies as soon as proofs exist.
* **Forged heights.** A package could claim proofs for blocks that do not exist. Section 5 requires a header check before storing a package from someone else.
* **Resource limits.** Readers SHOULD enforce the image and package limits before decoding, decode images in a sandboxed renderer, and bound the number of stored peer packages.
* **Copied claims.** Anyone can write `issuer <key> bapId <id>` into their own script. Section 6 requires the asset's own Sigma signer to be an active key in the chain, so a copied claim cannot borrow an identity.
