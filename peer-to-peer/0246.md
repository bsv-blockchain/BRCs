# BRC-246: Session Upgrade

Brandon Cryderman / HandCash (brandongcryderman@gmail.com)

**Status:** Draft (proposed number, not a BSVA assignment)

## Abstract

This BRC lets two online wallets, or two installs of one account, move [BRC-33](./0033.md) messagebox traffic onto a direct WebRTC data channel. One side sends a signed offer through the messagebox, the other a signed answer, and ICE connects them across NAT on IPv4 or IPv6, or directly on a local network. Each signature covers the whole session description, including its DTLS fingerprint, so the channel is encrypted and authenticated to the two identity keys, and no relay can sit in the middle.

The messagebox remains the rendezvous and the offline inbox. The channel carries the same message bodies the box would, and never carries custody.

## Motivation

A messagebox exists because the other wallet is often offline, firewalled, or unable to keep a listener. When both wallets are online, routing every chat line, remittance card and coordination message through a store-and-forward host adds latency for nothing.

The first draft of this BRC dialled a raw IPv6 listener. In practice that reached few peers: almost every IPv4 client sits behind NAT, routers and carriers commonly drop inbound IPv6, two devices on one home network could not use their local addresses, the socket was not encrypted, and two installs of one account could not connect at all. WebRTC solves each of these with parts every Chromium-based wallet shell already ships: ICE for NAT traversal and local candidates, DTLS for encryption, and SCTP data channels for framing. This revision replaces the raw socket with it.

## Specification

The key words "MUST", "MUST NOT", "SHOULD", "SHOULD NOT", and "MAY" are to be interpreted as described in RFC 2119.

### Scope

This BRC covers messages already sent over BRC-33: chat, remittance cards, and similar notices, and coordination between installs of one account such as [BRC-249](../wallet/0249.md) release requests. It does not cover coin selection, signing, or broadcast. An on-chain output remains the only proof of payment or item custody.

Out of scope: publishing an endpoint in a handle record, [BRC-169](./0169.md) resolve, or any public directory.

### Endpoints

An **endpoint** is one install: an identity key and a **device**, a random identifier of 1–128 characters from `[A-Za-z0-9._-]` that the install keeps for its lifetime. Two endpoints may share an identity key, as installs of one account do; they MUST then differ in device. The device SHOULD NOT be derived from any key or hardware identifier.

### Signatures

Every signature in this BRC is ECDSA on secp256k1 by the signer's identity key, over SHA-256 of the UTF-8 preimage, with low-S and deterministic nonces (RFC 6979). It is encoded as 64 bytes (`r ‖ s`, each 32 bytes big-endian) in lowercase hex. Preimages join their fields with `\n` and have no trailing newline.

### Signalling messages

An offer or answer is a UTF-8 JSON object:

```json
{
  "v": 2,
  "t": "offer" | "answer",
  "from": "<sender identity key>",
  "fromDevice": "<sender device>",
  "to": "<recipient identity key>",
  "toDevice": "<recipient device, or empty>",
  "offerNonce": "<the offer's nonce; empty in an offer>",
  "sdp": "<session description>",
  "expiresAt": 0,
  "nonce": "<32 hex>",
  "signature": "<128 hex>"
}
```

| Field | Rule |
|---|---|
| `from`, `to` | Compressed public keys, lowercase hex. |
| `fromDevice` | The sender's device. |
| `toDevice` | The recipient's device. In an offer to another identity it MAY be empty, meaning whichever install holds that identity. It MUST be set when `to` equals `from`, and in every answer, where it is the offer's `fromDevice`. |
| `offerNonce` | Empty in an offer. In an answer, the `nonce` of the offer it answers. |
| `sdp` | The sender's complete session description (see [Session description](#session-description)). |
| `expiresAt` | Unix milliseconds. In an offer, at most 120 seconds after signing. In an answer, the offer's `expiresAt`. |
| `nonce` | 16 bytes from a cryptographically secure source, lowercase hex. |
| `signature` | By `from`, over the preimage below. |

Preimage, where `sdpHash` is the lowercase hex SHA-256 of the UTF-8 `sdp`:

```
session-upgrade
v2
{t}
{from}
{fromDevice}
{to}
{toDevice}
{offerNonce}
{sdpHash}
{expiresAt}
{nonce}
```

### Transport for signalling

A sender seals each signalling message as a [BRC-78](./0078.md) message to `to` (its own key when `to` equals `from`) and sends it with BRC-33 `sendMessage` to `to`'s messagebox, in box **`session-upgrade`**. It MUST NOT put signalling messages in any other box. Wallets that do not implement this BRC never list that box, so they never show signalling as chat.

A wallet that implements this BRC lists box `session-upgrade` while it is online. When installs share an identity, they share that box, so an install:

- ignores a message whose `fromDevice` is its own device and whose `from` is its own identity;
- ignores a message whose `toDevice` names another device, and MUST NOT acknowledge it, so the addressed install still finds it;
- acknowledges every other message once it has processed it, and MAY acknowledge any expired message.

An install applies these rules before anything else, including whether it can open a data channel at all, so an install without WebRTC still leaves messages addressed to its siblings.

### Receiving an offer

A receiver MUST ignore an offer unless all of these hold:

- `to` is its identity key, and `toDevice` is empty or its device;
- if `from` equals `to`, `toDevice` is its device and `fromDevice` differs from it;
- `expiresAt` has not passed and is at most 120 seconds in the future (receivers MAY allow 5 seconds of clock skew);
- the session description is acceptable (see [Session description](#session-description));
- the signature verifies against `from`.

A wallet SHOULD answer offers only from identities the user has exchanged messages with and from its own installs, and MAY rate-limit them per sender.

To answer, the receiver applies the offer's `sdp` as the remote description, creates an answer, completes ICE gathering, and sends an answer whose `offerNonce` is the offer's `nonce`, whose `toDevice` is the offer's `fromDevice`, and whose `expiresAt` is the offer's.

A receiver MUST answer each offer `nonce` at most once while the offer is unexpired, and ignore a repeat of an offer it answered. The same box message can be listed again before it is acknowledged, and answering it again would replace the session the first answer is connecting.

### Receiving an answer

An offerer MUST ignore an answer unless it matches an offer it sent and still holds: `offerNonce` equals that offer's `nonce`, `from` equals the offer's `to`, `fromDevice` equals the offer's `toDevice` when that was set, `toDevice` is the offerer's device, `expiresAt` equals the offer's and has not passed, the session description is acceptable, and the signature verifies against `from`. It applies the answer's `sdp` as the remote description. An offerer that sent an offer with an empty `toDevice` takes the first acceptable answer and ignores the rest.

### Who offers

Either endpoint may offer when it wants a session with another endpoint and has neither a session, open or still connecting, nor an offer outstanding to it. An endpoint that has just answered an offer waits for that session to open or fail before it offers. A wallet SHOULD offer only to identities the user is talking to and to its own installs, and at most once per 20 seconds per endpoint. An offerer discards the pending connection when the offer expires.

**Glare.** When an endpoint receives an offer from an endpoint it has an offer outstanding to, the two compare `identityKey + "\n" + device`. The lower one keeps its own offer and ignores the incoming one. The higher one abandons its own offer and answers.

### Session description

Session descriptions follow WebRTC (RFC 8829, RFC 8831). A session description is acceptable when it:

- has exactly one media section, `m=application … UDP/DTLS/SCTP webrtc-datachannel`, and no audio or video;
- carries exactly one DTLS fingerprint, with hash function `sha-256`;
- contains its ICE candidates. Signalling is not trickled: each side waits until ICE gathering completes, or 3 seconds have passed, and signs the description it then has. Each message through a store-and-forward box costs a poll, so one round trip is the budget.

ICE MAY use IPv4 and IPv6 candidates. A wallet SHOULD configure at least one STUN server and MAY configure TURN. Host candidates expose local addresses. A wallet SHOULD send unobfuscated local addresses only to its own installs and otherwise SHOULD use multicast DNS host candidates (as browsers do by default) or omit host candidates.

Both sides open one data channel, negotiated out of band with `id` 0, label `brc246`, ordered and reliable.

### Messages

Once the data channel is open, each message to that endpoint is one UTF-8 text message on the channel:

```json
{ "t": "msg", "id": "<id>", "body": "<the body the messagebox would have carried>" }
```

The receiver MUST pass `body` to the same ingest path as a messagebox message from `from`, and acknowledge it after ingest accepts it:

```json
{ "t": "ack", "id": "<id>" }
```

A message MUST NOT exceed the smaller of 256 KiB and the peer's advertised maximum message size; a larger body goes through the messagebox. If the sender receives no `ack` within one second, it MUST close the session and send that message through the messagebox. A body can therefore arrive twice, once per path, so ingest MUST treat a repeat as it treats a repeated messagebox delivery.

A session ends when the data channel closes or ICE fails. Messages then go through the messagebox until a new offer and answer complete. A wallet SHOULD close a session that has been idle for ten minutes, and MUST close its sessions when it locks or switches account.

### What this is not

* Not a replacement for BRC-33. First contact, offline peers, and failed connections use the messagebox.
* Not a custody channel. An `ack` is not a payment.
* Not history sync. Installs of one account may hold a session to carry coordination messages, not to merge state continuously.
* Not a listener requirement. Neither side opens a port; ICE does the rest, and a wallet that cannot connect keeps using the box.

## Security considerations

* **Authentication.** Each side signs the hash of its whole session description with its identity key, so the DTLS fingerprint in it is bound to that key. The DTLS handshake then proves each side holds the certificate it advertised. A messagebox host, STUN server or TURN relay that alters a description breaks its signature, and one that substitutes its own cannot sign it.
* **Encryption.** The channel is DTLS-encrypted end to end. Each `body` keeps its own BRC-78 envelope as well, exactly as on the box.
* **Address exposure.** A session description reveals the sender's public address and possibly local addresses to its recipient. Sealing it with BRC-78 keeps it from the messagebox host. STUN servers learn a wallet's public address, and a TURN relay learns both endpoints' addresses and sees only encrypted traffic. Wallets SHOULD NOT offer or answer sessions with identities the user has not chosen to talk to.
* **Replay.** Offers expire within 120 seconds and carry a fresh nonce. An answer names the nonce of its offer, so a replayed answer finds no pending offer. A replayed offer draws no second answer while it is unexpired; after that it is refused as expired. Even an answer would not help the replayer, who lacks the offer's DTLS private key and cannot complete the handshake.
* **Abuse.** Anyone can put offers in a wallet's `session-upgrade` box. Answering only known identities and rate-limiting per sender bounds the work, and an ignored offer costs nothing but its acknowledgement.

## Rationale

* **Why WebRTC.** It is the deployed answer to NAT traversal (ICE with STUN and TURN), covers IPv4, IPv6 and local networks in one mechanism, encrypts by default, and ships in Electron and the Android WebView, so a wallet needs no open port, no port mapping and no native socket code.
* **Why sign the session description.** Binding the DTLS fingerprint to the identity key is what turns an anonymous encrypted channel into one between two known identities. Signing the whole description also fixes the ICE credentials and candidates.
* **Why a separate box.** Older wallets list only `inbox`, so signalling never reaches them as unreadable chat, and installs sharing an identity can each leave messages addressed to another device unacknowledged.
* **Why devices.** Two installs of one account have the same identity key. The device tells them apart in addressing, glare resolution and acknowledgement, which is what lets [BRC-249](../wallet/0249.md) coordinate a move over a direct session.
* **Why no trickle.** Trickle ICE sends each candidate as it is found. Through a store-and-forward box each extra message costs a poll, so one complete description each way connects sooner.
