# BRC-258: Shareable References and a URI Scheme for the Metanet

Crumbs

## Abstract

This document specifies a **reference**: one short string that names a thing on the Metanet, says what kind of thing it is, and optionally carries hints about where to find it. Five kinds are defined: an identity, a transaction, a transaction output, a piece of content named by its hash, and a room. A reference has three written forms, all carrying the same bytes: a bare form for chat, copy and paste (`mnout1...`), a URI form for links and inline mentions (`metanet:mnout1...`), and gateway links that work in any browser: a private one whose reference never reaches the server (`https://example.com/open#mnout1...`), and a public one that search engines can index (`https://example.com/mnout1...`).

A reference names its object by something that can be checked: a key, a transaction identifier, an outpoint or a hash. Everything else in it is a hint: it tells a resolver where to look, and the subject alone decides what was found. A resolver shows the object as verified only after proving it: by SPV for transactions and outputs, by hash for content, by key equality for identities, and by the room's signed manifest for rooms. Opening a reference only displays the object; a payment, a signature or a permission each goes through its own confirmation afterwards.

The format reuses what already exists. Outpoints are those of [BRC-36](../outpoints/0036.md), content hashes are those of [BRC-26](../overlays/0026.md), handles are those of [BRC-169](./0169.md), rooms are those of [BRC-190](../apps/0190.md), topic and lookup service names are those of [BRC-87](../overlays/0087.md), and proofs are BEEF ([BRC-62](../transactions/0062.md), [BRC-95](../transactions/0095.md), [BRC-158](../transactions/0158.md)). The encoding is bech32m with a type-length-value body, the design Nostr's NIP-19 and NIP-21 have run at scale for several years, changed where their experience shows it should be.

## Motivation

People share things by sending links. A wallet that holds a collectible, a client showing a payment, a chat in which someone says "look at this": each needs a way to hand the thing to somebody else, in a form that the other person's software, which may come from a different vendor, can find, check and open.

The Metanet has no such form. What exists covers one use each:

| Form | Defined by | Names |
| --- | --- | --- |
| `peerpay:<identityKey>?sats=...` | [BRC-125](../payments/0125.md) | A request to pay an identity |
| `uhrp://<base58check hash>` | [BRC-26](../overlays/0026.md) | Content by hash |
| `brc-wallet://pair#...` | [BRC-185](../wallet/0185.md) | A wallet pairing offer |
| `<txid>.<vout>` | [BRC-36](../outpoints/0036.md), [BRC-100](../wallet/0100.md) | An output, with no hint of where to find it |
| `<txid>_<vout>` | [BRC-159](../tokens/0159.md), [BRC-190](../apps/0190.md) section 2.2 | The same output, written differently |

[BRC-101](../overlays/0101.md) describes composite URIs for overlay hosts and marks itself aspirational, and [BRC-183](../overlays/0183.md) repeats that it does not imply them. [BRC-218](../apps/0218.md) section 5.20 says that the record of an asset transfer "SHOULD link to the transaction" and cannot say what the link looks like. [BRC-49](../opinions/0049.md) says users should never see an address, which leaves open what they see instead when one person shows another a thing.

A 64-digit hex string pasted into a chat could be a transaction identifier, a content hash or half a key, and the receiving client has to guess. A link to an item in one marketplace opens only in that marketplace. A mention of `@alice@example.com` in a document written today resolves, next year, to whoever holds that handle then, which BRC-169 section 4.3 allows to be somebody else. A QR code on a poster needs a format that a phone camera, a wallet and a web page all agree on.

Nostr solved the same problem with three short documents. NIP-19 encodes keys and event identifiers as bech32 strings whose prefix says what they are, with optional relay hints. NIP-21 makes those strings a URI. NIP-27 writes them inline in text so that clients can render mentions and previews. They are among the most widely implemented Nostr documents, because every client that shows or shares anything needs them. This document follows them closely and departs from them in five places, each for a reason that comes from their deployment:

| NIP-19, 21 and 27 | This document | Why |
| --- | --- | --- |
| A relay hint is effectively where the event is, and the event is self-signed | A hint is only a place to look. Every object is proven against the subject before it is shown as verified | Metanet objects are proven by SPV and hashes, wherever they were fetched from |
| Profiles are keys; a NIP-05 name is looked up separately | An identity reference may carry the handle it was shared under, and the resolver re-checks that the handle still names the key | BRC-169 handles can be released and reassigned, so a name in a link has to be checked against the key every time |
| A relay URL in a note is fetched automatically by many clients | A source URL taken from a reference is fetched only when the user opens it | An automatic fetch of an attacker's URL reveals the reader's address to the attacker |
| The `nostr:` scheme | `metanet:`, with `web+metanet:` accepted for browsers, and a gateway form whose fragment never reaches the server, beside a path form for public pages that should be indexed | Browsers let web pages register only safelisted schemes or `web+` schemes. A gateway that never learns what was opened is better for private sharing, and a page a search engine can read is better for public things |
| `nsec` is defined, then excluded from the URI | No kind encodes a secret, and section 11 forbids adding one | A format for sharing should not be able to carry what must never be shared |

What it adds is an encoding and a resolution order over standards that are already deployed, so an implementation needs a bech32m library and the BEEF and SPV code that wallets built on `@bsv/sdk` already have.

### Alternatives considered

| Alternative | What it lacks |
| --- | --- |
| Links to a block explorer or a marketplace | Each names one vendor, works only while that vendor does, shows only what that vendor shows, and gives the reader's software nothing to verify. A reference can still be opened at any such site through the gateway forms of section 4.3, without depending on it |
| Hex identifiers and BRC-36 outpoints as they are | They carry no kind, so 64 hex digits are a transaction or a hash depending on who guesses, and no hint of where to look. Section 10.2 keeps them as equivalent forms |
| UHRP links for everything | A BRC-26 URL is a permalink to bytes, and it is the right name for a file: `mnfile` carries exactly its hash. It cannot name a person, a transaction, an output or a room, and most things people share are one of those: an item held as an output, a catalog that is a chain of outputs, a payment, a contact. It also carries no hint of where the file is, and its case-sensitive encoding suits neither reading aloud nor compact QR codes. Section 10.2 rule 2 keeps UHRP links valid everywhere this document applies |
| Extending `peerpay:` and `uhrp:` with sibling schemes | One scheme per kind means one handler registration and one browser prompt per kind, and still no way to write a mention in text that any client recognises |
| Decentralized identifiers | BRC-202 already gives an identity key a `did:key`, and section 10.2 treats it as equal to `mnid`. DIDs are built for the subjects of credentials, and their URLs run too long for chat and QR codes |
| A readable path URI such as `metanet:output/<txid>.<vout>?topic=...` | Readable in a log, but it breaks in chat autolinking at `?` and `&`, needs percent-encoding for hints, has no checksum to catch a mistyped digit, and cannot use QR alphanumeric mode. Section 4.1 rule 3 lists what bech32m gives instead |

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, and MAY in this document are to be interpreted as described in RFC 2119.

### 1. Terminology

- **Reference**: a string in one of the forms of section 4 that decodes, under section 3, to a kind, a subject and zero or more hints.
- **Kind**: what the reference names. One of the five kinds of section 2, identified by the bech32m human-readable part.
- **Subject**: the bytes that identify the object and against which it is proven.
- **Hint**: any field other than the subject. A hint helps a resolver find or present the object and never changes which object is named.
- **Resolver**: software that decodes a reference, finds the object, proves it against the subject and presents it. A wallet, a Metanet client or a gateway page can be a resolver.
- **Sharer**: whoever wrote the reference.
- **Verified**: proven against the subject by the procedure section 6 gives for its kind.
- **Own sources**: the services a resolver is configured to use without reference to any particular reference: its wallet's storage, its chain tracker, the overlay hosts it already uses, its UHRP resolution.
- **Network**: the BSV network a reference belongs to, main network unless section 3.3 says otherwise.
- **Minimal form**: the reference re-encoded with only its subject and, where present, its `flags` and `network` fields (section 10.1). Every reference to the same object has one minimal form.

### 2. Kinds

| Prefix | Kind | Subject | Subject length | Proven by |
| --- | --- | --- | --- | --- |
| `mnid` | Identity | A compressed secp256k1 identity key, as BRC-100 `getPublicKey({ identityKey: true })` returns it | 33 bytes | Key equality, section 6.2 |
| `mntx` | Transaction | The transaction identifier | 32 bytes | SPV, section 6.3 |
| `mnout` | Output | The transaction identifier followed by the output index as a 4-byte big-endian unsigned integer | 36 bytes | SPV, section 6.4 |
| `mnfile` | Content | The SHA-256 hash of the content, as BRC-26 uses it | 32 bytes | Hash, section 6.6 |
| `mnroom` | Room | The ASCII room identifier `room:<domain>/<local>` of BRC-190 section 2.2 | 1 to 255 bytes | The room's signed manifest, section 6.7 |

1. A transaction identifier is carried as the 32 bytes obtained by decoding, as hexadecimal, the 64-character form in which BRC-36 and BRC-100 write it. A resolver MUST NOT reverse it.
2. A handle is not a kind. A reference to a person names their key and MAY carry the handle as a hint (section 3.2, type 5), because a handle can come to name somebody else and a key cannot.
3. An application is not a kind. A web application is named by its origin, which is already a link.
4. No kind encodes a private key, a seed, a mnemonic, a key linkage, a content key, a certificate keyring or any other secret. Section 11 rule 3 forbids adding one.

### 3. The Binary Form

#### 3.1 Fields

The body of a reference is a sequence of fields. Each field is one type byte, one length byte, and that many bytes of value.

```
field = type (1 byte) || length (1 byte) || value (length bytes)
body  = field || field || ...
```

1. The first field MUST be type 0, the subject, and there MUST be exactly one.
2. An encoder MUST write the remaining fields in ascending order of type, and fields of the same type in the sharer's order of preference.
3. An encoder MUST NOT write more than four fields of any one hint type, or a field of zero length.

#### 3.2 Field types

| Type | Name | Value | Applies to | Repeats |
| --- | --- | --- | --- | --- |
| 0 | `subject` | As section 2 | All | Exactly once, first |
| 1 | `source` | An `https` URL prefix, ASCII, ending in `/`. The resolver appends the object's name and fetches it, per section 6.1 rule 4 | `mntx`, `mnout`, `mnfile` | Up to 4 |
| 2 | `topic` | A BRC-87 topic manager name such as `tm_uhrp`, ASCII | `mntx`, `mnout` | Up to 4 |
| 3 | `lookup` | A BRC-87 lookup service name such as `ls_uhrp`, ASCII | `mntx`, `mnout`, `mnfile` | Up to 4 |
| 4 | `identity` | A 33-byte identity key the sharer associates with the object: its creator, its seller, its holder | `mntx`, `mnout`, `mnfile`, `mnroom` | Once |
| 5 | `handle` | A fully-qualified BRC-169 handle `@handle@domain`, lowercase ASCII, with no `+tag` | `mnid`, and any kind carrying type 4 | Once |
| 6 | `media` | A media type `type/subtype` per RFC 6838, lowercase ASCII, without parameters | `mnout`, `mnfile` | Once |
| 7 | `flags` | One byte. Bit `0x01`, **lineage**: the reference names the lineage that begins at the subject output, per section 6.5. Other bits are zero | `mnout` | Once |
| 8 | `network` | ASCII `test` for the BSV test network | All except `mnroom` | Once |

1. On an identity reference, a type 5 handle is the handle of the subject. On any other kind it is the handle of the type 4 identity, and is meaningless without one.
2. An encoder MUST NOT write type 8 for the main network. A reference without type 8 belongs to the main network.

#### 3.3 Decoding

1. A decoder MUST reject the reference as a whole, and treat the string as ordinary text, when the bech32m checksum fails, the string mixes upper and lower case, the prefix is not one of section 2, a field's length runs past the end of the body, the first field is not type 0, type 0 appears more than once, or the subject has the wrong length for its kind.
2. A decoder MUST ignore a field whose type it does not know. A decoder MUST ignore a known hint that does not apply to the kind, that repeats more often than section 3.2 allows (keeping the first ones), or whose value is malformed: a `source` that is not an absolute `https` URL ending in `/` with no query or fragment, a `topic` without the `tm_` prefix, a `lookup` without the `ls_` prefix, an `identity` that is not a valid compressed point, a `handle` outside the BRC-169 section 2.1 grammar or with a dotless ecosystem, a `network` value it does not know. Ignoring a hint never invalidates the reference.
3. A decoder MUST NOT treat a reference whose `network` value it does not recognise as belonging to the main network. It MUST present it as belonging to an unknown network and MUST NOT resolve it.
4. A decoder SHOULD accept hint fields out of ascending order. Equality never depends on encoding (section 10.1), so a non-canonical encoding names the same object.

### 4. Written Forms

#### 4.1 Bare form

The bare form is the body of section 3 encoded as bech32m (BIP-350) under the prefix of its kind.

```abnf
bare     = prefix "1" 7*char        ; bech32m, BIP-350
prefix   = "mnid" / "mntx" / "mnout" / "mnfile" / "mnroom"
char     = <a character of the bech32 alphabet "qpzry9x8gf2tvdw0s3jn54khce6mua7l">
```

1. BIP-173 limits a bech32 string to 90 characters. This document lifts that limit and caps a bare reference at **1000 characters**. A decoder MUST reject a longer one.
2. Writers MUST produce lowercase. Decoders MUST accept a string written wholly in uppercase as equal to its lowercase form.
3. **Why bech32m.** Each property below is one a person sharing a link meets directly:
   1. *The kind is checked.* The prefix is inside the checksum, so a transaction identifier cannot be pasted where a content hash is expected, and the 64-hex ambiguity of section 10.2 rule 3 does not arise.
   2. *One word.* The alphabet has no punctuation, so a bare reference survives chat autolinking, line wrapping in email, and a double-click selects all of it.
   3. *Hard to misread.* The alphabet omits `1`, `b`, `i` and `o`, and the string is case-insensitive, so it can be read aloud or printed in uppercase for compact QR codes (section 4.4).
   4. *Typing errors are caught.* The checksum detects any error in up to four characters of a short string, and bech32m, unlike the original bech32, also catches the `q` characters inserted or deleted just before a final `p` that the original bech32 misses.
   5. *Cheap.* Encoding and decoding are linear, unlike base58, whose conversion is quadratic in the length of the string.
   6. *Everywhere already.* Bitcoin addresses and Nostr use the bech32 family, so libraries exist in every language, and people and language models already recognise the shape.

   The cost is length: five bits a character against six for base64url, so a reference is about a fifth longer than it would be in base64url, and the string means nothing to a person without software.
4. BIP-173's error-detection guarantees are stated for strings of at most 90 characters. Beyond that the checksum still fails to notice a random error with a probability of roughly one in a billion. No object is shown as verified on the strength of the checksum: it catches typing and scanning errors, and section 6 catches the rest.

#### 4.2 URI form

```abnf
uri      = scheme ":" bare
scheme   = "metanet" / "web+metanet"
```

1. `metanet:` is the scheme. `web+metanet:` is accepted as an alias of it because a web page may register a handler only for a safelisted scheme or one beginning `web+` (section 9 rule 3). A decoder MUST treat the two identically, and the scheme case-insensitively per RFC 3986.
2. The scheme is not `web3:`. ERC-4804 defines `web3://` URLs as calls to Ethereum contracts, and `web3` is provisionally registered with IANA for that use, so a handler registered for it would receive Ethereum URLs and an Ethereum handler would receive these. `metanet` is unregistered, matches the `metanet.*` manifest namespace of [BRC-68](./0068.md), [BRC-73](../wallet/0073.md) and [BRC-180](../overlays/0180.md), and names nothing else, so a person or a language model meeting it has one thing to associate it with. Section 13 asks for its registration.
3. The URI has no authority, query or fragment. A decoder MUST reject a URI form containing `/`, `?` or `#` after the scheme.
4. The URI form is the form for links, for `href` attributes and for references written inside text (section 8).

#### 4.3 Gateway forms

A gateway form is an `https` URL that carries a bare reference, so that a link works for a reader with no Metanet software at all. There are two, and they differ in who learns what was opened.

| Form | Example | The gateway's server learns | Use for |
| --- | --- | --- | --- |
| Fragment | `https://example.com/open#mnout1...` | That some reference was opened, not which | Private sharing: messages, email, anything sent to a person |
| Path | `https://example.com/mnout1...` | Which reference was opened | Public pages meant to be found: a published item, a catalog, a profile, a post |

1. **Fragment form.** A URL whose fragment is exactly a bare reference. A browser does not send the fragment to the server, so the gateway page, which can be static, reads it in the browser, offers to open it with the reader's `metanet:` handler, and MAY resolve and display it itself under section 6.
2. **Path form.** A URL whose last path segment is exactly a bare reference, with no query or fragment. Because the server sees the reference, it can render the page itself, which is what lets search engines and language-model crawlers read and cite it. A gateway serving the path form:
   1. SHOULD render the verified object in the HTML it serves, not only in script, and SHOULD include `<link rel="alternate" href="metanet:...">` (section 4.5);
   2. SHOULD declare as `<link rel="canonical">` the path form of the reference's **minimal form** (section 10.1), whatever hints the requested URL carried, so that every link to one object, with whatever hints, is indexed as one page. A gateway MAY instead redirect a hinted path to the minimal one with HTTP status 301;
   3. MUST resolve from its own sources only, and MUST NOT fetch a `source` named in the requested URL. A request for a path is not a user opening a reference: it may come from a crawler, or from anybody who has composed a URL to make the gateway fetch an address of their choosing. Hints in the URL MAY be passed to the reader's browser, to be used there under section 6.1 if the reader opens the reference;
   4. MUST follow section 7: no hint as a title, and an object that does not verify shown as unverified;
   5. SHOULD serve a page that has not verified with `noindex`, so that a search engine never indexes what a reference only claims;
   6. SHOULD let shared caches keep pages for immutable objects (section 6.8 rule 1).
3. **Which to use.** A sharer SHOULD use the fragment form when sending a reference to a person whose software is unknown, and the bare or URI form within Metanet clients. A publisher SHOULD use the path form of the minimal form for a public object it wants found. A sharing control MUST NOT produce the path form by default, since it tells the gateway what a private message pointed at.
4. The gateway's host carries no meaning. It is not a source, does not attest the object, and any host can serve a gateway. A resolver that recognises either form MAY treat it as the reference it carries, and MUST keep the full URL available to the reader, because the reader may have meant to visit that host. Section 3.3 rule 1 makes a false match negligible: a path segment is a reference only if its checksum holds.

#### 4.4 QR codes

1. A QR code SHOULD encode the URI form in uppercase, `METANET:MNOUT1...`. Every character of the uppercase URI form is in the QR alphanumeric set, which stores a character in 5.5 bits instead of the 8 of byte mode, about 30 percent fewer.
2. A reference for print SHOULD carry no hints, or only those a reader would need, since every hint enlarges the code.

#### 4.5 Web pages

1. A page that presents a Metanet object MAY declare it with `<link rel="alternate" href="metanet:...">`.
2. Because a crawler indexes `https` links and does not follow `metanet:` ones, a page that links to an object SHOULD write the link as a gateway form, normally the path form, and MAY add the URI form beside it for readers with a handler.
3. A page MAY declare an identity with `<link rel="me" href="metanet:mnid1...">`. That is the page's claim about itself, not the identity's claim about the page. A resolver MUST NOT present the page as belonging to the identity unless something the identity controls says so too, such as a verified BRC-169 handle certificate whose domain is the page's host.

### 5. Writing a Reference

1. Software that **creates** a reference MUST take the subject from data it holds or has verified: the wallet's own identity key, a transaction it holds with its proof, a file it hashed. Software that **forwards** a reference it received MAY pass it on unchanged, and SHOULD NOT add hints it has not itself found useful, since a forwarded reference is the sharer's statement and not the forwarder's.
2. Hints SHOULD be few. A sharer SHOULD write a `topic` when the object is tracked by an overlay a resolver would not otherwise think to ask, a `source` when the object might not be found otherwise, and nothing that is only decoration.
3. A `source` MUST NOT carry credentials in its user information, and MUST NOT carry a query string or fragment, since references are shared further than their sharer intends.
4. A `handle` on an identity reference SHOULD be written only when that handle currently resolves to the subject key under BRC-169 section 5.7 with a verified certificate.
5. A sharer MUST NOT write a reference that contains anything private. A reference is public by construction: whoever sees it can resolve it. A reference to [BRC-369](./0369.md) keyed content names the published ciphertext and never the key.
6. The control that copies a reference SHOULD say what it copies: "Copy link" for the gateway form, "Copy reference" for the bare form.

### 6. Resolving a Reference

#### 6.1 General rules

1. **Hints never change the subject.** Whatever a hint says, the object is the one the subject names, and a resolver MUST discard any object found through a hint that does not prove against the subject.
2. **Order of looking.** A resolver SHOULD look first in its own sources, then use `topic` and `lookup` hints with the overlay hosts it already uses, and then `source` hints. A resolver that does not know the query a lookup service accepts MUST NOT guess one; the hint is then only an indication of what the object is.
3. **Source URLs are fetched only on opening.** A resolver MUST NOT fetch a `source` from a reference until the user opens that reference. Automatic previews MUST use only own sources and overlay hosts the resolver already uses. A resolver fetching a `source` MUST use HTTPS, and a resolver running on a server MUST refuse a `source` whose host resolves to a loopback, link-local or private address, and MUST cap the size and time of the fetch.
4. **What a source returns.** A resolver fetches a `source` by appending the object's name, in lowercase hexadecimal, to the prefix and making an HTTP GET. For `mntx` and `mnout` the name is the transaction identifier, and the response is the transaction as Atomic BEEF (BRC-95) or BEEF (BRC-62); for `mnout`, Outpoint BEEF (BRC-158) is also accepted. For `mnfile` the name is the content hash and the response is the content. A source prefix of `https://example.com/beef/` therefore means `https://example.com/beef/7001295a...dc39`. The subject is never written twice in one reference.
5. **Resolution has no side effects.** Resolving MUST NOT create an action, sign, encrypt, disclose a certificate, internalize an output, join a room or grant a permission. A resolver MUST NOT treat any result of resolution as a request from the sharer.
6. **Network.** A resolver MUST resolve a reference only against the network it belongs to, and MUST NOT look for a test-network reference on the main network or the reverse.

#### 6.2 Identity

1. The subject is the identity. Nothing found by resolution can change which key it is.
2. A resolver SHOULD name the identity, in this order of precedence: the user's own address book entry for the key ([BRC-169](./0169.md) section 10); the handle hint, if it resolves to the key under BRC-169 section 5.7 with a verified certificate; attributes the identity has published and certified under [BRC-189](../wallet/0189.md), labelled with their certifiers; otherwise no name, and an identicon derived from the key.
3. **A handle that has moved.** If the handle hint resolves to a different key, the resolver MUST keep the subject key, MUST NOT display the handle as naming it, and MUST tell the user that the handle the reference was shared under now belongs to someone else. This is BRC-169 section 4.4 applied to a link.
4. If the handle hint cannot be resolved, the resolver MAY show it labelled as unchecked, in the manner of BRC-169 section 2.4 rule 8.
5. Any action the user then takes towards the identity, such as paying it or messaging it, MUST address the subject key and MUST pass through that action's own confirmation, for example [BRC-218](../apps/0218.md) section 4.

#### 6.3 Transaction

1. The resolver obtains the transaction with a proof under section 6.1 and verifies it per [BRC-67](../transactions/0067.md): every Merkle path checks against a header the resolver trusts, and every unmined transaction in the BEEF passes script and amount checks back to proven ancestors.
2. The subject MUST equal the identifier computed from the transaction's bytes.
3. A transaction proven by a Merkle path is shown as in its block, with the height. An unmined transaction whose ancestors are proven is shown as not yet in a block. A transaction that cannot be proven is not shown as verified.

#### 6.4 Output

1. The resolver proves the containing transaction as in section 6.3, and the output index MUST exist in it.
2. SPV proves that an output was created and cannot prove that it is unspent. A resolver MAY show spent or unspent status only as reported, naming who reported it and when.
3. A resolver interprets an output only by a protocol it implements and whose rules the output's script satisfies, for example a [BRC-159](../tokens/0159.md) 1Sat token. A `topic` or `media` hint MUST NOT make a resolver treat an output as something its script does not show it to be.
4. An `identity` hint MUST NOT be displayed as the output's creator, seller or holder unless the protocol interpreting the output proves that relationship from the output itself.

#### 6.5 Lineage

Some things on the Metanet are a chain of outputs, each spending the last: a 1Sat token as it changes hands, a catalog or a key-value record as it is updated. A reference with the lineage flag names the chain that begins at the subject output, and asks for its current state.

1. A resolver that implements the protocol of the output MAY look for the latest output descended from the subject, in its own sources or with the overlay of the `topic` hint.
2. It MUST show a descendant as current only if the BEEF it holds proves an unbroken chain of spends from the subject to the descendant, in which each transaction spends the output that continues the lineage under that protocol's rules, for example BRC-159 sat ordering.
3. It MUST say which state it shows: "current as of block N", or "as first published, it may have changed since" when it cannot find or prove a descendant.
4. A resolver that does not implement the protocol MUST show the subject output as first published, with the second wording.

#### 6.6 Content

1. The resolver obtains the content from its own UHRP resolution ([BRC-26](../overlays/0026.md)), which today queries the lookup service `ls_uhrp` for host advertisements, from hosts found through a `lookup` hint, or, on opening, from `source` hints. A UHRP advertisement expires, so content that resolved once may not resolve later; the subject still names it, and a resolver that finds no host MUST say the content is unavailable, not that it does not exist.
2. The SHA-256 hash of the bytes MUST equal the subject. A resolver MUST discard bytes that do not match and MAY try the next location.
3. The `media` hint is a display hint. A resolver MUST NOT render content that can run code, such as HTML or SVG, with the privileges of the resolver's own origin, whatever the hint says. A resolver SHOULD cap the size it fetches without asking.

#### 6.7 Room

1. The subject is a BRC-190 room identifier. A resolver that implements BRC-190 resolves the room as that document says, including the verification of its signed manifest and its gates, and shows what BRC-190 section 6 says a reader is told.
2. Opening a room reference shows the room and its gates. It MUST NOT join the room, pay a fee, or evaluate a gate as passed. Joining is a separate act with its own confirmation.
3. A resolver that does not implement BRC-190 shows the room identifier, which names its domain, and nothing else.

#### 6.8 Performance

Proof makes speed safe: because nothing is believed until it is proven against the subject, a resolver can ask many places at once and keep what comes back first.

1. **Immutable results.** A verified transaction, a verified output's creation and verified content never change, so a resolver MAY cache them indefinitely, keyed by kind, subject and network (section 10.1), and SHOULD answer later references to the same subject from that cache without any network request. A Merkle path for a transaction first seen unmined MAY be fetched once and added.
2. **Results that change.** A handle check (section 6.2), a lineage tip (section 6.5), a room's manifest (section 6.7) and any reported spent status can change. A resolver MAY cache them for a short time, MUST record when it learned them, and MUST check again before any action that depends on them, such as paying the identity.
3. **Racing.** A resolver MAY query its own sources, the overlay hosts of `topic` and `lookup` hints and, once the user has opened the reference, `source` hints in parallel, and MAY take the first response that proves against the subject and cancel the rest. A response that fails to prove is discarded and does not end the race.
4. **Previews.** A client rendering several references, as in a busy chat, SHOULD resolve only those visible to the user, SHOULD deduplicate by subject before resolving, and SHOULD render the unverified state of section 7 at once rather than waiting.
5. **Decoding is cheap.** Decoding a reference is a linear pass with no arithmetic on large integers, so a client MAY decode every candidate token in a message as it renders it.

### 7. Display

1. **Before verification**, a resolver shows the kind and a short form of the subject: "Identity 0331409f...0747" with an identicon, "Transaction 7001295a...dc39", "Output 7001295a...dc39.0", "Content ea840e12...b776", or the full room identifier.
2. **No hint is a title.** A resolver MUST NOT show any hint as the object's name, title, author or description. A reference carries no free-text label at all, so that nobody can write "Your refund" into a link and have it rendered as a heading.
3. **After verification**, a resolver shows what the interpreting protocol shows, together with what was proven: in which block, or not yet in a block; content hash matched; handle checked or unchecked.
4. **Failure** is shown as failure. A resolver that found data that did not prove against the subject MUST say the object could not be verified and MUST NOT show the data.
5. A test-network reference MUST be marked as such wherever it is shown.
6. **Short forms are for recognition, not comparison.** A shortened subject can be imitated by grinding keys or transactions until the first and last digits match. Where a user must decide whether two things are the same, a resolver MUST compare full subjects for them, or offer the full subject, and MUST NOT leave them to compare short forms by eye.
7. **Accessible names.** A rendered reference's accessible name, as a screen reader announces it, MUST be its kind and verified name, or its kind and "unverified", and MUST NOT be the bech32m string, which is unpronounceable. The string remains available to copy.

### 8. References in Text

A reference may be written inside any text a person composes: a BRC-169 message, a [BRC-218](../apps/0218.md) chat line, a memo, a document.

1. **Writing.** References in text are written in the URI form. A client SHOULD convert a bare reference the user pastes into the URI form before sending.
2. **Finding.** A reference in text begins at `metanet:` or `web+metanet:`, case-insensitively, preceded by whitespace, the start of the text, an opening bracket or a quotation mark (so that Markdown link targets and HTML attributes are found), and ends before the next whitespace. Characters at its end that are not in the bech32 alphabet, such as `.`, `,`, `)` or `!`, are not part of it. A client MAY also recognise a bare reference standing alone as a whitespace-delimited token. A client SHOULD recognise a BRC-26 URL beginning `uhrp:` or `uhrp://` in the same way, as the `mnfile` reference with that subject and no hints (section 10.2), so that the UHRP links already in circulation render and open like any other reference.
3. **Rendering is not executing.** A reference in text received from somebody else is rendered and never acted on, as BRC-218 section 2 rule 4 requires of commands. A client MAY render a preview card under section 7, built from own sources only (section 6.1 rule 3).
4. **Rendering is not rewriting.** The stored text MUST keep the reference as written, as BRC-218 section 10 rule 3 requires of handles.
5. **Mentioning is not notifying.** Writing an identity reference in a message does not notify that identity. A client MAY offer to notify it, as a separate message under BRC-169 section 7, at the writer's choice.
6. **Pinned mentions.** A handle written as text names whoever holds it when the text is read. Where a user picks a person from autocomplete while composing text that will be kept, such as a post, an agreement or a [BRC-222](../apps/0222.md) envelope, a client SHOULD write an identity reference with the handle as a hint, so that the mention keeps naming the person meant even if the handle is later reassigned. The client renders it as the handle while section 6.2 rule 3 holds, and as the warning of that rule when it does not.
7. **Linking records.** Where BRC-218 section 5.20 rule 5 asks for a link to the transaction that settled a transfer, that link SHOULD be an `mntx` reference, and the asset itself MAY be shown by an `mnout` reference.

### 9. Opening a Reference

1. A wallet or Metanet client MAY register itself as the handler for `metanet:`. A registered handler MUST accept all five kinds, and MUST at least show the unverified state of section 7 for a kind it cannot resolve.
2. **Opening is showing.** Opening a reference displays the object. It MUST NOT perform any action. Actions offered from the displayed object, such as paying an identity, buying an item or joining a room, are separate requests, each with its own confirmation and permission checks under [BRC-100](../wallet/0100.md) and BRC-218 section 4, and each addressed to the verified subject, never to a hint.
3. **Web handlers.** A web application registers with `navigator.registerProtocolHandler("web+metanet", "https://example.com/open#%s")`, placing the reference in the fragment so that its server does not receive it. Because a browser may show the user a prompt the application did not write, an application SHOULD register only in response to a user action and never on page load, for the reasons [BRC-325](../wallet/0325.md) gives for browser permission prompts.
4. **Native handlers.** A native application registers `metanet:` with its operating system.
5. Where several handlers are registered, the user's choice decides. A handler MUST NOT make itself the default without the user choosing it.

### 10. Equality and Equivalent Forms

#### 10.1 Equality

1. Two references name the same object when their kinds, their subjects and their networks are equal. Other hints, field order, case and written form do not matter. A client comparing, deduplicating, caching or storing references MUST compare kind, subject and network only.
2. The **minimal form** of a reference is the bare form of its subject field followed by its `flags` field and its `network` field, each only if present, in that order. Two references to the same object differ in minimal form only when one asks for the object's lineage (section 6.5) and the other for the object as first published, which are two different views of it.
3. The minimal form is the reference's canonical spelling. A gateway uses it for its canonical URL (section 4.3 rule 2), and an index or a search engine that keys pages by it sees one page per object and view, however many hinted variants are shared.

#### 10.2 Equivalent forms

| Kind | The same subject is also written as |
| --- | --- |
| `mnid` | 66 hex digits, as BRC-100 returns an identity key; the `did:key` identifier [BRC-202](./0202.md) defines for the key. `peerpay:<key>` (BRC-125) names the same key but is a request to pay, not a reference |
| `mntx` | 64 hex digits |
| `mnout` | `<txid>.<vout>` per BRC-36 and BRC-100; `<txid>_<vout>` as BRC-159 and BRC-190 section 2.2 write it |
| `mnfile` | A BRC-26 UHRP URL, with or without `uhrp:` or `uhrp://` |
| `mnroom` | The BRC-190 room identifier itself |

1. A client converting between forms MUST preserve the subject exactly, and MUST treat the forms as one object.
2. **UHRP links stay valid.** An `mnfile` reference does not replace a BRC-26 URL; it is that URL's hash with room for hints. A handler for `metanet:` SHOULD also open `uhrp:` URLs. A writer that has no hint to add MAY write the BRC-26 URL, which every UHRP tool already reads, and SHOULD write `mnfile` when it carries a `source`, `lookup` or `media` hint, or when the reference will be read aloud or printed as a QR code, since a BRC-26 URL is case-sensitive and cannot use QR alphanumeric mode.
3. **A bare hex string has no kind.** A client given 64 hex digits MUST NOT guess whether they are a transaction identifier or a content hash. It MUST ask the user or refuse. Making that guess unnecessary is the purpose of the prefix.

### 11. Extension

1. A new kind is defined by a later BRC under a new prefix beginning `mn`, named for what it holds and never for a BRC number.
2. New field types are allocated by later BRCs from 9 to 255. Because section 3.3 rule 2 makes a decoder ignore a type it does not know, a new field MUST NOT change which object a reference names or how it is proven. A change of that kind needs a new kind.
3. No kind and no field may carry a secret, as section 2 rule 4 lists them.

## Security Considerations

**What a reference proves.** A reference names a subject that can be checked and carries hints that cannot, and the table below says which part is which.

| Part | Who can check it | How |
| --- | --- | --- |
| Subject | Anyone | SPV, hash, key equality or signed manifest, section 6 |
| Handle on an identity | Anyone | Re-resolution under BRC-169, section 6.2 |
| Lineage tip | Anyone holding the BEEF | The chain of spends, section 6.5 |
| `source`, `topic`, `lookup` | Nobody needs to | Used only to find; whatever they lead to is proven or discarded |
| `identity` on other kinds | Only where the interpreting protocol proves it | Otherwise never shown as authorship, section 6.4 rule 4 |
| Unspent status | Nobody, by SPV | Shown only as reported, with the reporter, section 6.4 rule 2 |

**Phishing through the card.** An attacker controls every hint. The format carries no free-text label, and section 7 forbids showing any hint as a title, so the card a reader sees is built from the verified object or shows only the kind and a short subject. An attacker can still link to a real object, and the card will show that object exactly as it is.

**Tracking through sources.** A `source` URL is chosen by the sharer. A resolver that fetched it on sight would tell the sharer the reader's address and the moment they read the message, which makes every reference a tracking pixel. Section 6.1 rule 3 confines such fetches to the moment the user opens the reference, which is when they expect network activity.

**The path gateway form tells the gateway what was opened.** That is its purpose for public pages and a leak for private messages, which is why section 4.3 rule 3 forbids a sharing control from producing it by default. A gateway serving the path form also controls the HTML a search engine sees; section 4.3 rule 2 and section 7 bind it to the verified object, and a reader who doubts a gateway can open the same reference in their own resolver.

**Server-side fetching.** A chat server that previews references fetches on a stranger's behalf. Section 6.1 rule 3 requires HTTPS, refuses internal addresses and caps size and time, which together close the usual server-side request forgery paths. A gateway serving the path form is exposed further, since anybody can compose a URL and make it render; section 4.3 rule 2 therefore forbids it to fetch any `source` named in a URL, which leaves an attacker nothing to direct but lookups at the gateway's own sources.

**The fragment form against a dishonest gateway.** A browser does not send the fragment to the gateway's server, but the gateway's own page script can read it and send it anywhere. The fragment form protects a reader from servers, logs and proxies along the way; it protects them from the gateway only as far as the gateway's script is honest. A reader with a `metanet:` handler, or a resolver that recognises gateway links, needs no gateway at all.

**Duplicate pages.** Because hints vary, one object can be shared under many strings. Section 10.1 gives each object one minimal form, and section 4.3 rule 2 makes gateways declare it as canonical, so a search engine cannot be flooded with copies of one page, and a reference with a misleading hint cannot outrank the plain one.

**Handle reassignment.** A handle can come to name a different key (BRC-169 section 4.3). An identity reference names the key, and checks the handle against it every time it is resolved (section 6.2 rule 3). A mention pinned under section 8 rule 6 keeps naming the person who was meant, even after `@alice@example.com` passes to someone else.

**Confusable identities.** Two keys can be given look-alike names. Section 6.2 puts the user's own address book first and draws an identicon from the key, so a reference to a stranger does not borrow a contact's name.

**Secrets.** No kind carries a secret and section 11 rule 3 forbids one being added. A reference to keyed content reveals that the content exists, which publishing it already did.

**What resolving reveals.** A lookup tells an overlay host that somebody is interested in an object, as fetching any public record does. Automatic previews use only hosts the resolver already uses, and the fragment form keeps the reference out of the gateway's request.

**Unknown fields.** Because a decoder ignores fields it does not know, a later field cannot be relied on to make a reference safer for old decoders. Section 11 rule 2 therefore forbids fields that change the subject or how it is proven, and requires a new kind for that.

**Resolution never acts.** Resolving and opening display; they never sign, pay, disclose or join (sections 6.1 rule 5 and 9 rule 2). A reference is therefore no more dangerous to open than the content it displays, and section 6.6 rule 3 keeps that content from running in the resolver's origin.

## Implementations

None yet. Everything a resolver needs exists:

- bech32m encoding and decoding: the BIP-350 reference code, or the `bech32` package on npm with its length limit raised to 1000. Section 12 was checked with both.
- BEEF parsing, SPV verification against a chain tracker, UHRP URL conversion (`StorageUtils`) and overlay lookups (`LookupResolver`): [`@bsv/sdk`](https://github.com/bsv-blockchain/ts-sdk).
- Handle resolution and certificate verification: a BRC-169 client.
- Room manifests and gates: a BRC-190 client.
