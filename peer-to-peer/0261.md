# BRC-261: Domain-Separated Signing Preimages for Structured Records

RexStarBSV (RexStarBSV@protonmail.com)

## Abstract

This BRC defines one way to build the bytes a party signs for a new structured record type: a fixed five-byte marker, a length-prefixed domain tag that names the record type and its version, and then the record's body. It also defines one canonical form for records written as JSON, a strict subset of RFC 8785, so that two implementations produce the same body bytes and a verifier refuses anything outside the subset instead of guessing. A signature made for one record type then cannot verify as a record of another type, another version, or another protocol that uses the same key, and two conforming implementations cannot disagree about which bytes were signed.

The construction is a preimage, not a signature scheme. It is passed unchanged to the signing paths that already exist: BRC-100 `createSignature`, a BRC-77 message signature, a Bitcoin Signed Message, or plain ECDSA over its SHA-256. Existing record formats and every existing signature stay as they are. The rule applies to record types defined after this document, and to new versions of existing ones that choose to adopt it.

## What this BRC does

**The problem.** A signature proves that a key signed some bytes. It does not say what the bytes were meant to be. Two things go wrong in practice. First, two protocols can sign bytes that look alike. If protocol A signs `{"text":"hello"}` as a note and protocol B, with the same key, accepts `{"text":"hello"}` as something else, a signature collected for A is valid for B, and nobody signed anything for B. Second, the same record can be written as bytes in more than one way: member order, spaces, `1` or `1.0`, an accented letter as one code point or two. The signer hashes one spelling, a verifier rebuilds another, and a valid signature fails with no clue why.

**The idea.** Before signing, put a short label in front of the bytes, and fix the bytes. The label, called the domain tag, names the record type and its version, such as `example.org/note/v1`. The signed bytes, called the preimage, are a fixed five-byte marker, one byte giving the tag's length, the tag, and then the record. A JSON record is first written in one canonical form, so that every conforming implementation produces the same bytes for the same record and refuses anything it cannot write in exactly one way. The verifier never takes the tag or the bytes from the sender: it knows which tags it accepts, parses the record, writes the canonical form itself, and checks the signature over the preimage it built.

**A worked example.** Take vector A1: the record `{"text":"hello"}` under the tag `example.org/note/v1`, signed by test key 1. The preimage is 41 bytes:

```
marker        0064737031
tag length    13  (19 bytes)
tag           6578616d706c652e6f72672f6e6f74652f7631  (example.org/note/v1)
body          7b2274657874223a2268656c6c6f227d  ({"text":"hello"})
```

Its SHA-256 is `bd3641bfdfb02e3f8c08dbef0ba5ac425ccfda21fb9b2a30020a9cf2fe14fb82`, and key 1 signs that digest with ECDSA. A verifier configured to accept `example.org/note/v1` parses the record, rebuilds the same 41 bytes, and the signature verifies.

Now replay it. A verifier for version 2 of the record type builds the same record under `example.org/note/v2`. One byte of the tag differs, so the preimage and its digest differ, and A1's signature is refused (vector R26). A verifier for another record type, which accepts only `example.org/access-grant/v1`, refuses the tag before it looks at the signature (R27). And a signature that some other protocol made with key 1 over the bare bytes `{"text":"hello"}`, with no marker and no tag, does not verify as a note (R29).

**What it does not do.** It is not a signature scheme, a key derivation, a registry or a transport. It does not stop a signer that will sign any bytes a caller hands it, it does not stop the same record being presented twice under its own tag (a record that must not be replayed carries its own nonce or expiry), and it does not change any existing format or signature.

**Who implements what.**

- An author of a new record type picks a tag in a namespace they control (`brc-N` for a BRC, otherwise a DNS name they hold), declares how each member is encoded, and publishes vectors.
- A signer, usually a wallet or an issuing service, builds the preimage and passes it as the message to the signing path it already has. A wallet needs no new method, and can show the tag before asking for approval.
- A verifier, usually an application or a service, keeps a list of the tags it accepts for each record type, rebuilds the body and preimage from what it parsed, and refuses with the codes of section 6.
- Libraries that offer canonical JSON can add the profile of section 5 as a strict mode. Nobody else has to change anything.

## Motivation

A signature says that a key signed some bytes. Whether those bytes mean "a grant of access", "a manifest", or "a policy" is decided by whoever reads them. Two things go wrong between the key and the meaning.

**The same bytes can mean two things.** Many BRCs sign records with keys that are also used elsewhere. BRC-77 signs every message under one BRC-43 protocol ID, `message signing`. BRC-369 signs the RFC 8785 form of a descriptor with the publisher's identity key directly. SIGMA and the Bitcoin Signed Message construction sign with an address key whatever message they are given. If a record of one protocol also parses as a valid record of another, or if a signer can be asked to sign bytes chosen by someone else, a signature collected in one context can be presented in another. BRC-43 protocol IDs separate keys, but only where the signer uses a derived key and a distinct protocol ID for each record type, and not where the identity key signs directly.

**Several BRCs already add a domain tag, each in its own way.** BRC-211 and BRC-370 write an ASCII tag and a `0x00` byte. BRC-177 writes an ASCII tag and a line feed. BRC-179 and BRC-181 put the tag inside the JSON as a member. BRC-222 length-prefixes it with four bytes. BRC-216 and BRC-220 write a bare ASCII prefix. BRC-192 defines `"BRC-OUTPUT/1/" + T || 0x00 || JCS(B)` for its own family of documents, 192 to 199. Each is sound on its own terms, but there is no shared grammar, no rule for who may use which tag, and a new author has nothing to cite, so the next record type invents an eighth construction.

**The body bytes drift.** Nineteen BRCs cite RFC 8785 by number and four more use it by its short name, JCS, while others define their own sorted-key JSON. Their outputs differ for the same value: BRC-179 and BRC-181 escape every non-ASCII character as `\uXXXX`, RFC 8785 writes it as UTF-8. BRC-52 records that its historical field order came from a host-dependent collation. Registry issue #360 asks which bytes a BRC-103 signature covers. Number formats, duplicate member names, Unicode normalization and lone surrogates are each a place where two parsers that pass their own tests produce different bytes, and then every signature fails with no hint of which side moved.

An open proposal, BRC-239 (pull request #370, "Canonical JSON for Signed Objects"), addresses the JSON bytes with a strict RFC 8785 profile. It fixes the bytes of a value and nothing else: domain separation, how the type and version of a record are bound into what is signed, is left to the citing protocol, and its canonical bytes may be one part of a larger preimage. This document supplies that part, the domain tag, and adds the record-level rules a signed record needs that BRC-239 does not set: NFC, the treatment of `null`, byte strings, times, a top-level object, and a depth limit that every verifier enforces. This document's JSON profile is stricter than BRC-239's and never contradicts it: a record valid here has the same canonical bytes under BRC-239.

## Scope and conformance

**Layer:** Interface. This document specifies bytes that cross a boundary between a signer and a verifier.

**Conformance targets.** Every MUST below binds one of these, and nobody else:

- a **record specification**: a document (a BRC or any other published specification) that defines a record type and claims conformance to this BRC;
- a **signer** that claims to produce records of such a type;
- a **verifier** that claims to check them.

An implementation that does not claim conformance does not follow this BRC; it is not thereby invalid, and nothing here changes the validity of any transaction, script or existing signature.

**In scope:**

1. The domain tag: its grammar, the namespacing rule, versioning (section 2).
2. The preimage: how the tag and the body are joined (section 3), and how the preimage enters existing signing paths (section 4).
3. One canonical form for structured records written as JSON (section 5).
4. Verifier rules and refusal codes (section 6), and migration (section 7).

**Not in scope (non-goals):**

- A universal serializer. Records with a binary body keep whatever layout their specification defines; only the tag rule applies to them.
- A signature algorithm, key derivation, or key choice. Those stay with BRC-3, BRC-42, BRC-43, BRC-77, BRC-100 and the record specification.
- A registry of tags. Namespacing is registry-free (section 2.2).
- Changing any existing format. BRC-77 envelopes, Bitcoin Signed Messages, BRC-52 certificates, BRC-103 and BRC-104 messages, the BRC-192 family, and every record that already defines its own tag keep their bytes.
- ECDSA signature malleability, nonce generation and low-S rules. A record specification may require low-S; this document does not.
- Transport, storage and how a record is found. These stay the implementer's choice.

## Relationship to existing standards

- **BRC-3, BRC-42, BRC-43, BRC-100.** A wallet signature already separates keys by protocol ID and key ID. That separation remains and is recommended alongside the tag (section 4, item 5). The tag adds separation inside the signed bytes, which still holds when a key is used directly or one protocol ID serves several record types.
- **BRC-77.** The preimage is the BRC-77 message. The envelope (version `0x42423301`) does not change. Existing BRC-77 signatures are unaffected.
- **Bitcoin Signed Message, BRC-217, SIGMA (BRC-247, BRC-248).** The preimage can be the message `M`. The Bitcoin Signed Message construction adds its own prefix and double SHA-256 as before.
- **BRC-239 (proposed, pull request #370).** BRC-239 leaves domain separation to the protocol that cites it, and this document is such a protocol. Section 5's canonical form is RFC 8785 restricted to a subset of BRC-239's inputs. Where both apply they give the same bytes. If BRC-239 is adopted, a record specification may cite it for the serialization and this document for the further restrictions and the tag.
- **BRC-192 to BRC-199.** Their `BRC-OUTPUT/1/` construction is a family rule with the same purpose. It stays as it is.
- **BRC-145, BRC-177, BRC-179, BRC-181, BRC-211, BRC-216, BRC-220, BRC-222, BRC-370.** Each defines its own tag. Nothing here changes them. A later version of any of them may adopt this construction under section 7.
- **BRC-369.** Signs the RFC 8785 form of a descriptor with the identity key and no tag. It is an example of the case section 4, item 5 describes, not a document this one amends.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are used as in RFC 2119 and RFC 8174.

### 1. Terminology

- **Record type**: a kind of signed statement, defined by one record specification, with one body format.
- **Domain tag** (tag): the ASCII string that names one version of one record type.
- **Body**: the bytes that carry the record's content. For a JSON record, its canonical form (section 5). For a binary record, the bytes its specification defines.
- **Preimage**: the bytes of section 3. This is what is signed, after whatever hashing the signing path applies.
- `||` is byte concatenation. `u8(n)` is the single byte with value `n`. `0x..` is hexadecimal. `SHA-256` is FIPS 180-4.

### 2. The domain tag

#### 2.1 Grammar

A tag is a string of ASCII bytes, at least 1 and at most 255 bytes long, matching:

```
tag        = namespace "/" name "/v" version
namespace  = brc-ns / dns-ns
brc-ns     = "brc-" pos-int-6               ; "brc-" then 1 to 6 digits, no leading zero
dns-ns     = label 1*("." label)            ; at least two labels
label      = alnum [ *61( alnum / "-" ) alnum ]
name       = alnum [ *62( alnum / "-" / "." ) alnum ]
version    = pos-int-9                      ; 1 to 9 digits, no leading zero
alnum      = %x61-7A / %x30-39              ; a to z, 0 to 9
```

`pos-int-6` and `pos-int-9` are a digit from 1 to 9 followed by at most 5, or at most 8, digits. As a regular expression that must match the whole string, with no trailing line feed:

```
^(?:brc-[1-9][0-9]{0,5}|L(?:\.L)+)/[a-z0-9](?:[a-z0-9.-]{0,62}[a-z0-9])?/v[1-9][0-9]{0,8}$
where L = [a-z0-9](?:[a-z0-9-]{0,61}[a-z0-9])?
```

Upper-case letters, other punctuation, empty parts, and leading zeros in a number are not part of the grammar. A record specification MUST give its tag or tags as literal strings. Examples: `brc-1234/access-grant/v1`, `example.org/note/v2`.

#### 2.2 Namespacing, without a registry

- **`brc-N`.** Only the BRC numbered `N`, or an amendment to it, may define tags in the namespace `brc-N`. A record specification that is a BRC SHOULD use its own number. While its number is not final, its vectors are drafts; a change of number changes its tags and so its vectors.
- **A DNS name.** A record specification that is not a BRC uses a DNS name, in lower-case ASCII form (an internationalized name is written as its A-labels), that its author holds when the tag is first published. Holding the name later is not required, and losing it does not transfer the tags: a later holder of the name MUST NOT define a different meaning for a tag already published under it.
- **Reserved for examples.** The names `example.org`, `example.com` and `example.net` and names ending in `.example`, `.test` or `.invalid` are for documentation and test vectors only. A record specification MUST NOT use them for records meant to be relied on.

There is no registry, and none is needed: a verifier never learns which tags are acceptable from the record. It is configured, in code or in its own settings, with the tags it accepts for each record type it checks (section 6).

#### 2.3 Versioning and meaning

A tag names exactly one body format and one meaning. Once a tag is published:

- its body format and meaning MUST NOT change;
- any change to which bytes are signed, or to what a valid record means, MUST use a new version number or a new name;
- a record specification MAY accept several versions, and lists each one.

The version in the tag is the version of the record format, not of this document. The marker of section 3 carries this document's version.

### 3. The preimage

```
MAGIC     = 0x00 0x64 0x73 0x70 0x31            ; 0x00 then ASCII "dsp1", 5 bytes
preimage  = MAGIC || u8(len(tag)) || tag || body
```

- `len(tag)` is the tag's length in bytes, 1 to 255.
- The body runs to the end of the preimage. It is not length-prefixed; the preimage is always built by the party that signs or verifies it, never taken from the wire (section 6).
- For a JSON record the body is its canonical form (section 5). For a binary record the body is the byte layout its specification defines, and that layout MUST have exactly one parse: every variable-length field carries its length, and no bytes may follow the last field.

The marker begins with `0x00`. No JSON text begins with that byte, nor does a Bitcoin Signed Message preimage (which begins `0x18`) or any of the ASCII-tagged preimages listed in the Motivation. BRC-222's four-byte length prefix begins `0x00 0x00`, where the marker continues with `0x64`. A conforming preimage therefore does not coincide with a preimage of those formats. A future, incompatible preimage construction would change the marker, not the tag grammar.

### 4. Signing the preimage through existing paths

The preimage is the message. Each path below hashes and signs it as that path always has.

1. **BRC-100 `createSignature`.** The signer passes the preimage as `data`. The wallet computes ECDSA over one SHA-256 of it, and `verifySignature` with the same `data` checks it. A signer that hashes first MUST pass `SHA-256(preimage)` as `hashToDirectlySign`, and a verifier that hashes first MUST pass it as `hashToDirectlyVerify`. A signer or verifier MUST NOT pass the digest as `data`, because that signs or checks `SHA-256(SHA-256(preimage))`, which does not match a signature over the preimage.
2. **BRC-77.** The preimage is the message. The envelope is unchanged.
3. **Bitcoin Signed Message, and SIGMA tapes that use it.** The preimage is the message `M`. The construction adds its own prefix and computes its double SHA-256 as usual.
4. **Plain ECDSA** with a key held outside a BRC-100 wallet, such as an issuer key: the signer computes ECDSA over `SHA-256(preimage)`.
5. **Key separation is still recommended.** Where a record is signed through BRC-100 or BRC-3, its specification SHOULD also give it a BRC-43 protocol ID that no other record type uses. The tag does not replace key separation, and key separation does not replace the tag: key separation fails when a key is used directly or a protocol ID is shared, and the tag fails when a signer will sign any bytes a caller supplies (Security Considerations).
6. **Carrying the tag.** A record need not carry its tag on the wire, because the verifier knows which tags it expects. If a container does carry it, the verifier compares it with its expected tags (section 6, step 1) and never adopts a tag only because the container names it.

### 5. Canonical form for JSON records

#### 5.1 The profile

A JSON record is within the profile when all of the following hold. A signer MUST NOT sign a record outside the profile, and a verifier MUST refuse one (section 6).

1. **Text.** The input is UTF-8 without a byte order mark, and is exactly one JSON text (RFC 8259) with nothing after it but JSON whitespace.
2. **Top level.** The value is an object.
3. **Member names.** Every member name, at every depth, is ASCII (U+0000 to U+007F). No object has two members whose names are equal after escapes are decoded.
4. **Numbers.** Every number is written as an integer: an optional `-`, then digits, with no fraction, no exponent, and not `-0`. Its value lies between −(2^53 − 1) and 2^53 − 1 inclusive.
5. **No null.** The literal `null` does not appear. A member that has no value is absent. A record specification states what absence means.
6. **Strings.** After escapes are decoded, every string, whether a value or a member name, is a sequence of Unicode scalar values (no unpaired surrogate), every code point in it is assigned in the verifier's Unicode data (general category other than `Cn`), and it is in Normalization Form C.
7. **Depth.** Objects and arrays nest at most 32 deep. The top-level object is depth 1.

`true`, `false`, strings, integers, arrays and objects are the only values.

#### 5.2 The canonical form

The canonical form of a record within the profile is its RFC 8785 serialization, encoded as UTF-8. For values within the profile that comes to:

- no whitespace;
- object members sorted by name, comparing the names' bytes (for ASCII names this is the same as RFC 8785's UTF-16 order), each written as name, `:`, value, separated by `,`;
- array elements in their original order, separated by `,`;
- strings between `"`, with `"` and `\` written as `\"` and `\\`; U+0008, U+0009, U+000A, U+000C and U+000D written as `\b`, `\t`, `\n`, `\f` and `\r`; any other character below U+0020 written as `\u00` and two lower-case hexadecimal digits; every other character, including `/`, U+007F, U+2028, U+2029 and all non-ASCII characters, written as itself in UTF-8;
- integers in decimal with no leading zeros and a leading `-` when negative, zero as `0`;
- `true` and `false`.

This is the same output as the BRC-239 proposal gives for these values. The profile only refuses more inputs: `null`; a top-level value that is not an object; non-canonical integer text, which BRC-239 lets a verifier refuse; strings not in NFC; unassigned code points, including the noncharacters such as U+FFFF and U+FDD0, which BRC-239 permits; and nesting beyond 32, which BRC-239 lets a verifier refuse.

#### 5.3 Typed members

A record specification declares the type of each member. For the following kinds of value it MUST use these encodings, so that one value has one spelling:

- **Byte string** (keys, digests, signatures, nonces): a JSON string of lower-case hexadecimal digits, two per byte. The empty byte string is `""`. Upper-case digits and an odd number of digits are refused. Large binary content SHOULD be referenced by its digest rather than embedded.
- **Time**: a JSON integer, the number of seconds since 1970-01-01T00:00:00Z, not counting leap seconds (POSIX time), zero or more. Text forms such as RFC 3339 are not used in signed members.
- **Amount or count**: a JSON integer. A satoshi amount always fits.
- **Decimal fraction, or an integer beyond 2^53 − 1**: a JSON string whose exact pattern the record specification gives. JSON numbers are not used for them.

A record specification also states whether its objects are closed (a member it does not define is refused) or open (an unknown member is kept, canonicalized and covered by the signature like any other). Either way, the verifier canonicalizes every member present.

#### 5.4 Why this profile

- **Against full RFC 8785.** Full JCS orders names by UTF-16 code unit and formats numbers the ECMAScript way, the two places where implementations in other languages drift. Restricting names to ASCII and numbers to safe integers removes both, as BRC-211 and the BRC-239 proposal already do.
- **Against deterministic CBOR (RFC 8949, section 4.2).** CBOR has native byte strings, which is its real advantage. But a deterministic profile still needs choices of its own (map key order of section 4.2.1 versus the length-first order of section 4.2.3, preferred float encoding, tags, indefinite lengths), most signed-record BRCs are JSON and already use RFC 8785, JSON records can be shown to a person approving a signature, and a binary record can use its own exact layout under section 3 without a general-purpose encoder.
- **NFC rather than normalizing.** A verifier never normalizes, because normalizing changes the signed bytes. It refuses, and the signer decides whether to normalize text before it builds the record. This is a record rule only: BRC-43 key IDs, BRC-52 fields and BRC-188 passwords keep their rule of no normalization.
- **No null.** Two spellings for "no value", absent and `null`, are one more way for two implementations to disagree. The profile keeps one.
- **Noncharacters refused.** The 66 noncharacters (U+FDD0 to U+FDEF, and the last two code points of every plane, such as U+FFFE and U+FFFF) have general category `Cn`, so rule 6 refuses them like any unassigned code point. BRC-239 permits them, relaxing RFC 7493, section 2.1, because they do not make implementations disagree on bytes, and refusing them would only make implementations disagree on what they refuse. That reasoning fits a profile that uses no Unicode data. This profile uses Unicode data anyway, for NFC and for unassigned code points, so refusing noncharacters adds no new mechanism and no new way to disagree. They are reserved for a program's internal use and are not meant for interchange, which a signed record is. Unicode never assigns a noncharacter, so every verifier refuses them under every Unicode version, and the refusal adds no version skew. Refusing them keeps the profile a strict subset of BRC-239: a record that contains one is refused here and accepted there, never given different bytes.

### 6. Verifier rules

A verifier is configured with, for each record type it checks, the set of tags it accepts and the record specification behind each. To check a record of that type it MUST, in order, and fail closed at the first failure:

1. Check the tag against the grammar of section 2.1 (`ERR_TAG_SYNTAX`), then check that it is one of the accepted tags for this record type (`ERR_TAG_MISMATCH`). A tag carried by the record or its container is compared, never trusted.
2. For a JSON record, parse the input and check every rule of section 5.1, then the typed members of section 5.3, using the codes below. For a binary record, parse the body by its specification and refuse anything that specification refuses.
3. Build the body itself: for a JSON record, the canonical form of the value it parsed. It MUST NOT use canonical bytes, a body, or a preimage supplied by the sender in place of its own.
4. Build the preimage (section 3) and verify the signature over it by the path the record specification names (section 4) (`ERR_SIGNATURE`).
5. Read the record's fields only from the value it parsed in step 2.

A verifier MUST NOT repair a record to make it pass: it does not normalize strings, drop duplicate members, round numbers, change case, or try a second tag or a second construction after the first fails.

| Code | Refused because |
|---|---|
| `ERR_TAG_SYNTAX` | The tag does not match section 2.1, or is longer than 255 bytes. |
| `ERR_TAG_MISMATCH` | The tag is well formed but not one the verifier accepts for this record type. |
| `ERR_JSON_SYNTAX` | The input is not UTF-8, carries a byte order mark, is not one JSON text, is truncated, has data after the value, or contains a token JSON does not have, such as `NaN`. |
| `ERR_NOT_OBJECT` | The top-level value is not an object. |
| `ERR_DUPLICATE_MEMBER` | An object has two members with the same name. |
| `ERR_MEMBER_NAME` | A member name contains a non-ASCII character. |
| `ERR_NUMBER` | A number has a fraction or an exponent, is `-0`, or lies outside ±(2^53 − 1). |
| `ERR_NULL` | `null` appears. |
| `ERR_STRING_UNICODE` | A string contains an unpaired surrogate. |
| `ERR_STRING_UNASSIGNED` | A string contains a code point unassigned in the verifier's Unicode data. |
| `ERR_STRING_NOT_NFC` | A string is not in Normalization Form C. |
| `ERR_DEPTH` | Nesting exceeds 32. |
| `ERR_FIELD_ENCODING` | A typed member breaks section 5.3. |
| `ERR_SIGNATURE` | The signature does not verify over the preimage the verifier built. |

When a record breaks several rules, a verifier MAY report any one of the matching codes. Each refusal vector below breaks exactly one rule. The codes are names for reporting and testing; how an implementation surfaces them is its own choice.

**Unicode versions.** The NFC check and the unassigned-code-point check use the verifier's Unicode data. Two verifiers with different Unicode versions can disagree about a string that contains a code point assigned in the newer version only: the older refuses it with `ERR_STRING_UNASSIGNED`, the newer accepts it. That disagreement only ever fails closed: it never lets one verifier accept a string that another reads as differently normalized. A signer SHOULD keep text in signed records to characters assigned in Unicode versions that its verifiers can be expected to have. Vector U1 shows the split.

### 7. Migration

- Existing record formats, and every signature already made over them, are unchanged. This document gives no reason to re-sign anything.
- A record specification adopts this construction only for a new record type or a new version of an existing one, and gives the new version a tag.
- A verifier that accepts both an older construction and this one MUST decide which applies from information outside the signature, such as a version member in a container, a distinct output type, or a distinct transport. It MUST NOT verify a record under one construction and then, on failure, under the other: trying both lets a signature made for the older, untagged bytes stand in for a tagged record.
- A signer SHOULD NOT sign the same logical record under both constructions.

## Security Considerations

**Cross-protocol replay.** A signature over a preimage covers the tag. A verifier builds the preimage with a tag it chose, so a signature made for another record type, another version, or a protocol that signs bare canonical JSON does not verify (vectors R26, R27 and R29). This holds whichever key is used, including an identity key used directly.

**What the tag cannot stop.** If a signer will sign any bytes a caller supplies with the same key, a caller can submit a preimage of any record type, tag included. The tag does not help against such a signing oracle; key separation does (section 4, item 5), and so does a signer that shows a person what it is signing. A wallet that receives `data` beginning with the five marker bytes MAY decode and display the tag before it asks for approval.

**Type confusion within one tag.** The tag separates record types. Within one tag, the record specification must make its body unambiguous: a closed or open member set (section 5.3), and for a binary body, exactly one parse (section 3).

**Collision with other formats.** The marker starts with `0x00`, which none of the ASCII-tagged preimages listed in the Motivation, no JSON text and no Bitcoin Signed Message preimage starts with (section 3). Transaction signature digests and Bitcoin Signed Messages use double SHA-256, while the paths of section 4 other than the Bitcoin Signed Message use one; a collision across those would need a preimage equal to a 32-byte SHA-256 output, which also begins with the marker and a valid tag. Other formats a record's signing key also signs remain the record specification's concern; using a key for one purpose is the stronger defence.

**Truncation and extension.** The tag is length-prefixed, so no tag is a prefix of another tag's preimage, and the verifier always builds the preimage itself. Truncated JSON fails to parse (R12) and trailing data is refused (R13). SHA-256 length extension does not affect a signature, but a record specification MUST NOT turn the preimage into a keyed hash by prepending a secret; it uses HMAC (RFC 2104).

**Canonicalization attacks.** Each rule of section 5.1 removes a known way for two parsers to read different values from the same text. Duplicate members (R1) are read as the first by some parsers and the last by others. Numbers beyond 2^53 − 1 (R7) lose precision in some languages before canonicalization begins. Non-canonical number text (R4 to R6) maps to one integer in one parser and a float in another. Strings that are canonically equivalent but differ in bytes (R9) look identical on screen. Unpaired surrogates (R10) are rejected by some decoders and replaced by others. Deep nesting (R16) exhausts stacks. The verifier refuses each instead of choosing an interpretation.

**Namespace capture.** A DNS name can change hands. A later holder cannot change what a published tag means to a verifier, because verifiers accept only tags they were configured with, and section 2.2 forbids redefining one. A record specification SHOULD use a name its author expects to keep, or a `brc-N` namespace.

**Downgrade.** Section 7 forbids verifying under an older construction after the new one fails.

**Signature malleability** of ECDSA is out of scope. A record specification that relies on a signature's bytes being unique, for example as an identifier, must require low-S and DER minimal encoding itself.

## Cryptographic basis

### Primitives

Nothing here is new cryptography. The construction uses:

- **SHA-256** (FIPS 180-4), the hash every signing path of section 4 applies to the preimage: once for BRC-100 `createSignature` and for plain ECDSA, twice for a Bitcoin Signed Message after its own prefix.
- **ECDSA over secp256k1** (SEC 1, SEC 2), as BRC-3 and BRC-100 already use it, with a key derived by BRC-42 and BRC-43 or with a key used directly.
- **The existing envelopes**: BRC-100 `createSignature` and `verifySignature`, the BRC-77 signed message, and the Bitcoin Signed Message construction that BRC-217 states to the byte. The preimage is their message. None of them changes.

The test vectors use one SHA-256 and ECDSA with RFC 6979 nonces and low-S. A round trip through each of the first two envelopes was run (Test Vectors, Envelopes).

### Properties relied on

- **Collision resistance of SHA-256**: it is infeasible to find two different byte strings with the same digest. Every ECDSA signature here covers a digest, so this is what lets a signature over a digest stand for a signature over the preimage.
- **Second-preimage resistance of SHA-256**: given a preimage, it is infeasible to find another with the same digest. An outside attacker, who did not choose the signed record, has to break this, which is harder than finding a collision.
- **Existential unforgeability of ECDSA under chosen-message attack.** This document assumes, as every BRC that signs with ECDSA does, that nobody without the private key can produce a valid signature on a digest the key holder never signed, even after seeing signatures on digests of their choosing.

ECDSA is not strongly unforgeable: if `(r, s)` verifies, so does `(r, n - s)`, where `n` is the group order. The generator's checks confirm this on A1's signature. It gives an attacker a second signature on the same preimage, never a signature on a different one, so it does not touch the separation argument below. A record specification that needs unique signature bytes requires low-S itself (Security Considerations).

### What the tag adds

Without a tag, the assumptions above give only this: a valid signature means the key holder signed these bytes in some protocol. With the tag, they give: the key holder signed this record as this version of this record type. The step between the two is the injectivity of the preimage, proved in the Mathematical basis. Two different pairs of tag and body never produce the same preimage, so two different pairs only share a digest through a SHA-256 collision. Suppose a verifier that expects tag `t` accepts a signature on body `b`. Then either the signature is a forgery, or the key holder signed, through some path, a message whose digest equals the digest of `preimage(t, b)`. If that message was a conforming preimage of a different pair, the two digests are a SHA-256 collision. If it was a message of another format, the message must equal `preimage(t, b)` byte for byte, which would require it to start with `0x00`, `dsp1`, a length byte and a tag the verifier accepts. JSON texts, Bitcoin Signed Message preimages and the ASCII-tagged preimages of the Motivation never do (section 3).

A Bitcoin Signed Message is hashed twice, so a signature on one could be presented as a single-hash signature on a preimage only if that preimage were itself the 32-byte inner digest. The inner digest would have to begin with at least 14 fixed bytes: the marker, a length byte and a tag of at least 8 bytes, 112 bits in all. Treating SHA-256 as a random function, finding such a digest takes about 2^112 attempts. The attack also needs a signer that signs a message the attacker chose, which is the case below.

### What the tag does not prevent

- **A signer that signs anything.** A signer that signs whatever bytes a caller supplies can be handed a complete preimage, tag included. The tag gives no protection here; key separation (section 4, item 5) and a signer that shows what it signs do.
- **The same tag used for two meanings.** Section 2.3 forbids it and section 2.2 assigns namespaces, but neither can stop an author who breaks the rule. Two record types under one tag are not separated.
- **A wrong parser.** The argument assumes the verifier reads the record's meaning from the value it parsed and canonicalized (section 6, steps 3 and 5). A verifier that checks the signature over its rebuilt bytes and then reads fields from the raw input, or a parser that accepts input outside the profile, can act on a value nobody signed.
- **Replay under the same tag.** A record presented twice is the same record. Freshness, if a record type needs it, comes from a nonce, an expiry or a counter that the record specification defines.
- **Key compromise.** Anyone holding the private key can sign any preimage.

### Relationship to RFC 8785 and the BRC-239 proposal

RFC 8785 defines its output by reference to ECMAScript: strings as `JSON.stringify` writes them, numbers as ECMAScript's `Number::toString` writes them, and members sorted by UTF-16 code unit. On the profile of section 5 these rules give exactly section 5.2's bytes. Member names are ASCII, and for ASCII strings UTF-16 code unit order and byte order are the same. Numbers are integers within ±(2^53 − 1), which ECMAScript writes in plain decimal; it uses exponent form only from 10^21. The string escapes of section 5.2 are those of RFC 8785, section 3.2.2.2. So the profile is RFC 8785 restricted to fewer inputs, and a conforming body is also a valid RFC 8785 output. This was checked by running: 5,000 random records within the profile, including control characters, quotes, U+2028, U+007F and characters outside the Basic Multilingual Plane, were serialized by the reference implementation and by `JSON.stringify` with members sorted by UTF-16 code unit, with identical bytes in every case. Outside ASCII the two orders do differ (U+1F600 sorts before U+FF61 by UTF-16 code unit and after it by byte), which is why member names are kept to ASCII.

The BRC-239 proposal (pull request #370) is itself a profile of RFC 8785. The text cited here is its file `peer-to-peer/0239.md` at commit `89ddbbb`, with its vector file at the same commit. Its section 4 (lines 105 to 109) leaves to the citing protocol which key signs and domain separation, "how the type and version of a record are bound into what is signed", and says that the canonical bytes may be one part of a larger preimage. This document is such a protocol: section 3's preimage is that larger preimage, and its body is BRC-239's canonical bytes for every record this profile accepts.

Its section 1 (lines 42 to 65) sets five rules: no duplicate member names, compared after unescaping; no unpaired surrogate, written raw or escaped; ASCII member names; integers within ±(2^53 − 1), a bound that a citing profile MUST NOT widen; and nesting that a verifier MUST accept up to 32 deep and MAY refuse beyond. It also says that a verifier applies the five rules itself, because an RFC 8785 library does not. This profile has the same bound and the same depth of 32, refuses everything those rules refuse, and refuses more: it makes the depth limit a MUST, and it refuses `null`, a top-level value that is not an object, non-canonical integer text, strings not in NFC and unassigned code points. Rule 2 of BRC-239 (lines 46 to 49) permits the noncharacters, such as U+FFFF and U+FDD0, and this profile refuses them (section 5.4).

Run against BRC-239's 30 vectors at that commit, this profile gives identical bytes for the 12 it accepts and refuses the other 18: the 11 that BRC-239 refuses; the 4 it lets a verifier refuse, which are the three non-canonical number writings and nesting 33 deep; and 3 that it accepts, which are `null` (its V11), the noncharacters (V26) and an array nested 32 deep at the top level (V29), refused here because a record is an object. None differ. Both implementations written for this document give these results.

### Unicode normalization

Strings that look the same can differ in bytes: `é` is one code point in NFC and two (`e` and U+0301) in NFD. A verifier that normalized before hashing would sign or check bytes the signer never produced, and two verifiers that normalized differently would disagree. So a verifier refuses a string that is not already NFC (R9) and never repairs it.

Normalization depends on the Unicode version. Two policies of the Unicode Consortium bound the effect. Encoding stability: once a character is encoded it is not moved or removed. Normalization stability: a string that contains only characters assigned in a given version and is normalized under that version stays normalized under every later version. Section 5.1 refuses code points unassigned in the verifier's own Unicode data. Together these mean that a string an older verifier accepts gets the same verdict from a newer one, and a string only a newer verifier accepts contains a code point the older one refuses as unassigned. Version skew can therefore make one verifier refuse a record another accepts, and can never make two verifiers accept the same bytes as different records.

This was measured between Python 3.14 (Unicode 16.0) and Node.js 22 (Unicode 17.0). 4,803 code points are unassigned in 16.0 and assigned in 17.0, the number the Unicode Consortium gives for the characters added in 17.0. No code point assigned in 16.0 is unassigned in 17.0. The NFC verdict agrees for every one of the 292,531 code points assigned in both, and for 100,000 random strings built from letters, precomposed characters and combining marks. Vector U1 shows the one case that splits: U+088F, new in 17.0, refused by the older verifier and accepted by the newer.

## Mathematical basis

### Notation

`B*` is the set of finite byte strings, `|x|` the length of `x` in bytes, and `x || y` concatenation. `M` is the five-byte marker `00 64 73 70 31`. `T` is the set of tags: the strings matched by the grammar of section 2.1 that are at most 255 bytes long.

### The tag language

The grammar of section 2.1 describes a regular language: every part is a character class repeated a bounded number of times, except that a DNS namespace may have any number of dot-separated labels, and that repetition is still regular. The regular expression in section 2.1 is the same language. The 255-byte cap makes `T` a finite set. Four facts about it are used below.

1. **Every tag is printable ASCII** and contains no `0x00` byte.
2. **Length.** The shortest tag is 8 bytes (`a.b/c/v1`): a namespace needs two labels and a dot, then `/`, a name of at least one character, `/v` and one digit. The shortest `brc-N` tag is 10 bytes (`brc-1/a/v1`). An exhaustive search confirmed that no string of 1 to 7 bytes matches: the alphabet was reduced to one representative of each class the grammar treats differently (`a`, `b`, `r`, `c`, `v`, `0`, `1`, `.`, `/`, `-`), and all 11,111,110 strings of those lengths were tried. So a header, the marker, length byte and tag, is 14 to 261 bytes.
3. **One reading.** Namespaces and names contain no `/`, so every tag has exactly two, and splits into namespace, name and version in one way. A `brc-N` namespace has no dot and a DNS namespace has at least one, so the two kinds never overlap. The version has no leading zero, so each version number has one spelling.
4. **The length fits one byte.** `1 <= |t| <= 255` for every `t` in `T`, so `u8(|t|)` is defined and distinct tag lengths give distinct length bytes.

### The preimage is injective

For `t` in `T` and `b` in `B*`, define

```
P(t, b) = M || u8(|t|) || t || b
```

**Claim 1.** If `P(t, b) = P(t', b')` then `t = t'` and `b = b'`.

*Proof.* The two strings are equal, so they are equal byte by byte. Byte 6 of each is the length byte, so `|t| = |t'|`; call it `L`. Bytes 7 to `6 + L` are `t` in one and `t'` in the other, so `t = t'`. What remains after byte `6 + L` is `b` in one and `b'` in the other, so `b = b'`.

The proof needs fact 4. If a tag could be 256 bytes long, its length byte would wrap to `0x00` and the proof fails; vector R25 is such a tag and is refused. It also needs the length byte itself: without it, `t || b` is not injective. The tags `example.org/note/v1` and `example.org/note/v12` are both valid, and `example.org/note/v1` followed by the body `32 01` is the same byte string as `example.org/note/v12` followed by `01`. With the length byte the two preimages differ in byte 6.

The header `u8(|t|) || t` is prefix-free over `T`: if the header of `t` is a prefix of the header of `t'`, their first bytes give `|t| = |t'|`, and then the two headers are equal. This is why the body needs no length of its own. The whole preimage is not prefix-free, since `P(t, b)` is a prefix of `P(t, b || x)`. That does no harm: the signature covers the digest of the whole preimage, the verifier builds the preimage from the record it parsed, and a binary body must have exactly one parse (section 3).

Claim 1 was also exercised by running: 200,000 random pairs of valid tag and body, a third of them with bodies beginning with digits so that the unprefixed form would collide, all decoded back to their pair and no two shared a preimage.

### Canonical JSON as a function

Let `V` be the set of values within the profile of section 5.1: `true` and `false`; integers `z` with `|z| <= 2^53 - 1`; strings that are sequences of Unicode scalar values, each assigned, in NFC; finite arrays of values; finite maps from ASCII strings to values; nesting at most 32 deep. A record is a map at the top level. Two values are equal when they have the same kind and the same content; maps are compared as sets of name and value pairs, so member order is not part of a value.

Let `canon` be the function from `V` to `B*` of section 5.2, and `parse` the function from `B*` that returns a value of `V` or a refusal code (sections 5.1 and 6).

**Claim 2 (round trip).** For every record `v`, `parse(canon(v)) = v`. The output of `canon` is one UTF-8 JSON text with no byte order mark; each string is written so that decoding its escapes gives back the same scalar values, which are still assigned and in NFC; each integer is written in its one canonical spelling and lies in range; member names are unique because a map has unique keys; and the nesting depth is unchanged. So `parse` accepts `canon(v)` and returns `v`.

**Claim 3 (idempotence).** For every record `v`, `canon(parse(canon(v))) = canon(v)`. This follows from Claim 2 by applying `canon` to both sides. For any accepted input `x`, `canon(parse(x))` is therefore a fixed point: canonicalizing a canonical body changes nothing.

**Claim 4 (uniqueness).** If `canon(v) = canon(v')` then `v = v'`. Apply `parse` to both sides and use Claim 2. Conversely, two inputs that parse to the same value, whatever their spacing, member order or escapes, have the same canonical body (vector A3). So each record has exactly one body, and each body belongs to exactly one record.

Composing Claims 1 and 4, the map from a tag and a record to `P(t, canon(v))` is injective on `T` times the set of records: different tag, or different record, means different signed bytes. Claims 2 to 4 were exercised by running 20,000 random records through the reference implementation, with no failure.

### Integer range

`2^53 - 1 = 9,007,199,254,740,991`. IEEE 754 binary64 has a 53-bit significand, so every integer up to `2^53` in magnitude is exact, and `2^53 + 1` is not: it rounds to `2^53`. A parser that reads JSON numbers as binary64, which is the default in JavaScript and common elsewhere, gives the texts `9007199254740992` and `9007199254740993` the same value, and the two would canonicalize alike. The profile stops one below `2^53`, at `Number.MAX_SAFE_INTEGER` and at the bound RFC 7493 gives for integers a receiver can treat as exact, so that any parser that reads numbers as binary64 or wider reads an accepted integer exactly (R7 is the first refused value). The range is wide enough for its uses: the satoshi supply, 21,000,000 × 10^8 = 2.1 × 10^15, is about 4.29 times below the limit, and `2^53 - 1` seconds is about 285 million years. Larger values go in strings (section 5.3).

### The depth limit

Nesting is limited to 32 so that every implementation accepts the same inputs, whatever its stack or recursion limit (Python's default recursion limit is 1,000), and so that a verifier can bound the work it does before it rejects. Depth does not follow from size: the top-level object costs at least 5 bytes (`{"":` and `}`) and each further container at least 2 (`[` and `]`), so the shortest record that exceeds the limit is 5 + 2 × 32 = 69 bytes. The generator's checks confirm that this 69-byte record is refused with `ERR_DEPTH` and the 67-byte record one level shallower is accepted. Vectors A7 (188 bytes, depth 32) and R16 (199 bytes, depth 33) show the limit with objects only.

### Sizes

A preimage is `6 + |t| + |body|` bytes: the header is 14 to 261 bytes, and the shortest JSON preimage is 16 bytes (an 8-byte tag and the body `{}`). SHA-256 processes the preimage in 64-byte blocks after appending at least 9 bytes of padding and length, so it runs `ceil((n + 9) / 64)` compressions for an `n`-byte preimage; a 255-byte tag alone fills five. ### Probabilities

- **Collision.** For SHA-256 modeled as a random function, the chance that any two of `q` distinct preimages share a digest is at most `q(q - 1) / 2^257`. For `q = 2^64` preimages that is below `2^-128`.
- **Bitcoin Signed Message as a preimage.** As shown under Cryptographic basis, a double-hashed signature can stand for a single-hashed one only if the inner 32-byte digest begins with at least 14 fixed bytes. That is 112 bits, so about `2^112` attempts, and it leaves at most 18 bytes for a body, which must still be one the verifier accepts.
- **Unicode skew.** Between Unicode 16.0 and 17.0, 4,803 code points change from unassigned to assigned, and none the other way (Cryptographic basis, Unicode normalization). Between the data of Java 21.0.11 and that of Node.js 22 the count is 10,615 (Cryptographic basis, Cross-implementation results). Records whose text uses only characters assigned in both versions are verified identically.

### Envelopes

These were run as round trips with the second library, not as fixed vectors, because a BRC-77 key ID is random. With A1's preimage as the input:

- BRC-100 `createSignature` with `data` = preimage, through that library's in-process implementation of a widely used wallet interface (protocol `[2, "example record signing"]`, key ID `1`, counterparty `anyone`), verifies with `verifySignature` and the same `data`, and verifies as plain ECDSA over `SHA-256(preimage)` under the derived public key.
- The same signature does not verify when `data` is `SHA-256(preimage)` (the double-hash mistake of section 4, item 1). It does verify with `hashToDirectlyVerify` = `SHA-256(preimage)`, and a signature made with `hashToDirectlySign` = `SHA-256(preimage)` verifies with `data` = preimage.
- A BRC-77 envelope (version `42423301`) over the preimage, to a named verifier and to anyone, verifies. The same envelope does not verify against A2's preimage, the same record under version 2 of the tag.

## Implementations

A reference implementation in Python and a second, independent implementation in JavaScript were written for this document and produced and checked the vectors above. No wallet, SDK or service is known to produce or verify this construction yet.

## Not tested

- The tag, the preimage, the signatures and the envelopes were not run against the Go, Rust, Java or Python SDKs of the ecosystem; only the second library in Node.js, and the Python `ecdsa` package.
- The canonical form alone was run through eleven RFC 8785 implementations in Python, JavaScript, Java, Go and Rust (Cryptographic basis, Cross-implementation results): `rfc8785` 0.1.4, `jcs` 0.2.1 and 0.3.0, `canonicalize` 5.1.0, `encoding/json/jsontext` of Go 1.27.4, `serde_jcs` 0.2.0, `serde_json_canonicalizer` 0.4.1, and the cyberphone reference implementations in Python, Node.js, Java and Go (commit `32a4819`). They only canonicalize; none of them applies this profile's refusals, so the refusal vectors were checked by the two implementations written for this document alone. Other RFC 8785 libraries, and other versions of these, were not tried. The canonical form was also compared with the BRC-239 proposal's 30 vectors (pull request #370, commit `89ddbbb`): identical bytes for the 12 this profile accepts; the other 18 are refused here, as that proposal refuses or permits refusing them, except `null`, the noncharacters and a top-level array, which it accepts and this profile refuses.
- Not run through a real BRC-100 wallet with a permission prompt, only through the in-process wallet implementation of the second library.
- Bitcoin Signed Message and SIGMA paths: not exercised.
- Unicode: the verifier ran only with versions 16.0 (Python) and 17.0 (Node.js). The unassigned code points of Java 21.0.11 and Go 1.27.4 were counted and compared, but no verifier ran on them.
- No on-chain use; nothing here was broadcast.
- A streaming parser, which might see a record before it is complete, is not covered.
