# BRC-239: Canonical JSON for Signed Objects

Todd Price (todd@realblockchainsolutions.com)

## Abstract

This BRC specifies how to turn a JSON value into the exact bytes a party signs, so that independent implementations
in any language produce the same bytes and verify each other's signatures. It is a profile of
[RFC 8785](https://www.rfc-editor.org/rfc/rfc8785) (the JSON Canonicalization Scheme). It restricts the input to
ASCII member names and integers within ±(2⁵³ − 1), which are the cases where every common JSON implementation
already agrees. It also says how to sign the bytes through [BRC-100](../wallet/0100.md), and lists the
implementation shortcuts that silently break agreement.

A BRC that signs JSON can cite this one instead of defining its own sorted-key form.

## Motivation

Many BRCs sign JSON objects. Seventeen cite RFC 8785, and others describe a sorted-key form of their own. Two
implementations that each pass their own tests can still disagree on the bytes, and when they do, every signature
fails with no hint of which side moved.

Full RFC 8785 leaves two places where implementations drift in practice:

- **Member order.** RFC 8785 sorts member names by UTF-16 code unit. Byte-order and code-point sorts agree with that
  for names below U+10000 and disagree above it. [BRC-211](../overlays/0211.md) already restricts its member names
  to ASCII for this reason.
- **Numbers.** RFC 8785 formats numbers as ECMAScript does, with its own exponent thresholds and shortest
  round-trip digits. Many languages format floats differently, and JSON parsers in some languages lose precision on
  integers beyond 2⁵³ before canonicalization begins.

This profile removes both by refusing them. Within the profile, the common shortcuts still go wrong in ways that
pass casual testing; the implementation notes list the ones found while building three interoperating
implementations. Registry issue [#360](https://github.com/bsv-blockchain/BRCs/issues/360) is the same family of
problem: two implementations signing over different bytes for the same message.

## Specification

The key words MUST, MUST NOT, SHOULD, SHOULD NOT, RECOMMENDED and MAY are used as in RFC 2119.

### 1. The values the profile covers

A JSON value is within the profile when:

1. it is I-JSON ([RFC 7493](https://www.rfc-editor.org/rfc/rfc7493)): its strings are well-formed Unicode, and no
   object has two members with the same name;
2. every member name, at every depth, consists only of ASCII characters, U+0000 to U+007F;
3. every number is an integer between −(2⁵³ − 1) and 2⁵³ − 1 inclusive.

A signer MUST NOT sign a value outside the profile. A verifier MUST refuse one, as far as its parser lets it tell. A
parser that keeps only the last of two duplicate members can't detect duplicates, so a signer's obligation not to
produce them matters most.

### 2. The canonical form

The canonical form of a value within the profile is its RFC 8785 serialization, encoded as UTF-8. For values within
the profile, that comes to the following rules:

- **Whitespace.** None.
- **Objects.** Members are sorted by name, comparing the names' bytes. For ASCII names, byte order and RFC 8785's
  UTF-16 order are the same. Each member is written as its name, `:`, then its value, and members are separated by
  `,`.
- **Arrays.** Elements are written in their original order, separated by `,`.
- **Strings**, whether member names or values, are written between `"`:
  - `"` and `\` are escaped as `\"` and `\\`;
  - U+0008, U+0009, U+000A, U+000C and U+000D are written as `\b`, `\t`, `\n`, `\f` and `\r`;
  - every other character below U+0020 is written as `\u00` followed by two lower-case hexadecimal digits;
  - every other character is written as itself in UTF-8, including `/`, U+007F, U+2028, U+2029 and all non-ASCII
    characters.
- **Numbers** are written in decimal: no leading zeros, no fraction, no exponent, a leading `-` for negative values,
  and zero as `0`.
- **Literals** are written as `true`, `false` and `null`.

### 3. Number text

A verifier that canonicalizes the value it parsed sees integers, not the text that wrote them. `1`, `1.0` and `1e2`
denote the integers 1, 1 and 100, and canonicalize as `1`, `1` and `100`. A verifier whose parser keeps the number's
text MAY refuse text that is not the canonical writing of its integer: a fraction, an exponent, or `-0`. A signer
SHOULD write integers in their canonical form, so that every verifier accepts them.

### 4. Signing

A protocol that signs a value under this profile signs its canonical bytes.

- **Making the signature.** Through BRC-100, the signer passes the canonical bytes as `data` to `createSignature`.
  The signature is then ECDSA over one SHA-256 of the bytes, and `verifySignature` with the same `data` checks it.
- **Hashing first.** A signer that hashes the bytes itself MUST pass the digest as `hashToDirectlySign`, never as
  `data`. Passing the digest as `data` signs SHA-256(SHA-256(bytes)), which a verifier checking the bytes refuses.
- **Verifying.** A verifier parses the received JSON, canonicalizes the value, and verifies over those bytes. The
  text as transmitted need not be canonical: whitespace, member order and escape choices in transit don't matter.

The rest of a signature — which key, protocol ID, key ID and counterparty — belongs to the protocol that cites this
one.

## Implementation Notes

Each of these produced bytes that disagreed with another implementation, while passing its own tests.

- **JavaScript: don't stringify a sorted copy.** JavaScript objects enumerate integer-like member names (`"0"` to
  `"4294967294"`) first, in numeric order, however the object was built. `JSON.stringify` of a copy built in sorted
  order therefore writes `{"2":…,"10":…,"b":…}` where the canonical form is `{"10":…,"2":…,"b":…}`. Write the sorted
  members out yourself. `Object.keys(o).sort()` with the default comparison is correct for ASCII names.
- **JavaScript: don't sort with `localeCompare`.** It depends on the host's locale data, and it orders some ASCII
  characters, such as `_`, differently from code-unit order.
- **JavaScript: keep `__proto__`.** `JSON.parse` creates `__proto__` as an ordinary member, and object spread
  keeps it. `Object.assign` and any copy made by assignment (`copy[k] = v`) set the prototype instead, and the
  member disappears.
- **JavaScript: arrays with holes.** `Array.prototype.map` skips holes, so a hand-written encoder can write `[,1]`
  where JSON requires `[null,1]`. Iterate with an index or `Array.from`.
- **Erlang and Elixir: map order.** Maps of up to 32 keys iterate in term order, which is byte order for binaries, so
  a sort-then-`Map.new` encoder looks correct in tests. At 33 keys and more, a map iterates in hash order. Keep the
  sorted members in a list.
- **Python.** `json.dumps(value, sort_keys=True, separators=(",", ":"), ensure_ascii=False)` matches every vector
  below, except that a float survives: `1.0` stays `1.0`. Refuse floats, or convert integral ones, before
  canonicalizing.
- **Go.** `encoding/json` (checked with Go 1.24) needs `SetEscapeHTML(false)`, without which `<`, `>` and `&` are
  escaped. Even then it escapes U+2028 and U+2029, and writes negative zero as `-0`, so it can't be used as is.

## Test Vectors

[Test vectors](./0239-vectors.json) accompany this BRC. Each gives JSON text as input and one of three expected
results:

- **`accept`:** the canonical form, its bytes, their SHA-256, and a DER ECDSA signature over them by a test key
  (secp256k1, one SHA-256, low-S, RFC 6979).
- **`refuse`:** the value is outside the profile.
- **`accept-or-refuse`:** the input writes an integer in a non-canonical way (§3). An implementation may refuse it,
  and if it accepts it, it MUST produce the canonical form given.

The vectors cover:
- member order at every depth, including integer-like names, upper and lower case, and `-` and `_`;
- a member named `__proto__`;
- non-ASCII string values;
- every class of escape, plus the characters that are not escaped;
- the integer limits;
- literals and empty containers;
- whitespace in the input;
- the three non-canonical number writings;
- the refusals.

The canonical forms come from a direct transcription of RFC 8785 §3.2. The test key is SHA-256 of a label listed in
the file. It is for testing only and MUST NOT hold value.
