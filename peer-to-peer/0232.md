# BRC-232: Unsolicited Transaction Delivery to a BRC-169 Mailbox

David Case

## Abstract

This specification defines how a sender hands a recipient a transaction containing outputs for them (a token transfer, an ordinal, a [BRC-29](../payments/0029.md) payment, or any combination) inside a [BRC-169](./0169.md) envelope, without broadcasting it. The recipient's wallet internalizes each output per [BRC-100](../wallet/0100.md) and broadcasts. The envelope's `payment` member is untouched and remains the operator-visible toll or payment; the delivery travels in the encrypted `content`.

## Motivation

BRC-169 delivers one BRC-29 payment, visibly, in `payment`. Anything else a counterparty may want to hand over, such as tokens, ordinals, or several outputs of one transaction, has no defined place, and has no business being readable by the messagebox operator. The PeerPay body described in BRC-29 assumes a BRC-29 output, and BRC-29 itself leaves a multi-output message to a higher-level protocol.

One format for "here is a transaction; these outputs are yours", independent of the asset, lets a wallet support a new asset type by recognizing a derivation protocol rather than a new message.

## Specification

### Content framing

Per BRC-169 section 7.2, the decrypted `content` is a MIME entity ([RFC 2045](https://www.rfc-editor.org/rfc/rfc2045), [RFC 5322](https://www.rfc-editor.org/rfc/rfc5322)): a header block, CRLF CRLF, then the body. `Content-Type` is required and unknown headers are ignored. This is a convention, not a new mechanism.

This specification registers the content type `application/vnd.metanet.transaction+cbor` for the body below.

### Body

The body is a [DAG-CBOR](https://ipld.io/specs/codecs/dag-cbor/spec/) map:

| Key | Type | Meaning |
| --- | --- | --- |
| `memo` | tstr, optional | Free text from the sender. |
| `txid` | bstr(32) | The transaction whose outputs are delivered. |
| `beef` | bstr | A [BRC-62](../transactions/0062.md) BEEF containing that transaction and whatever ancestry and proofs the sender chooses to include. |
| `outputs` | array, at least one entry | The outputs of `txid` that belong to the recipient. |

`beef` is plain BEEF, not Atomic BEEF; `txid` names the subject. A wallet whose `internalizeAction` takes Atomic BEEF produces it from `beef` and `txid`.

Each entry of `outputs` is one of two maps, discriminated by `protocol`, which takes exactly the two values BRC-100 `internalizeAction` defines.

**Wallet payment** (a BRC-29 output):

```
{ outputIndex: uint, protocol: "wallet payment",
  derivationPrefix: tstr, derivationSuffix: tstr, counterparty: bstr(33) }
```

The recipient internalizes the output with protocol `wallet payment` and `paymentRemittance { derivationPrefix, derivationSuffix, senderIdentityKey }`, where `senderIdentityKey` is `counterparty`: the key the output was derived against. It is carried in the entry rather than taken from the envelope's `sender.identityKey` because the party delivering a transaction is not necessarily the party that derived its outputs.

**Basket insertion** (any other derived output):

```
{ outputIndex: uint, protocol: "basket insertion",
  protocolID: [uint, tstr], keyID: tstr, counterparty: bstr(33) }
```

The recipient derives the key with that `protocolID`, `keyID` and `counterparty` per [BRC-42](../key-derivation/0042.md) and [BRC-43](../key-derivation/0043.md), and internalizes the output with protocol `basket insertion`, writing the triple into `customInstructions`. Basket and tags are the recipient's choice. What the output is, how to read its script and which basket is conventional for it, is defined by the specification of the protocol named in `protocolID` (for example a token standard), not here.

Rules:

1. `outputIndex` must exist in the transaction named by `txid`, and no index appears twice.
2. The recipient MUST validate `beef` (SPV) before internalizing any output.
3. The recipient broadcasts by internalizing, as BRC-100 `internalizeAction` does.
4. The sender MUST NOT broadcast the transaction. This is the same invariant as BRC-169 section 6.1: if the delivery is rejected, the sender can reclaim the inputs by spending them elsewhere. A sending wallet can build such a transaction without locking other funds as a prefunded protected `noSend` action per [BRC-177](../wallet/0177.md).

### Routing

The envelope is submitted to a named [BRC-33](./0033.md) box at the recipient's messagebox. The box name is a convention between ecosystems; none is mandated here. A wallet collecting from the box decrypts `content`, checks `Content-Type`, and for this type processes `outputs`.

## Security Considerations

- **Operator visibility.** The messagebox operator cannot see what is delivered, by design. Only the envelope's `payment`, if any, is visible to it.
- **Validation.** The recipient must SPV-check `beef` before trusting or internalizing anything in it; an unvalidated transaction may never confirm.
- **Unknown protocols.** A delivery whose `protocolID` the wallet does not recognize should be held, not dropped: the outputs are still the recipient's, and a later wallet version may know how to use them.
- **Replay.** The same delivery may arrive twice. A wallet dedupes on `txid` and `outputIndex`.
- **Broadcast decision.** Nothing here grants the sender any claim on whether or when the recipient broadcasts.
