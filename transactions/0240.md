# BRC-240: Merkle Path Verification Rules for SPV Verifiers

RexStarBSV (RexStarBSV@protonmail.com)

## Abstract

This BRC sets the rules a verifier follows when it decides, from a transaction's bytes, a [BRC-74](./0074.md) Merkle path and a block header, that the transaction is in that block. A header commits to a Merkle root and to nothing else about the tree: not its height, not the number of transactions. So the same root can be reached from bytes that are not a transaction of the block. The rules close the known cases: a 64-byte transaction is never taken as included, no step of the transaction's own path may hash 64 bytes that decode as a transaction, a duplicate, or a sibling equal to the working hash, may stand only on the right, the fold takes exactly the path's declared tree height, and the root is compared only with the header at the path's own height. A second, separate claim adds what the verifier checks of that header: its proof of work against its own target, and its link to the chain below it. 36 test vectors, made by code and checked by a second implementation, cover paths a block produces, of several shapes, and a refusal for each rule but those the Not tested section lists.

## Motivation

Simplified payment verification rests on one comparison: a transaction's Merkle path, folded from its txid, gives the Merkle root of a block header the verifier trusts. Wallets, overlays, BEEF readers and payment processors all make it, and most take a path in the [BRC-74](./0074.md) form.

The comparison is weaker than it looks, for three reasons that are old and public.

1. **The tree height is not authenticated.** A header holds the root, and nothing in the header says how tall the tree below it is. A BRC-74 path declares a tree height in one byte, and the verifier cannot check it. A transaction's txid is the double SHA-256 of its bytes, and an inner node of the tree is the double SHA-256 of its two children, 64 bytes. So a 64-byte transaction and an inner node hash alike. Two attacks follow (Rationale). In the first, two inner nodes read together as a transaction, and a path one level shorter than the real one proves it. In the second, a real 64-byte transaction is mined, and its two halves are offered as the bottom step of a path one level taller, so that a transaction whose txid is the first half appears proven. Neither needs anything from the verifier but a fold and a root comparison.
2. **Duplicates.** A Merkle tree pairs the last node of an odd level with itself. BRC-74 marks that with flag `01` and says nothing about where it may stand. Issue [#357](https://github.com/bsv-blockchain/BRCs/issues/357) records two readings of a `01` node at an even offset, and implementations that read it differently.
3. **The header.** A path proves inclusion under a header only if the header is real. A verifier that asks a service whether a root is valid at a height has handed the whole check to that service.

No BRC tells a verifier about the first, and none settles the second. [BRC-9](./0009.md) asks that proofs link to the genesis block and the chain with the most work, for its own envelope, without saying what a verifier checks of a header; [BRC-62](./0062.md) assumes an independent source of headers. [BRC-9](./0009.md), [BRC-62](./0062.md), [BRC-67](./0067.md), [BRC-74](./0074.md), [BRC-95](./0095.md) and [BRC-96](./0096.md) are silent on 64-byte transactions and on the tree height. [BRC-237](./0237.md) closes both 64-byte attacks, but only for the anchors of its own payment evidence statements (its section 1, conditions (d) and (e), and its Security Considerations).

The base rules allow a 64-byte transaction. SV Node's context-free transaction check refuses a transaction with no inputs or no outputs, one above the maximum size, and outputs outside the money range, and sets no minimum size ([`src/validation.cpp` L519-L569](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.cpp#L519-L569)); its `MIN_TRANSACTION_SIZE` is the size of an empty transaction ([`src/validation.h` L67-L68](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.h#L67-L68)) and is used only to bound the number of transactions in a block ([`src/validation.cpp` L5803](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.cpp#L5803)). Teranode's port of the same check has the same shape ([`model/block_coinbase_common_rules.go` L53-L91](https://github.com/bsv-blockchain/teranode/blob/6f8e745e5f7b667d3ebaf7a99ccef14dcb0879c4/model/block_coinbase_common_rules.go#L53-L91)). Neither has a minimum size anywhere in those paths. The fix therefore belongs to verifiers, and costs them almost nothing: no ordinary payment is 64 bytes long, since a transaction of one input and one output of that length has 4 bytes for both of its scripts together.

## Scope and conformance

**Layer.** Interface: what a verifier concludes from bytes handed to it, a transaction, a BRC-74 path and the headers it holds. No validity rule changes. A path that this document refuses is not thereby invalid under BRC-74; a conforming verifier only declines to draw the conclusion "included" from it.

**Conformance targets.** A MUST binds only an implementation that claims one of these:

- **the path rules**: a verifier that claims them follows sections 1 to 3, 4.1, 4.3 and 5;
- **the header rules**: a verifier that claims them follows the path rules and section 4.2.

A verifier that compares roots with headers it has not checked, for example one that asks a remote service, can claim the path rules and SHOULD say that it does not claim the header rules.

Adoption is voluntary. A verifier that claims neither does not follow this document, and nothing else about it changes.

**What this document does not require.** How a verifier obtains headers or paths, how it stores them, and which transport carries them; the API it offers; how a path is framed inside a BEEF ([BRC-62](./0062.md), [BRC-95](./0095.md), [BRC-96](./0096.md)); script, signature and amount checks ([BRC-67](./0067.md)); whether an output can be spent, coinbase maturity included; how deep a block must be before the verifier acts on it; and how it handles a reorganisation. A verifier MAY apply further checks of its own.

**Out of scope.** Subtree paths, [BRC-119](./0119.md) (STUMP): these rules read a BRC-74 path for a whole block.

**The one status word.** "Included" in this document means: the verifier holds a header at height `h` (under the header rules, a header it checked), and the transaction whose bytes it holds is in the block that header commits to, at the offset the result gives. It does not mean the block is on the verifier's best chain or at any depth, or that the transaction is valid, final or spendable. Depth is the verifier's own business: its tip height minus `h`, plus one, on its own chain.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in capitals.

## Specification

### 1. Terms

- **Txid**: the double SHA-256 of a transaction's bytes. In a BRC-74 path and in a header, hashes are in internal byte order, the order the hash gives; in this document's tables they are in display order, reversed. The verifier computes the txid from the bytes it holds; a txid written beside the bytes is a claim.
- **Path**: a BRC-74 path in its binary form: a block height (VarInt), a tree height (one byte), then for each level from 0 a count of nodes (VarInt) and the nodes, each an offset (VarInt), a flag byte and, unless the flag is `01`, a 32-byte hash.
- **Duplicate**: a node with flag `01`. It carries no hash and stands for the node at its offset XOR 1, which is the working hash when it is that hash's sibling.
- **Own path**: for the transaction at offset `x` of level 0 of a path of tree height `h`, the `h` steps that fold its txid. At step `i`, from 0 to `h - 1`, the working hash and its sibling, the node at offset `(x >> i) XOR 1` of level `i`, are hashed together, the left node first, as the double SHA-256 of their 64 bytes. The working hash starts as the txid; its last value is the root.
- **Decodes as a transaction**, for 64 bytes: read in the standard transaction serialization, they give, ending exactly at byte 64, a 4-byte version; an input count of at least 1; each input as a 32-byte txid, a 4-byte index, a script length and that many bytes, and a 4-byte sequence number; an output count of at least 1; each output as an 8-byte value, a script length and that many bytes, with every value, and the running sum of the values, at most 2,100,000,000,000,000; and a 4-byte lock time. Counts and lengths are VarInts, in any of their forms. This is BRC-237's definition. The bounds are the ones a mined transaction meets, since SV Node refuses a transaction with no inputs, no outputs or a value out of range ([`src/validation.cpp` L519-L569](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.cpp#L519-L569)).
- **Header source**: the 80-byte block headers the verifier holds, by height. Under the header rules it is a chain that starts at a **checkpoint**, a header the verifier trusts by its own means (the genesis header, or one built into its software), and runs up from there.

### 2. Reading a path

#### 2.1 The bytes

A verifier MUST refuse a path, with `MALFORMED`, when:

1. it ends inside a field;
2. its tree height is 0 or above 64;
3. a level's node count is more than half the bytes left after it (a node is at least 2 bytes), checked before any node of that level is read;
4. a flag is other than `00`, `01` or `02` (`03` included);
5. two nodes of one level have one offset;
6. a node of level `i` has an offset of `2^(h - i)` or more, where `h` is the tree height: it lies outside a tree of that height;
7. bytes follow the last level.

The verifier is told the path is complete: it holds every byte of it. A reader that finds a path's end inside a larger structure, such as a BEEF, applies item 7 to the bytes it took as the path, which by construction has none.

Two shapes that writers produce are refused deliberately. A path whose level 0 lists a whole block under a tree height of 1, with the height left to be inferred from its offsets, is refused by item 6: the tree height is the field BRC-74 gives for it (vector N20). A flag of `03`, the duplicate and txid bits set together, is refused by item 4: BRC-74 defines `00`, `01` and `02` only.

The flag `02` marks a txid the path was made for. A verifier MUST NOT require it on the transaction it is checking, and MUST NOT treat a hash as a txid because of it.

#### 2.2 Where a duplicate may stand

A verifier MUST refuse a path that has a duplicate at an even offset, at any level, with `DUPLICATE_LEFT`.

A Merkle tree duplicates the last node of a level with an odd count, so the copy is always the right-hand node, at an odd offset. No block produces a duplicate on the left. Read as the working hash's left sibling, such a node proves the last transaction of an odd level at the offset one past its real one (vector N11). Section 3.3 refuses the same shape when the equal node is given as a hash. Refusing it costs nothing for any path a block can produce. This is the second reading recorded in issue #357. If the maintainers settle #357 on the first reading before this document is merged, this section and vector N11 change to follow it.

A writer MAY give the duplicated node's hash with flag `00` instead of a duplicate; that node is an ordinary node (vector P9).

#### 2.3 The nodes a path gives

At each level the path gives the nodes it declares, and the nodes computed from two nodes it gives at the level below, offsets `2j` and `2j + 1` giving offset `j`. A duplicate gives the node at its offset XOR 1. A verifier MUST refuse a path, with `MALFORMED`, in which a declared node, or a duplicate, differs from the node computed at its offset from the two below it. Pairs hashed here are hashed plainly; section 3.2 applies only to the steps of the own path.

### 3. The transaction and its own path

#### 3.1 A 64-byte transaction is never included

A verifier MUST refuse, with `TX_64_BYTES`, a transaction that is exactly 64 bytes long, whatever its path.

This applies to a transaction whose bytes the verifier holds. A verifier that holds only a txid cannot apply this section, and this document draws no conclusion about such a txid. (A [BRC-96](./0096.md) txid-only entry names a transaction the receiver already holds, and the receiver applies this section to the bytes it holds.)

#### 3.2 No step may be a transaction

A verifier MUST refuse, with `STEP_IS_TRANSACTION`, a path in which any step of the transaction's own path hashes 64 bytes, the two nodes in the order hashed, that decode as a transaction.

#### 3.3 The fold

The transaction is at the lowest offset of level 0 whose declared hash equals its txid; if no node of level 0 holds it, the verifier MUST refuse with `NOT_IN_PATH`.

A path of tree height 1 whose level 0 holds exactly one node, the txid at offset 0, is a block of one transaction: there is no step, and the root is the txid.

Otherwise the verifier folds the own path, exactly the declared tree height of steps, no more and no fewer. At each step the sibling is the working hash where the path has a duplicate at the sibling's offset, else the node the path gives there (section 2.3). If there is none, the verifier MUST refuse with `NO_SIBLING`. The working hash is the left node when its offset at that level is even.

At a step where the sibling equals the working hash, the working hash MUST be the left node; otherwise the verifier MUST refuse with `DUPLICATE_LEFT`. A block's tree pairs two equal nodes only where it duplicates the last node of an odd level, and the copy is on the right: SV Node refuses a block whose tree pairs two equal nodes anywhere else ([`src/consensus/merkle.cpp` L97](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/consensus/merkle.cpp#L97), [`src/validation.cpp` L5770-L5780](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.cpp#L5770-L5780)). Without this rule the last transactions of a block can be shown at offsets past its end, with the equal node given as a hash rather than as a duplicate (vectors N25, N26).

### 4. The header

#### 4.1 Which header

The verifier compares the root with the header its source holds at the block height the path declares. If the source holds none there, the verifier MUST refuse with `NO_HEADER`. A height given anywhere else, by a BEEF, a service or the sender, is a claim: when the verifier has one, it SHOULD refuse a path whose block height differs from it. Under the header rules the source holds no header below its checkpoint, so a path naming a lower height is refused with `NO_HEADER`.

#### 4.2 The header rules

A verifier that claims the header rules MUST refuse, with `HEADER_UNCHECKED`, unless every header of its source from the checkpoint up to and including the one at the path's height:

1. has a double SHA-256, read as a 256-bit little-endian number (its display-order hex read as a big-endian number), at or below the target its bits field encodes, where that target is positive, is not negative or overflowing in the compact form, and is at or below the network's proof-of-work limit (as SV Node's `CheckProofOfWork`, [`src/pow.cpp` L150-L171](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/pow.cpp#L150-L171); the limits are in [`src/chainparams.cpp`](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/chainparams.cpp#L1047-L1048), for mainnet, and [L1471-L1472](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/chainparams.cpp#L1471-L1472), for regtest);
2. other than the checkpoint, names as its previous block (bytes 4 to 35) the double SHA-256 of the header one below it;
3. other than the checkpoint, has the bits value the network's difficulty rules give at that height from the headers below it, and a time above the median of the times of the 11 headers before it, or of all of them near the genesis block (SV Node's `ContextualCheckBlockHeader`, [`src/validation.cpp` L5933-L5960](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/validation.cpp#L5933-L5960), with `GetNextWorkRequired`, [`src/pow.cpp` L95](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/pow.cpp#L95)). Where item 3 reads headers below the checkpoint, the verifier holds them as part of its checkpoint.

Such a verifier also MUST follow the chain of most work it knows. `HEADER_UNCHECKED` means that a header from the checkpoint up to the path's height is not one the verifier checked and found good: one that fails an item above is refused with it. A yes or no answer from a service about a root at a height is not a header the verifier checked.

#### 4.3 The root

If the root equals the header's Merkle root (bytes 36 to 67 of the header), the transaction is included. Otherwise the verifier MUST refuse with `ROOT_MISMATCH`. The root is compared with the header at the path's own height only: a root that equals another height's header proves nothing under this document (vector N7).

### 5. The order of the checks and the result

A verifier MUST refuse when any rule above refuses. It SHOULD apply the rules in this order and report the first refusal's code, so that implementations report alike:

1. `TX_64_BYTES` (3.1);
2. `MALFORMED` and `DUPLICATE_LEFT` (2.1, 2.2, 2.3), in the order the bytes are read, taking for each node its flag (item 4), its hash, items 5 and 6, then section 2.2; then item 7; then the nodes of section 2.3 level by level;
3. `NOT_IN_PATH`, then `NO_SIBLING`, `DUPLICATE_LEFT` (3.3) and `STEP_IS_TRANSACTION` step by step (3.3, 3.2);
4. `NO_HEADER` (4.1);
5. `HEADER_UNCHECKED` (4.2), under the header rules only;
6. `ROOT_MISMATCH` (4.3).

The result of a verification that does not refuse is: the txid, the offset of section 3.3, the block height the path declares, the hash of the header and the root. A refusal records nothing as included.

### 6. Relation to other documents

- **BRC-74.** Unchanged. Its binary form is what section 2 reads.
- **BRC-237.** Sections 2, 3.1 and 3.2 are the same rules as BRC-237's anchor conditions (a), (d) and (e) and its reading of a path, stated for any verifier. Section 2.1 items 3 and 7 are added for a path read on its own. Two rules differ: BRC-237 folds a duplicate at either offset, and a sibling equal to the working hash on either side; sections 2.2 and 3.3 refuse both on the left. A BRC-237 maker that also claims this document refuses such paths, which no block produces.
- **BRC-62, BRC-95, BRC-96.** A BEEF carries paths; these rules apply to each path a reader takes from one, to the transaction the path is for.
- **BRC-67.** This document covers the inclusion step of simplified payment verification, not the script, signature and amount checks.

## Rationale

**Why the two size rules, and why both.** In the first attack, the bytes offered as a transaction are two inner nodes `L` and `R` of the real tree, ground by whoever orders the block until `L || R` also decodes as a transaction with an output anyone can spend; its txid is their parent, a real node, and the path above that parent is real. Section 3.1 closes it: those bytes are 64 long. In the second, a real 64-byte transaction `T` is mined, and the verifier is shown a transaction `X` whose txid is the first 32 bytes of `T`, beside a sibling that is the last 32: the first step gives `T`'s txid, a real leaf, and the rest of the path is real. `X` is not 64 bytes, so section 3.1 does not catch it; section 3.2 does, since the first step hashes `T`. Vectors N1 and N3 build each shape, and each gives the real root when the rules are left out.

**Why only the bottom.** A path whose declared tree height is too large or too small at the top gives a root no header holds (vectors N5 and N6). Raising the height anywhere but at the bottom would need a preimage of a real node. So the bottom step, where the two halves of a real transaction can stand, is the one that matters; section 3.2 checks every step because that costs nothing and needs no argument about which step is safe, and it matches BRC-237.

**The cost of section 3.2.** Whoever orders a block can, for a transaction whose txid has `01` at byte 4 in internal byte order (one in 256), search for another transaction to place beside it whose txid completes a transaction after the first one's: about 2^37 hashes for the layout vector N4 uses, less with others. That transaction's path then fails section 3.2 (vector N4). The rule fails closed: a payment is refused, never wrongly found included.

**Why a 64-byte transaction is refused even when honest.** A verifier cannot tell an honest 64-byte transaction from two inner nodes (vectors N1 and N2 are refused alike). None is needed for a payment.

**Why duplicates only on the right.** See sections 2.2 and 3.3. The root comparison already refuses a duplicate that stands where the tree has another node (vector N12); a node equal to the working hash on its left, whether flagged as a duplicate or given as a hash, is the case where the root matches and the position does not (vectors N11, N25 and N26). It is the shape of CVE-2012-2459 ([`src/consensus/merkle.cpp` L18-L52](https://github.com/bitcoin-sv/bitcoin-sv/blob/6504a3aff65ba97c0f6c80962b033e35ecbfed4b/src/consensus/merkle.cpp#L18-L52)).

**Why the root is compared at the path's height only.** A verifier that searched its headers for any matching root would accept a path whose declared height is wrong, and anything it then computed from that height, depth or a lock time, would be wrong too.

**Why the header rules are a separate claim.** Many verifiers today take their headers from a service. They can still apply the path rules, which close the 64-byte and duplicate cases, and say plainly that the header is the service's word. A verifier that checks proof of work says so with the header rules.

## Test Vectors

Every vector in this document was made by code from its rules, with the standard library only, and the expected results are what that code's verifier returns. A second implementation, written from this document's text in plain Node with no shared code, recomputed every result. Neither is part of this document; every byte they compare is printed here.

Each vector gives a transaction (by name, in the table below), a path, and a header source. The verifier is told the path is complete. Equality: for **included**, the same decoded values, the txid, offset, block height, block hash and root; for a **refusal**, a refusal, and the code given is the first in the order of section 5. A verifier that does not follow that order, which is a SHOULD, matches a refusal vector on "refused" alone. Under the path rules only, every vector has the same result except N9 and N10, which a verifier that does not claim the header rules finds included.

Blocks are synthetic. In each, the transaction a vector is about has bytes; every other leaf is a filler hash, the SHA-256 of `merkle path verification test vector: filler ` followed by the height, a space and the index. The regtest headers have version 1, the previous header's hash, the block's root, the time 1,793,318,400 plus 600 for each height above 1000, bits `207fffff`, and the least nonce that meets that target. The genesis vector uses mainnet's genesis block, rebuilt from its known fields.

Vectors marked "without the rule" give the root a fold computes when the rule named in their section is left out, and whether it equals the header's root: in every such vector it does, so the rule is what refuses.

No vector covers a request without the required authority: this interface has none.

Issue #357's nine shapes (`Calhooon/bsv-rs` at `3428530`, `tests/vectors/merkle_path_even_offset_duplicate_167.json`) are all refused `DUPLICATE_LEFT` under this document; the issue records that a reader taking the first reading accepts four of them.

## Implementations

A reference implementation exists, the code that made the vectors. A second, written from this document over Node's standard library, agrees on every vector, 195 checks in all, including the plain folds, every txid and header hash, and every byte string as printed in this document.

## Security Considerations

**The header source decides everything.** Under the path rules alone, a verifier is exactly as safe as whoever supplies its headers or answers its root queries: that party can make any path "included". The header rules move the trust to proof of work and to the verifier's checkpoint.

**Difficulty.** Item 3 of section 4.2 is what makes the proof of work count. Without it each header need only meet the network's proof-of-work limit, which on mainnet is about 2^32 hashes a header: cheap for a forged chain above an old checkpoint. Difficulty also depends on the headers' times, so a verifier that skips the time rule can be walked down in difficulty.

**Headers from the payer.** Headers that the paying party supplies protect little: the payer chooses them, and the verifier checks only the work they carry. A verifier SHOULD take headers from the network, not from the payer.

**A block's orderer can make an honest transaction unprovable.** See the cost of section 3.2 in the Rationale. The failure is a refusal.

**A txid alone.** Sections 3.1 and 3.2 need the transaction's bytes. A verifier that takes a path for a txid whose bytes it does not hold, and then accepts bytes for that txid from someone else, has skipped section 3.1. Such a verifier SHOULD apply section 3.1 when the bytes arrive.

**Depth and reorganisation.** "Included" is a statement about one header. A header can be replaced by a reorganisation, and a verifier that acts on depth decides that depth itself.

**Bounds.** Section 2.1 item 3 bounds what a declared count can make a reader allocate or loop over, before it reads a node. A verifier SHOULD also bound the size of a path it reads.

## Not tested

- No mainnet path other than the genesis block: the other vectors use synthetic regtest blocks and headers.
- Section 4.2 item 3 (difficulty and time) and the most-work rule are not exercised. The regtest headers meet item 3 (regtest does not retarget, and each time is 600 seconds above the one below), but no vector breaks it, and the code that made the vectors checks items 1 and 2 only.
- Section 4.1's comparison with a height given elsewhere has no vector.
- The order inside section 5's step 2 is not tested: each vector has one fault.
- No path is read from inside a BEEF.
- No vector has a txid at two offsets of level 0, a tree taller than 4, or a VarInt written in a longer form than it needs.
- No vector has a duplicate that differs from the node computed at its offset (the second case of section 2.3).
- No vector has flag `03`. N20 is the only vector of a path whose tree height would have to be inferred from its offsets.
- The second implementation shares no code with the generator, but has the same author and reads the same vectors file.
- No result from an SDK or other implementation is reported here.
