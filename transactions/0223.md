# BRC-223: Multicast Topic Interest Protocol

Jeff Harris (jeff@lightweb.net)

## Abstract

This BRC defines topic interest: the signal by which a consumer of overlay
topics tells the network which topics it wants now. A host announces
soft-state interest in whole topics, named by the [BRC-149](./0149.md)
TopicID, upward and hop by hop through optional relays to the multicast
delivery edge that serves the consumer, and the edge applies it to that
consumer's delivery filter on the BEEF object plane of
[BRC-148](./0148.md). Four UDP control messages carry it, the same at every
hop: ANNOUNCE, DIGEST, ACK and RESYNC. Every request is acknowledged, and a
digest of the held set lets the two ends of a hop detect and repair drift.
Interest ends at the delivery edge: no multicast group, proxy, retry endpoint
or frame format carries it, and nothing upstream of an edge grows with the
number of topics. This BRC specifies wire version 0.

## Motivation

A delivery edge delivers to each consumer the topics it has elected, its
standing election ([BRC-149](./0149.md)). An election is account state and
changes through the account. Software at the consumer, an overlay host for
example, needs topics as its work comes and goes. Topic interest lets it ask
for a topic when it needs it and let it go when it stops, within limits the
edge enforces, without changing the account.

Topics are unbounded in number, while a plane has at most 2^15 groups
([BRC-148](./0148.md)). Interest therefore stops at the delivery edge, where
topics become joins of the groups they map to: state per topic is kept where
the consumer is served and never in the fabric. This is the aggregation and
summarization layer that [BRC-82](../peer-to-peer/0082.md) places between
MLDv2 at the edges and mBGP in the core, applied at the service edge.

## Specification

### Overview

| Property | Value |
|---|---|
| Key | TopicID: SHA-256 of the UTF-8 topic name ([BRC-149](./0149.md)), 32 bytes. Names never travel |
| Granularity | whole topics |
| State | soft: an interest lapses unless it is refreshed |
| Direction | upward, from host to edge, acknowledged at every hop |
| Reach | ends at the delivery edge that serves the consumer |
| Transport | UDP, one datagram per message, IPv4 or IPv6 |

Out of scope:

- **The fabric.** No multicast group, proxy, retry endpoint or frame format
  carries interest, and nothing upstream of a delivery edge grows with the
  number of topics.
- **Payment.** An interest carries no payment and changes nothing about how
  delivery is paid for. An extension type for terms is reserved.
- **Parts of topics.** Interest names whole topics; overlays have no sub-topics.
- **Delivery guarantees.** A delivery lane ([BRC-149](./0149.md)) stays
  at-most-once ([Lane Numbering][lanes]); interest adds no repair or replay.
- **Discovery of supply.** Which hosts serve a topic is the concern of
  [BRC-88](../overlays/0088.md) (SHIP).

### Conventions and Terminology

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted
as described in RFC 2119 and RFC 8174 when, and only when, they appear in
capitals. All integers are big-endian. Offsets are in bytes from the start of
the structure described. Examples use `2001:db8::/32` and `192.0.2.0/24`.

| Term | Meaning |
|---|---|
| Interest | a TopicID with a lifetime, held as soft state by the next hop up |
| Announcer | a process that wants topics; it sends interest to its upstreams with Hops 0 |
| Relay | a hop with senders below it; it holds the union of their interest and announces that union upward |
| Terminus | the multicast delivery edge that serves the consumer; interest ends there |
| Upstream | the next hop toward the terminus: a configured address and port |
| Sender | the party that announces in one exchange: an announcer, or a relay's upward side |
| Receiver | the party that holds interest in one exchange: a relay's downward side, or a terminus |
| Principal | whoever a bound belongs to: the consumer at a terminus, the accepted senders at a relay. Several senders may share one |
| Held | a receiver keeps soft state for a topic for one sender |
| Live set | the topics held for a principal by at least one of its senders |
| SenderID | the sender identity: a nonzero 64-bit value naming one sender at its source address |
| Delivered scope | the groups one path delivers on one plane ([BRC-148](./0148.md)) |

### Roles and Topology

```text
 announcers          relays (optional)                  termini
 host --+
 host --+--> relay --+
                     +--> relay at the consumer --+--> delivery edge A --> group joins
 host -----> relay --+                            +--> delivery edge B (standby)
```

1. **One wire at every hop.** Host to relay, relay to relay and relay to
   terminus carry the same four messages. A host may talk to the terminus
   directly; a relay is never required, and a relay's upstream sees one sender
   and does not learn how many hosts stand behind it.
2. **Upstream is configuration, like a default route.** A sender is configured
   with one or more upstreams. Version 0 has no discovery.
3. **Identity is per hop.** A receiver identifies the principal from the source
   address of each datagram: a terminus from the consumer's own addresses, a
   relay from the prefixes it is configured to accept. Version 0 carries no
   signature.

### Transport

| Property | Value |
|---|---|
| Carrier | UDP (RFC 768), unicast, IPv4 or IPv6, one message per datagram |
| Port | 8729 by default, the same at every hop, because the wire is |
| Size | at most 1,232 bytes: the IPv6 minimum MTU (1,280) less the IPv6 and UDP headers, so no hop fragments a message. An ANNOUNCE holds up to 31 records without extensions |
| Answers | to the source address and port of the datagram answered, from the address and port it was sent to |

A sender MUST NOT send a message longer than 1,232 bytes, and a receiver MUST
treat a longer datagram as not an interest message. On the socket it sends
from, a sender MUST ignore a datagram whose source address and port are not
those of an upstream it sends to, so a receiver MUST send every answer, and
every RESYNC to a sender it knows, from the address and port that sender sends
to. A RESYNC to an address no sender has announced from yet (see Delivery Edge
Policy) is sent from the receiver's interest port. On a host with
several addresses, a receiver bound to a wildcard address needs each
datagram's destination address (`IP_PKTINFO`, `IPV6_PKTINFO`) to keep this
rule.

Port 8729 lies in a range IANA lists as unassigned, and continues the
fabric-side 872x block of [Lane Numbering][lanes], since interest travels
toward the edge of the fabric. A deployment MAY use another port.

### Header

Every message starts with the same 40-byte header.

```text
Offset  Size  Field
     0     4  NetworkMagic  0xE3E1F3E8
     4     2  ProtoVer      0x02BF
     6     1  MsgType       0x50 ANNOUNCE, 0x51 DIGEST, 0x52 ACK, 0x53 RESYNC
     7     1  Flags         per message type, below
     8     1  Version       wire version: 0
     9     1  Hops          relays between the farthest announcer and the sender;
                            0 in ACK and RESYNC
    10     1  Result        ACK only; 0 in other messages
    11     1  Reserved
    12     2  Count         records (ANNOUNCE) or statuses (ACK); 0 in other messages
    14     2  Reserved
    16     8  SenderID      the sender; echoed in ACK, named in RESYNC
    24     8  Token         issued by the receiver in ACK, echoed by the sender; 0: none
    32     8  Seq           the sender's sequence number, never 0; echoed in ACK
```

Reserved bytes, and flag bits not defined for a message type, MUST be zero on
send and MUST be ignored on receipt. A receiver MUST discard, without an answer,
a datagram shorter than 40 bytes, one that does not start with the magic and
ProtoVer above, and one whose MsgType is not 0x50 to 0x53.

| Flag | Bit | Messages | Meaning |
|---|---|---|---|
| ScopeWanted | 0x01 | ANNOUNCE, DIGEST | include the delivered scope in the answer |
| Sync | 0x02 | ANNOUNCE | part of a full replay; informational |
| Probe | 0x02 | DIGEST | answer only: compare, refresh and remove nothing |
| NoticesTruncated | 0x01 | ACK | more notices exist than the ACK holds |

**Version.** The header layout is the same in every version, so a receiver can
always answer a version it does not implement. A receiver MUST answer an
ANNOUNCE or DIGEST from an identified source whose Version it does not
implement with an ACK of result 5 (version): the header alone, carrying the
receiver's own Version, Token 0, and the SenderID and Seq of the request. It
MUST apply nothing.

**Hops.** An announcer sends 0; a relay sends one more than the largest Hops
below it (see Relay Behavior). A receiver MUST refuse a message whose Hops
exceeds its limit (16 by default) with result 6.

**SenderID.** A sender identity MUST be nonzero, SHOULD stay the same when the
sender restarts, and MUST differ from that of any other sender at the same
source address. A receiver MUST discard an ANNOUNCE or DIGEST with SenderID 0.

### Messages

#### ANNOUNCE (0x50)

Sent upward. It carries deltas: each record adds or refreshes a topic for the
sender with the lifetime it asks for, or withdraws the topic. The bytes after
the last record, to the end of the datagram, are the message extension area.

```text
Offset  Size  Field
     0    32  TopicID
    32     4  Lifetime    seconds; 0 withdraws; 0xFFFFFFFF asks for the receiver's default
    36     2  ExtLen      bytes of record extensions that follow
    38     *  Extensions
```

An ANNOUNCE is malformed when Count x 38 exceeds the bytes after the header, or
a record's ExtLen runs past the end of the datagram. A record for a topic the
sender holds refreshes it, with the lifetime and delivery address the new
record gives. An ANNOUNCE with no records is valid.

#### DIGEST (0x51)

Sent upward. A DIGEST shorter than 88 bytes is malformed.

```text
Offset  Size  Field
     0    40  Header      Count 0
    40     8  Since       0: the sender's whole set. Otherwise: the topics set by
                          messages whose Seq is at or after Since
    48     4  SetCount
    52     4  Reserved
    56    32  SetDigest
    88     *  Extensions  none defined; a receiver ignores them
```

The set digest of a set of topics is the bitwise XOR of their TopicIDs, all
zero for the empty set. It does not depend on order and changes in constant time
when a topic is added or removed. It is always compared together with the
count. TopicIDs are SHA-256 outputs, so distinct sets do not collide by
accident; the digest guards two cooperating ends against drift, not against an
adversary.

| Use | Since | SetCount, SetDigest | Flags | Effect at the receiver |
|---|---|---|---|---|
| First contact | 0 | 0, zero | | none: it carries no token, so the answer is a token |
| Refresh | 0 | the set the sender believes held | | on a match, every held topic is refreshed |
| End of replay | the replay's first Seq | the topics the replay confirmed | | on a match, topics set before Since are removed, the rest refreshed |
| Probe | 0 | 0, zero | Probe, ScopeWanted | none on the set; answered with result 0 |
| Farewell | its own Seq | 0, zero | | everything held for the sender is removed |

#### ACK (0x52)

Sent downward: the interest acknowledgment. It answers one ANNOUNCE or DIGEST
and echoes its SenderID and Seq. It is not the ACK of
[BRC-126](./0126.md) (0x12); here ACK means 0x52.

```text
Offset  Size  Field
     0    40  Header           Result; Count = statuses; Token issued
    40     8  LastSeq          the last Seq applied from this sender
    48     4  SetCount         topics held for this sender
    52     4  ScopeGen         changes when the delivered scope does; 0: no scope
    56    32  SetDigest        set digest of the topics held for this sender
    88     4  LifetimeMin      seconds
    92     4  LifetimeDefault  seconds
    96     4  LifetimeMax      seconds
   100   4xN  Statuses         N = Count
     *     *  Extensions
```

An ACK of result 1 (token) or 5 (version) is the header alone, 40 bytes with
Count 0, so an answer to a source that has not proven it can receive is never
larger than the smallest request. Every other ACK carries the body, which
describes the receiver's state for the sender after the message; an answer of
result 4 (busy) has no such state, and its LastSeq, SetCount and SetDigest are
zero. The lifetimes MUST satisfy 0 < Min <= Default <= Max.

A status names a record of the ANNOUNCE answered by its position, from 0. Only
records whose status is not 0 are listed, in record order; an ACK to a DIGEST
lists none.

```text
Offset  Size  Field
     0     2  Index     the record's position in the ANNOUNCE
     2     1  Status
     3     1  Reserved
```

| Value | Result | Body | Meaning | The sender |
|---|---|---|---|---|
| 0 | ok | yes | applied | settles what the message carried |
| 1 | token | no | not applied. The Token here is the one to echo; the receiver holds nothing it trusts for this sender | adopts the token and replays |
| 2 | stale | yes | not applied: Seq was not newer than LastSeq | moves its next Seq past LastSeq and says the content again |
| 3 | mismatch | yes | a DIGEST did not match the set held; nothing was refreshed or removed | replays |
| 4 | busy | yes | not applied: a cap on senders is reached | waits, then says it again |
| 5 | version | no | not applied: the Version here is the one the receiver implements | waits long, then tries again |
| 6 | hop limit | yes | not applied: Hops exceeds the receiver's limit | waits as for busy |

Only result 0 means the message was applied. A sender treats a Result it does
not know as not applied and as carrying the body. It does not check the Version
of an ACK or a RESYNC: a version mismatch is told by result 5 alone.

#### RESYNC (0x53)

Sent downward: a poke, "check in now". It is the header alone, with Token, Seq
and Count 0. SenderID names the sender poked; 0 pokes every sender at the
address. It carries no authority: the answer to the DIGEST it prompts decides
what happens.

### Extensions

```text
Offset  Size  Field
     0     1  Type     bit 7 (0x80) is the critical bit
     1     2  Length   bytes of Value
     3     *  Value
```

An extension area is a run of extensions that MUST end exactly at the end of
the area. A record's area (inside its ExtLen) applies to that record; the
message area of an ANNOUNCE applies to every record in it; the area after the
statuses of an ACK applies to the answer. No DIGEST extension is defined.

**The critical bit.** Types are compared as whole bytes. A receiver that finds
in an ANNOUNCE an extension area that does not parse, or a type with the
critical bit set that it does not implement, MUST refuse every record the area
applies to with status 0x05 (unsupported); a delivery address that does not
parse refuses them with 0x06. It MUST skip any other unknown type. A refusal
caused by the message area applies to every record except withdrawals, which
are always applied. An area is read in order and
the first failure decides the status. A sender MUST skip ACK extension types
it does not implement, ignores an ACK extension area that does not parse, and
uses the first extension of a type. Version 0 defines no critical type.

| Type | Name | Carried in | Value |
|---|---|---|---|
| 0x01 | delivery | ANNOUNCE: a record's area, or the message area as the default for every record | delivery address, below |
| 0x02 | scope | ACK | delivered scope (see Delivered Scope) |
| 0x03 | notice | ACK | 33-byte entries, each a TopicID and a status: notes on topics held for the sender |
| 0x04 | assign | ACK | a TopicID, then a delivery address: where the topic will be found |
| 0x05 | reach | | reserved: interest that travels beyond the edge |
| 0x06 | terms | | reserved: an offer carried with the interest |
| 0x07 | signature | | reserved: proof of identity beyond the hop |

A sender MUST NOT send the reserved types in version 0. An assignment is the
downward form of a delivery address, natural for multicast, where a hop names a
group and the host joins it. A receiver MAY send one; it is not critical, so a
sender that does not act on assignments ignores it.

**Delivery address.** Where the objects for a topic should arrive:

```text
Offset  Size     Field
     0     1     Kind      1 unicast; 2 multicast, any source; 3 multicast, source-specific
     1     1     Encoding  1 BRC-149 delivery records on a TCP stream; 2 BRC-149 frames in UDP
     2     1     Family    4 or 6
     3     1     Reserved
     4     2     Port
     6  4 or 16  Address   the host, or the group
     *  4 or 16  Source    kind 3 only: the group's source, of the same family
```

The value is 10 or 22 bytes for kinds 1 and 2, 14 or 38 bytes for kind 3, and
MUST end where its fields do. A kind 1 Address MUST be unicast and not the
unspecified address; a kind 2 or 3 Address MUST be a multicast group; a kind 3
Source MUST be of the group's family and MUST NOT be a multicast address, and
a sender MUST NOT send the unspecified address as a Source. An IPv4 address MUST be
sent with Family 4; a receiver treats an IPv4-mapped IPv6 address as the IPv4
address. A value that breaks these rules, or names another kind or family, does
not parse. Encoding is not checked when the value is parsed: whether a hop
delivers in it is the hop's decision. In the message area the address is the
default for every record, and a record's own address overrides it. An area
SHOULD carry at most one delivery address; a receiver uses the last.

### Statuses

A status is the outcome of one record. A value below 0x80 other than 0 is a
refusal: the receiver does not hold the topic. A value from 0x80 is a note: the
receiver holds the topic, with a caveat.

| Value | Status | Class | Used when |
|---|---|---|---|
| 0x00 | ok | held | held, and served as far as this hop knows; never listed in an ACK |
| 0x01 | not served | refused | the topic's group is outside the delivered scope; nothing is kept or charged |
| 0x02 | outside bound | refused | the principal's bound does not allow the topic, or would draw it from a quota of 0 |
| 0x03 | over cap | refused | a cap on topics per sender, or the principal's quota, is reached |
| 0x04 | rate limited | refused | the sender adds topics faster than the hop allows; refused for now |
| 0x05 | unsupported | refused | an extension area that does not parse, or a critical type the hop does not implement |
| 0x06 | bad address | refused | the delivery address does not parse, or is not one this hop may deliver to for this sender |
| 0x80 | address not honored | held | the delivery address is ignored; delivery is as provisioned |
| 0x81 | unserved | held | held at a relay, but no upstream path delivers the topic's group |
| 0x82 | upstream refused | held | held at a relay, but refused upstream |

Only 0x00 and 0x80 mean a stream can be expected. Values 0x07 to 0x7E and 0x83
to 0xFF are reserved; a sender treats an unknown value below 0x80 as a refusal
and one from 0x80 as held. 0x7F is never sent; implementations use it locally
for an outcome not yet known. A refusal of a topic the sender held removes it.

### Receiver Processing

A receiver checks each datagram in this order and stops at the first failure.

| Step | Check | On failure |
|---|---|---|
| 1 | 40 to 1,232 bytes, the magic and ProtoVer, MsgType 0x50 to 0x53 | discarded, no answer |
| 2 | an ANNOUNCE or a DIGEST, with a nonzero SenderID | discarded, no answer |
| 3 | identification: the source address belongs to a principal | discarded, no answer |
| 4 | the Version is one the receiver implements | result 5, header only |
| 5 | the Token is the one issued for this source address, port and SenderID | result 1, header only, with that token |
| 6 | the message decodes in full | discarded, no answer; no state changes, no Seq is consumed |
| 7 | a sender not yet known fits the caps on senders, in all and per principal | result 4 |
| 8 | Hops does not exceed the limit | result 6 |
| 9 | Seq is newer than the last Seq applied for the sender, if any | result 2 |
| 10 | apply: Seq becomes the last applied; the records or the digest are processed | result 0, or 3 for a DIGEST that does not match |

A receiver keeps a sender's state under its source address and SenderID. When
the principal of that address changes, what was held for the old principal is
dropped before step 7.

**Records.** The message area of an ANNOUNCE is read once, first: it gives a
default delivery address or, when it fails, a refusal for every record. Then
each record is processed in order:

| Step | Check | Status |
|---|---|---|
| 1 | Lifetime 0: the topic is withdrawn if held, even under a message-area refusal | 0x00 |
| 2 | extensions: the message area's refusal, then the record's own area | 0x05 or 0x06 |
| 3 | scope: the topic's group is inside the principal's delivered scope | 0x01 |
| 4 | bound and quota | 0x02 or 0x03 |
| 5 | delivery address, if any: the hop decides whether it honors it | honored: kept; not honored: 0x80, held without it; refused: 0x06 |
| 6 | the cap on topics per sender, for a topic not yet held | 0x03 |
| 7 | the change rate, for a topic not yet held | 0x04 |
| 8 | held: the lifetime is granted; a note on the topic (0x81, 0x82) replaces the status | 0x00, 0x80, 0x81 or 0x82 |

A refusal at steps 2 to 5 removes the topic if the sender held it. Scope comes
before the bound, the caps and the rate, so a topic the path does not deliver is
charged against none of them; the address is decided before the caps and the
rate, so a refused address costs nothing. An ANNOUNCE that passed step 9 is
answered with result 0, whatever its records' statuses.

**Lifetimes.** A receiver grants the lifetime asked for within its bounds:
0xFFFFFFFF gets the default, less than the minimum the minimum, more than the
maximum the maximum. Unless configured otherwise the minimum is 30 s, the
default 300 s and the maximum 3,600 s.

**Digests.** A DIGEST with the Probe flag is answered with result 0, and nothing
is compared, refreshed or removed. A DIGEST with Since 0 matches when SetCount
and SetDigest equal the count and digest of the topics held for the sender. A
DIGEST with another Since matches when they equal those of the held topics whose
last setting Seq is not older than Since, in serial number arithmetic; on a
match every other topic held for the sender is removed. A match refreshes every
topic still held and is answered with result 0; a mismatch is answered with
result 3 and changes nothing.

**Expiry.** A held topic lapses when its granted lifetime has passed since the
later of the ANNOUNCE that last set it and the last matching DIGEST. A receiver
SHOULD check for expiry about once a second, and SHOULD remember a sender that
holds nothing for the maximum lifetime after last hearing from it, so an old
datagram of that sender cannot be applied again.

**Answers.** An answer carries the scope when the request set ScopeWanted, the
receiver has a scope to advertise, and the extension fits the room the statuses
leave. A receiver that notes topics (0x81, 0x82) MUST list, in its answer to a
matching DIGEST that is not a probe, every topic held for the sender that
carries a note, with the note, as far as the datagram has room, and MUST set
NoticesTruncated when some do not fit. No other answer carries notices. A
sender that receives such an answer without NoticesTruncated clears the note
of every held topic the answer does not list, and ignores a notice for a topic
it does not hold or whose status is a refusal.

**Changes.** When the scope or bound of a principal changes, a receiver MUST
drop the held topics no longer allowed; when a quota shrinks, the topics that
became live most recently go first. It SHOULD poke every sender that lost a
topic, every sender of the principal when its advertised scope changes, and
every sender of the principal when its bound widens (a larger quota, a topic
newly allowed), so the senders learn of it at once, and ask again for what was
refused, instead of at their next refresh.

### Sender Behavior

**Tokens.** A sender with no token for an upstream sends a first-contact DIGEST
(Token 0, Since 0, the empty set). The receiver answers with result 1 and the
token, and applies nothing. The sender adopts the token and replays its set. A
sender MUST echo the token its upstream last issued, and adopts the token of
every ACK that carries a nonzero one. A later result 1 (the receiver restarted,
or the sender's address or port changed) is handled the same way.

A token MUST NOT be zero, MUST be bound to the source address, source port and
SenderID, and MUST be unpredictable to a party that cannot receive at that
address. Its derivation is local to the receiver and SHOULD need no state per
sender; a keyed hash of the three does. A restarted receiver SHOULD issue
different tokens, so its senders learn that it holds nothing.

**Sequence numbers.** A sender numbers every datagram to an upstream with the
next 64-bit Seq, wrapping from 2^64 - 1 to 1; 0 is never used. Seq a is newer
than b when (a - b) mod 2^64, read as a signed 64-bit integer, is positive
(serial number arithmetic, RFC 1982). A sender SHOULD start above any Seq it
used before; the time in nanoseconds does so without stored state. On result 2,
a sender whose next Seq is not newer than LastSeq moves it to the number after
LastSeq.

**Nothing is retransmitted.** A sender MUST NOT send a datagram twice under one
Seq. What went unanswered, or was answered without being applied, is still to
be said, and is said as it stands now under a new Seq: a wanted topic with the
lifetime asked for and its current extensions, a topic no longer wanted with
Lifetime 0. A late or duplicated datagram therefore never undoes a newer one.

**Timeouts.** A sender SHOULD time answers as TCP does (RFC 6298), within the
bounds under Constants Reference, and double its wait after a round in which a
datagram goes unanswered. An upstream that stays silent is unreachable: the
sender keeps trying at the longest wait, and while another upstream answers it
does not wait for this one to learn a topic's outcome. After result 4, 5 or 6 a
sender waits before it sends to that upstream again.

**Refresh.** A sender reckons its granted lifetime as its upstream does, from
the bounds the upstream reported (the defaults until it has), and every third
of it, but not more often than once a second, sends a DIGEST with Since 0 and
the count and digest of the set it believes held. A refresh that goes
unanswered is sent again as its timeout allows, so an interest lapses only when
no DIGEST is answered for two thirds of its lifetime. A sender MUST NOT send a
refresh or end-of-replay DIGEST while datagrams to that upstream are in flight
or anything is ready to be said, so that the digest is exact. After a matching
refresh the sender asks again for every topic refused with a status other than
0x01; a topic outside the scope is asked again only when the scope changes. A
sender ignores reported lifetimes that break 0 < Min <= Default <= Max.

**Drift and replay.** When nothing is in flight or queued and an ACK to the
sender's latest datagram shows a count or digest other than what it believes
held, the sender replays; so it does on result 1 and result 3. A replay says
every wanted topic again, with the Sync flag. When all of it has been said and
answered, the sender sends a DIGEST whose Since is the replay's first Seq, with
the count and digest of the topics the replay confirmed. On a match the
receiver removes what was set before Since: what the sender no longer wants
goes only after everything it does want is confirmed. Replays that follow one
another closely SHOULD back off.

**Pokes.** A sender acts on a RESYNC that names its SenderID or 0, from the
address and port of an upstream it sends to. A relay also acts on a RESYNC that
reaches its listening socket from the address of one of its upstreams, from
any port and whatever SenderID it names. A RESYNC is not authenticated, so a
sender MUST act on at most one per upstream per second, and MUST let it cause
nothing but datagrams to that upstream: a DIGEST at once, and, if the upstream
had stopped answering, everything in flight said again with its waits started
over.

**Several upstreams.** A sender keeps a token, Seq, set and timers per upstream,
and tells each upstream every wanted topic inside its scope, or every wanted
topic while its scope is unknown, so a standby already holds the interest when
it takes over. When a scope changes, the sender withdraws from that upstream
what is no longer inside and announces what now is. When every upstream's scope
is known and none contains a topic, the topic is not served (0x01) and is not
sent. The outcome a sender reports for a topic is the best among the upstreams
that answer.

**Withdraw on exit.** A sender that leaves for good SHOULD send each upstream
one DIGEST with Since equal to that DIGEST's own Seq, SetCount 0 and a zero
digest, without waiting for an answer: it removes everything held for the
sender, so delivery stops at once. A sender about to start again SHOULD NOT.

### Relay Behavior

A relay is a receiver whose live set feeds a sender.

- **Who may announce.** A relay MUST accept interest only from sources inside
  the prefixes it is configured to accept, and MUST ignore, without an answer,
  interest from the address of any of its own upstreams.
- **Union.** A topic that becomes live below is announced upward, and one that
  stops being live is withdrawn; no other change below causes a record upward.
- **Hops.** A relay announces with one more than the largest Hops among the
  senders whose topics it holds, and at least 1. Relays configured in a loop
  count upward until a receiver refuses them with result 6.
- **Scope downward.** A relay advertises the union of its upstreams' scopes.
  The union is unknown, and none is advertised, when any upstream's scope is
  unknown or the upstreams disagree about the plane (domain, width or
  generation). With a known union the relay MUST refuse a topic outside it
  with 0x01 and keep no state for it. When the union changes, the relay
  re-evaluates what it holds and pokes every sender.
- **Routing by shard.** A relay sends each topic only to the upstreams whose
  scope contains the topic's group.
- **Notes.** A held topic is noted 0x81 when no upstream path delivers its
  group and 0x82 when it was refused upstream. The relay keeps holding it and
  keeps asking, and pokes the senders that hold it when the note changes.
- **Restart.** A relay starts empty and learns its set again from below. It
  SHOULD delay the DIGEST that ends its first replay to each upstream until
  the senders below have had one refresh interval to announce again, and MUST
  send it before two thirds of the lifetime its upstream granted has passed.

### Delivered Scope

A path may deliver only some groups of a plane. An interest in a topic whose
group the path does not deliver has no stream behind it, so it is not processed
there. The group of a topic is the BRC-148 derivation with the TopicID as the
shard key, the one the edge uses to join and route:

```text
group = planeBase(domain) + (uint32(TopicID[0:4], big-endian) >> (32 - ShardBits))
planeBase(domain) = domain << 12
```

With ShardBits 0 every topic maps to planeBase; implementations MUST treat that
case explicitly, as BRC-148 requires. The scope extension (0x02):

```text
Offset  Size  Field
     0     1  Domain        BRC-148 plane selector; 0x1 is the BEEF object plane
     1     1  ShardBits     the plane's width, 0 to 15
     2     1  Flags         0x01 All: every group of the plane; 0x02 Bitmap
     3     1  Reserved
     4    16  GenerationID  the plane's generation id (BRC-139, BRC-148)
    20     2  N             groups in the list, or bytes in the bitmap; 0 with All
    22     *  Groups        list: N group indexes, 16 bits each, ascending, unique
                            bitmap: bit i, least significant bit first, is group planeBase + i
```

Domain and ShardBits MUST satisfy BRC-148: domain at most 0x0E, ShardBits at
most 15 (12 on domain 0x0), and planeBase + 2^ShardBits at most 0xF800. With
All, N is 0 and nothing follows, whether or not Bitmap is also set; other flag
bits are ignored. A bitmap is exactly ceil(2^ShardBits / 8)
bytes, with every bit past the plane's width clear. A list is exactly 2N bytes
of indexes inside the plane, strictly ascending. A value that breaks these
rules is malformed, and a sender ignores it. An empty list is a path that
delivers nothing on the plane. A receiver sends the list when its 2N bytes are
no more than the bitmap's length, the bitmap otherwise; a sender MUST accept
either. A receiver MUST NOT put a scope value longer than 1,024 bytes in an
ACK; a scope too large for that is not advertised, and its senders learn what
is not served from record statuses alone.

**Generation.** Every ACK with a body carries ScopeGen: 0 when the receiver
has no scope for the principal, otherwise (also for a scope too large to
advertise) a value that changes whenever the scope does and is never 0. It is
the CRC-32C (Castagnoli, as in BRC-139) of the encoded scope value, over the
whole encoding even when the value is too large to advertise,
with 0 replaced by 1. A sender treats it as opaque. It sets ScopeWanted on every
ANNOUNCE and DIGEST while it knows no ScopeGen other than 0 for an upstream;
when ScopeGen changes, it sets ScopeWanted on its next DIGEST and sends that
DIGEST at once. The GenerationID inside lets a sender tell a re-shard of the
plane from a change of membership. Routing by scope is under Sender Behavior.

### Delivery Addresses

**The address is hop-local.** A delivery address means something only to the
next hop up, as "next hop self" does in routing. A hop that distributes
replaces it with its own address when it announces upward, and delivers to the
addresses below it. A hop that does not distribute drops it. The terminus
therefore never learns the hosts behind a relay.

**Not honored.** For a record that carries a well-formed address, a receiver
that does not distribute MUST hold the topic without the address and answer
0x80, unless a note on the topic (0x81, 0x82) replaces that status. A terminus
does not honor delivery addresses in this version: it delivers as provisioned
for the consumer.

**Honored.** A distributing hop MUST NOT honor an address unless it equals the
sender's source address, or lies inside a prefix the hop accepts senders from
that also contains the sender's source address. It refuses any other address,
or Port 0, with 0x06, and answers 0x80 for a kind or encoding it does not
deliver. It writes each delivery record ([BRC-149](./0149.md)) at most once to
each address that holds the record's topic. Withdrawal and expiry of a topic
take its address with them.

### Delivery Edge Policy (informative)

What a terminus allows is local policy and is not carried on the wire beyond
the statuses above. A typical delivery edge identifies the consumer by the
longest of its address prefixes that contains the source address, and ignores
other sources. Its scope is the groups the consumer's path delivers. Its bound
admits the topics of the consumer's standing election freely and draws any
other topic from a quota of live topics, answering 0x02 for a quota of 0 and
0x03 for a full one. The consumer's delivery filter becomes its standing
election joined with its live set, and nothing about the live set is sent
upstream of the edge. An edge that takes a consumer over, or restarts, sends a
RESYNC with SenderID 0 to the consumer's own address on the interest port.

### Security Considerations

- **Off-path spoofing.** A message is applied only with the token issued for
  its source address, port and SenderID, which a party that cannot receive at
  that address never sees.
- **Amplification.** Unknown sources get no answer. An answer to a source that
  has not proven its address (results 1 and 5) is the 40-byte header, never
  larger than the smallest request.
- **Pokes.** RESYNC is not authenticated. It is rate limited at the sender,
  causes nothing but datagrams to the upstream it came from, and decides
  nothing.
- **Redirection.** A delivery address is honored only under the rule in
  Delivery Addresses, so a stream cannot be pointed at a third party.
- **No signature in version 0.** Identity is per hop, from the source address.
  A party on the path can read tokens and forge messages; a deployment that
  needs integrity or confidentiality carries interest inside an encrypted
  tunnel. The set digest detects drift between cooperating ends, not
  tampering.
- **Replay.** A receiver applies only a Seq newer than the last it applied,
  and remembers an idle sender for the maximum lifetime.
- **Resource exhaustion.** No state exists for an unidentified source, and the
  token needs none. Caps on senders, on topics per sender and on quotas, and a
  change rate, bound what one principal can hold; a topic outside the scope is
  refused before any of them.
- **Loops.** Hops counts relays, a receiver refuses a message over its limit,
  and a relay never accepts interest from the address of its own upstreams.
- **Privacy.** Each hop learns the topics wanted below it. A relay hides how
  many hosts stand behind it. A TopicID conceals nothing from a party that
  knows the topic's name.

## Interactions With Other BRCs

- **BRC-124, BRC-126, BRC-127, BRC-139 (message types).** Interest shares the
  preamble of the BRC-126 and BRC-139 control messages: magic, ProtoVer and the
  type at offset 6. That offset already carries frame versions 0x01 to 0x09 and
  control types 0x10 to 0x13, 0x20, 0x30 and 0x40. Interest takes 0x50 to
  0x53, on its own port. BRC-126's ACK is 0x12; the interest acknowledgment is
  0x52.
- **BRC-139 and BRC-148 (groups, planes).** A scope names its plane by domain
  and width, carries the plane's GenerationID, and lists group indexes in a
  shard manifest's two forms. Its indexes include the plane's base, so they
  equal a manifest's shard indexes only on the transaction plane, whose base
  is 0.
- **BRC-149 (TopicID, delivery record).** Interest names topics by the same
  SHA-256 of the UTF-8 name, and a distributing hop forwards BRC-149 delivery
  records.
- **BRC-88 (SHIP).** SHIP is the supply side: hosts advertise the topics they
  host. Topic interest is the delivery side: what a consumer wants delivered.
  They share nothing on the wire.
