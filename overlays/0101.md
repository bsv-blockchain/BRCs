# Diverse Facilitators and URL Protocols for SHIP and SLAP Overlay Advertisements

Ty Everett (ty@projectbabbage.com)

## Status

This document is currently **aspirational** rather than descriptive of the interoperable behavior implemented by `bsv-blockchain/ts-sdk`.

Current resolver and broadcaster implementations:

- expect concrete host base URLs in SHIP and SLAP advertisements,
- use `https:` in production,
- allow plain `http:` only for the SDK's `local` preset,
- and do **not** currently negotiate composite schemes such as `https+bsvauth+smf:` or non-HTTP transports directly from advertisement URLs.

Implementers SHOULD therefore treat the mechanisms described below as future extension ideas, not as present-day interoperability requirements.

Currently, there are only HTTPS URLs within SHIP and SLAP advertisements.

This `https:` scheme indicates that, according to pre-defined rules (like headers and the /submit or /lookup paths), submission or lookups are facilitated over the HTTPS protocol.

However, sometimes we want to do things like:

- Authenticate users before accepting transactions or facilitating lookup
- Charge a payment for transaction submission, or pay the sender if a transaction is accepted
- Charge a payment for lookup queries
- Submit private or off-chain values alongside a transaction
- Submit non-final transactions that deal with interim states
- Facilitate real-time lookups with WebSocket or based on live / non-final transactions
- Advertise certain IPv6 capabilities and bridges
- Advertise non-HTTPS or non-internet communications systems like radio / JS8 Call

In these scenarios, other schemes can be used within the "protocol" portion of the URL.

For example, current SHIP/SLAP only contemplates URL schemes like `https://example.com`.

However, a new URL might be something like:

SHIP `https+bsvauth+smf://example.com` (HTTPS with BSV Auth and Service Monetization Framework enabled)

SHIP `https+bsvauth+scrypt-offchain://example.com` (HTTPS with BSV Auth and sCrypt off-chain values for transaction submission)

SHIP `https+rtt://example.com` (HTTPS with real-time transacting support, e.g. non-finals accepted)

SLAP `wss://example.com` (real-time event-listening live web-socket lookup response streaming)

SLAP `js8c+bsvauth+smf:?lat=40&long=130&freq=40meters&radius=1000miles` (lookup is advertised using JS8 Call protocol at a given set of GPS coordinates, a given frequency and radius, with BSV Auth and Service Monetization Framework enabled.

These SHIP and SLAP schemes would allow the advertisement of Overlay Services with more advanced capabilities, including real-time updates from lookup services, non-final transaction submission, mutual authentication, payment, off-chain/private value submission, and non-HTTP transport mechanisms.

Compared to plain HTTPS, they may eventually provide a significant improvement. However, until a concrete facilitator specification and interoperable implementation exist, wallets and overlay clients SHOULD assume plain HTTPS base URLs (or local HTTP for development) when processing SHIP and SLAP advertisements.

## Onion Service Base URLs (Optional Profile)

This section defines an optional profile. It is an **interface** rule between overlay operators who advertise a Tor onion service and the overlay clients that choose to support it: resolvers, broadcasters, and SHIP or SLAP topic managers. Each MUST below binds an implementation that claims the BRC-101 onion profile, and nobody else. An implementation that does not claim the profile is not affected, except that rule 4 repeats what RFC 7686 already requires of every application.

### Why plain HTTP is enough for a version 3 onion address

A version 3 onion address is the base32 encoding of the service's ed25519 public key, a two-byte checksum, and a version byte, followed by `.onion` ([Tor Rendezvous Specification, Encoding onion addresses](https://spec.torproject.org/rend-spec/encoding-onion-addresses.html)). A Tor client that connects to the address reaches only the holder of that key, over a circuit that is encrypted end to end. TLS on top adds no authentication of the host beyond what the address already gives, and a certificate for an onion name binds that same name. Requiring `https:` therefore asks the operator for a certificate from one of the few authorities that issue them for onion names, without making the connection more authentic.

### Rules

1. **Form.** An onion base URL is `http://`, then a version 3 onion host name, then an optional port, then an empty path or `/`. The host is exactly 56 base32 characters followed by `.onion`, with no further labels. A user information part, a query and a fragment are not allowed. Submission and lookup use the same paths and headers as an `https:` base URL.
2. **Checking the address.** A client that claims this profile MUST compare the host case-insensitively, decode it, and refuse the advertisement unless the version byte is 3 and the checksum equals the first two bytes of `SHA3-256(".onion checksum" || PUBKEY || VERSION)`. A version 2 address (16 characters) MUST be refused.
3. **Transport.** A client that claims this profile MUST connect to an onion base URL only through Tor. It MUST NOT resolve the name in DNS, and MUST NOT fall back to another host or transport when Tor is unavailable; it reports the advertisement as unreachable instead.
4. **Clients without the profile.** A client that does not claim this profile treats an onion base URL as unsupported, as it treats the composite schemes above, and skips it. As [RFC 7686](https://www.rfc-editor.org/rfc/rfc7686) already requires, it does not look the name up in DNS.
5. **Topic managers.** A SHIP or SLAP topic manager that claims this profile SHOULD admit an advertisement whose URL is a valid onion base URL under rules 1 and 2. Every other admittance rule is unchanged. A lookup service returns such advertisements like any others; whether a client can use them is the client's decision.
6. **Other URLs are unchanged.** An `https:` URL with an onion host is handled as any `https:` URL, and needs Tor to connect. Plain `http:` with any host that is not a valid version 3 onion name keeps the rule in the Status section: local development only.

### What this profile does not require

No operator is required to offer an onion service, and no client is required to run Tor. An operator MAY advertise an `https:` URL and an onion base URL for the same service as separate advertisements. Which Tor implementation a client uses, and how it is configured, is the implementer's choice.

### Security considerations

- The advertisement links the operator's identity key to the onion address, as it does for an `https:` host. An operator who wants the two unlinked should not advertise the onion address.
- An onion service is reachable only through Tor, so latency is higher, and denial-of-service defences differ from those of a clearnet host.
- A client that sends onion names to DNS or to a clearnet proxy reveals which services it uses. Rules 3 and 4 forbid this.
