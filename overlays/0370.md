# BRC-370: Competitive Delivery Markets for Overlay Lookups and Message Boxes

Deggen (d.kellenschwiler@bsvassociation.org)

## Abstract

This BRC specifies a client-enforced market for serving overlay lookups and message-box deliveries across a set of independent operators. A client broadcasts an authenticated query, measures which operators respond first, requires a threshold of distinct operators to attest the same content hash, and pays a Fibonacci-weighted split of a protocol-minimum fee to the fastest qualifying responders. Operators are paid for being fast and for replicating content. Clients are identified on every request by [BRC-103](../peer-to-peer/0103.md) mutual authentication as implemented by `@bsv/auth`. Recipients who hold no BSV can still collect messages because the sender funds collection in advance. The design fills the monetization gap left open by [BRC-33](../peer-to-peer/0033.md) and the optional payment layer noted by [BRC-24](./0024.md), without introducing a new consensus protocol or a staking token.

## Motivation

[BRC-33](../peer-to-peer/0033.md) message boxes and [BRC-24](./0024.md) overlay lookups are today typically served by a single host URL. That is an acceptable trust model when the operator is already a regulated counterparty, for example a licensed stablecoin issuer that both mints the asset and hosts identity resolution. It is not a robust model for an open network of operators.

Three problems appear as soon as more than one host is expected to serve the same identity-keyed account:

1. **No native incentive to run a host.** Message-box and overlay nodes are not Bitcoin miners. [BRC-33](../peer-to-peer/0033.md) explicitly left monetization to a later specification via [BRC-41](../payments/0041.md). [BRC-24](./0024.md) likewise permits but does not specify payment.
2. **Hoarding.** A host that already holds a message or a lookup result is rewarded if it withholds the payload from peers, because fewer competitors can win a winner-take-all race.
3. **Monopoly drift.** A pure first-arrival payout concentrates revenue on the lowest-latency operator and starves the long tail that the network needs for availability.

Proof-of-work is the only large-scale Byzantine fault-tolerant incentive system that has been demonstrated in production, but hashing is the wrong work here. The work that matters is *delivering the requested content to the client*. This BRC treats delivery itself as the scarce resource, prices it with ordinary BSV micropayments, and lets the client act as the judge of arrival order. Because BSV can settle very small outputs, the payout can be spread across a Fibonacci-weighted tail of responders rather than a single winner.

A separate, pragmatic deployment remains valid: an application that already trusts one regulated party MAY keep using a single message-box URL for both identity resolution and forwarding. This BRC specifies the distributed alternative.

## Specification

### 1. Roles

| Role | Description |
| --- | --- |
| Client | The party that wants a payload. For message collection this is the recipient wallet. For overlay or relay lookup this is the querying wallet. |
| Operator | An independent message-box or overlay host that stores and serves payloads addressed by identity key or lookup query. |
| Sender | The party that originates a message-box payload. The sender funds later collection so the recipient need not hold BSV. |
| Market | The set of operators a client is willing to query for a given request class. |

Identity keys are [BRC-42](../key-derivation/0042.md) identity public keys. Every client-to-operator and operator-to-client request MUST be mutually authenticated with [BRC-103](../peer-to-peer/0103.md) over [BRC-104](../peer-to-peer/0104.md) HTTP transport. Implementations SHOULD use the `@bsv/auth` package so the identity key is bound to the request bytes.

### 2. Request Classes

The same market rules apply to any request whose correct answer is a byte string that can be hashed. This BRC defines three request classes:

| `class` | Payload | Existing interface |
| --- | --- | --- |
| `messagebox.list` | The canonical encoding of the messages returned for `{ recipient, messageBox }` | [BRC-33](../peer-to-peer/0033.md) `POST /listMessages` |
| `overlay.lookup` | The canonical encoding of the [BRC-24](./0024.md) lookup answer for `{ service, query }` | `POST /lookup` |
| `relay.lookup` | The canonical encoding of a keyed record returned for `{ registry, key }` | Deployment-defined |

Additional classes MAY be defined by later BRCs provided they specify a canonical byte encoding for the payload.

### 3. Canonical Payload Hash

Operators and clients compute:

```
contentHash = SHA-256(canonicalBytes)
```

`canonicalBytes` is class-specific:

- `messagebox.list`: UTF-8 JSON with keys sorted lexicographically, messages ordered by `messageId` ascending, no insignificant whitespace. Each message object contains exactly `messageId`, `sender`, and `body`.
- `overlay.lookup`: the compact `application/octet-stream` encoding defined by [BRC-24](./0024.md) when available; otherwise UTF-8 JSON with keys sorted lexicographically and no insignificant whitespace.
- `relay.lookup`: SHA-256 of the raw record bytes as stored.

Two operators attest the *same answer* if and only if they produce the same `contentHash`.

### 4. Query Commitment

A client that wishes to buy a payload constructs a `QueryCommitment` and sends it in parallel to every operator in its market.

#### QueryCommitment Fields

| Field | Type | Description |
| --- | --- | --- |
| `type` | String | Always `query-commitment`. |
| `class` | String | One of the request classes in Section 2. |
| `query` | Object | Class-specific query. For `messagebox.list` this is `{ recipient, messageBox }`. For `overlay.lookup` this is `{ service, query }`. |
| `queryId` | String (hex) | SHA-256 of the canonical UTF-8 JSON of `{ class, query, client, issuedAt }`. |
| `client` | String (hex) | Compressed identity public key of the client. |
| `issuedAt` | String (ISO 8601) | Time the commitment was created. |
| `windowMs` | Integer | Collection window in milliseconds, starting at the client's receipt of the first valid attestation. Default `250`. |
| `threshold` | Integer | Minimum distinct operator attestations required for a `contentHash` to be payable. Default `3`. |
| `maxPayouts` | Integer | Maximum number of operators that share the fee. Default `8`. |
| `feeSats` | Integer | Total fee the client will pay if a payable hash is obtained. MUST be at least `floorFeeSats`. |
| `floorFeeSats` | Integer | Protocol floor for this request class, advertised by the market or configured by the client. |
| `collectGrant` | Object or `null` | Sender-funded collection grant, see Section 8. Required when the client cannot pay from its own wallet. |
| `depositOutpoint` | String or `null` | Optional query-deposit outpoint, see Section 10. |

The [BRC-103](../peer-to-peer/0103.md) session already binds `client` to the request. Operators MUST reject a commitment whose `client` field does not match the authenticated identity key.

Operators MUST reject a commitment whose `issuedAt` differs from their clock by more than 30 seconds, and MUST reject a replayed `queryId` from the same client within that window.

### 5. Hash Attestation

An operator that can serve the query responds with a `HashAttestation` as quickly as possible. The attestation does **not** include the payload body. This keeps the first round small and lets the client compare hashes before pulling bytes.

#### HashAttestation Fields

| Field | Type | Description |
| --- | --- | --- |
| `type` | String | Always `hash-attestation`. |
| `queryId` | String (hex) | The `queryId` being answered. |
| `operator` | String (hex) | Compressed identity public key of the operator. |
| `contentHash` | String (hex) | SHA-256 of the canonical payload. |
| `payloadBytes` | Integer | Length of `canonicalBytes`. |
| `attestedAt` | String (ISO 8601) | Operator's clock. Informational only. MUST NOT be used to rank operators. |
| `signature` | String (base64) | [BRC-3](../wallet/0003.md) signature over `queryId || contentHash || operator` using protocol ID `race market attestation` at security level `2` and key ID equal to `queryId`. Counterparty is the client. |

Ranking is determined solely by the time the attestation arrives at the client. An operator cannot win by backdating `attestedAt`.

If the operator does not hold a payload for the query, it MUST either remain silent or return `type: empty` with no `contentHash`. Empty responses are not ranked and are not paid.

### 6. Client Judging Procedure

The client is the enforcement point. After broadcasting the `QueryCommitment` it performs the following steps:

1. Record the local arrival time of every valid `HashAttestation` whose signature verifies against the operator identity key and whose `queryId` matches.
2. Discard attestations from operators not in the client's current market set.
3. Start `windowMs` at the arrival of the first valid attestation.
4. When the window closes, group remaining attestations by `contentHash`.
5. A hash is **payable** if at least `threshold` distinct operators attested it.
6. If several hashes are payable, the client selects the payable hash whose earliest attestation arrived first.
7. If no hash is payable, the client MAY extend the window once by `windowMs` and MAY retry against additional operators. It MUST NOT pay.
8. The client then requests the payload body from one or more operators that attested the winning hash, beginning with the earliest arrival (see Section 7).
9. Upon receipt, the client computes `SHA-256(canonicalBytes)` and MUST reject the body if it does not equal the winning `contentHash`.
10. If the body verifies, the client pays the operators that attested the winning hash, ranked by attestation arrival time, according to Section 9.

This procedure punishes hoarding without a second consensus layer. An operator that withholds a payload from peers can still be first to attest, but if fewer than `threshold` operators hold the same hash, the attestation set is not payable and the hoarder is not paid.

### 7. Body Delivery

After a payable hash is selected the client issues a `BodyRequest`:

| Field | Type | Description |
| --- | --- | --- |
| `type` | String | Always `body-request`. |
| `queryId` | String (hex) | The query being collected. |
| `contentHash` | String (hex) | The winning hash. |
| `payer` | String (hex) | Identity key that will fund the Section 9 payment. Either the client or the `collectGrant.funder`. |

The operator returns `canonicalBytes` for that hash. The client MAY request the body from several operators in parallel and accept the first body that hashes to `contentHash`.

Operators SHOULD gossip any payload they accept for storage to a random subset of market peers within a few seconds of receipt. Gossip is not independently enforced by consensus. It is enforced economically: payloads that are not replicated do not reach `threshold` and therefore do not pay.

### 8. Sender-Funded Collection

A recipient that holds no BSV cannot pay a collection fee. The sender therefore funds collection at send time.

When a sender submits a [BRC-33](../peer-to-peer/0033.md) `sendMessage` request, it SHOULD attach a `collectGrant`:

| Field | Type | Description |
| --- | --- | --- |
| `funder` | String (hex) | Sender identity key. |
| `maxFeeSats` | Integer | Maximum total collection fee the sender will fund. MUST be at least the market `floorFeeSats`. |
| `expiresAt` | String (ISO 8601) | After this time the grant MUST NOT be used. |
| `payment` | Object | A [BRC-29](../payments/0029.md) payment template or a [BRC-121](../payments/0121.md) prepaid authorization spendable by operators that deliver a matching `contentHash` for this message box. |

The recipient includes that grant on its `QueryCommitment`. Operators that win a rank on the resulting payout redeem against the grant rather than against the recipient wallet. The recipient's only online requirement is the ability to run the judging procedure and to present the grant.

If no grant is present, the client pays from its own wallet and MUST hold sufficient BSV.

The market MUST enforce a protocol floor fee. A sender MUST NOT be allowed to starve collection by setting `maxFeeSats` below `floorFeeSats`. `floorFeeSats` MAY vary with payload size and recent market load. A deployment SHOULD publish its current floor.

### 9. Fibonacci Payout

Let `N` be `min(maxPayouts, number of distinct operators that attested the winning hash)`. Rank those operators `1 .. N` by client-measured arrival time of their valid attestation, earliest first.

Define the Fibonacci sequence by `F(1) = 1`, `F(2) = 1`, and `F(k) = F(k-1) + F(k-2)` for `k > 2`.

The weight for rank `r` is `F(N - r + 1)`. The total weight is

```
W = F(1) + F(2) + ... + F(N)
```

Rank `r` is owed

```
payout(r) = floor( feeSats * F(N - r + 1) / W )
```

Any remainder satoshis after the floor division are added to rank 1.

Worked example for `feeSats = 1200` and `N = 5`:

| Rank | Arrival | F(N-r+1) | Share |
| --- | --- | --- | --- |
| 1 | first | F(5) = 5 | 500 |
| 2 | second | F(4) = 3 | 300 |
| 3 | third | F(3) = 2 | 200 |
| 4 | fourth | F(2) = 1 | 100 |
| 5 | fifth | F(1) = 1 | 100 |

`W = 12`, and `1200 / 12 = 100`, so the shares above are exact.

The first responder is paid the most. Later responders in the tail still receive a non-zero amount. Because BSV can carry dust-level outputs, a deployment MAY raise `maxPayouts` well beyond 5 so that an operator that is usually fifteenth still earns something for staying online.

Payments SHOULD use [BRC-121](../payments/0121.md) Simple 402 Payments or [BRC-105](../payments/0105.md) when the operator is serving over HTTP. Each ranked operator is paid independently. The client SHOULD issue the payments immediately after the body hash verifies.

### 10. Honor, Reputation, and Optional Deposit

Micropayment disputes cost more than the fee. This BRC therefore specifies honor plus identity-key reputation as the default enforcement for non-payment, not an on-chain court.

#### Default honor rules

- A conforming client MUST pay after a verified body delivery.
- A conforming operator MUST NOT hoard: it should replicate payloads so that `threshold` can be met.
- Operators MAY keep a local reputation score keyed by client identity key.
- An operator MAY refuse service to a client identity key that has collected verified bodies without paying, or MAY demand a query deposit from that key on subsequent requests.
- Clients SHOULD prefer operators that have historically responded quickly and honestly, because that is how the client keeps receiving a good market.

These rules are self-reinforcing. Operators stay fast and share because that is how they get paid next time. Clients pay because that is how operators keep answering.

#### Optional query deposit

When reputation is not enough, the client MAY lock a small deposit referenced by `depositOutpoint`:

1. The client creates a time-locked output of at least `feeSats` satoshis.
2. The output is spendable by the client after `expiresAt`, or immediately by a threshold of ranked operators once a payable hash has been demonstrated.
3. If no valid body arrives before `expiresAt`, the client reclaims the deposit.
4. If a valid body arrives and the client pays, the deposit is returned unused.
5. If a valid body arrives and the client does not pay, operators redeem the deposit as compensation.

Deployments that deal only in satoshi-scale fees SHOULD omit the deposit and rely on honor plus reputation. The deposit exists for higher-value payloads and for clients with no history.

### 11. Market Membership and Discovery

This BRC does not replace host discovery.

- Message-box operators continue to advertise with [BRC-34](../peer-to-peer/0034.md) PHIP tokens.
- Overlay operators continue to advertise with [BRC-23](./0023.md) CHIP and [BRC-101](./0101.md) SHIP / SLAP.
- Handle-to-host resolution MAY use [BRC-28](../payments/0028.md) Paymail or [BRC-169](../peer-to-peer/0169.md) Universal Handles as a pointer to the market, not as a source of truth for identity bindings.

A client constructs its market set from those advertisements plus any locally configured operators. Byzantine agreement on the *directory* is out of scope. Byzantine agreement on the *payload* is approximated by the `threshold` hash-attestation rule: a minority of malicious operators cannot make a fake payload payable unless they also outrun honest operators and gather `threshold` attestations for the same fake hash.

### 12. Bootstrapping

A new market has no clients, so operators earn nothing until traffic exists. A deployment MAY pay a declining per-request subsidy to operators during a published bootstrap window. The subsidy is not a consensus rule. After the window, only race fees remain.

Seed operators run by the deploying project SHOULD participate in the same race as everyone else so that the client software is exercised against a multi-operator market from day one.

### 13. Threat Model

| Attack | Mitigation |
| --- | --- |
| Operator serves a swapped or stale payload | Client verifies `SHA-256(body) == contentHash` and requires `threshold` attestations of that hash. |
| Operator hoards to win the race alone | Hoarded payloads fail `threshold` and are not paid. |
| Operator lies about response time | Ranking uses client arrival time, not operator timestamps. |
| Client collects the body and does not pay | Identity-key reputation; optional query deposit; operators stop serving that key. |
| Sender underpays so nobody collects | Protocol `floorFeeSats`. |
| Recipient has no BSV | Sender-funded `collectGrant`. |
| Single operator outcompetes everyone | Fibonacci tail keeps additional operators paid. |
| Query traffic leaks intent | Accepted for autocomplete-style UX. Honest operators MUST treat partial queries as ephemeral and MUST NOT persist them. |
| Compromised discovery host points at a hostile market | Client still verifies hashes and signatures. Discovery is a pointer, not a trust root for payload correctness. |

### 14. Non-Goals

- This BRC does not put message bodies on chain.
- This BRC does not define a new overlay topic manager or lookup service.
- This BRC does not replace [BRC-33](../peer-to-peer/0033.md), [BRC-34](../peer-to-peer/0034.md), or [BRC-24](./0024.md). It specifies how those interfaces are paid when more than one operator serves them.
- This BRC does not require staking or slashing.

## Examples

### Example HashAttestation

```json
{
  "type": "hash-attestation",
  "queryId": "a3e1c0b9d8f7e6a5b4c3928170654433221100ffeeddccbbaa99887766554433",
  "operator": "028d37b941208cd6b8a4c28288eda5f2f16c2b3ab0fcb6d13c18b47fe37b971fc1",
  "contentHash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
  "payloadBytes": 184,
  "attestedAt": "2026-09-18T18:44:01.233Z",
  "signature": "MEUCIQDk0exampleSignatureWouldGoHereAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=="
}
```

### Example Client Decision

A client with `threshold = 3` and `maxPayouts = 5` receives attestations in this arrival order:

1. Operator A, hash `H1`
2. Operator B, hash `H1`
3. Operator C, hash `H2`
4. Operator D, hash `H1`
5. Operator E, hash `H1`

`H1` has four attestations and is payable. `H2` has one and is not. The client pulls the body for `H1`, verifies the hash, and pays A, B, D, and E using the `N = 4` Fibonacci split. C is not paid.

## Implementations

There is no production implementation of this market at the time of writing. Intended reference surfaces:

- Client authentication: `@bsv/auth` implementing [BRC-103](../peer-to-peer/0103.md) and [BRC-104](../peer-to-peer/0104.md).
- Message-box interface: existing [BRC-33](../peer-to-peer/0033.md) hosts, including the historical PeerServ API.
- Overlay lookup interface: `POST /lookup` as specified by [BRC-24](./0024.md) in `bsv-blockchain/ts-stack`.
- Payment rail: `@bsv/402-pay` implementing [BRC-121](../payments/0121.md).

A conforming client library SHOULD expose a single `raceQuery(commitment)` helper that performs discovery, parallel query, judging, body fetch, hash check, and Fibonacci payout.
