# BRC-260: Quantum-Migration Outputs: A Hidden Hash-Based Key and a Hybrid Spend

RexStarBSV (RexStarBSV@protonmail.com)

## Abstract

This BRC defines one locking-script template that lets a wallet move coins into outputs which do not depend only on the hardness of the elliptic-curve discrete logarithm. Each output carries one 32-byte commitment `C` and nothing else that varies. `C` is a SHA-256 hash over a suite identifier, a compressed secp256k1 public key `P` and the public key `K` of a hash-based one-time signature, so neither key appears on chain until the output is spent.

A spend must carry a valid ECDSA signature under `P` and an LM-OTS one-time signature, as defined in RFC 8554 with the parameter set `LMOTS_SHA256_N32_W4`, over the exact bytes of that ECDSA signature. The script verifies both. An adversary who can compute discrete logarithms still cannot spend the output, either while it rests or while its spend waits to be mined, without finding a SHA-256 preimage. The template uses only opcodes that every post-Genesis interpreter runs. The locking script is 15,096 bytes and a one-input spend is about 2.5 kB.

The one-time signature is not new: it is RFC 8554's LM-OTS, unchanged, and the reference implementation reproduces the RFC's own test case. What this BRC adds is the binding to the ECDSA signature, the script that checks it, a deterministic derivation from the wallet seed, and the wallet rules that keep a one-time key used once. A one-byte suite identifier leaves room for later suites. Test vectors were produced by a reference implementation and checked against two script interpreters that share no code with it and against SV-Node itself.

## Overview: what this BRC does

### The problem

A BSV coin is normally locked to a secp256k1 key. Whoever knows the private key `d` behind the public key `P = dG` can spend it. Finding `d` from `P` is the elliptic-curve discrete-logarithm problem, which no classical computer can solve at this size. Shor's algorithm ([SHOR]) solves it in polynomial time on a quantum computer large enough to run it for secp256k1. No such machine is known to exist.

Such a machine would only be a danger to keys it can see. A public key is visible while a coin rests if it was paid to directly, if its address was spent from and paid again, or if the key was published for another purpose, such as an identity key. Every other coin shows its key during its spend: the unlocking script reveals `P`, and the transaction waits in mempools until it is mined.

### The idea

Put a second key in the output that a quantum computer cannot attack, and keep both keys hidden until the spend. The second key is a hash-based one-time key, RFC 8554's LM-OTS, whose security rests only on SHA-256. The output holds just a 32-byte hash `C` of the suite, `P` and the one-time public value `K`. A spend must carry two signatures, and the script checks both:

1. an ordinary ECDSA signature under `P` over the transaction, and
2. a one-time signature, under the key committed in `C`, over the exact bytes of that ECDSA signature.

Because the second signature signs the first, it also pins the transaction: a given ECDSA signature under a given key is valid for only two transaction digests. A thief who recovers `d` can make new ECDSA signatures, but each of them needs a new one-time signature, which needs a SHA-256 preimage.

### A worked example

The numbers below are those of the test vectors (account 0, index 0).

1. **Create.** The wallet derives `d` and a 32-byte `pq_seed` from its seed (section 10), then `P`, the 67 one-time private values `x[i]`, their public value `K` (1,005 chained hashes) and `C`. It gives `C` to the payer. The payer builds a 15,096-byte locking script in which every byte except the 32 bytes of `C` is the same for every template output.
2. **Rest.** An observer sees `C` and the amount. Neither key is on chain, so a quantum attacker has nothing to run Shor's algorithm on. To spend the coin it would have to find keys that hash to `C`.
3. **Spend.** The wallet builds the transaction, signs it with `d` (sighash type `0x41`), which gives the 71-byte `sigt`, and records the one-time key as used. It hashes `sigt` with a 32-byte randomizer into `Q`, reads `Q` as 64 four-bit digits and appends 3 checksum digits (the vector's digits begin 6 4 6 5 2 1 6 0, and its checksum digits are 2 2 7). For each digit `a[i]` it releases `x[i]` hashed `a[i]` times. Here the signer computes 420 chain hashes, and a verifier completes the chains with 585 more and checks that the result hashes to `C`. The unlocking script is 2,371 bytes and the whole transaction 2,458.
4. **What an observer sees in the spend:** `P`, the key identifier `I`, the randomizer, the 67 values `y[i]` and `sigt`. That is enough to check the spend and not enough to sign anything else.
5. **What a quantum attacker sees and can do.** It computes `d` from `P` while the spend waits, and signs a transaction paying itself. That gives a new `sigt`, so it needs a one-time signature over new bytes. The values it holds can only be hashed forward, so it can only produce digits at least as large as the honest ones, and the checksum guarantees that any other `Q` has some digit that is smaller (Mathematical basis). At least one chain must then be run backwards, which is a SHA-256 preimage. The vectors include a thief that tried 4,096 randomizers: its best candidate still needed 16 of the 67 chains run backwards, and every interpreter refused it. Replaying the honest one-time signature unchanged fails too, because it signs the honest `sigt`, and that `sigt` is valid only for the honest transaction and for one other digest that nobody can steer a transaction to.

### What it does not do

- **It does not survive a second signature.** If a one-time key signs twice, or a payer funds the same commitment twice and both outputs are spent, a thief can forge by trial without any preimage: over random pairs of signatures the median cost is about 2^61 tries, one pair in ten needs fewer than 2^36, and the easiest about 2^30 (Mathematical basis). The wallet rules in section 11.3 exist to prevent this.
- **It does not help coins whose keys are already exposed until they are moved,** and the move is an ordinary spend, exposed in the ordinary way while it waits to be mined. It is worth moving them while no one is believed able to compute a discrete logarithm in that time.
- **It does not make a spend confirm.** A miner, or anyone who reaches miners first, cannot redirect the coins without a SHA-256 preimage, but it can delay or refuse the honest spend. Delay is where the one-signature rule matters most: a wallet that "fixes" a stuck spend by signing it again hands the attacker two signatures. The safe responses are to rebroadcast the same bytes or to pay more with a child transaction.
- It does not protect a coin whose seed is stolen, and it is not a NIST-approved signature scheme (Cryptographic basis).

### Who implements what

- **Wallets** implement the builder, signer and reader roles, the derivation (section 10), the used-key record (section 11.3), recovery (section 11.6) and the offer to move exposed coins.
- **Payers** that pay to a commitment they were given need only build the locking script from 32 bytes (section 5).
- **Indexers and explorers** may implement the reader role: rebuild the script from `C` and compare every byte.
- **Miners and node operators** implement nothing. The script uses only opcodes that every post-Genesis node runs, and SV-Node's default policy accepts and mines it (section 9).

### Migration path for a wallet

1. Implement the derivation, the builder and the signer with its used-key record, and check them against the test vectors.
2. Offer to move the coins whose classical key is exposed first: pay-to-public-key outputs, reused addresses, and coins on published keys (section 11.1).
3. Receive into template outputs, with a fresh index for every commitment handed out (section 11.2), and send change from a template output to a fresh template output.
4. Keep ordinary outputs for everything else for as long as wanted: nothing on chain forces a move. At 100 satoshis per 1,000 bytes, creating and later spending a template output costs about 1,700 satoshis more than a pay-to-public-key-hash output.
5. Carry the used-key record in every backup and export (section 11.6).

## Motivation

Every standard output on BSV today is spendable by whoever knows the discrete logarithm of a secp256k1 public key. A quantum computer large enough to run Shor's algorithm ([SHOR]) on secp256k1 would compute that logarithm from the public key. No such machine is known to exist, and nobody can say when, or whether, one will. What can be said is what would be lost if one did:

1. **Coins whose public key is already visible.** Pay-to-public-key outputs, every address that has been spent from and paid again, and every key published for another purpose (an identity key, a certificate subject, a counterparty key) expose the key while the coin rests. A thief has as long as the coin stays put.
2. **Keys derived from a published key.** Under [BRC-42](../key-derivation/0042.md), a child private key is the master private key plus a tweak computed from a shared secret, and the master public key of a wallet is commonly published as its identity key. Whoever computes the discrete logarithm of that one public key holds the master private key, and with it every child private key for every counterparty and invoice number it can enumerate.
3. **Coins in the act of being spent.** Spending any pay-to-public-key-hash output reveals its public key. A thief fast enough to compute the logarithm before the spend is mined, and able to get a miner to take its transaction instead, can sign a competing spend.

The registry has no template that hedges against this. [BRC-220](../apps/0220.md) names post-quantum signature algorithms for notarised hashes, verified off chain, and locks nothing. A wallet that wants to hedge today has to invent its own output format, and a format invented separately by each wallet cannot be recognised, recovered or audited by another.

Two things make a hedge possible on BSV now, without any change to the protocol. Script can hash, split and concatenate, and the default policy allows scripts of up to 500,000 bytes ([NODE]), so a hash-based one-time signature can be verified in script. And a hash-based signature can be bound to the transaction by signing the transaction's own ECDSA signature: for a fixed signature and key, the ECDSA verification equation admits only two message digests (section 8), so changing anything the signature covers needs a SHA-256 preimage, not a discrete logarithm. The same binding was described for Schnorr signatures on another chain ([CONDUITION]); this BRC applies it to ECDSA on BSV with a standard one-time signature, fixes every byte, and adds the derivation and wallet rules that make it safe to use.

No cryptographically relevant quantum computer has been demonstrated, and this BRC does not depend on any prediction of when one might exist. It rests on a simpler fact: an output whose public key is already exposed cannot be hardened after the fact, only moved, and the move is itself an exposed spend. The extra bytes of a template output are an optional cost paid now by a wallet that chooses them, which makes them insurance and not a forecast. The design assumes only that SHA-256 resists preimages and second preimages, a conservative assumption about a hash function already in wide use, and no newer lattice or code-based assumption. A spend needs both the ECDSA signature and the one-time signature, so a flaw in the hash-based scheme alone cannot spend a coin; it would leave the output protected by ECDSA, as an ordinary output is. The one-time key is derived from the user's own wallet seed (section 10), with no outside party to trust or to contact.

## Scope and conformance

This BRC specifies the suite identifiers (section 2), the commitment (section 3), the one-time signature and its inputs (section 4), the locking and unlocking scripts (sections 5 and 6), the spend rule (section 7), the derivation of keys from a seed (section 10), wallet behaviour (section 11) and the requirements by role (section 12).

It does not specify: how a payer obtains a commitment from a payee (any channel that delivers 32 bytes and a suite identifier will do, and section 11.2 says what the payee must ensure), the outputs a spend creates, the fee rate, storage, transport, or any overlay. It does not define a general signature envelope for other records; section 2 is written so that such an envelope can adopt its table.

**Layer.** Interface: the template, the derivation and wallet behaviour. Nothing here asks a miner or relay to run any check beyond script.

The key words MUST, MUST NOT, SHOULD, SHOULD NOT and MAY are to be interpreted as described in RFC 2119 and RFC 8174 when, and only when, they appear in capitals. A MUST binds an implementation that claims conformance to this document in one of these roles, and nobody else:

- a **builder** creates a template output;
- a **signer** produces the signatures for a spend;
- a **reader** recognises template outputs and reports their suite and commitment;
- a **wallet** derives keys and decides when to move coins (sections 10 and 11).

A wallet that does not adopt this BRC does not follow it; its outputs are not made invalid by it.

## Threat model

An **adversary with a discrete-log oracle** can compute `d` from `P = dG` for any secp256k1 key. It is assumed able to run Grover-type search, which costs about `2^(n/2)` evaluations for an `n`-bit preimage. It is assumed unable to find SHA-256 preimages or second preimages faster than that. A **long-exposure** attack has as long as a key stays visible. A **short-exposure** attack must finish between the broadcast of an honest spend and its mining, and also needs a miner to take the thief's transaction instead of the honest one; SV-Node keeps the first spend it sees and refuses a conflicting one (`txn-mempool-conflict`), so the thief must reach a miner first or find one that ignores that rule.

| Coin | Rests with key hidden | Rests with key exposed | Short-exposure attack on its spend |
|---|---|---|---|
| Pay to public key hash | Generic bound only: a second preimage of HASH160 is about 2^80 Grover iterations | Lost | Lost if a miner takes the thief's spend |
| Template output | Hidden behind SHA-256 | Safe: a spend also needs the one-time key | Safe: needs a SHA-256 preimage (section 8) |

"Key exposed" means the classical key `P` is known, for instance because the same `P` was used elsewhere. The one-time key is never exposed before its one spend. A classical adversary, with no discrete-log oracle, faces ECDSA, as for any ordinary output.

What the template cannot do: protect a coin before it is moved into one (the move is an ordinary spend, exposed in the ordinary way), protect a coin whose seed is stolen, or protect an output whose one-time key has signed twice (section 11.3).

## Relationship to existing standards

**RFC 8554 (LMS).** Section 4 uses LM-OTS exactly as RFC 8554 section 4 defines it, with `LMOTS_SHA256_N32_W4`, and RFC 8554 Appendix A to generate the private key. RFC 8554 defines LM-OTS as the leaf signature of an LMS tree; this BRC uses one LM-OTS key per output with leaf number `q = 0` and its own identifier `I`, the same inputs LMS gives each leaf, without a tree. NIST SP 800-208 approves LMS and HSS with these LM-OTS parameter sets; it does not approve LM-OTS on its own, and this BRC does not claim that it does.

**BRC-220 (NotaryHash).** It names `ML-DSA-44`, `ML-DSA-65`, `ML-DSA-87` and the twelve SLH-DSA parameter sets as algorithm identifiers for signed-hash certificates. Section 2 reserves codes for them, so that a later BRC can use the same names. Nothing in BRC-220 changes.

**BRC-21 (Push TX) and BRC-215.** Push TX authenticates a transaction's signature preimage by an ECDSA check with a private key that everyone knows (`d = 2`), so its soundness rests on arithmetic and SHA-256, not on the hardness of discrete logarithms. A variant could sign the preimage's digest through Push TX instead of signing the ECDSA signature. It would cost the preimage in the unlocking script and about 1 kB of gate; signing the ECDSA signature gives the same binding for less, so this BRC does not use Push TX.

**BRC-16 (P2PKH), BRC-42 and BRC-43.** Template keys are not derived through BRC-42 or BIP-32 (section 10.3 says why), and a template output is not a P2PKH output. A wallet keeps using BRC-42 for everything else.

**Prior art outside the registry.** [BIP360] (now Pay-to-Merkle-Root) defines an output that commits only to a Merkle root of scripts, with no key-path spend, and leaves post-quantum signatures to later work; it needs a soft fork. [CONDUITION] verifies a Winternitz signature over the hash of a Schnorr signature in script and depends on `OP_CAT`, which is not active on that chain; this BRC is the same idea for ECDSA on BSV, where `OP_CAT` is enabled, with RFC 8554's LM-OTS in place of a purpose-built Winternitz scheme. [DRYJA] proposes a commit/reveal soft fork; [BCH-LOCK] builds a commit/reveal lock with introspection opcodes and records the reveal race that a commitment without a verified signature has (see Rationale).

## Specification

### 1. Notation

- `||` is concatenation. `u8(x)`, `u16(x)` and `u32(x)` are one, two and four bytes, big-endian, as `u8str`, `u16str` and `u32str` in RFC 8554.
- `SHA256` is SHA-256. `HMAC512(k, m)` and `HMAC256(k, m)` are HMAC with SHA-512 and SHA-256.
- `P` is a compressed secp256k1 public key, 33 bytes. Uncompressed keys are not used.
- `sigt` is an ECDSA signature in DER followed by its one-byte sighash type, exactly as pushed for `OP_CHECKSIGVERIFY`.
- `NUM(x)` is the minimal push of the script number `x`; `PUSH(b)` is the minimal push of the byte string `b`, which for a single byte from `0x01` to `0x10` is `OP_1` to `OP_16`.
- Constants are ASCII strings: `KEY_TAG = "QMO1/key"` (8 bytes), `ROOT_KEY = "QMO1/root"`, `OUT_LABEL = "QMO1/output"`, `ID_LABEL = "QMO1/id"`, `RAND_LABEL = "QMO1/randomizer"`.
- `D_MESG = 0x8181` and `D_PBLC = 0x8080` are RFC 8554's domain values.

### 2. Suite identifiers

A suite identifier is one byte. It is hashed into the commitment, so a coin committed under one suite cannot be spent under another.

| Code | Name | One-time or post-quantum signature | Status |
|---|---|---|---|
| `0x00` | reserved | | never assigned |
| `0x01` | `QMO-LMOTS-SHA256-N32-W4` | RFC 8554 LM-OTS, typecode 3, bound to ECDSA as in this document | defined here |
| `0x02` to `0x04` | `ML-DSA-44`, `ML-DSA-65`, `ML-DSA-87` | FIPS 204 | reserved, not defined |
| `0x05` to `0x10` | `SLH-DSA-*` | the twelve FIPS 205 parameter sets | reserved, not defined |
| `0x11` to `0xEF` | | | unassigned |
| `0xF0` to `0xFE` | | | private use, never interoperable |
| `0xFF` | reserved | | never assigned |

A later BRC MAY assign an unassigned or reserved code, and SHOULD assign a reserved code only to a suite whose signature the spending script, or consensus, verifies. It MUST NOT change the meaning of an assigned code: a new version of a suite takes a new code. A general signature envelope MAY adopt this table by reference; the codes and names here then keep their meaning.

### 3. Commitment

```
C = SHA256( KEY_TAG || u8(suite) || P || K )
```

`K` is the 32-byte LM-OTS public key value of section 4.2. `C` hides both keys. HASH160 is not used, because its 160-bit output gives about 2^80 Grover iterations for a second preimage.

### 4. One-time signature

#### 4.1 Parameters

`LMOTS_SHA256_N32_W4` from RFC 8554 Table 1: hash SHA-256, `n = 32`, `w = 4`, `p = 67`, `ls = 4`. The private key is 67 values `x[0]` to `x[66]`; the identifier `I` is 16 bytes; the leaf number `q` is always 0.

#### 4.2 Keys

From the 32-byte `pq_seed` of section 10:

```
I    = first 16 bytes of HMAC256( pq_seed, ID_LABEL )
x[i] = SHA256( I || u32(0) || u16(i) || u8(0xFF) || pq_seed )         for i = 0 to 66
```

which is RFC 8554 Appendix A with `SEED = pq_seed`. The public value is RFC 8554 section 4.3:

```
K = SHA256( I || u32(0) || u16(D_PBLC) || z[0] || ... || z[66] )
```

where `z[i]` is `x[i]` after the chain steps `j = 0` to `14`, each step `tmp = SHA256( I || u32(0) || u16(i) || u8(j) || tmp )`.

#### 4.3 Signing

The message is `sigt`, the ECDSA signature with its sighash byte, exactly as it is pushed. RFC 8554 Algorithm 3:

```
Q    = SHA256( I || u32(0) || u16(D_MESG) || R || sigt )
a[i] = coef( Q || Cksm(Q), i, 4 )                                      for i = 0 to 66
y[i] = x[i] after the chain steps j = 0 to a[i] - 1
```

`R` is the 32-byte randomizer that RFC 8554 calls `C` (renamed here because `C` is the commitment). A signer MAY take `R` from a random source or derive it as `HMAC256( pq_seed, RAND_LABEL || sigt )`; a verifier cannot tell the difference, and the vectors use the derived form. With `w = 4`, `a[0..63]` are the 64 nibbles of `Q`, high nibble of each byte first, and with `c` the sum over those 64 nibbles of `(15 - nibble)`, `a[64] = c >> 8`, `a[65] = (c >> 4) & 15`, `a[66] = c & 15`.

The LM-OTS signature is `R` and `y[0..66]`. RFC 8554's four-byte typecode is not carried: the suite byte in `C` fixes it.

### 5. Locking script

```
LOCK(C) = PRE || BYTE x 32 || MID || CHAIN(66) || ( OP_SWAP || CHAIN(i) || OP_SWAP OP_CAT ) for i = 65 down to 0 || TAIL(C)
```

`PRE` (25 bytes): checks the ECDSA signature, moves `P` to the alt stack, checks the sighash type, and computes `Q` from `I || u32(0)`, `R` and `sigt`.

```
6ead6b76828c7f770141880145790281817e7b7e7c7ea8007c
OP_2DUP OP_CHECKSIGVERIFY OP_TOALTSTACK OP_DUP OP_SIZE OP_1SUB OP_SPLIT OP_NIP 41 OP_EQUALVERIFY 45 OP_PICK 8181 OP_CAT OP_ROT OP_CAT OP_SWAP OP_CAT OP_SHA256 OP_0 OP_SWAP
```

`BYTE` (21 bytes, repeated 32 times): takes one byte of `Q`, puts its two nibbles on the alt stack, and adds them to a running sum.

```
517f7c01007e81766096766b7c6097766b937b937c
OP_1 OP_SPLIT OP_SWAP 00 OP_CAT OP_BIN2NUM OP_DUP OP_16 OP_DIV OP_DUP OP_TOALTSTACK OP_SWAP OP_16 OP_MOD OP_DUP OP_TOALTSTACK OP_ADD OP_ROT OP_ADD OP_SWAP
```

`MID` (21 bytes): turns the sum into `c = 960 - sum` and puts the three checksum digits on the alt stack.

```
7502c0037c9476020001966b76609660976b60976b
OP_DROP c003 OP_SWAP OP_SUB OP_DUP 0001 OP_DIV OP_TOALTSTACK OP_DUP OP_16 OP_DIV OP_16 OP_MOD OP_TOALTSTACK OP_16 OP_MOD OP_TOALTSTACK
```

`CHAIN(i)` (210 to 211 bytes): requires `y[i]` to be 32 bytes, builds the prefix `I || u32(0) || u16(i)` by copying `I || u32(0)` from depth `t` (67 for `i = 66`, otherwise `i + 2`), takes `a[i]` from the alt stack, and applies step `j` if and only if `a[i] <= j`, for `j = 0` to `14`:

```
CHAIN(i) = OP_SIZE NUM(32) OP_EQUALVERIFY NUM(t) OP_PICK PUSH(u16(i)) OP_CAT OP_SWAP OP_FROMALTSTACK
           ( OP_DUP NUM(j) OP_LESSTHANOREQUAL OP_IF OP_2 OP_PICK PUSH(u8(j)) OP_CAT OP_ROT OP_CAT OP_SHA256 OP_SWAP OP_ENDIF ) for j = 0 to 14
           OP_DROP OP_NIP
```

The step for `j = 3` is `7653a1635279537e7b7ea87c68`. `CHAIN(0)` in full is

```
8201208852790200007e7c6c7600a163527901007e7b7ea87c687651a1635279517e7b7ea87c687652a1635279527e7b7ea87c687653a1635279537e7b7ea87c687654a1635279547e7b7ea87c687655a1635279557e7b7ea87c687656a1635279567e7b7ea87c687657a1635279577e7b7ea87c687658a1635279587e7b7ea87c687659a1635279597e7b7ea87c68765aa16352795a7e7b7ea87c68765ba16352795b7e7b7ea87c68765ca16352795c7e7b7ea87c68765da16352795d7e7b7ea87c68765ea16352795e7e7b7ea87c687577
```

`TAIL(C)`: hashes `I || u32(0) || u16(D_PBLC)` and the 67 chain ends into `K`, takes `P` back from the alt stack, and compares the commitment.

```
7c0280807e7c7ea86c7c7e09514d4f312f6b6579017c7ea8 20 <C> 87
OP_SWAP 8080 OP_CAT OP_SWAP OP_CAT OP_SHA256 OP_FROMALTSTACK OP_SWAP OP_CAT 514d4f312f6b657901 OP_SWAP OP_CAT OP_SHA256 <C> OP_EQUAL
```

`LOCK(C)` is 15,096 bytes for every `C`. Every byte is fixed except the 32 bytes of `C`, which sit just before the final `OP_EQUAL`.

### 6. Unlocking script

```
PUSH(I || u32(0)) PUSH(y[0]) PUSH(y[1]) ... PUSH(y[66]) PUSH(R) PUSH(sigt) PUSH(P)
```

`I || u32(0)` is pushed first and stays at the bottom. The script processes the chains from 66 down to 0, because the digits come off the alt stack in the reverse of the order they went on, so `y[66]`, nearest the top, is processed first.

### 7. The spend rule

The script accepts a spend when, and only when:

1. `sigt` is a valid ECDSA signature under `P` for this input (`OP_CHECKSIGVERIFY`), with sighash type exactly `0x41` (`SIGHASH_ALL | SIGHASH_FORKID`);
2. each `y[i]` is 32 bytes;
3. completing each chain from `a[i]` gives ends whose LM-OTS public value, with the suite byte `0x01` and `P`, hashes to `C`; that is, `R, y` is a valid LM-OTS signature of `sigt` under the committed key (RFC 8554 Algorithm 4b, with `Kc` compared through `C`).

The rule is an AND: a spend needs both signatures, and every node that validates the script enforces both. The final stack item is the result of the last `OP_EQUAL`, and the script leaves nothing else.

### 8. Why the signature binds the transaction

For a fixed `(r, s)` and key `P = dG`, ECDSA verification succeeds for a digest `z` exactly when `(z + r d) / s` is `k` or `-k` mod n, where `kG` has x-coordinate `r` ([SEC1]). So exactly two digests mod n pass: the honest `z` and `-z - 2 r d` (the Cryptographic basis gives the derivation and its rare exceptions). An adversary who knows `d` and wants to reuse the one-time signature, which covers `sigt` byte for byte, must find a transaction whose sighash digest equals one of those two 256-bit values: a preimage of double SHA-256, about 2^128 Grover iterations. Signing a new `sigt` instead needs a new LM-OTS signature, and after one signature that needs at least one chain run backwards, a SHA-256 preimage, because the checksum makes every other digest lower somewhere.

The sighash guard matters: under `SIGHASH_NONE`, `SIGHASH_SINGLE` or `ANYONECANPAY`, one digest covers many transactions, so the same `sigt` would be valid for outputs the owner never chose. Requiring exactly `0x41` also excludes the `CHRONICLE` bit `0x20`, which selects a different digest ([CHRONICLE]).

### 9. Sizes, fees and validation cost

| | Bytes |
|---|---|
| Locking script | 15,096 |
| Unlocking script | 2,371 |
| One input, one P2PKH output, version 1 | 2,458 |

A builder pays for the locking script once; the spender pays for the unlocking script. SV-Node mines a transaction when its fee is at least `size x rate / 1000`, rounded down, where `rate` is the miner's `-minminingtxfee` in satoshis per 1,000 bytes; it admits transactions below that to its mempool but leaves them unmined ([NODE-RUN]). `-minminingtxfee` has no built-in default in SV-Node v1.2.2 (each miner sets it); the source constant `DEFAULT_BLOCK_MIN_TX_FEE` is 500 ([NODE]). At 100 satoshis per 1,000 bytes, one template output adds 1,510 satoshis to the funding transaction (15,107 bytes with its value and length) and the spend above costs 245; at 500, 7,553 and 1,229. SV-Node mined the spend at exactly those fees and left it unmined at one satoshi less, and mined a whole funding transaction with one template output and change (15,298 bytes) at 1,529 and 7,649 ([NODE-RUN]).

An output of 0 satoshis is refused as dust under standard policy; 1 satoshi is accepted ([NODE-RUN]). An output worth less than its spend fee is not worth spending.

Verifying one spend takes about 2.2 ms of script time on the machine of [NODE-RUN] (`verifyscript` round trip of about 2.6 ms, less about 0.4 ms of RPC; Mathematical basis). SV-Node's standard validation budget, `-maxstdtxvalidationduration`, is 3 ms by default. A spend that exceeds it is validated again under the non-standard budget (1,000 ms by default) and accepted: with the standard budget set to 1 ms, the node still accepted every honest spend. The `verifyscript` RPC, by contrast, enforces the standard budget with no second pass and can report `timeout` for a valid spend on a busy machine.

### 10. Derivation

#### 10.1 The root

```
pq_root = HMAC512( ROOT_KEY, seed )        (64 bytes)
```

`seed` is the 64-byte BIP-39 seed. A wallet that has no seed, only a root private key, MUST NOT derive `pq_root` from that key (section 10.3); it generates 64 random bytes as `seed`, and that secret becomes part of what a backup must hold (section 11.6).

#### 10.2 One output

For suite `s`, account `a` and index `i`:

```
k        = HMAC512( pq_root, OUT_LABEL || u8(s) || u32(a) || u32(i) )
d        = the integer whose big-endian bytes are k[0..31]
pq_seed  = k[32..63]
```

If `d` is 0 or not less than the group order, index `i` is unusable and is skipped. `P = dG`, compressed. `I`, `x` and `K` follow from `pq_seed` as in section 4.2.

#### 10.3 Why not BIP-32 or BRC-42

The one-time secret must not be computable from anything a discrete-log oracle reveals. An oracle turns any public key into its private key. Under BIP-32's non-hardened derivation a child private key and the parent's extended public key give the parent private key; under BRC-42 a published master public key gives the master private key at once. If the one-time secret were derived from an elliptic-curve private key, the oracle would reveal it too. The BIP-39 seed is not a function of any public key, and HMAC keeps `d` and `pq_seed` independent: learning `d` from `P` says nothing about `pq_seed`.

### 11. Wallet behaviour

#### 11.1 When to move coins

A wallet SHOULD offer to move first the coins whose classical key is exposed (pay-to-public-key outputs, addresses spent from and paid again, keys published for other uses), because those are open to a long-exposure attack. The move itself is an ordinary spend and is exposed while it is unconfirmed; it is worth doing while no adversary is believed able to compute a discrete logarithm in that time. Change from a template output SHOULD go to a fresh template output.

#### 11.2 Receiving

A wallet MUST give out a fresh index for each commitment it hands to a payer, and MUST NOT publish a commitment as a reusable address. A payer that reuses a commitment it was given creates a second output under the same one-time key (section 11.3).

#### 11.3 One signature per key

A one-time key MUST sign once. After one signature, a valid signature for any other message needs a SHA-256 preimage. After two signatures under one key, a classical thief that tries randomizers needs, over 1,000 random pairs of signatures, a median of about 2^61 tries to find a message it can complete by hashing forward; one pair in ten falls below 2^36 and the easiest needs about 2^30 (Mathematical basis). That is practical. Therefore:

- a signer MUST record a key as used before it releases the signature, and MUST NOT sign if it cannot record it;
- a signer MUST NOT produce a second signature for a key, even if the first transaction was never mined; it rebroadcasts the same bytes, or pays a higher fee with a child transaction (SV-Node mines a parent below its fee floor together with a child that pays enough, [NODE-RUN]);
- a spend of a template output SHOULD have no input the signer does not control, so that nobody else can make it invalid;
- if a commitment was funded twice, a wallet MUST warn its user that the second output is protected only against a classical adversary once the first is spent.

#### 11.4 Fail closed

A builder MUST refuse to build an output for a suite it does not implement. A signer MUST refuse to sign with a sighash type other than `0x41`. A wallet MUST NOT fall back to an ordinary output when a template output was requested.

#### 11.5 Privacy

Every template output has the same 15,096 bytes except `C`, so it is recognisable as one. Nothing on chain links two outputs of one wallet until they are spent together; `I` is derived per output and appears only in the spend.

#### 11.6 Exit and recovery

An export for recovery contains the seed (or the 64 random bytes of section 10.1), the suites and accounts in use, and the highest index used per account. Recovery derives `C` for each index, rebuilds the locking script, and looks up its SHA-256 (the usual script-hash index) or scans the chain. No provider beyond a source of transactions is needed. What recovery cannot know is whether a key signed a transaction that was never broadcast or never mined; a wallet SHOULD treat a key as used once any spend of its output has been seen, and the export SHOULD carry the used-key record.

### 12. Requirements by role

- R1 (builder): build `LOCK(C)` exactly as in section 5, with `C` from section 3.
- R2 (builder): refuse an unimplemented, reserved or unassigned suite.
- R3 (signer): sighash type `0x41` only; produce the ECDSA signature first and the LM-OTS signature over its exact bytes (section 4.3).
- R4 (signer): one signature per key, recorded before release (section 11.3).
- R5 (reader): recognise a template output by rebuilding the script from its `C` and comparing every byte; report the suite and `C`.
- R6 (wallet): derive as in section 10, never from an elliptic-curve private key; fresh index per commitment.

## Rationale

**Why LM-OTS, unchanged.** A purpose-built Winternitz chain with a two-byte position tag would make the locking script about 1.7 kB smaller (13,429 bytes, built and measured for this document). It would also be a new construction whose security argument needs SHA-256's collision resistance, and whose hashes are the same function for every key, so an attack on many keys at once costs less per key. LM-OTS puts the key identifier `I`, the leaf number and the chain position into every hash, which separates every key from every other; RFC 8554 cites proofs in the random-oracle model, including a bound for up to 2^64 keys, and needs only second-preimage resistance. It is published, has test vectors, and is already implemented in several libraries. The cost is about 12 percent more locking script and 53 more bytes per spend.

**Why not WOTS+ (RFC 8391, FIPS 205).** WOTS+ at `n = 32` with SHA-2 compresses its public key with SHA-512 in FIPS 205, which script has no opcode for; RFC 8391's WOTS+ adds a bitmask and a keyed hash to each step, about three hash calls per step instead of one. LM-OTS needs one SHA-256 call of 55 bytes, a single compression, per step.

**Why one key per output, not a tree.** A Merkle tree of one-time keys (LMS, XMSS) would let one output be signed for more than once, so a wallet could re-sign to change a fee. A template output is spent once, a child transaction can raise the fee, and a tree makes the wallet keep state across many signatures, which is where hash-based signatures fail in practice. This BRC leaves trees out; a later suite can add one.

**Why no commitment-only profile.** A cheaper output could commit to an ML-DSA public key and carry an ML-DSA signature that script does not verify (ML-DSA verification needs SHAKE and number-theoretic transforms, estimated, not measured, at hundreds of kilobytes of script). Its script would enforce the ECDSA signature and the reveal of the committed key. That is a hash lock: it protects a coin whose classical key is exposed while it rests, as any secret behind SHA-256 would, and the ML-DSA signature adds nothing that a node enforces. Once its spend is broadcast, an adversary who computes `d` can build a competing spend that the script accepts with any bytes of the right length as the signature; such a transaction was built for this document, and SV-Node accepted it into its mempool ([NODE-RUN]). Only a miner that checked ML-DSA off script could tell the two apart, and none is known to. Labelled as post-quantum, such an output would promise more than it gives, so this BRC reserves the ML-DSA codes for a suite whose signature script or consensus verifies.

After Chronicle a version 2 transaction is exempt from that rule, and SV-Node, like `bitcoinx` with the rule turned off, refuses it at the commitment, because the one-time signature covers the exact bytes of `sigt`.

## Implementations

A reference implementation exists (pure Python: secp256k1 ECDSA with RFC 6979, the BIP143 digest with `SIGHASH_FORKID`, LM-OTS, the scripts and the derivation). Its vectors agree with a second, independently written library's interpreter, with `bitcoinx` and with SV-Node v1.2.2, and its derivation and LM-OTS values with a separate JavaScript implementation. On a private regtest chain, SV-Node v1.2.2 at default standardness accepted honest spends of outputs created before and after the Chronicle activation, in version 1 and version 2 transactions, mined them once their fee met its floor, and refused every negative case above with a script error ([NODE-RUN]). No wallet ships the template yet.

### Not tested

- No broadcast on mainnet or testnet; the node runs were on a private regtest chain.
- The LM-OTS code was checked against RFC 8554's test case and a second implementation written for this document, not against a third-party LM-OTS library.
- Validation time was measured on one machine with no other load.
- No spend with the `CHRONICLE` sighash bit was built; the guard's refusal of it follows from the byte comparison and was not run.
- Recovery by script-hash lookup was not run against an indexer.

## Cryptographic basis

### The one-time signature

The scheme is LM-OTS from [RFC8554] with the parameter set `LMOTS_SHA256_N32_W4`, a Winternitz one-time signature. The private key is 67 secret 32-byte values. Hashing each of them 15 times gives 67 chain ends, and the hash of those ends, under a fixed prefix, is the public value `K`. To sign, the signer hashes the message to a 256-bit digest `Q`, reads `Q` as 64 digits of 4 bits, appends 3 checksum digits, and for each digit `a[i]` reveals its secret value hashed `a[i]` times. A verifier hashes each revealed value the remaining `15 - a[i]` times and checks that the ends hash to `K`.

Anyone can hash a revealed value further, so a signature on `Q` would also let anyone claim any digest whose digits are all at least as large, if nothing else were checked. The **checksum** closes that gap: it is the sum of `15 - a[i]` over the 64 message digits, written as 3 more digits that are signed the same way. Raising any message digit lowers the checksum, so some checksum digit must fall, and lowering a digit means running a chain backwards: finding a SHA-256 preimage. The Mathematical basis section proves that with one signature no other digest can be reached by hashing forward alone.

Every hash input in the scheme starts with the 16-byte **key identifier** `I`, the 4-byte leaf number `q` (always 0 here) and either a 2-byte chain number and 1-byte step number or a 2-byte domain value ([RFC8554] section 9.1). No two hash calls inside one key share a prefix, and keys with different `I` share none. Work an attacker spends on one chain step, or on one output, therefore tells it nothing about any other. The **randomizer** (`C` in RFC 8554, `R` here) is hashed into `Q` together with the message, so the digest that gets signed depends on a value fixed only at signing time, as in the RFC's design and its proofs.

### Security assumptions

Security against an adversary who can compute discrete logarithms rests on SHA-256 alone:

- **Second-preimage resistance** for LM-OTS: [RFC8554] section 9 requires it of `H`, and [SP800-208] section 1 states that the security of these schemes "depends only on the security of the underlying hash functions", meaning the infeasibility of finding a preimage or a second preimage.
- **Preimage resistance** for running a chain backwards, for the commitment `C`, and for the binding of the next subsection, which needs a preimage of double SHA-256.

The published proofs are for LMS, the scheme of which LM-OTS is the leaf signature. [KATZ16] proves LMS secure in the random-oracle model. [FLUHRER17] models the SHA-256 compression function as the random oracle and covers many keys at once; its Corollary 1, as quoted in [RFC8554] section 9, bounds the chance of a single forgery against any of up to 2^64 keys, by an attacker allowed 2^120 compression calls and a signing oracle, below 2^-129. This is the multi-target argument: because every key's hash calls carry their own prefix, attacking a million outputs is not a million times cheaper per output. [EATON17] repeats the analysis in the quantum random-oracle model, where the attacker can query the hash in superposition, and reports bounds that match Grover's search within a constant factor and stay tight with many users ([SP800-208] Appendix C.3).

**Why quantum computers only halve the exponent.** Grover's algorithm ([GROVER96]) finds one marked item among `N` in about `sqrt(N)` steps, and no quantum algorithm for unstructured search does better by more than a constant factor. A 256-bit SHA-256 preimage or second preimage therefore costs about 2^128 sequential evaluations of SHA-256 on a quantum computer, against 2^256 classically. Shor's algorithm, which breaks ECDSA, relies on the algebraic structure of the group and has no counterpart for SHA-256 that is known today. The 2^128 figure assumes that no attack on SHA-256 better than generic search is found.

### Why a one-time key must never sign twice

Two signatures under one key, on digests `Q1` and `Q2`, reveal every chain at the smaller of its two digits. A forger can then sign any `Q'` whose 67 digits are each at least that minimum, and with two different checksums the minimum is low enough that such `Q'` are no longer rare. The thief here knows `d`, so it can make its own `sigt` and then try randomizers freely: each try costs one computation of `Q`, three SHA-256 compressions. The Mathematical basis computes the success chance exactly. Over 1,000 random pairs of signatures the median cost is about 2^61 tries, one pair in ten needs fewer than 2^36, and the easiest about 2^30, on ordinary computers. [BH16] reaches the same conclusion for Winternitz signatures in general, and [SP800-208] section 9.1 states that signatures on two different messages under one key make forgery computationally feasible.

### The hybrid binding

Write `n` for the order of secp256k1 and `p` for its field prime. Let `(r, s)` be the ECDSA signature inside `sigt`, `P = dG` the key, and `z` the transaction's sighash digest read as an integer. A verifier computes `R' = (z / s) G + (r / s) P = ((z + r d) / s) G` and accepts when the x-coordinate of `R'`, reduced mod `n`, equals `r` ([SEC1] section 4.1.4). The signer used a nonce `k` with `x(kG) mod n = r`. The points whose x-coordinate is `r` are `kG` and `-kG`; if `r + n < p` there is a second x-coordinate, `r + n`, and two more points, but `p - n` is about 2^128.35, so this happens for about one signature in 2^127.7. Leaving that aside, the verifier accepts exactly when `(z' + r d) / s = k` or `-k` mod `n`, that is when

```
z' = z    or    z' = -z - 2 r d    (mod n)
```

Each of these residues is one 256-bit digest, or two when the residue is below `2^256 - n` (again about one chance in 2^127.7). So the fixed bytes of `sigt` are valid for two digests, and rarely up to four. `binding_check` in the reference implementation confirms numerically that both `z` and `-z - 2 r d` verify for the honest vector and that 200 random digests do not.

A thief who knows `d` has three options, and each needs SHA-256 to fail:

1. Keep `sigt`, so that the one-time signature still verifies, and build a transaction whose BIP143 digest, a double SHA-256 of the signing preimage, equals `z` or `-z - 2 r d`. Knowing `d` only tells it the second target; finding a transaction for either is a preimage search, about 2^255 classical tries or 2^127.5 Grover iterations for two targets.
2. Make a new `sigt` for its own transaction. That needs a one-time signature on new bytes under a key that has signed once: an LM-OTS forgery.
3. Re-encode `sigt` (the high-S twin, another DER form). The bytes change, the one-time signature no longer matches, and the script refuses it; the vectors include this case.

What the argument shows: given a one-time key that has signed once, a discrete-log adversary cannot change anything the sighash commits to (outpoint, value, locking script, outputs, lock time and version, under `0x41`) without a SHA-256 preimage or an LM-OTS forgery. What it does not show: it is a reduction sketched here, not a proof in a stated model, and it treats the sighash digest as an ideal hash. It holds only for sighash type `0x41`, which the script enforces (section 8). It says nothing about availability: delay and censorship remain possible. It gives nothing if `pq_seed` leaks or the key signs twice. [CONDUITION] made the same observation for Schnorr signatures; this text works it out for ECDSA.

### NIST status

[SP800-208] approves LMS and HSS, and XMSS and XMSS^MT, and lists `LMOTS_SHA256_N32_W4` (typecode `0x00000003`) among the LM-OTS parameter sets approved for use within LMS (Table 1). It approves no one-time scheme on its own. It also requires that key and signature generation run only in hardware modules validated at FIPS 140 Level 3 or higher that never export private keys (section 8.1), and that `I`, `SEED` and the randomizer come from an approved random bit generator (section 6.1). This BRC departs from all of that on purpose: it uses one LM-OTS key without a tree, and it derives `I`, `SEED` and optionally the randomizer from the wallet seed, so that a wallet can restore from its recovery phrase.

This matters in three ways. The construction cannot be described as NIST-approved, and a product bound by federal rules cannot rely on it as such. Its security argument rests on the published analysis of the same algorithm ([KATZ16], [FLUHRER17], [EATON17]), not on an approval. And the guarantee that a hardware module gives against signing twice is absent, so the software rule of section 11.3 has to carry it alone.

### Seed derivation, and why not BIP-32 or BRC-42

The first step, `HMAC512(ROOT_KEY, seed)`, hashes the seed under a fixed public key, as BIP-32 derives its master key under the string "Bitcoin seed" ([BIP32]). The second step is HMAC keyed by the secret `pq_root`, used as a pseudorandom function ([RFC2104]). `d` and `pq_seed` are the two halves of one output of that function, so learning `d` says nothing about `pq_seed` unless HMAC-SHA-512 fails as a pseudorandom function.

The point is isolation from a discrete-log break. A discrete-log oracle turns any visible public key into its private key. Under BIP-32 a non-hardened child private key together with its parent's extended public key gives the parent private key, and a hardened child is a function of its parent's private key, which the oracle yields from the parent's public key once that key has been seen. Under [BRC-42] the master private key is one oracle call from the identity key that wallets commonly publish. If the one-time secret were any function of an elliptic-curve private key, breaking that key would break it too. Here the path from the seed to `pq_seed` never passes through an elliptic-curve key. What remains is a Grover search over the seed itself (Security Considerations).

### Honest limits

- The published proofs are for LMS. This BRC uses its leaf signature with one leaf and no tree, and with `I` derived by HMAC rather than drawn at random. The argument that the LMS bounds carry over is reasoning in this document, not a published proof.
- The binding is argued, not proved in a formal model.
- The quantum costs count Grover iterations. How many years or dollars an iteration of SHA-256 will cost on real hardware is unknown.
- The forgery figures after two signatures assume a forger that only hashes forward. They are lower bounds on what a key that signed twice gives away, not an analysis of every attack.
- Every node must run the script as written. That was checked on SV-Node v1.2.2 and two other interpreters, not on every implementation that miners run.

## Mathematical basis

### Definitions

The parameters are those of [RFC8554] Table 1 and Appendix B, with `n = 32` bytes and `w = 4` bits:

```
u  = ceil(8n / w)                                   = 64    digits for the hash
v  = ceil((floor(lg((2^w - 1) u)) + 1) / w)         = ceil((floor(lg 960) + 1) / 4) = ceil(10 / 4) = 3
ls = 16 - v w                                       = 4
p  = u + v                                          = 67    chains
```

`coef(S, i, 4)` is the `i`-th 4-bit digit of the byte string `S`, the high nibble of each byte first. The checksum of a digest `Q` is

```
sum     = (15 - coef(Q, 0, 4)) + ... + (15 - coef(Q, 63, 4))        0 <= sum <= 64 x 15 = 960 = 0x3C0
Cksm(Q) = u16(sum << ls)
a[i]    = coef(Q || Cksm(Q), i, 4)                                   for i = 0 to 66
```

so `a[64] = sum >> 8`, `a[65] = (sum >> 4) & 15` and `a[66] = sum & 15`. The chain function, with `tmp` starting at `x[i]`, is

```
tmp = SHA256( I || u32(q) || u16(i) || u8(j) || tmp )                for j = a .. b - 1
```

and its input is 16 + 4 + 2 + 1 + 32 = 55 bytes. SHA-256 pads a message with one `0x80` byte and an 8-byte length, and 55 + 9 = 64, so each step is exactly one compression ([RFC8554] section 9 notes the same); the private-value derivation of Appendix A has the same length. The other hashes are

| Hash | Input | Bytes | Compressions |
|---|---|---|---|
| `Q` | `I \|\| u32(q) \|\| u16(0x8181) \|\| R \|\| sigt` | 54 + length of `sigt` (71 in the vector) | 3 |
| `K` | `I \|\| u32(q) \|\| u16(0x8080) \|\| z[0] \|\| ... \|\| z[66]` | 22 + 67 x 32 = 2,166 | 34 |
| `C` | `KEY_TAG \|\| u8(suite) \|\| P \|\| K` | 8 + 1 + 33 + 32 = 74 | 2 |

The signature is `y[i]` = `x[i]` after steps 0 to `a[i] - 1`, and verification continues each chain from step `a[i]` to step 14. RFC 8554 serialises a signature as `u32(typecode) || C || y[0] || ... || y[66]`, 4 + 32 x 68 = 2,180 bytes; this BRC carries `R` and `y[0..66]`, 2,176 bytes, as separate pushes in the unlocking script (section 6), and fixes the typecode through the suite byte. Key generation costs 67 hashes for `x`, 67 x 15 = 1,005 chain steps and 34 compressions for `K`. Signing and verifying share the 1,005 chain steps between them: the signer computes the sum of `a[i]` and the verifier the rest; for the vector, 420 and 585.

### The checksum width, and why the top unit holds 0 to 3

The checksum can take any value from 0 to 960, which needs 10 bits. In 4-bit units that is `v = 3` units, 12 bits. RFC 8554 keeps the sum in a 16-bit field and shifts it left by `ls = 4`, so that the 12 bits read by `coef` are the ones that hold the value. The three units are therefore `sum >> 8`, `(sum >> 4) & 15` and `sum & 15`. The largest sum is 960, and `960 >> 8 = 3`, so the top unit is a 4-bit unit whose value is never more than 3: the 10-bit value fills two units and two bits of a third. A digest of all zero bytes gives 3, 12, 0; a digest of all `0xFF` bytes gives 0, 0, 0. In the honest vector the sum is 551 and the digits are 2 2 7. The script computes the same thing in `MID`: `960 - sum`, then division by 256 and by 16 and remainders mod 16.

### One signature allows no forward-only forgery

Let `a` be the digits of a signed `Q` and `a'` those of any other digest `Q'`. Suppose `a'[i] >= a[i]` for all 67 digits. The 64 message digits give `sum a' >= sum a` over the message part, so the checksum value `c' = 960 - (sum of a')` is at most `c`. The three checksum digits are the base-16 digits of `c'` and `c`, and if every digit of `c'` is at least the matching digit of `c`, then `c' >= c`. So `c' = c`, the message digit sums are equal, and with every `a'[i] >= a[i]` that means `a'[i] = a[i]` for all 64 message digits. Those 64 digits are all 256 bits of the digest, so `Q' = Q`. A forger that only hashes forward must therefore produce exactly the signed `Q` from a different randomizer or message: a SHA-256 second preimage with a fixed 22-byte prefix, about 2^256 classical tries or 2^128 Grover iterations. Otherwise some `a'[i] < a[i]` and it must invert a chain step, a preimage of the same cost.

### Forgery chance after two signatures

Assumptions: the two signed digests `Q1` and `Q2` are independent and uniformly random, which holds because each covers a different `sigt`; the forger knows `d` and chooses its randomizer freely, so each try yields a fresh uniform `Q'`; and it only hashes forward. With `m[i] = min(a1[i], a2[i])`, one try succeeds with probability

```
Pr[ a'[i] >= m[i] for all i = 0 .. 66 ]
```

The message digits are independent and uniform over 0 to 15, so the distribution of their sum is computed exactly, digit by digit, and the checksum digits follow from `960 - sum`; summing over the sums whose checksum digits meet `m[64..66]` gives the probability exactly. The expected number of tries is its inverse. Over 1,000 random pairs: median 2^61.1 tries, 10th percentile 2^35.7, easiest 2^29.9, hardest 2^89.3. Each try costs three compressions. A quantum forger running Grover over the randomizer needs about the square root, a median near 2^30.5 iterations. With three signatures the classical median falls to about 2^30.5. With one signature the probability is 2^-256 per try, as the lemma above requires.

### Generic costs

| Target | Classical tries | Grover iterations |
|---|---|---|
| SHA-256 preimage or second preimage (a chain step, `Q' = Q`, the commitment) | 2^256 | 2^128 |
| Double SHA-256 preimage onto one of two digests (the binding) | 2^255 | 2^127.5 |
| HASH160 second preimage (a P2PKH output at rest, for comparison) | 2^160 | 2^80 |
| A 12-word seed (128 bits of entropy) | 2^128 | 2^64 |
| A 24-word seed (256 bits of entropy) | 2^256 | 2^128 |

The figures are generic search costs, without constant factors. [FLUHRER17] bounds the classical case directly: with up to 2^64 keys and 2^120 compression calls, the chance of one forgery is below 2^-129.

### Script size

The locking script is `PRE` (25 bytes), `BYTE` 32 times (672), `MID` (21), 67 chains (14,122), 66 times the 3 bytes `OP_SWAP` before and `OP_SWAP OP_CAT` after a chain (198), `TAIL` (24), and the 33-byte push of `C` with `OP_EQUAL` (34).

One step is `OP_DUP NUM(j) OP_LESSTHANOREQUAL OP_IF OP_2 OP_PICK PUSH(u8(j)) OP_CAT OP_ROT OP_CAT OP_SHA256 OP_SWAP OP_ENDIF`: 13 bytes when `j` is 1 to 14, where `NUM(j)` and `PUSH(u8(j))` are one byte each, and 14 bytes for `j = 0`, where `PUSH(u8(0))` is `01 00` because `OP_0` pushes the empty string. Fifteen steps take 14 + 14 x 13 = 196 bytes. A chain adds `OP_SIZE NUM(32) OP_EQUALVERIFY` (4 bytes), `NUM(t) OP_PICK` (2 bytes while `t <= 16`, otherwise 3), `PUSH(u16(i))` (3), `OP_CAT OP_SWAP OP_FROMALTSTACK` (3) and `OP_DROP OP_NIP` (2): 210 bytes for the 15 chains with `t = i + 2 <= 16`, and 211 for the other 52. In total:

```
25 + 672 + 21 + 14,122 + 198 + 24 + 34 = 15,096 bytes
```

The purpose-built chain measured for the Rationale hashed `x || u8(i) || u8(j)`, 34 bytes, with a step of `OP_DUP NUM(j) OP_LESSTHANOREQUAL OP_IF OP_SWAP PUSH(u8(i) || u8(j)) OP_CAT OP_SHA256 OP_SWAP OP_ENDIF`, 12 bytes, and a chain of 5 + 15 x 12 + 1 = 186 bytes, 67 x 186 = 12,462 in all. LM-OTS adds one byte per step (`OP_2 OP_PICK`, a one-byte push of `j` and `OP_CAT OP_ROT OP_CAT`, 6 bytes, where the purpose-built step had `OP_SWAP`, a three-byte push and `OP_CAT`, 5 bytes), one more at `j = 0`, and 8 or 9 bytes per chain to build the prefix and drop it: 24 or 25 bytes per chain, 1,660 in all. The surrounding code grows by 7 bytes. 13,429 + 1,667 = 15,096, 12.4 percent more.

The unlocking script is `PUSH(I || u32(0))` (21 bytes), 67 pushes of 33 bytes (2,211), `PUSH(R)` (33), `PUSH(sigt)` (1 + 71) and `PUSH(P)` (34): 2,371 bytes. A low-S DER signature with its sighash byte is 71 or 72 bytes, and rarely shorter, so the unlocking script is 2,371 or 2,372 bytes. The spend of the vectors is 4 (version) + 1 (input count) + 36 (outpoint) + 3 (script length) + 2,371 + 4 (sequence) + 1 (output count) + 34 (one P2PKH output) + 4 (lock time) = 2,458 bytes.

### Fees

SV-Node mines a transaction when its fee is at least `floor(size x rate / 1000)` ([NODE-RUN]). The output adds 8 (value) + 3 (script length) + 15,096 = 15,107 bytes to its funding transaction.

| Rate (satoshis per 1,000 bytes) | One output (15,107 B) | Spend (2,458 B) | Funding tx measured (15,298 B) |
|---|---|---|---|
| 100 | 1,510 | 245 | 1,529 |
| 500 | 7,553 | 1,229 | 7,649 |

The node mined the spend and the funding transaction at exactly these fees and left them unmined at one satoshi less. Against a pay-to-public-key-hash output (34 bytes) and its one-input, one-output spend (about 192 bytes), creating and spending a template output costs about 1,733 satoshis more at 100 and about 8,669 more at 500. The rates are examples; each miner sets its own.

### Validation time

Measured on one machine ([NODE-RUN]): the median `verifyscript` round trip for the honest spend was 2.58 ms in one run and 2.61 ms in another, and a plain RPC round trip 0.38 ms and 0.42 ms, which leaves about 2.2 ms of script time. The rest of this subsection is estimate, not measurement.

For the vector, the verifier runs 585 chain steps (about 506 on average over random digests), 34 compressions for `K`, 3 for `Q` and 2 for `C`: 624 compressions, plus the double SHA-256 of the sighash. OpenSSL on the same machine hashes a 64-byte message, two compressions, in about 0.48 microseconds, so hashing accounts for about 0.15 ms, about 7 percent. The rest is the interpreter: the locking script holds 14,693 operations, about 150 ns each on average. Against SV-Node's default standard budget of 3 ms this leaves about 0.8 ms of headroom on this machine, and a spend over the budget is validated again under the non-standard budget, as section 9 describes. One core would check about 450 such spends a second, and a block of 10,000 of them about 22 core-seconds of script time, before any parallelism.

## Security Considerations

**Hash assumptions.** Security against a discrete-log adversary rests on SHA-256: second-preimage resistance for LM-OTS (RFC 8554 section 9) and the commitment, and preimage resistance of double SHA-256 for the binding (section 8). Grover's algorithm brings a 256-bit preimage to about 2^128 iterations. LM-OTS's per-key identifier keeps an attack on many outputs from being cheaper per output than an attack on one.

**One-time keys.** Section 11.3 is the most important rule in this document. A wallet that re-signs to change a fee, or restores from a backup that lost its used-key record, can turn a template output into one a classical thief can take.

**Classical security.** The spend keeps ECDSA, so it is not weaker than an ordinary output against a classical adversary, provided the LM-OTS layer does not leak `d`, which it does not: `d` and `pq_seed` are independent outputs of HMAC.

**Seed strength.** A discrete-log adversary that also runs Grover against a 12-word seed (128 bits of entropy) needs about 2^64 iterations, each a seed derivation and a key comparison. That is far beyond any machine described today, but a wallet that offers these outputs SHOULD prefer a 24-word seed.

**Malleability.** At and after the Chronicle activation, a transaction of version greater than 1 is exempt from the low-S and minimal-push rules ([CHRONICLE]). A third party can re-encode pushes in the unlocking script and so change the txid (SV-Node accepted such a re-encoding of a version 2 spend and refused it for version 1, [NODE-RUN]), but cannot change `sigt`, so the spend's effect is fixed. A spender SHOULD track the spend of the outpoint, not one txid.

**Opcodes.** The template uses `OP_CAT`, `OP_SPLIT`, `OP_BIN2NUM`, `OP_DIV`, `OP_MOD`, `OP_SHA256`, `OP_LESSTHANOREQUAL`, `OP_PICK` and stack operations, all available to every output created after Genesis; it uses no opcode that the Chronicle release added or re-enabled (`OP_SUBSTR`, `OP_LEFT`, `OP_RIGHT`, `OP_LSHIFTNUM`, `OP_RSHIFTNUM`, `OP_2MUL`, `OP_2DIV`, `OP_VER`, `OP_VERIF`, `OP_VERNOTIF`), so it behaves the same in outputs created before or after Chronicle ([NODE], [NODE-RUN]).

**Script size.** The locking script is about 15 kB, below the default policy limit of 500,000 bytes, and a node accepts non-standard output scripts by default ([NODE]). A miner may still choose to charge more for, or refuse, large outputs.
